## 概要

`.github/ISSUE_TEMPLATE/feature_request.md` のテンプレートを使って GitHub issue を作成する。
会話の流れから内容を推論し、確認なしで作成まで進める。「概要」には課題のみ、「機能要件」には課題が解決したと言える条件のみを書き、実装方法や課題から導けない振る舞いの細部は書かない。

## 手順

### 1. テンプレートを読む

`.github/ISSUE_TEMPLATE/feature_request.md` を読み、セクション構造を把握する。
テンプレートのセクション名・順序は変えずにそのまま使う。

### 2. 既存ラベルを取得する

```bash
gh label list --json name,description --limit 100
```

取得したラベル一覧を把握し、次のステップでの選択に備える。

### 3. コンテキストから内容を推論する

現在の会話の流れを振り返り、テンプレートの各セクションを埋める。

- **タイトル**: issue の件名（例: `ユーザープロフィール編集機能の追加`）。推論に迷う場合でも、会話の主な変更対象からもっとも近い名詞句で仮決めし、確認せずに進める
- **概要**: 解決したい課題（現状困っていること・背景）のみを書く。解決策・実装方針・新しい振る舞いはここに書かない
- **機能要件**: 課題が解決したと言える条件を、次のステップ4の基準を満たす形で書く。「どう実現するか（実装方法）」ではなく「何が達成されればよいか（結果条件）」を書く
- **制約**: 非機能要件・技術的制約・スコープ外のみを書く。無ければ「なし」とする

ユーザーに確認なしで最後まで作成を進める（ステップ4・6を参照）。

### 4. 機能要件をセルフチェックする

機能要件は auto 系ワークフロー（`/bugfix-auto` など）でそのまま完了条件に分解される。ステップ3で組み立てた機能要件の各項目を、次の2段階でチェックする。

**4-1. 検証可能性チェック**

何をアサートすれば充足と言えるかが一意に決まる形で書けているかを確認する。次のいずれかを満たせば合格とする（`.claude/skills/bugfix-auto/judgment-criteria.md` の Q1 と同じ基準）:

- 入力と出力（リクエスト → レスポンス、引数 → 戻り値）
- 状態遷移（操作前後の DB・UI・ストアの状態）
- 具体的な文言（表示テキストの全文または一部）
- 数値閾値（件数・時間・サイズ・コントラスト比など）
- 参照先が一意に特定できる規約（デザインシステム定義（例: `DESIGN.md`）のトークン名、ADR の決定事項、`docs/specs/` の記述など）

「〜できる」「〜が表示される」のような動詞形だけの項目は、何が起きれば充足かが決まらないため不合格とする。

**4-2. 実装非依存性チェック**

4-1 に合格した項目について、次の両方を満たすかを確認する:

- **必須性**: その項目を取り除くと、概要に書いた課題が解決したと言えなくなるか（課題解決に不可欠な条件か）
- **実装非依存性**: 異なる実装方式・既存の仕組みでもその項目を満たせるか（特定の処理順序・内部状態遷移のタイミング・データ構造・既存実装と矛盾する具体的な振る舞いを指定していないか）

いずれかを満たさない項目（課題解決に不可欠でない具体化、または特定の実装方法を指定している）は、その部分を削り、結果として観測できる状態（UI・レスポンスの見え方）だけを条件として書き直す。

例（通知の未読表示）:
- 不合格: 「通知一覧ページを開くと、既読タイミングは一覧を開いた時のみとし、個別選択では既読にしない」（既読になるタイミング・手段という実装方法を指定しており、既存の個別既読の仕組みと矛盾しうる）
- 合格: 「未読の通知がある間はナビゲーションにドットを表示し、すべて既読になるとドットが消える」（結果として観測できる状態のみを条件にしている。既読にする手段・タイミングは問わない）

**4-3. 不合格の項目の扱い**

4-1 に不合格の項目（最初から不合格の項目と、4-2 の書き直しで 4-1 を満たさなくなった項目の両方）は、ユーザーに確認せず次の順で扱う。

1. 会話と概要に書かれた情報だけで、結果として観測できる状態を 4-1 の基準で書ける場合は、その形に書き直す
2. 書けない場合（書くには実装方法や課題から導けない振る舞いの細部を仮定する必要がある）は、その項目を機能要件から外す

4-1 に不合格の項目を機能要件に残したまま起票しない。外した項目を補う項目を仮定で作らず、項目が1つも残らない場合は機能要件を `- なし` とする。外した点は、issue を処理する後続のワークフローが実装前に人間へ確認する（feature は `/dev-requirements` の不明点確認、`refactoring` / `bug` / `skill-improvement` は `/refactor-auto`・`/bugfix-auto` の不明点への質問）。

### 5. ラベルを選択する

ステップ2で取得したラベル一覧を、issue のタイトル・概要・機能要件・制約と照合し、内容に合うラベルを選ぶ。
該当するラベルがない場合はラベルなしとする（新しいラベルは作成しない）。

### 6. 推論で確定しない項目を確定する

タイトル・制約が推論できない場合も、**ユーザーに確認せずここで確定させる**。

- タイトル: 会話の主な変更対象から最も近い名詞句で仮決めする
- 制約: 「なし」とする

機能要件のチェックで不合格になった項目は、ステップ4-3で扱いが決まっている。いずれの場合も、仮定した内容を確認する質問はしない。

### 7. issue 本文を組み立てる

テンプレートのセクションに内容を埋める。箇条書きの項目がない場合は `- なし` とする。

### 8. issue を作成する

ラベルがある場合:
```bash
gh issue create --title "[タイトル]" --body "[本文]" --assignee @me --label "label1,label2"
```

ラベルがない場合:
```bash
gh issue create --title "[タイトル]" --body "[本文]" --assignee @me
```

作成後、返ってきた issue URL をユーザーに伝える。

## 出力例

```
issue を作成しました: https://github.com/owner/repo/issues/42
```

## 注意

- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- テンプレートの構造は変えない（セクション名・順序を保つ）
- `/create-issue` の実行中にユーザーへ確認・質問をしない（内容の解釈確認も含む）。推論に自信が持てない場合も、確認せず最も妥当な解釈で作成まで進める
- 「概要」には課題のみ、「機能要件」には課題解決の結果条件のみを書く。実装方法・課題から導けない振る舞いの細部は書かない（ステップ4-2）
