## 概要

内側ワークフロー（/refactor-auto・/bugfix-auto）は「1 issue を1周回すループ本体」であり、
人間のタッチポイント（コメント投稿許可・不明点への回答・計画承認）で停止する。
この skill はその外側に立つ指揮役として、Herdr の pane で子エージェント（claude + 内側ワークフロー）を
起動し、タッチポイントに人間の代わりに応答しながら複数 issue を順次処理する。

指揮役の機構（pane 操作・監視・エスカレーションと後片付け・PR 一次レビュー）はワークフローに
依存しない。ワークフロー固有の値（対象ラベル・投入コマンド・終端マーカー・計画の承認基準・
エスカレーション条件の差分）は「ワークフロー定義表」に集約し、手順本文はそこを参照するだけにする。
ワークフローを増やすときは定義表に1ワークフロー分を足せばよく、機構側は触らない。

人間の検証が消えるわけではなく、「毎 issue の計画承認」から「最後の PR レビュー」へ移動する
（human-in-the-loop → human-on-the-loop）。そのため以下の多層検証が前提になる:

1. 指揮役による計画の批判的レビュー（本 skill の承認基準）
2. 内側ワークフロー内蔵の reviewer エージェント（最大3回・計画準拠の観点）
3. テスト・型チェック・フォーマッタ（決定論的な拒否権）
4. PR 上での一次レビューと修正（/code-review・1周のみ・品質の観点）と CI チェックの確認
   （一次レビューは修正の適用と見送った指摘の PR への記録だけを担い、自動マージの条件には使わない）
5. 自動マージの条件判定（2h。機械的な情報だけで判定する許可リスト）
6. 条件を満たさない PR についての、人間による PR レビューとマージ（最後の独立した検証層・最終ゲート）

ループは issue ごとに PR 作成と一次レビュー・修正・CI チェックの確認までを行い、
定義表「自動マージの条件」をすべて満たした PR だけを自分でマージする（2h）。
1つでも満たさない PR はマージせず、満たさなかった条件を添えて人間に引き渡す。
PR 作成は人間の承認なしで進めてよい（PR を作成しただけでは既存のコードに影響が出ないため）。
承認なしでマージしてよいのは自動マージの条件を満たした PR に限り、さらにプロジェクトの CLAUDE.md が
`/auto-loop` による自動マージを例外として許可していることを前提とする（線引きの考え方は定義表
「自動マージの条件」の「導入判断の要点」）。

## 引数

- `<issue番号...>`（省略可）: 処理対象の issue 番号を空白区切りで複数指定できる。指定順に処理する
- `--limit N`（省略可）: 1回の実行で処理する issue 数の上限。1以上の整数（上限値は設けない）。
  **省略時は 5**。不正な指定（1未満・整数として読めない・`--limit` に値が続かない）があったら、
  **どれに該当したかが分かるエラー**（範囲外なのか、整数として読めないのか、値が無いのか）を伝えて、
  issue の処理を始めずに終了する。「範囲外」で一括りにしない（`--limit` が次の引数を値として
  飲み込んでいる場合など、原因が範囲と無関係なときに利用者が誤った直し方をするため）。
  検証は **Step 0 の前提チェック・ラベル準備より前**に行う（ラベルの作成・改名は
  リポジトリに対する副作用であり、不正な引数のまま実行しないため）。
  `--limit` の直後の値は件数であり、issue 番号として扱わない
  （`/auto-loop --limit 2 12 34` の `2` は issue #2 ではなく件数）。件数の適用規則は Step 1 手順3が正
- issue 番号省略時: 定義表の対象ラベル・補助ラベル（`refactoring` / `bug` / `skill-improvement`）が
  付いた open issue から指揮役が選定する（最大 N 件。N は `--limit` の値、省略時は5）

番号を指定した場合も省略した場合も、**どのワークフローで処理するかは issue のラベルで判定する**
（Step 1 参照）。

## ワークフロー定義表

手順本文（Step 0〜3・エスカレーション・対象外終了）はワークフロー固有の値を直接書かず、
すべてこの節を参照する。**ワークフローを追加するときはこの節に1行ずつ足すだけで済むようにし、
手順本文にワークフロー名を直接書き足さない。**

### 基本定義

| 項目 | refactor ワークフロー | bug ワークフロー |
|---|---|---|
| 対象ラベル | `refactoring` | `bug` |
| 対象ラベル経由の処理優先度（auto-loop Step 1 手順3） | 2 | 2 |
| 補助ラベル | （なし） | `skill-improvement` |
| 補助ラベル経由の処理優先度（auto-loop Step 1 手順3） | （なし） | 1 |
| 内側ワークフロー | `/refactor-auto` | `/bugfix-auto` |
| 子 pane 名（2a 手順2） | `refactor-auto-<番号>` | `bugfix-auto-<番号>` |
| ブランチ名（2a 手順4） | `<番号>-refactor/<kebab-case-name>` | `<番号>-fix/<kebab-case-name>` |
| 投入コマンド（2b 手順3） | `/refactor-auto <番号>` | `/bugfix-auto <番号>` |
| 計画コメントの名称（2c 手順4） | 承認済みリファクタ計画 | 承認済み修正計画 |
| 実装完了マーカー（2b 手順0・エスカレーション理由コメント） | `## リファクタ実装完了` | `## バグ修正実装完了` |
| 修正試行カウンタ見出し（2b 手順0・前方一致） | `## リファクタ修正試行` | `## バグ修正試行` |
| 自動マージの対象（2h 条件 M1） | 対象ラベル経由で振り分けた issue | 対象ラベル経由で振り分けた issue のうち、完了条件の判定方式が回帰テストで、`テスト対象外` の検証項目を含まないもの |
| 計画からの逸脱の記録欄（2h 条件 M5） | 実装完了マーカーの「計画外の変更（機械的な import パス変更のみ）」「変換できなかった箇所」と、修正試行カウンタのコメントの「計画外の変更（機械的な import パス変更のみ）」（修正エージェントにも計画外の import パス変更を許しているため） | 実装完了マーカーの「計画から逸脱した点」（修正エージェントは計画外の変更を許されていないため、修正試行カウンタのコメントには欄が無い） |

ブランチ名の `<kebab-case-name>` は `.claude/rules/core.md` の命名規約に従う
（ASCII のみ・issue 内容を表す短い名前）。

**対象ラベルと補助ラベルの違い**（振り分けの手順は Step 1）:

- **対象ラベル**: ワークフローと1対1に対応する主ラベル。2つ以上付いている issue は
  振り分け不能として処理対象から外す
- **補助ラベル**: そのワークフローに従属させるラベル。**対象ラベルが1つも付いていないときだけ**
  その列のワークフローへ振り分け、対象ラベルと併用されているときは無視する
  （振り分け不能の判定にも数えない）
- 候補の収集（Step 1 手順1）は対象ラベル・補助ラベルの両方について行う
- 補助ラベル経由で振り分けた issue も、pane 名・ブランチ名・投入コマンド・終端マーカーは
  その列の定義をそのまま使う

`skill-improvement`（skill 定義の改善）を bug ワークフローの補助ラベルにしているのは、
issue の機能要件をそのまま完了条件にできるためである
（完了条件を issue の機能要件から直接引くのは bug ワークフローだけで、
refactor は承認済みリファクタ計画を経由する）。

**処理優先度**（引数省略時の処理順を決める値。並べ替えの手順は auto-loop Step 1 手順3）:

- 数値が小さいほど先に処理する。issue の優先度は、その issue が対象ラベル経由・補助ラベル経由の
  どちらで振り分けられたかで決まる
- 同じ優先度の issue 同士は issue 番号の小さい順とする
- 引数で issue 番号が指定された場合は優先度を適用せず、指定順を処理順とする
- `skill-improvement`（補助ラベル経由）を最優先の 1 にしているのは、ループ機構そのものの品質を
  上げる変更だからである。後回しにすると、改善前の skill 定義のまま後続の issue を処理し続けることになる
- ワークフローを追加するときは、定義表の処理優先度2行にも値を入れる（既存ワークフローと
  同じ扱いでよければ対象ラベル経由は 2）

### 終端マーカー表

内側ワークフローが issue コメントとして投稿する見出し行。子の最終出力にも同じ見出しが現れる。

| ワークフロー | 終端マーカー | 結果分類 |
|---|---|---|
| refactor | `## /refactor-auto 完了` | 完了 |
| refactor | `## /refactor-auto — 自動修正できませんでした` | エスカレーション |
| bug | `## /bugfix-auto 完了` | 完了 |
| bug | `## /bugfix-auto — 自動修正できませんでした` | エスカレーション |
| bug | `## /bugfix-auto — 対象外（人間確認が必要）` | 対象外 |

結果分類ごとの扱い:

| 結果分類 | ラベル付与 | PR 工程（2e〜2h） | worktree・ブランチ | 全体停止カウント |
|---|---|---|---|---|
| 完了 | なし | 実行する | 2h で自動マージした場合は指揮役が削除する（2h 手順8）。それ以外は PR のマージ後に人間が片付ける | — |
| エスカレーション | `auto-loop:escalated` | スキップ | 成果ゼロなら削除する（「エスカレーション時の後片付け」） | 加算する |
| 対象外 | なし | スキップ | 成果ゼロなら削除する（「対象外終了」の手順5） | 加算もリセットもしない |

- **Step 1 の除外マーカーは、そのワークフローの終端マーカー全行**（完了・エスカレーション・対象外の
  いずれかが投稿済みの issue は処理対象から外す）
- **「対象外」はエスカレーションではなく正常終了**として扱う。bug ワークフローで完了条件が
  人間確認（見た目・主観判断）に該当したときの終端であり、指揮役側の失敗ではないため
  ラベルも付けず、全体停止のカウントにも含めない（「対象外終了」を参照）

### 計画の承認基準（内側ワークフローの Step 4）

承認前に必ず1回は批判的観点で計画を読む。指摘が見つからなくても
「この計画の一番弱い箇所はどこか」を自問してから承認する。
何も差し戻さずに全件承認が続く指揮役は検証として機能していない。

**共通のチェック項目**（全ワークフロー）:

| # | 項目 |
|---|---|
| C1 | 変更対象ファイルが issue のスコープと一致しているか（過剰・不足がないか） |
| C2 | 「スコープ外」が明示されているか |
| C3 | 例外・エッジケースへの言及が対象ファイルの実態と合っているか |
| C4 | エスカレーション条件に触れていないか |

**refactor ワークフロー固有**:

| # | 項目 |
|---|---|
| R1 | 「機能変更なし」が明記され、変換ルールがそれと矛盾しないか |
| R2 | 変換ルールに具体的なコード例（置き換え前→後）があるか |

**bug ワークフロー固有**:

| # | 項目 |
|---|---|
| B1 | バグの原因と修正方針が対応しているか（原因に対する修正になっているか。症状の打ち消しになっていないか） |
| B2 | 完了条件の判定方式（回帰テスト / AI照合）の分類が妥当か。`.claude/skills/bugfix-auto/judgment-criteria.md` の判定手順（Q1〜Q4）・集約ルール・境界ケースに照らして確認する。**回帰テストで判定できるのに AI照合になっていないか**（同ファイルは回帰テストを優先すると定めている） |
| B3 | 判定方式が回帰テストの場合: red → green の計画があり、どのテストが issue の機能要件のどの項目に対応するかが示され、要件を漏れなくカバーしているか |
| B4 | 判定方式が AI照合の場合: 「何と何を突き合わせれば充足と言えるか」が事前に一意に決まっているか |
| B5 | issue の機能要件に含まれない変更（リファクタ・機能追加・周辺の類似バグの巻き取り）が混入していないか |

C1〜C3・R1〜R2・B1・B3〜B5 に問題があればフィードバックとして具体的に差し戻す。
C4 に該当したらエスカレーション。

**B2 の判定に疑いが残る場合は承認せずエスカレーションする**（フィードバックで差し戻さない）。
判定方式は承認済み修正計画に固定され、実装エージェントもレビュアーもそれを前提に動くため、
分類を誤ったまま承認すると「回帰テストで機械的に判定できたはずのバグが AI照合で通る」
「人間確認相当のものが自動判定される」という検証の穴になる。分類の是非は issue の書き方
（期待動作が検証可能な形で書かれているか）に踏み込む判断であり、人間の領分に近い。

**パターン3（確認事項付き承認）の扱い**

計画そのものへの修正は不要だが、実装時に踏まえてほしい確認事項を添えて承認する応答
（パターン3）が発生しうる。実装時に踏まえてほしい補足事項に気づき、かつ次の**すべて**を
満たすときに限りパターン3を返す:

- 共通のチェック項目（C1〜C4）および該当ワークフロー固有の項目（refactor は R1〜R2、
  bug は B1〜B5）を満たし、差し戻し不要と判断できる
- 確認事項が計画のスコープを超える変更を求める内容ではない
  （超えるなら通常のフィードバック（差し戻し）とする）
- 確認事項が B2 の分類への疑い・「判断に確信が持てない」事項のいずれでもない
  （どちらもエスカレーション条件であり、確認事項に格下げして承認してはならない）
- 内側ワークフロー側に受け取りの定義がある。**現時点で定義があるのは bug だけ**
  （`/bugfix-auto` の Step 4）。refactor は受け取りが未定義で、送っても確認事項が
  実装フェーズに渡らないため、パターン3にはせず、差し戻すに値するなら通常の
  フィードバックとし、値しないなら送らない

パターン3を返すときは、2c 手順4 の承認文言に続けて確認事項を**同じ1行に連結して**送る
（承認文言は 2c 手順4 を正とし、ここでは再掲しない）:

```
<2c 手順4 の承認文言>実装時の確認事項として、以下も踏まえてください: (1) <確認事項1> / (2) <確認事項2>
```

`pane run` に渡す文字列に改行を含めない。改行は送信として解釈されるため、承認文言だけが
先に届いて子が Step 5 に進み、残りの確認事項は子が `working` の間に送ることになる
（確認事項が実装に反映されないうえ、「注意事項」の「`pane run` を送る前に `pane get` で
子の状態を確認する（`working` 中に送らない）」にも反する）。確認事項が複数あるときも
`(1) … / (2) …` の形で1行に連結する。

### エスカレーション条件

**共通**（全ワークフロー）:

- **DB スキーマ・認証・セキュリティ** に触れる（ADR 確認が必要な領域）
- **新規ライブラリの導入** を伴う（core.md によりユーザー承認が必須）
- 子 pane が permission ダイアログ等で `blocked` になった
- 計画承認で2回フィードバックしても基準を満たさない、または判断に確信が持てない
- そのワークフローの終端マーカーのうち **結果分類が「エスカレーション」のもの** が投稿された
- worktree 準備でベースラインテストが green にならなかった
- 完了検証に失敗した
- PR の作成に失敗した、または一次レビューの修正後にテストが green に戻らなかった
- 一次レビューの修正コミットが PR ブランチに push されていなかった（2g 手順1で検出）
- CI チェックの結果が失敗（`fail`/`cancel`）を含む、または CI チェック確認（2g）が
  待機上限（30分）を超えてもチェックの完了が確定しなかった
- エスカレーション回答の前処理（2b 手順0）の実行に失敗した
- 内側ワークフローから、issue 本文が経緯・前提として参照する他 issue/PR の状態が実際の state と
  食い違うと報告された（食い違いの解消は issue 本文の前提を書き換える判断であり、issue を書いた
  人間の領分に近いため）。issue 本文を直さないまま再実行すると内側ワークフローが同じ食い違いを
  再検出して再び止まるので、エスカレーション理由コメントの「判断が決まった後にすること」に
  **issue 本文の前提の修正が必要**である旨を必ず書く。結果分類「対象外」の終端マーカーで
  食い違いが報告された場合はこの条件ではなく「対象外終了」で扱う（正常終了の分類を崩さないため）

**ワークフロー固有**:

| ワークフロー | 条件 |
|---|---|
| refactor | 計画・質問が **ユーザーに見える動作の変更** を含みうる |
| bug | 計画・質問が **issue の機能要件を超える挙動変更** を含みうる（issue に記録された期待動作を実現するのに必要な範囲を超えた挙動の変更。バグ修正は挙動を変えること自体が目的なので、refactor の「ユーザーに見える動作の変更」をそのまま適用すると全件が該当してしまう。線引きは「issue の機能要件で説明できるか」に置く） |
| bug | 完了条件の判定方式の分類（承認基準 B2）に疑いが残る |

bug ワークフローは refactor に比べてエスカレーションに倒れやすい（B2 の疑い・期待動作を
指揮役の裁量で決めることになる質問・ベースライン red・他 issue/PR との前提の食い違いが
いずれもエスカレーション。最後の1つは検証指示が bugfix-auto の Step 1 にしか無いため、
共通条件に置いてあっても実際に発火するのは bug ワークフローだけである）。
issue の書き方によっては最初の数件で「エスカレーション3 issue 連続」の全体停止に届きうる。
これは意図した安全側の挙動なので条件を緩めないが、**全体停止したときは指揮役側・環境側の
異常だと決めつけず、対象 issue 群の書き方（期待動作が検証可能な形か）も点検の対象に含める**。

### 自動マージの条件

2h で PR を自動マージしてよいのは、次の M1〜M6 を**すべて**満たすときだけである（許可リスト方式）。
1つでも満たさない場合、判定材料が取れない場合はマージせず、満たさなかった条件を添えて
人間に引き渡す（迷うケースは人間の確認に回す）。判定はラベル・変更ファイルのパスと差分の内容・issue コメントに
残るループの記録・git / gh の状態・CI の結果といった機械的な情報だけで行い、指揮役の裁量で
「実質的には問題ない」と条件を読み替えない（指揮役の判断で線を引くと、そこが検証の穴になるため）。

GitHub 側（ブランチ保護・rulesets・auto-merge）ではこの条件を強制していない前提で書いている。条件を守らせるのは
指揮役自身の判定だけなので、判定を省略したり推測で済ませたりしない。

**導入判断の要点**（プロジェクトで自動マージを有効にするかを決めるときの観点。決めた内容は CLAUDE.md の
例外規定と、ADR を運用しているなら ADR に残す）:

- 人間のマージが検証として機能しているか（PR の内容をほとんど確認せずにマージしているなら、
  人間のマージを最終ゲートとして残しても検証は増えず、マージを遅らせるだけになる）
- 誤ったマージの影響の大きさ（本番稼働前など影響が小さい時期を前提にした線引きなら、
  デプロイ開始などの節目で線引きを見直す）
- ループが作ったすべての PR を対象にはしない。ループ自身のルールを変える `skill-improvement`・
  AI照合の bug のように機械的なゲートが無いもの、人間が持つべき判断を含むもの（機能追加など）は対象外にする
- 自動マージした PR は人間が見ないため、文章でしか書かれていない規約や ADR・仕様との不整合が溜まりうる。
  定期的な規約・セキュリティの調査などで補う

**CLAUDE.md が `/auto-loop` による自動マージを許可していない場合**は、2h の手順1〜2 で条件を判定・記録するだけにとどめ、
main への追従・マージ・worktree とブランチの削除（手順4〜8）は行わない。その PR は
`自動マージ: 未実施（CLAUDE.md で自動マージが許可されていない）` として人間に引き渡す（満たさなかった条件もあわせて書く）。

一次レビュー（2f）の結果（指摘の件数・一次レビュー後の修正コミットの有無・見送った指摘の有無）は
条件に含めない。一次レビューは PR の差分の外にある既存の問題も指摘するため、指摘の有無で止めると
PR の変更に問題が無くても人間に回り、しかも人間に回した PR はレビューされていなかった。一次レビューの
役割は修正の適用と見送った指摘の記録（2f）に限る。一次レビュー後の修正の差分は、ほかの変更と同じく
2g の CI チェックと M2 の検出（2h 手順1 は修正コミットを含む `origin/main...HEAD` を対象にする）で検証する。
ただし、コミットされていない修正はこの検証の対象に
ならないため、worktree に未コミットの変更が残っていないこと（M6）は、一次レビューの結果ではなく git の状態として判定する。

2h 手順4 で main を取り込んだときに起きたコンフリクトは、ループが解消して判定を続ける（2h「main への追従で起きたコンフリクトの解消」）。
人間に引き渡しても人間は PR をレビューしておらず、解消の手間がかかるだけで検証が増えないためである。
解消した差分も一次レビュー後の修正と同じく、一次レビュー（2f）をやり直さずに 2g の CI チェックと M2 の検出で検証する
（一次レビューの結果は自動マージの条件に含めないため、やり直しても可否の判定に使えず、処理時間だけが延びる）。
M2 は解消後のコミットで判定し直す（2h 手順5。解消によって main 側の変更〈テストなど〉が落ちたり、
人間の確認が必須な領域に触れたりしうるため）。

| # | 条件 | 判定方法 |
|---|---|---|
| M1 | 自動マージの対象ワークフローの issue である | Step 1 の振り分けが対象ラベル経由で、定義表「自動マージの対象」を満たすこと（補助ラベル経由は常に満たさない）。bug では `gh issue view <番号> --json comments` で**最新の** `## 承認済み修正計画` を読み、「### 完了条件の判定方式」が回帰テストで、かつ機能要件×テストケースの対応表に区分が `テスト対象外` の行が1行も無いことを確認する（回帰テストが主判定でも、`テスト対象外` の項目は AI照合だけで確認されるため） |
| M2 | 変更が「人間の確認が必須な領域」に1件も含まれない | 2h 手順1で取得した変更ファイル一覧を、下の「人間の確認が必須な領域」のパターンと突き合わせる。あわせて、同じ手順で実行した「差分の内容で判定する領域」の検出がすべて該当なしであること。2h 手順4 でコンフリクトを解消した場合は、2h 手順5 で解消後のコミットに対して判定し直す。領域のパターン・検出コマンドに未設定のプレースホルダ（`<…>`）が残っている場合は満たさない |
| M3 | 最新の main に追従した状態で、CI チェックがすべて成功している | 2g の CI 結果が「成功」であること（「対象外」は満たさない。機械的なゲートが無いため）。そのうえで 2h 手順4〜5 で main への追従と CI の再確認を行う。追従でコンフリクトを解消できなかった（2h「main への追従で起きたコンフリクトの解消」）、main の取り込みがコンフリクト以外の理由で失敗した、追従を push できなかった、マージ直前に main がさらに進んでいた場合は満たさない（追従は1回まで） |
| M4 | エスカレーションを経て再開した issue ではない | 次の3つがどれも無いこと: `## /auto-loop エスカレーション`（旧名 `## /refactor-loop エスカレーション`）のコメント、終端マーカー表で結果分類が「エスカレーション」のマーカーのコメント、ラベル `auto-loop:escalated`（旧名 `refactor-loop:escalated`）の付与イベント（取得方法は表の下）。照会に失敗した場合は満たさない |
| M5 | 計画外の変更・計画からの逸脱の記録がない | 定義表「計画からの逸脱の記録欄」に挙げたコメント（同じ見出しのコメントが複数あればすべて）で、その欄の値がすべて「なし」であること。実装完了マーカーのコメントかその欄が見つからない場合は満たさない。修正試行カウンタのコメントは無くてもよい（修正ループに入らなかった場合）が、あるのに欄が見つからない場合は満たさない |
| M6 | worktree に未コミットの変更が無い | `git -C <worktree パス> status --porcelain` が空であること（コマンドが失敗した場合は満たさない）。満たさない場合はその出力を記録する。2f の `/code-review --fix` で当てたままコミットされなかった修正を、人間の確認に回すため（そうした修正は PR に含まれず、2g の CI チェックと M2 の検出の対象にならない。修正を当てているため 2f の見送った指摘の記録にも載らず、そのままマージすると修正が記録なしに落ちる） |

M4 のラベル付与イベントは次で取得し、出力に `auto-loop:escalated` か `refactor-loop:escalated` が1行でもあれば満たさない:

```
gh api "repos/{owner}/{repo}/issues/<番号>/events" --paginate --jq '.[] | select(.event == "labeled") | .label.name'
```

コメントとマーカーだけで判定しないのは、再実行の手順（「エスカレーション理由コメント」の「判断が決まった後にすること」）で
人間が終端マーカーのコメントを削除してラベルを外すうえ、`## /auto-loop エスカレーション` は分類器にブロックされて
投稿されていないことがあるためである。ラベルの付与イベントは、ラベルを外した後も残る。

**人間の確認が必須な領域**（M2）

パターンはリポジトリルート起点で書く。末尾が `/` のものはそのディレクトリ配下のすべて、
`*` はパスの区切り（`/`）をまたがない任意の文字列に一致し、それ以外はファイルパスの完全一致とする。

`<…>` で囲んだものはプロジェクトの構成に合わせて導入時に実際のパターンへ置き換えるプレースホルダ
（`docs/architecture/`・`docs/specs/technical-environment.md` を見て決める）。置き換えずに残っている間は
M2 を満たさない扱いになる（設定漏れのまま検査が素通りしないようにするため）。該当するファイルが
存在しない領域（例: DB を持たない）は、プレースホルダを消して「該当なし」と書く。

| 領域 | パターン | 人間の確認を残す理由 |
|---|---|---|
| DB スキーマ・マイグレーション | `<マイグレーションのディレクトリ>/`・`<スキーマ定義ファイル>`・`<DB / ORM の設定ファイル>`・`<DB のバインディングやマイグレーションの設定を持つデプロイ設定ファイル>` | データの形は後から覆すコストが高い。マイグレーションの適用先や設定がデプロイ設定・エントリポイントに書かれている構成では、それらも含める |
| 認証・認可 | `<認証・CSRF 等の middleware のディレクトリ>/`・`<middleware・認証ガードを登録するエントリポイント>`・`<フロントエンドの認証ガード・認証機能のディレクトリ>/` | 認証の入口（middleware の登録と認証ガード）。各モジュールでの認証ガードの登録がルート定義と同じファイルにある構成では、パスではなく下の「差分の内容で判定する領域」で検出する。個々の処理の中の認可はパスで押さえられないため対象にせず、別途の規約・セキュリティの調査で検出する |
| 依存関係 | `<パッケージマニフェスト（例: package.json・*/package.json・composer.json・pyproject.toml）>`・`<ロックファイル>`・`<パッケージマネージャ・ワークスペースの設定ファイル（例: .npmrc）>` | 新規ライブラリの追加はユーザー承認が必須（`.claude/rules/core.md`）。パッケージマネージャの設定が依存のサプライチェーン対策を持つこともある |
| ループのルール | `.claude/`・`CLAUDE.md`・`scripts/` | ループ自身のルールが変わり、誤りが以降のすべての実行に広がる。`scripts/` の `wt-new.sh`・`wt-rm.sh` は、ループが毎回使う worktree の作成・削除（ブランチの削除を含む）を担う |
| ADR・仕様・アーキテクチャ定義 | `docs/adr/`・`docs/specs/`・`docs/architecture/` | 人間が持つ決定の置き場 |
| GitHub の設定 | `.github/` | CI ワークフローそのもの（M3 のゲート） |
| CI の検査を決める設定ファイル | `<フォーマッタ・リンタの設定ファイル>`・`<型チェックの設定ファイル（例: tsconfig*.json）>`・`<テストランナーの共有設定ファイル>`・`<テストの共通 setup・テスト用スタブの置き場>/`・`<ビルド設定ファイル>`・`<依存関係ルール・アーキテクチャ制約の検査設定やその検査テスト>` | 検査を緩めたまま M3 の「CI がすべて成功」を満たせてしまう。テストの共通 setup とテスト用のスタブは、書き換えるとテスト全体を緩められる。依存関係ルールの検査に既知違反リストを持つ構成では、ファイルを移動するリファクタがそのリストも書き換えるため自動マージの対象から外れるが、これは受け入れている |

**差分の内容で判定する領域**（M2）

パスでは押さえられない変更を、PR の差分の内容で検出する。2h 手順1 で、変更ファイル一覧と同じ worktree・同じ
`origin/main` に対して次のコマンドを実行し、1つでも該当すれば M2 を満たさない。
正規表現と pathspec はプロジェクトの言語・テストランナーに合わせて導入時に置き換える（下の例は
JavaScript / TypeScript のテストランナー〈`it` / `test` / `describe` 形式〉の場合。例: pytest なら
`@pytest.mark.skip`・`def test_`、PHPUnit なら `markTestSkipped`・`public function test`）。

- **認証ガードの登録**: 認証ガードをモジュールごとのルート定義ファイルで登録する構成（例: `.use("*", requireAuth)`）では、
  そのファイルはルート定義も兼ねており、パスで対象にするとバックエンドのほとんどの変更が外れるため、middleware の登録
  か middleware の import を含む行が追加・削除されたかで判定する。出力が空でなければ該当
  （該当する構成が無ければ、この検出は「該当なし」と書いて省く）:
  ```
  git -C <worktree パス> diff --name-only --no-renames -G '<middleware の登録・import を表す正規表現（例: \.use\(|middleware/）>' origin/main...HEAD -- <バックエンドのソースディレクトリ>/ ':!<テストファイルの pathspec（例: *.test.ts）>'
  ```
- **テストの無効化**: `it.skip`・`describe.only`・`test.todo` などの修飾子を含む行が追加・削除された。出力が空でなければ該当:
  ```
  git -C <worktree パス> diff --name-only -M -G '\b(it|test|describe|suite)\.(skip|only|todo|fails|skipIf|runIf)\b|\b(xit|xtest|xdescribe)\(' origin/main...HEAD -- '*.test.ts' '*.test.tsx'
  ```
- **テストの削除**: テストケースの宣言（行頭の `it(`・`test(` と、`it.each(` のような修飾子付きの形）の削除行数が、
  追加行数より多い。1行目のコマンドで削除行数、2行目で追加行数を数える（`-M` は移動だけのファイルを数えないため）。
  `grep -c` は0件のとき終了コード1で `0` を出力するので、照会の失敗と取り違えない:
  ```
  git -C <worktree パス> diff -M -U0 origin/main...HEAD -- '*.test.ts' '*.test.tsx' | grep -c -E '^-[[:space:]]*(it|test)(\.[A-Za-z]+)*\('
  git -C <worktree パス> diff -M -U0 origin/main...HEAD -- '*.test.ts' '*.test.tsx' | grep -c -E '^\+[[:space:]]*(it|test)(\.[A-Za-z]+)*\('
  ```

テストを削除・無効化すると、検査を緩めたまま M3 の「CI がすべて成功」を満たせてしまう。使われなくなったコードと
そのテストを一緒に削除するリファクタや、無効化されていたテストを戻す変更も該当して自動マージの対象から外れるが、
これは受け入れている。

ワークフローを追加するときは、定義表の「自動マージの対象」「計画からの逸脱の記録欄」の行にも値を入れる。
自動マージの対象にしないワークフローは「対象外」と書く（空欄にしない）。

## 副指揮役モード（/auto-loop-parallel 配下での実行）

メタ指揮役（`.claude/skills/auto-loop-parallel/SKILL.md`）が本 skill を副指揮役として
起動する場合、呼び出しプロンプトに「副指揮役モード」と明記される。このモードでは
単一 issue を通常の手順どおり処理しつつ、以下の差分のみを適用する。
**計画の承認基準・タッチポイントへの応答基準・エスカレーション条件は通常時と同一**であり、
副指揮役モードで判断品質に関わる基準を変えてはならない。

1. **対話ダイアログの禁止**: 質問・確認・承認依頼は AskUserQuestion などの対話ダイアログを
   使わず、必ず通常のテキスト出力で行う（メタ指揮役は pane 経由のテキストでしか応答
   できないため。子へ 2b で同じ制約を課すのと同型）
2. **セットアップ完了マーカー**: 2b 手順3（ループ本体の投入）が完了した直後・2c の
   監視ループに入る前に、`SETUP` と `_DONE_` と issue 番号をこの順に連結した文字列を
   単独行で出力する（issue #42 なら `SETUP_DONE_42`）。メタ指揮役はこのマーカーで
   セットアップ直列化のブロックを解除し、次の系統の起動へ進む
3. **セットアップ失敗マーカー**: 子を起動する前の失敗（2a の worktree 準備・ベースラインテスト、
   および 2b 手順0 のエスカレーション回答の前処理）でエスカレーションする場合は、
   `SETUP` と `_FAIL_` と issue 番号をこの順に連結した文字列を
   単独行で出力してから、通常のエスカレーション処理を行う
4. **終了報告**: 完了・エスカレーション・対象外に限らず、前提条件エラー・対象 issue の除外など
   **どのような理由で終了する場合でも**、必ず Step 3 のサマリー
   （`## /auto-loop 終了` 見出しを含む）を出力してターンを終える。メタ指揮役は
   この見出しを終了マーカーとして回収する
5. **タブは閉じない**: エスカレーション・対象外終了時の後片付け（子 pane の閉鎖・成果ゼロの
   worktree とブランチの削除）は通常時と同じく副指揮役が行うが、
   自分が動いているタブは閉じられないためメタ指揮役に委ねる。**後片付けを終えてから**
   終了サマリーを出力する（メタ指揮役はサマリーを回収した後にタブを閉じるため、
   サマリーより後に後片付けを行うとタブごと消える可能性がある）。
   サマリーには後片付けの結果（子 pane の閉鎖・worktree とブランチの削除有無）を含める。
   2h 手順8 の削除も含め、「worktree・ブランチの削除手順」の wait がタイムアウトして pane を残した場合は、
   サマリーに `削除処理の pane を残した（<pane ID>）` と書く（メタ指揮役はその系統のタブを閉じない。
   閉じると実行中の `wt-rm.sh` が途中で止まるため）
6. **実行記録の投稿を行わない**: 実行記録ブロック（開始/終了日時・計画承認の差し戻し回数・
   一次レビュー指摘件数と修正の有無・エスカレーション条件の該当要約・トークン消費量
   〈フィールド別〉）の算出とStep3終了サマリーへの出力はこのモードでも行うが、
   トラッキングissueへの `gh issue comment` 投稿はメタ指揮役が実行1回につき1件だけ行うため、
   副指揮役モードでは投稿しない。具体的には「実行記録の投稿」の実行順序のうち手順1〜3だけを行い、
   手順4〜7（トラッキング issue の特定・投稿・実在確認・フォールバック）は行わない。組み立てた記録本文
   （記録テンプレートの見出し行を除く）は、終了サマリーの末尾に `### 実行記録ブロック` の見出しを付けて
   出力する（メタ指揮役が完了回収で読み取る）。投稿を試みていないため「人間への依頼」に `- 実行記録:` 行は
   書かない。Step 0 の告知文の実行記録の一文は「実行記録はメタ指揮役がまとめて投稿します」と読み替える

マーカーを自分の出力として書くときは完成形をそのまま書いてよい（自分の出力は入力エコーに
ならない。分割表記が必要なのは pane にコマンド・プロンプトとして送る側だけであり、
だからこそ本セクションと 2・3 の指示ではマーカーの完成形をメタ指揮役のプロンプトに
含めない取り決めになっている）。

メタ指揮役（/auto-loop-parallel）も定義表の対象ラベル・補助ラベル
（`refactoring` / `bug` / `skill-improvement`）の issue を対象とする。
副指揮役として起動されたときも、ワークフローの判定は通常時と同じくラベルで行う
（メタ指揮役は起動前に同じ判定で振り分け不能・処理済みの issue を落とすが、
判定の正は本 skill の Step 1 側にある）。

## worktree スクリプトの前提

issue ごとの worktree の作成・削除は、プロジェクトが `scripts/wt-new.sh` / `scripts/wt-rm.sh` として用意する
（設計パターンと具体例は `docs/examples/README.md`・`docs/examples/scripts/`）。本 skill の手順は次の振る舞いを
前提にしている。**★を付けた振る舞いは `docs/examples/scripts/` の具体例に含まれていない**ため、
自プロジェクト用のスクリプトを作るときに追加すること。

本 skill では次の表記を使う:

- `<worktree ベース名>`: `wt-new.sh` が worktree を置くディレクトリの名前。プロジェクトルートの親ディレクトリ
  直下に置く（例: `<リポジトリ名>-wt`）
- `<worktree パス>`: issue の worktree の、プロジェクトルート起点の相対パス（`../<worktree ベース名>/issue-<番号>`）

**`scripts/wt-new.sh <番号> <ブランチ名>`**

- `<worktree パス>` に worktree を作る（1 issue = 1 worktree）。`.worktree-registry` に登録し、
  既に登録済みなら `Error: issue N already exists in registry` で失敗する
- ブランチはローカルにあればそれを as-is で使い、リモートにあれば fetch して使い、どちらにも無ければ
  `gh issue develop <番号> --name <ブランチ名> --base main` で作る（分岐点をリモートの main 先端にする。
  後片付けの削除可否判定が `origin/main` を基準にしている前提）
- 並列に動く worktree 同士が衝突しないよう、ポート・DB 名・コンテナのプロジェクト名などを worktree 単位で分離する
- 依存インストール・ローカル DB のマイグレーションなど、ベースラインテストを実行できる状態まで準備する
- `.env` 系の秘密情報ファイルが必要な構成では本体チェックアウトからコピーし、コピーできなかった場合は
  警告を出力する（失敗にはしない）
- 成功したときだけ、最後に `Worktree created successfully` を含む行を出力する（2a 手順4 の wait の成功マーカー）
- ★ `.worktree-registry` の書き換えを排他制御する（`/auto-loop-parallel` では複数の系統が `wt-new.sh` / `wt-rm.sh` を
  同時に実行しうるため。例: アトミックに作成できる `mkdir` をロックに使い、一定時間取れなければ異常終了する）

**`scripts/wt-rm.sh <番号> [--delete-branch]`**

- ★ worktree の中のコピーから実行されても、`git rev-parse --git-common-dir` で本体チェックアウトを解決し、
  本体側の registry・worktree ベースを使う（worktree 側に解決すると別の worktree を消しにいくため）
- 対応するコンテナ等を止めてから `git worktree remove` し、registry から行を消す
  （★ registry の書き換えは `wt-new.sh` と同じく排他制御する）
- 未コミットの変更・未追跡ファイルがあって削除できない場合は削除確認プロンプトを出し、
  ★ 60 秒応答が無ければ中断して非 0 で終了する（無人実行で入力待ちのまま止まらないようにするため）
- ★ `--delete-branch`: worktree のブランチをローカル・リモートとも削除する。ただし、ブランチの先端が
  `origin/main`（fetch して最新化したもの）の祖先であるか、ブランチの先端を head に含むマージ済み PR がある場合
  だけ削除し（squash マージしたブランチは `origin/main` の祖先にならないため）、どちらにも含まれないコミットが
  あれば削除せず `KEPT: ...` とする。既定ブランチは削除しない（`KEPT: refusing to delete the default branch`）
- 最後に `Worktree removed successfully!` の完了バナーを出し、`--delete-branch` 指定時は ★ `Branch: <ブランチ名> (<結果>)`
  行も出す。結果は `local: deleted / remote: deleted`・`local: deleted / remote: not found`・`KEPT: ...`・`SKIPPED: ...`・
  `FAILED` / `UNKNOWN` を含む形のいずれかで、マージ済み PR を根拠に削除した場合は `[merged via PR #<番号>]` を付ける
- ★ ブランチの処理結果が `FAILED` / `UNKNOWN` を含む場合は、完了バナーを出した後に終了コード 1 で終了する

```
指揮役（この skill を実行するセッション、Herdr の1 pane）
├── Step 0: 前提チェック・エスカレーションラベル準備
├── Step 1: 対象 issue の決定・ワークフローの振り分け・処理計画の表示
├── Step 2: issue ごとの処理ループ（並列度1）
│   ├── 2a: 子 pane 作成と worktree 準備（pane 内で wt-new.sh・ベースラインテスト）
│   ├── 2b: 前処理の実行（該当issueのみ）と子 claude 起動（worktree 内で claude → 定義表の投入コマンドを送る）
│   ├── 2c: 監視ループ（タッチポイントへの応答・終端の分類・エスカレーション判定）

│   ├── 2e: PR の実在確認（未作成なら子 pane で /create-pr）
│   ├── 2f: PR 一次レビューと修正（opus で起動し直したレビュー pane で /code-review --fix・1周のみ）・見送った指摘の PR への記録・クリーンアップ

```

worktree は **1 issue = 1 worktree**。子は
`<worktree パス>` で作業するため、指揮役のチェックアウトは汚れず、
エスカレーションした issue は保留理由を issue コメントに残して次の issue へ進める
（保留した系統の pane・worktree の後片付けは「エスカレーション時の後片付け」を参照）。
並列度は本 skill では1（同時に動かす子 pane は1つ）。`wt-new.sh` がポート割当まで worktree 単位で

## 手順

### Step 0: 前提チェック・ラベル準備

**まず引数を検証する**（規則は「引数」節。`--limit` の値の範囲・形式・値の有無）。不正なら
以降の操作を一切行わずに終了する。ラベルの準備はリポジトリに対する副作用のある操作であり、
不正な引数のまま実行しないため、検証は前提チェックよりも前に置く。

前提条件4点を確認する。次にエスカレーションラベル `auto-loop:escalated` を準備する
（旧名 `refactor-loop:escalated` からの移行を含む）:

1. `gh label list` を取得する
2. `auto-loop:escalated` があれば何もしない
3. 無く、旧名 `refactor-loop:escalated` がある場合は**改名する**:
   ```
   gh label edit "refactor-loop:escalated" --name "auto-loop:escalated" --description "auto-loop が人間の判断待ちにした issue"
   ```
   新規作成＋付け替えではなく改名にするのは、GitHub のラベル改名が付与済み issue の紐付けを
   そのまま引き継ぐためである。付け替え作業が要らず、保留中の issue が Step 1 の除外判定から
   漏れる隙間も生まれない
4. どちらも無ければ作成する:
   ```
   gh label create "auto-loop:escalated" --description "auto-loop が人間の判断待ちにした issue" --color "D93F0B"
   ```

改名・作成後は `gh label list` で再取得して実在を確認する（実行したコマンドの出力だけを信用しない）。
改名した場合は `gh issue list --label "auto-loop:escalated" --state all --json number` も実行し、
付与済み issue が新ラベルで引けることを確認する。

**移行の過渡期に旧ラベルが復活していないか**もここで見る。改名を導入したコミットより前に
切られた worktree・チェックアウトには旧 `/refactor-loop` skill が残っており、そこで実行すると
`refactor-loop:escalated` を新規作成してラベルが2つに分かれる。手順1の `gh label list` に
**両方が存在した**場合は、旧名側が付いた issue を
`gh issue list --label "refactor-loop:escalated" --state all --json number,title` で洗い出し、
新名へ付け替えたうえで旧ラベルを削除するか、判断が必要ならユーザーへ報告して指示を仰ぐ
（黙って片方だけを見て進めると、保留中の issue が Step 1 の除外判定から漏れる）。

開始日時を確定し（`date -u +%Y-%m-%dT%H:%M:%SZ`）、続けて `herdr pane get "$HERDR_PANE_ID"` を実行して
`result.pane.agent_session.value`（指揮役自身のセッションID）を控える。どちらも「実行記録の投稿」の
トークン消費量集計・記録テンプレートの開始日時で使う。`herdr pane current --current` を使わないのは、
`--current` がフォーカス中タブの pane に解決され（2a 手順1 と同じ理由）、非フォーカスタブで動く
副指揮役が別 pane のセッションIDを控えてトークン消費量を二重計上するため。

PR 作成の承認確認は行わない（PR 作成は人間の承認なしで進めてよい）。
完了した issue ごとに Step 2e〜2h を実行し、自動マージの条件を満たした PR はマージし、
満たさない PR はレビュー済みの状態で人間へ引き渡す。
あわせて CLAUDE.md が `/auto-loop` による自動マージを許可しているかを確認し、許可していなければ
告知文の自動マージに関する文を「自動マージの条件を判定して結果を添えますが、マージはせずにすべての PR を
引き渡します（CLAUDE.md で自動マージが許可されていないため）」と読み替える。
以下をユーザーへ伝えてから Step 1 へ進む（確認待ちはしない。表示は監査用のログ）:

```
このループで完了した issue は、PR 作成と一次レビュー・修正（1周）・CI チェックの確認まで
自動で進めます。自動マージの条件をすべて満たした PR はマージし、満たさない PR は
満たさなかった条件を添えて引き渡します。自動マージの前に PR へ main を取り込んでコンフリクトした場合は、
コンフリクトを解消した merge コミットを PR ブランチに push します（解消できなければマージせずに引き渡します）。
一次レビューで修正せずに見送った指摘がある PR には、
その指摘を PR にコメントとして投稿します（自動マージの可否には影響しません）。
エスカレーション（人間の判断待ち）にした issue には、
ラベル付与とあわせて保留理由を issue コメントとして投稿します。実行終了時には、この実行の記録
（開始/終了日時・処理結果・トークン消費量等）をトラッキング issue（ラベル `auto-loop:log`）に
コメントとして投稿します。

指揮役は計画承認を人間の代わりに行うため、opus 以上のセッションで実行する前提です。
セッションモデルはこちらから確認できないため、opus 未満で動いている場合は
`/model opus` に切り替えてから再実行してください。
```

### Step 1: 対象 issue の決定とワークフローの振り分け

**候補の収集 → 除外 → 処理順の決定 → 上限件数（`--limit N`。省略時5）の適用**の順に行う。**除外と並べ替えを先に
適用してから N 件を取る**のは、処理済み・保留中・振り分け不能の issue が枠を消費して、候補が
十分あるのに実処理が N 件未満になるのを防ぐため、また優先度の低い issue が枠を埋めて優先度の
高い issue が N 件から漏れるのを防ぐためである。

**1. 候補を集める**

- **引数で番号が指定された場合**: 各番号を `gh issue view <番号> --json number,title,state,labels` で
  実在確認する。指定順を処理順とする
- **引数省略の場合**: 定義表の対象ラベル・補助ラベルごとに
  `gh issue list --label <ラベル> --state open --json number,title,labels` を実行し、
  結果の和集合を候補とする（処理順は手順3で決める）

**2. ワークフローを振り分け、対象外の候補を落とす**

取得したラベルで**ワークフローを振り分ける**（この判定は引数指定・省略のどちらでも同じ）:

| ラベルの状態 | 扱い |
|---|---|
| 定義表の対象ラベルがちょうど1つ付いている | 対応するワークフローで処理する（補助ラベルが併用されていても無視する） |
| 対象ラベルが2つ以上付いている（例: `refactoring` と `bug` の両方） | 処理対象から外す。どちらのワークフローで扱うかは issue の分類そのものの問題であり、人間が決めるべきものだから |
| 対象ラベルが1つも付いておらず、補助ラベルがちょうど1つ付いている | その補助ラベルの列のワークフローで処理する（`skill-improvement` 単独 → bug ワークフロー） |
| 対象ラベルが1つも付いておらず、補助ラベルが2つ以上付いている | 処理対象から外す（対象ラベルが2つ以上の場合と同じ理由） |
| 対象ラベルも補助ラベルも1つも付いていない | 処理対象から外す |

さらに、各 issue について以下に該当するものも処理対象から外す。外した issue は
理由とともに Step 3 の報告に含める（結果欄は「スキップ」）:

- `state` が `CLOSED`（引数指定時のみ発生する。閉じた issue は処理しない）
- `auto-loop:escalated` ラベルが付いている（人間の判断待ち）
- issue コメントに、**振り分け先ワークフローの終端マーカー**（定義表「終端マーカー表」の
  該当ワークフローの全行。完了・エスカレーション・対象外のいずれも）がある

コメントの確認には `gh issue view <番号> --json comments` を使う（`--comments` は
auto mode の環境で空出力になる既知事象があり、空出力を「マーカーなし」と誤判定して
処理済み issue を再処理してしまうため。2d の完了検証と同じ）。

**3. 処理順を決めて上限を適用する**

残った候補を**定義表の「処理優先度」の規約**に従って並べ替える。各 issue の優先度は、手順2の
振り分けが対象ラベル経由・補助ラベル経由のどちらだったかで定義表から引く
（引数で番号が指定された場合は並べ替えを行わず、指定順が処理順になる）。

確定した処理順で最大 N 件（`--limit N`。省略時は5）を取る。候補が N 件未満のときは
候補数がそのまま処理対象になる。番号を明示指定した場合も同じ規則で、指定順を処理順としたまま、
手順2の除外（`CLOSED`・`auto-loop:escalated`・終端マーカー済み・振り分け不能）を先に適用した残りの
候補から取る。除外後に残った指定番号が N 件を超えたら、処理順（指定順）の先頭から N 件だけを処理する
（例: `--limit 2 10 11 12` で #10 が除外対象なら、#11・#12 が処理対象になる）。
**上限で処理対象から外れた候補は、結果「未処理（上限）」として Step 3 の報告に含める**
（明示指定した issue が黙って落ちると、利用者は指定したつもりの issue が処理されたと誤解するため。
`--limit` を利用者が下げられるようになった以上、上限に当たるのは例外ではなく通常の経路である）。
候補が0件なら「対象 issue がありません」と報告して終了する（除外された issue がある場合は
その一覧と理由も添える）。

処理対象・処理順・各 issue の振り分け先ワークフローが決まったら、一覧に適用された上限件数
（`--limit N`。省略時は既定の5）を含めてユーザーに表示してからループを開始する
（確認待ちはしない。表示は監査用のログ）。

### Step 2: issue ごとの処理ループ

対象 issue を1件ずつ、以下の 2a〜2h で処理する。各手順でワークフロー固有の値が必要な箇所は、
その issue の振り分け先ワークフローの行を定義表から引く。

#### 2a: 子 pane 作成と worktree 準備

**worktree 作成とベースラインテストは指揮役の Bash では実行しない**。指揮役のサンドボックスは
プロジェクトルート外（`../<worktree ベース名>/`）への書き込み・`.git/config` の更新・SSH を遮断しており、
`excludedCommands` の除外はトップレベルコマンドにしか効かないため、スクリプト内部の
git / gh はサンドボックス内で失敗する。代わりに先に子 pane（サンドボックスのない通常の
ターミナル）を作り、その中で実行する。

1. `herdr pane layout --pane "$HERDR_PANE_ID"` で自分の pane の形状を確認し、
   横長なら right・縦長なら down で分割する。split は `--current` ではなく必ず自分の
   pane ID 起点で行う（herdr の `--current` はフォーカス中タブの pane に解決されるため、
   非フォーカスタブで動く副指揮役が使うとユーザーが見ているタブに子 pane が作られる）。
   `--cwd` にはプロジェクトルート（`git rev-parse --show-toplevel` で取得）を指定し、
   新 pane の cwd を split 元 pane に依存させない:
   ```
   herdr pane split --pane "$HERDR_PANE_ID" --direction <向き> --no-focus --cwd <プロジェクトルート>
   ```
2. 応答 JSON の `result.pane.pane_id` を読み取り（ID を推測で組み立てない）、
   `herdr pane rename <pane-id> "<定義表の子 pane 名>"` で名前を付ける
3. worktree の有無を次のコマンドで確認する（出力があれば有る）。既にあれば
   worktree 作成をスキップして手順5へ（内側ワークフローは issue コメントから再開ポイントを
   判定できる）:
   ```
   git worktree list --porcelain | grep -E '^worktree .*/<worktree ベース名>/issue-<番号>$'
   ```
   パスの末尾まで照合するのは、`git worktree list` の出力に `issue-<番号>` が含まれるかで見ると
   `issue-80` が `issue-801` に誤マッチするため。worktree の有無を確かめる箇所（手順4 の実在確認・
   「worktree・ブランチの削除手順」）はすべてこのコマンドを使う
4. worktree を pane 内で作成する。ブランチ名は定義表の「ブランチ名」に従う:
   ```
   herdr pane run <pane-id> 'bash -c "scripts/wt-new.sh <番号> <定義表のブランチ名>"'
   herdr wait output <pane-id> --match "Worktree created successfully" --timeout 900000
   ```
   成功マーカーには wt-new.sh 自身の完了メッセージを使う（タイプしたコマンド行に現れないため
   入力エコーに誤マッチしない）。wait が成功したら手順3 のコマンドで実在を確認する。
   タイムアウトしたら `herdr pane read <pane-id> --source recent-unwrapped --lines 80` で
   失敗原因を読んで記録し、その issue をエスカレーションして次へ進む。
   スクリプトがブランチ作成（`gh issue develop` 込み）・ポート割当・依存インストール・
   ローカル DB のマイグレーション・`.env` 系の秘密情報ファイルのコピーまで行う（「worktree スクリプトの前提」）
5. ベースラインテストも pane 内で実行し、**green であることを確認してから**子を起動する
   （テストコマンドは `docs/specs/technical-environment.md` の `## 実行コマンド` を参照）:
   ```
   herdr pane run <pane-id> 'bash -c "cd <worktree パス> && <テストコマンド> && echo TE""ST_RESULT=PASS || echo TE""ST_RESULT=FAIL"'
   herdr wait output <pane-id> --match "TEST_RESULT=" --timeout 900000
   herdr pane read <pane-id> --source recent-unwrapped --lines 40
   ```
   マーカーを `TE""ST_RESULT=` と分割しているのは、入力エコー（タイプされたコマンド行）に
   `TEST_RESULT=` が現れて wait が誤マッチするのを防ぐため（隣接する引用文字列の連結は
   主要なシェルで共通の挙動なので可搬）。red のまま始めると変更起因の失敗と
   切り分けられなくなるため、FAIL ならその issue をエスカレーションして次へ進む。
   これは bug ワークフローでも同じ——バグを捉える回帰テストは子がこれから書くのであって、
   起点は「既存テストが green」でなければ red の意味を切り分けられない。
   ただし bug では**バグの症状そのものが既存テストの失敗**である issue（すでに落ちるテストが
   `main` にある）もここで止まる。この場合「ベースラインが red」だけを理由にすると、
   実態（そのテストを green にするのが issue の目的）と食い違って見えるため、
   エスカレーション理由には**どのテストがどう落ちているか**と、それが issue の症状と
   一致するかどうかの所見まで書く。
   `wt-new.sh` の出力に `.env` 系の秘密情報ファイルのコピー失敗の警告が出ていた場合は
   記録しておき、テストが env 不足で落ちるならエスカレーション理由に含める

#### 2b: 前処理の実行と子 claude 起動

0. **エスカレーション回答の前処理判定・実行**（該当issueのみ。前処理が無ければ即座に手順1へ進む）:
   - Step 1 の除外判定で取得済みの issue コメントを再利用する（取り直す場合も
     `gh issue view <番号> --json comments` を使う。`--comments` は auto mode の環境で
     空出力になる既知事象があるため使わない）。この判定は読み取りのみなので、
     2a の worktree 準備より先に済ませてもよい（前処理が失敗する issue で
     `wt-new.sh`・ベースラインテストの時間を捨てずに済む）
   - `## /auto-loop エスカレーション` コメントが無ければ手順1へ進む
   - あれば、**最新の** `## /auto-loop エスカレーション` コメント以降の「人間の回答コメント」を
     読む。複数回のやり取りがあれば最新のものを含む全体を対象とする。
     **「人間の回答コメント」とは、見出しが次のいずれにも該当しないコメントを指す**
     （denylist 方式。定義表「内側ワークフロー」各 skill の Step 0 再開判定表・
     Step 1 指示はこの定義を参照する）:
     - `## /auto-loop` で始まる見出し（エスカレーション・前処理完了・後片付け訂正・終了など
       auto-loop 自身のマーカー全て）
     - 終端マーカー表の全マーカー（定義表「内側ワークフロー」のコマンド名で始まる見出し）
     - `## 確認済み不明点`
     - 定義表「計画コメントの名称」の各列に `## ` を付けた見出し
       （この列だけ他と違って `## ` を含まない値を持つ。2c 手順4 が文中で名前として使うため）
     - 定義表「実装完了マーカー」の各列
     - 定義表「修正試行カウンタ見出し」で始まる見出し
   - **最新の `## /auto-loop エスカレーション` より後に `## /auto-loop 前処理完了` があれば
     その回の前処理は実行済みなので手順1へ進む**（二重実行防止。指揮役と子の重複実行
     の再発を防ぐ唯一の歯止めなので省略しない）。**「issue のどこかに1件でも
     あればスキップ」にしてはならない**——2回目以降のエスカレーションでは、前回の
     前処理完了コメントが今回の前処理を握り潰し、子も実行しないため誰も実行しなくなる
   - 人間の回答に前処理指示（別issueへの切り出し・他issueへの修正指示など）が含まれるか判定する:
     - 含まれない場合: 手順1へ進む
     - 含まれる場合: **指揮役がここで前処理を実行する**。子はこの前処理を実行しない
       （責務境界は定義表「内側ワークフロー」各 skill の「注意事項」にも明記されている）。
       実行後、次を投稿してから手順1へ進む（本文は一時ファイルに書き出して
       `gh issue comment <番号> --body-file <一時ファイル>` で投稿する）:
       ```
       ## /auto-loop 前処理完了

       - 実行した前処理: <内容>
       - 実行主体: 指揮役（/auto-loop）。子（<定義表の内側ワークフロー>）はこの前処理を実行しない
       ```
     - **投稿後は `gh issue view <番号> --json comments` で実在を確認してから手順1へ進む**。
       auto mode の分類器にブロックされた等で投稿できなかった場合は、**子を起動せずに
       この issue をエスカレーションする**（投稿できなかった本文は Step 3 の「人間への依頼」に
       全文を含める）。前処理は実行済みなのにマーカーが残っていない状態で先へ進むと、
       次回実行の二重実行防止が効かず、指揮役と子が同じ前処理を重複実行する
     - 前処理の実行に失敗した場合は、この issue をエスカレーションして次の issue へ進む
       （子は起動しない）。途中まで実行できていた場合は**どこまで実行したか**を
       エスカレーション理由コメントの「調査で判明した事実」に書く
       （人間が再開するときに重複を避けられるようにするため）

1. 2a と同じ pane で worktree に移動し、auto mode の対話モードで claude を起動する:
   ```
   herdr pane run <pane-id> "cd <worktree パス> && claude --permission-mode auto --model sonnet"
   ```
   auto mode にするのは、子が個別の permission プロンプトで待機してループが停止するのを
   防ぐため（危険な操作は分類器がブロックし、子はエラーとして受け取って報告する）。
   `--model sonnet` を渡すのは、子が担うのが内側ワークフローのオーケストレーション
   （マーカー確認・分岐・コミット）であり、探索・計画・実装・レビューの実作業はすべて
   model 指定済みのサブエージェント（いずれも sonnet）で走るため。内側ワークフローの
   frontmatter には `model:` を置かない方針なので（各 skill の「注意事項」参照）、
   子のモデルはこの起動時の指定で固定する。
   **これは `--model` なしで起動した場合（起動ユーザーの既定モデルを引き継ぐため、
   opus 運用なら opus）からのダウングレードにあたる**。実装は承認済み計画に従う作業であり、
   レビュアー（refactor-auto-reviewer / bugfix-auto-reviewer）も sonnet で対称なため妥当と
   判断しているが、実装品質の劣化が観測されたらここを見直す。品質ゲートである
   PR 一次レビューだけは、2f で opus の別セッションに分離する。
   このリポジトリの共有設定（`.claude/settings.json` の `autoMode.allow`）には
   内側ワークフローの進捗コメント投稿を許可するカスタマイズがあり、worktree にも引き継がれる。
   プロンプトの argv 渡しや非対話フラグ（`-p` 等）は使わない
2. `herdr wait agent-status <pane-id> --status idle --timeout 60000` で起動完了を待ち、続けて
   `herdr pane get <pane-id>` を実行して `result.pane.agent_session.value`（子paneのセッションID）を控える
   （「実行記録の投稿」のトークン消費量集計で使う。`pane run` の直後は claude がまだ起動しておらず
   値が空になるため、起動完了を待ってから取得する。pane を閉じる 2f より前なので取りこぼさない）
3. ループ本体を投入する。定義表の「投入コマンド」に、質問・承認依頼が対話ダイアログ
   （AskUserQuestion）で出されると pane 経由で応答できないため、テキストで行う制約を添えて送る:
   ```
   herdr pane run <pane-id> "<定義表の投入コマンド> 補足: 質問・計画承認の確認は AskUserQuestion などの対話ダイアログを使わず、通常のテキスト応答で行ってください（オーケストレータが pane 経由のテキストで応答するため）"
   ```

#### 2c: 監視ループ

投入後、以下を子が終端（完了 / エスカレーション / 対象外）に達するまで繰り返す:

1. `herdr wait agent-status <pane-id> --status working --timeout 60000` で作業開始を確認する
2. `working` から抜けるのを待つ。`herdr wait agent-status <pane-id> --status idle --timeout 300000`
   のような中程度のタイムアウトで `idle` を待ち、タイムアウトするたびに
   `herdr pane get <pane-id>` で現在状態を確認して分岐する。wait は単一ステータスしか
   待てないため、`blocked` への遷移（対話ダイアログ等。herdr は `blocked` として検出する）は
   このタイムアウト時チェックで拾う——タイムアウトを長くしすぎると blocked の検出が
   その分遅れる:
   - まだ `working`: 実装フェーズ等は時間がかかるため、そのまま待ち直す。ただし
     `herdr pane read <pane-id> --source visible` の表示が数回連続で進んでいない場合は
     ハングを疑い、画面を確認してエスカレーションを検討する
   - `blocked`: 手順3へ
   - `idle` / `done`: 手順4へ
3. **`blocked` の場合**（permission ダイアログや選択式 UI で止まっている）:
   `herdr pane read <pane-id> --source visible --lines 60` で内容を確認する。
   **ダイアログへの自動応答はしない**。権限の承認は人間に残すべき制御であり、
   キー送信での操作は誤爆リスクも高い。エスカレーション（後述）に進む。
   このとき読み取ったダイアログ・エラーの内容は、エスカレーション理由コメントの
   「調査で判明した事実」に転記する（子 pane は後片付けで閉じるため、画面にしか
   存在しない情報はここで書き残さないと失われる。ハング疑いで保留する場合も同じ）
4. **`idle` / `done` の場合**（子のターンが終了。質問・承認依頼・終端報告のいずれか）:
   `herdr pane read <pane-id> --source recent-unwrapped --lines 200` で子の最終出力を読み、
   内容で分岐する:
   - **Step 0 のコメント投稿許可の質問** → `herdr pane run <pane-id> "はい"` で許可する
   - **Step 2 の不明点質問** → 「タッチポイントへの応答基準」に従って回答を作り、
     `pane run` で送る。エスカレーション条件に該当する質問が含まれていたらエスカレーション
   - **Step 4 の計画承認依頼** → 定義表「計画の承認基準」に従って批判的にレビューする。
     指摘があればフィードバックを `pane run` で送る（修正→再提示は複数回対応）。
     フィードバックを送って計画の修正・再提示を求めるたびに、その issue の
     「計画承認の差し戻し回数」カウンタ（issue の処理開始時点で0）を1増やす
     （「実行記録の投稿」の記録テンプレートで使う）。**カウントするのはこの「フィードバックを
     送って修正・再提示を求めた回数」のみとし、パターン3（確認事項付き承認）や、
     判断できない出力への問い合わせ（本手順4「判断できない出力」）はカウントしない**。
     基準を満たしたら次を送って承認する（`<計画コメントの名称>` は定義表から引く）:
     ```
     OK。承認者: auto-loop 指揮役エージェント（自動承認）。この注記を「<計画コメントの名称>」コメントのフィードバック履歴に含めてください。
     ```
     確認事項がある場合は「計画の承認基準」節の「パターン3（確認事項付き承認）の扱い」に従う。
   - **終端マーカーを含む報告** → 定義表「終端マーカー表」で結果分類を引いて分岐する:
     - **完了** → 2d へ
     - **エスカレーション** → エスカレーション（後述）
     - **対象外** → 対象外終了（後述）
   - **判断できない出力** → 1回だけ「現在の状況と次に必要な入力を教えてください」と
     `pane run` で問い合わせる。それでも判断できなければエスカレーション
5. 応答を送ったら手順1に戻る

タッチポイントへの回答・承認・フィードバックの内容は、その都度指揮役自身の出力にも
記録する（何をどう判断したかの監査ログとして残すため）。

#### 2d: 完了検証

子の完了報告を pane 出力だけで信用せず、以下で検証する:

1. `gh issue view <番号> --json comments` の出力に、定義表の**完了マーカー**が
   あること（`--comments` は auto mode の環境で空出力になる既知事象があるため
   `--json comments` を使う）
2. `git -C <worktree パス> log origin/main..HEAD --oneline` にこの issue の
   コミットが積まれていること（比較対象がローカル `main` ではなく `origin/main` なのは
   後片付けの削除可否判定と同じ理由。「エスカレーション時の後片付け」を参照）

両方確認できたら 2e へ進む。検証に失敗したら（マーカーなし・コミットなし）
エスカレーションする。

#### 2e: PR の実在確認（作成されていなければ子 pane で作成）

PR は内側ワークフローが最終 Step で自分で作成する。指揮役はその結果を検証する:

```
gh pr list --head <ブランチ名> --json number,url
```

PR が存在すれば番号・URL を記録して 2f へ進む（子 pane の出力に書かれた PR URL は
鵜呑みにせず、必ずこのコマンドの結果で確認する）。

PR が存在しない場合のみ、フォールバックとして子 pane に作成を指示する:

```
herdr pane run <pane-id> "/create-pr を実行してください"
```

2c と同じ要領で完了を待ち、再度 `gh pr list --head <ブランチ名>` で実在を確認する。
それでも作成されていなければエスカレーションする（ブランチは引き渡せる状態なので
人間が対応できる）。

#### 2f: PR 一次レビューと修正（レビュー pane・1周のみ）・クリーンアップ

一次レビューは、実装を行った子ではなく **opus で起動し直した別セッション** に行わせる。
まず実装用の子 pane を閉じ、同じ worktree にレビュー用の pane を新しく用意する:

```
herdr pane close <実装 pane-id>
herdr pane split --pane "$HERDR_PANE_ID" --direction <向き> --no-focus --cwd <プロジェクトルート>
herdr pane rename <レビュー pane-id> "review-<番号>"
herdr pane run <レビュー pane-id> "cd <worktree パス> && claude --permission-mode auto --model opus"
```

```
herdr wait agent-status <レビュー pane-id> --status idle --timeout 60000
herdr pane get <レビュー pane-id>
```

起動完了を待った後の `pane get` の応答から `result.pane.agent_session.value`（レビューpaneのセッションID）を
控える（「実行記録の投稿」のトークン消費量集計で使う。取得のタイミングは 2b 手順2 と同じ理由）。

split の要領（形状の確認・向きの決定）は 2a 手順1と同じ。
セッションを作り直す理由は3つ:

1. 実装まで終えた子のコンテキストは大きく、そのままレビューさせると圧迫・自動コンパクションで
   品質が落ちる
2. 実装の文脈を持ったままのレビューは「自分の作業に同意する」バイアスがかかる——まっさらな
   文脈で diff を読ませることで、人間の一次レビューに近い独立性を確保する
3. 一次レビューは人間のレビューの代理であり、生成側（2b で sonnet に固定した子）より弱い
   モデルで通すと非対称なゲートになる（同じ理由で /dev-auto の実装レビュアーも opus）

起動済みセッションに `/model opus` を送ってモデルを引き上げる方式は採らない。モデル選択 UI が
開くと pane が `blocked` になり、「ダイアログへの自動応答はしない」という本 skill の方針
（2c 手順3）と衝突するため。起動時の `--model opus` なら指定は確実に効き、状態の確認も不要になる。

pane の作り直しは必ず 2e（PR の実在確認）の後に行う（PR 本文の推論には実装の文脈があるほうが
良く、フォールバックで /create-pr を投入する可能性もあるため）。

起動を確認したら、まず対話ダイアログを使わない制約を単独で送る（2b 手順3 で子に課すのと
同じ制約。レビューセッションも指揮役とは pane 経由のテキストでしかやりとりできない）:

```
herdr pane run <レビュー pane-id> "このセッションでは、質問・確認・判断の相談を AskUserQuestion などの対話ダイアログで出さず、必ず通常のテキスト応答で行ってください（指揮役が pane 経由のテキストで応答するため）。了解したら次の指示を待ってください"
herdr wait agent-status <レビュー pane-id> --status idle --timeout 60000
```

2b と違って投入コマンドに補足として添えないのは、`/code-review` が引数をレビュー対象
（PR 番号・ブランチ・パス）として解釈するため、制約文を後ろに繋ぐとレビュー範囲が
壊れるからである。

制約を送ったら、品質観点の一次レビューを実行させる（レビュー対象の diff は会話ではなく
git の状態から取れるため、実装セッションを捨てても成立する）:

```
herdr pane run <レビュー pane-id> "/code-review --fix"
```

2c と同じ要領で完了を待つ（ターン終了は `idle` / `done` のどちらもありうるため、
`herdr pane get` での状態確認を挟んで分岐する）。続けて後処理を指示する。
レビューセッションは issue の文脈を持たないため、issue 番号を明示する:

```
herdr pane run <レビュー pane-id> "修正が入った場合は、既存テストを実行して green を確認し、#<番号> プレフィックスのコミットメッセージで追加コミットして push してください（amend は使わない）。修正がなければ何もしなくてよいです"
```

このレビュー・修正は **1周のみ**。内側ワークフロー内で計画準拠のレビューは最大3回実施済みで、
ここは観点の異なる品質レビューの追加層にすぎない——1周で収束しないものは自動で
こね続けるより人間に渡すほうが安全である。修正後のテストが green に戻らない場合は
エスカレーションする。

後処理の完了を待ったら、一次レビューの結果（指摘件数・修正の有無）を記録する（「実行記録の投稿」の
記録テンプレートで使う。修正の内容は PR に残る追加コミットで追えるため記録しない。レビューの出力から
読み取れない値は「不明」とする）。一次レビューの結果は自動マージの条件には使わない（理由は定義表
「自動マージの条件」の冒頭）。

続けて、修正後のテストの結果にかかわらず、下の「見送った指摘の記録」を行う。そのうえで、修正後のテストが green に
戻らなかった場合はエスカレーションし（閉じる対象はレビュー pane。「エスカレーション時の後片付け」の手順2）、それ以外は
レビュー pane を閉じて 2g へ進む。worktree・ブランチはここでは削除しない（2h で自動マージした場合は 2h 手順8 で削除する。
それ以外は PR のマージ後に人間が `scripts/wt-rm.sh <番号>` で片付ける）。

**見送った指摘の記録**

一次レビューの指摘のうち修正を当てなかったもの（修正不要と判断したもの・PR の差分の外にある既存の問題を含む。
以下「見送った指摘」）を、PR にコメントとして残す。見送った指摘はレビュー pane と指揮役の出力にしか残らず、
pane を閉じた後は内容を追えなくなるため。

1. レビュー pane に見送った指摘の列挙を指示する（`pane run` に渡す文字列に改行を含めない）:
   ```
   herdr pane run <レビュー pane-id> "一次レビューの指摘のうち、修正を当てなかったもの（修正不要と判断したもの・PR の差分の外にある既存の問題を含む）をすべて、1件ずつ「指摘の内容」「対象ファイル」「見送った理由」の3項目で列挙してください。該当が無ければ「見送った指摘は0件です」とだけ答えてください"
   ```
   2c と同じ要領で完了を待ち、`herdr pane read <レビュー pane-id> --source recent-unwrapped --lines 200` で読み取る。
   見送った指摘を読み取れなかった場合は、コメントを投稿せずに手順5へ進む
2. 見送った指摘が0件なら、コメントを投稿せずに手順5へ進む
3. 1件以上なら、投稿の前に、同じ見出しのコメントの件数を次で控える:
   ```
   gh pr view <PR番号> --json comments --jq '[.comments[] | select(.body | startswith("## /auto-loop 一次レビューで見送った指摘"))] | length'
   ```
   続けて、次の本文を一時ファイルに書き出して `gh pr comment <PR番号> --body-file <一時ファイル>` で投稿する。
   見出しは検索用の固定文字列（**変更しない**）:
   ```
   ## /auto-loop 一次レビューで見送った指摘

   - 対象 issue: #<番号>（<ワークフロー>）
   - 一次レビューの指摘件数: <件数>（修正 <件数> 件・見送り <件数> 件）
   - この記録は自動マージの可否に影響しない。対応が必要な指摘を別の issue にするかは人間が判断する

   ### 見送った指摘 1
   - 指摘の内容: <内容>
   - 対象ファイル: <リポジトリルート起点のパス。複数あれば読点で区切る>
   - 見送った理由: <理由>

   ### 見送った指摘 2
   - …
   ```
4. 投稿後に手順3の件数のコマンドを実行し直し、件数が1増えていることで実在を確認する（コマンドの出力だけを
   信用しない。同じ PR に過去の同じ見出しのコメントがあっても投稿の失敗を見逃さないよう、見出しの有無ではなく
   件数の増加で確認する）。確認できたら、次でコメントの URL を取得する（最後の1件が今回の投稿）:
   ```
   gh pr view <PR番号> --json comments --jq '[.comments[] | select(.body | startswith("## /auto-loop 一次レビューで見送った指摘"))] | last | .url'
   ```
   投稿に失敗した場合（auto mode の分類器によるブロックを含む）と、件数の増加を確認できなかった場合は、
   本文全文と失敗の理由を記録する。どちらもエスカレーションにせず、ループの処理を続ける
5. 結果を記録する。見送った指摘がある PR（手順1で読み取れなかった PR を含む）は、Step 3 のサマリーの
   「人間への依頼」の「一次レビューで見送った指摘」に、PR 番号とコメントの URL（投稿できなかった場合は本文全文と
   失敗の理由、読み取れなかった場合はその旨）を書く

見送った指摘の有無は、issue の結果分類（「完了」のまま）・全体停止のエスカレーション集計・2h の自動マージの可否の
いずれにも影響させない。

#### 2g: CI チェック確認

一次レビューの修正・追加コミットの push（2f）が終わった PR について、GitHub Actions の CI
チェック結果を指揮役自身の Bash で確認する（読み取り専用の `gh` の直接実行は 2d・2e と同じ
前例であり、「環境を変更する操作は子 pane で行う」の対象外）。この工程は結果分類「完了」の
issue にのみ適用し、エスカレーション・対象外の issue は 2e〜2h すべてをスキップする
（定義表「結果分類ごとの扱い」参照）。

1. `gh pr checks <PR番号> --json name,state,bucket,workflow` を実行する**前に**、
   `gh pr view <PR番号> --json headRefOid` を取得し、その値が worktree の HEAD
   （`git -C <worktree パス> rev-parse HEAD`）と一致することを確認する。
   **一致しない間は `gh pr checks` の照会結果を採用せず、30秒待って再照会する**（2f の追加 push 直後は
   `gh pr checks` が直前コミットのチェック結果を返すことがあり、それを最新コミットの結果と
   誤読するのを防ぐため）。一致確認を待つ時間も手順4の30分上限に含める。
   ただし一致しないときは、先に `git ls-remote --heads origin <ブランチ名>` のリモート先端を
   worktree の HEAD と比べる。リモート先端が HEAD と異なる（2f の修正コミットが push されて
   いない）場合は待っても一致しないため、待機せずにエスカレーションする（理由コメントには
   未 push のコミットと worktree パスを書く）。リモート先端が HEAD と一致している場合、
   または `ls-remote` が失敗・空で判定できない場合だけ、PR への反映待ちとして再照会を続ける
2. 一致を確認したら `gh pr checks <PR番号> --json name,state,bucket,workflow` を実行する。
   `bucket` は `skipping` を `pass` 相当、`cancel` を `fail` 相当として扱う。チェックは
   `workflow` と `name` の組（例: `frontend test / test`）で識別する（`test`・`lint`・`ci` のように
   同じ `name` が複数のワークフローに存在しうり、`name` だけでは失敗箇所を特定できないため）:
   - 手順3の発火条件の突合で発火するはずのワークフロー（YAML の `name:` が `workflow` の値に
     対応する）のうち、`workflow` にまだ現れていないものが1つでもある → チェックの登録待ちとして
     `pending` と同じく扱う（先に登録されたチェックだけが `pass` の時点で「成功」と誤判定しないため）
   - `pending` が1件も無く、全チェックが `pass`（`skipping` を含む） →
     CI結果「成功」で完了へ（手順6）
   - `pending` が1件でも残っている場合は、`fail`（`cancel` を含む）を検出していても
     即座にエスカレーションへ回さず、**全チェックの完了（`pending` が無くなること）を
     待ってから判定する**（30秒待って再照会）。`pending` が無くなった時点で `fail`
     （`cancel` を含む）を含む → 該当する**チェック（`workflow / name`）をすべて収集**して
     エスカレーションへ（手順7）
3. **0件時**（出力が `no checks reported`）: 終了コード1は照会エラー（通信・認証・API 制限）でも
   返るため、終了コードだけで0件と判定しない。`no checks reported` 以外のエラーは照会失敗として
   30秒後に再照会する（30分上限に含める）。0件なら30秒間隔で最大3回（約90秒）再照会。
   それでも0件なら `gh pr view <PR番号> --json files` の変更ファイルと
   `.github/workflows/*.yml` の `on.pull_request.paths` を突合し、どのワークフローの
   発火条件にも一致しない場合のみ CI結果「対象外」として完了へ（手順6）。該当するのに
   0件のままなら待機継続（YAML解析が曖昧な場合も安全側＝待機継続）。突合では次に従う:
   - ワークフロー定義は指揮役のチェックアウトではなく worktree 側
     （`<worktree パス>/.github/workflows/`）を読む。`pull_request` は PR 側の定義で
     発火するため。拡張子 `.yaml` のファイルも含める
   - `on.pull_request` に `paths` が無いワークフローはすべての変更に一致するものとし、
     `paths-ignore` は列挙外の変更に一致するものとして扱う
   - `files` は取得件数に上限（100件）があるため、100件に達していたら一致ありとみなす
4. 上記ポーリング（手順1の一致確認待ちを含む）を最初の照会から合計1,800,000ms（30分）まで
   継続する（Bash 1回の呼び出しのタイムアウト上限が600000msのため、複数回に分割して実行する）
5. 30分超過で未確定ならタイムアウトとしてエスカレーションへ（手順7）。この時点で
   `fail`/`cancel` のチェックが既にある場合は、手順7の理由コメントに失敗チェックと
   あわせて**未完了（`pending`）のチェックも書く**（いずれも `workflow / name` で書く）
6. **完了**: CI結果（成功/対象外）を Step 3 サマリーの完了行の備考に `CI: 成功` /
   `CI: 対象外` として反映し、2h へ進む（2h 手順4 または 2h「main への追従で起きたコンフリクトの解消」から
   2g を再実行している場合は、2h 手順5 へ戻る）
7. **エスカレーション**（CI失敗・タイムアウト）: 既存の「エスカレーション（issue単位の保留）」
   手順に従うが、「判断が決まった後にすること」はこのケース限定で以下に置き換える:
   - PR番号・失敗（`fail`/`cancel`）チェックの `workflow / name`（タイムアウト時はその時点の
     各チェックの状態。手順5の未完了チェックを含む）・worktreeパスを理由コメントに明記する
   - CI失敗の修正自体はこのループのスコープ外であり、人間がPRブランチ上で直接対応する
   - 完了マーカーが残っている限り `/auto-loop` のStep1除外判定で再実行対象にならない
     （「ラベルを外して再実行」はこのケースでは成立しない旨を明記する）
   - 2h「main への追従で起きたコンフリクトの解消」で push した後の再実行で失敗・タイムアウトした場合は、
     コンフリクトを解消した merge コミットを push したことと、コンフリクトしたファイルのパスも理由コメントに書く。
     Step 3 サマリーのエスカレーションの行の備考にも、2h 手順9 の書式（`コンフリクト解消: <パス>`）で書く
     （CI の失敗がコンフリクトの解消に起因するかを、人間が切り分けられるようにするため）

#### 2h: 自動マージ

2g で結果が「完了」になった PR について、定義表「自動マージの条件」（M1〜M6）を判定し、
すべて満たせばマージして worktree・ブランチを削除する。1つでも満たさなければマージせず、満たさなかった条件を Step 3 の
サマリーに書いて人間に引き渡す（結果分類は「完了」のまま。エスカレーションにはしない。
ただし手順4 で main に追従した後〈コンフリクトを解消した場合を含む〉の 2g で CI が失敗した場合は、2g のとおりエスカレーションになる）。
CLAUDE.md が `/auto-loop` による自動マージを許可していない場合は、手順1〜2 で判定した結果を記録して手順9へ進む
（定義表「自動マージの条件」を参照）。

1. **変更ファイル一覧と差分の内容の検出結果を取得する**。読み取りと remote-tracking ref の更新だけなので、指揮役の Bash で
   実行してよい（後片付けの判定と同じ）:
   ```
   git fetch origin main --quiet
   git -C <worktree パス> diff --name-only --no-renames origin/main...HEAD
   ```
   `--no-renames` を付けるのは、領域の外へ移動したファイルの移動元も一覧に出すため。
   続けて、定義表「自動マージの条件」の「差分の内容で判定する領域」のコマンドを実行し、結果を記録する。
   `git fetch` が失敗した場合は `origin/main` が古く一覧が正しくない可能性があるため、M2 を満たさない扱いにする
   （差分の内容の検出コマンドが失敗した場合も同じ）
2. **副作用のない条件を判定する**。M1・M2・M4・M5・M6 と、M3 のうち CI 結果（2g の CI 結果が
   「対象外」なら満たさない）を判定する（判定方法は定義表「自動マージの条件」）
3. **分岐する**。手順2で満たさない条件が1つでもあれば、満たさなかった条件をすべて記録して手順9へ進む。
   M3 を CI 結果で満たさないと判定していない場合は、M3 を「未判定（他の条件を満たさないため
   追従していない）」と記録する（main への追従は PR ブランチへの push を伴うため、マージしないと
   決まった PR には行わない）。すべて満たしていれば手順4へ
4. **M3 の後半: main に追従させる**。`gh pr view <PR番号> --json headRefOid,baseRefName` を取得し、
   PR の head が base から遅れているコミット数を比較 API で確認する:
   ```
   gh api "repos/{owner}/{repo}/compare/<baseRefName>...<headRefOid>" --jq .behind_by
   ```
   - `0` → 追従は不要。手順5へ
   - `1` 以上 → PR ブランチに base を取り込む。環境を変更する操作なので、2a 手順1 の要領で
     pane を新しく split し（`--cwd` にプロジェクトルート・`--no-focus`）、その中で実行する:
     ```
     herdr pane run <pane-id> 'bash -c "cd <worktree パス> && git fetch origin <baseRefName> || { echo FOL""LOW_RESULT=FETCH_FAILED; exit 0; }; if git merge -m \"#<番号> <baseRefName> を取り込む\" origin/<baseRefName>; then git push origin HEAD && echo FOL""LOW_RESULT=PUSHED || echo FOL""LOW_RESULT=PUSH_FAILED; elif git diff --name-only --diff-filter=U | grep -q .; then echo FOL""LOW_RESULT=CONFLICT; else git merge --abort; echo FOL""LOW_RESULT=MERGE_FAILED; fi"'
     herdr wait output <pane-id> --match "FOLLOW_RESULT=" --timeout 300000
     herdr pane read <pane-id> --source recent-unwrapped --lines 40
     ```
     マーカーを分割しているのは 2a 手順5 と同じ理由（入力エコーへの誤マッチ防止）。
     rebase・force push ではなく merge にするのは、内側ワークフローが amend・rebase を禁じ、
     force push も `.claude/settings.json` で拒否されているため（手順6 の squash マージでまとめられるので、
     merge コミットは main の履歴に残らない）。
     merge が失敗したときに未解消のファイル（`--diff-filter=U`）があればコンフリクトとして `CONFLICT` を出し、
     `merge --abort` せずに merge の途中の状態を残す（解消に進むため）。未解消のファイルが無い失敗は、
     `merge --abort` で戻して `MERGE_FAILED` を出す。
     読み取ったら pane を閉じ、結果で分岐する:
     - `PUSHED` → 2g を手順1から再実行し、追従後のコミットで CI チェックを確認する。2g の判定は
       そのまま適用する（CI の失敗・タイムアウトは 2g 手順7 のエスカレーションになる。main を
       取り込んだ状態で壊れており、人間の対応が必要なため）。2g が「完了」になったら手順5へ
     - `CONFLICT` → 下の「main への追従で起きたコンフリクトの解消」を行う。解消して push できたら、
       同手順のとおり 2g を手順1から再実行して手順5へ。解消できなかった場合は M3 を満たさないとして手順9へ
     - `MERGE_FAILED`（コンフリクト以外の理由で merge が失敗した） → M3 を満たさない（理由: main の取り込みに
       コンフリクト以外の理由で失敗した。読み取った出力の要点を添える）。
       `git -C <worktree パス> status --porcelain` が空であること（`merge --abort` で
       戻っていること）を確認し、空でなければその事実も記録する。手順9へ
     - `PUSH_FAILED` → M3 を満たさない（理由: 追従した merge コミットを push できなかった）。worktree に
       未 push の merge コミットが残っていることと worktree パスを記録する。手順9へ
     - `FETCH_FAILED`・wait のタイムアウト → M3 を満たさない（理由と、読み取った出力の要点を記録する）。手順9へ
5. **マージ直前の確認**。次の M3 の確認と、コンフリクトを解消した場合の M2 の判定し直しをすべて行う。
   満たさないものがあれば、満たさなかった条件をすべて記録して手順9へ
   （追従は1回までとし、ここで再度追従しない。並列実行で main が進み続けると、追従と CI 待ちを
   繰り返して終わらなくなるため。コンフリクトを解消した場合も同じ）。

   M3 の確認（1つでも満たさなければ M3 を満たさない）:
   - 最後に実行した 2g の CI 結果が「成功」である。手順4 で追従して 2g を再実行した場合は、その再実行の結果で
     判定する（手順2 は追従前の CI 結果しか見ていないため。「対象外」なら理由は「追従後のコミットの CI 結果が対象外」）
   - `gh pr view <PR番号> --json headRefOid` を取り直し、その値が 2g で CI を確認したコミット（worktree の HEAD）と一致する
   - ここで取り直した headRefOid で比較 API を呼び、`behind_by` が `0` である（`1` 以上なら理由は「CI の確認中に
     main が進んだ」）。手順4 で取得した追従前の headRefOid を使わない（追従前のコミットは main を含まないため、
     常に `1` 以上になる）:
     ```
     gh api "repos/{owner}/{repo}/compare/<baseRefName>...<ここで取り直した headRefOid>" --jq .behind_by
     ```

   M2 の判定し直し（手順4 でコンフリクトを解消して push した場合だけ行う）: 手順1 を実行し直し、その結果で M2 を
   判定し直す（worktree の HEAD は、上の確認で headRefOid と一致した解消後の merge コミットである）。
   人間の確認が必須な領域のパターンか、差分の内容の検出に1件でも当たれば M2 を満たさない（理由: 解消後のコミットで
   当たったパス。差分の内容の検出で当たった場合は、検出の名前と出力の要点も添える）。解消した差分が main 側の変更
   （テストなど）を落としていないか、人間の確認が必須な領域に触れていないかを、一次レビュー後の修正と同じく M2 の検出で
   確かめるため
6. **マージする**。プロジェクトルートで次を実行する:
   ```
   gh pr merge <PR番号> --squash --match-head-commit <手順5で確認した headRefOid>
   ```
   - `--squash` にするのは、main の履歴を PR ごとに1コミットに揃える運用を前提にしているため
     （手順4 の merge コミットが main の履歴に残らないのもこの前提による）
   - `--match-head-commit` を付けるのは、確認した後に PR へ別のコミットが push されていたら
     マージを拒否させるため
   - `--delete-branch` は付けない（worktree がブランチをチェックアウトしているため。
     リモートブランチはリポジトリの設定〈GitHub の「Automatically delete head branches」〉が有効ならマージ時に
     自動削除され、無効でも手順8 の `wt-rm.sh --delete-branch` がローカルブランチとあわせて削除する）
   - 実行後、`gh pr view <PR番号> --json state,mergedAt` で `state` が `MERGED` であることを確認する
     （コマンドの出力だけを信用しない）。コマンドが失敗した、auto mode の分類器にブロックされた、
     `MERGED` になっていない場合は、マージ失敗としてエラーの要点を記録して手順9へ
7. **自動マージの記録を PR にコメントする**。本文を一時ファイルに書き出して
   `gh pr comment <PR番号> --body-file <一時ファイル>` で投稿し、`gh pr view <PR番号> --json comments` で
   実在を確認する。投稿できなかった場合（分類器のブロック等）は、本文を Step 3 の
   「人間への依頼」の「自動マージの記録コメント」欄に全文含める:
   ```
   ## /auto-loop 自動マージ

   - 対象 issue: #<番号>（<ワークフロー>）
   - マージしたコミット: <headRefOid>（squash）

   ### 満たした条件
   - M1 自動マージの対象ワークフロー: <refactor（対象ラベル経由） / bug（対象ラベル経由・判定方式: 回帰テスト・テスト対象外の検証項目なし）>
   - M2 人間の確認が必須な領域: 変更ファイル <件数> 件のいずれも該当しない。差分の内容の検出（認証ガードの登録・テストの無効化・テストの削除）も該当なし<コンフリクトを解消した場合のみ: 。コンフリクトの解消後のコミットで判定し直した>
   - M3 main への追従と CI: <追従不要 / main を取り込んで push（<merge コミット>） / main を取り込み、コンフリクトを解消して push（<merge コミット>）>。CI チェック <件数> 件がすべて成功
   - M4 エスカレーション: 経ていない
   - M5 計画外の変更・計画からの逸脱: 記録なし
   - M6 worktree の未コミットの変更: なし

   ### main への追従で解消したコンフリクト
   - <コンフリクトしたファイルのパス。1行に1件>
   ```
   「main への追従で解消したコンフリクト」の節は、手順4 でコンフリクトを解消した場合だけ書く（解消していなければ節ごと省く）。
   パスは「main への追従で起きたコンフリクトの解消」の手順1 で控えたものを使う。
8. **worktree・ブランチを削除する**（手順6 でマージを確認した場合だけ行う。手順9 へ直接進んだ PR の worktree・ブランチは
   削除しない）。自動マージした PR には人間が関わらないため、ここで削除しないと誰も片付けない。ローカルブランチまで
   削除するのは、残すと同じ issue を再実行したときに `wt-new.sh` がマージ済みのブランチを as-is で再利用し、
   古い分岐点からやり直すことになるため。

   「worktree・ブランチの削除手順」で削除する。この時点で実装用・レビュー用・追従用・コンフリクトの解消用の pane はすべて閉じているため、
   同手順の pane は新しく split する。
   - squash マージしたブランチは `origin/main` の祖先にならないが、`wt-rm.sh --delete-branch` はブランチの先端を head に
     含むマージ済み PR があれば削除する（手順6 は `--match-head-commit` でマージしているため、通常は該当する）
   - 未コミットの変更が無いことは M6 で確認済みのため、事前に確認し直さない（残っていれば `wt-rm.sh` が削除確認
     プロンプトで中断し、削除失敗として記録される）

   削除に失敗しても結果分類は「完了」のまま変えず、エスカレーションもしない（PR はマージ済みで、残るのは
   ローカルの worktree・ブランチだけのため）。
9. **結果を記録する**。Step 3 サマリーの完了行の備考に、自動マージした場合は `自動マージ: 済み`、
   条件を満たさずマージしなかった場合は `自動マージ: 未実施（<満たさなかった条件の番号と理由>）`、
   マージに失敗した場合は `自動マージ: 失敗（<エラーの要点>）` と書く
   （例: `自動マージ: 未実施（M2: db/migrations/0017_add_x.sql / M5: 実装完了マーカーの「計画から逸脱した点」が「なし」以外）`）。
   手順4 でコンフリクトを解消して push した場合は、自動マージしたかどうかにかかわらず、`コンフリクト解消: <コンフリクトしたファイルのパス。複数あれば読点で区切る>`
   も書く（例: `CI: 成功。コンフリクト解消: src/x/service.ts、web/x/api.ts。自動マージ: 済み`）。
   push した後の 2g で CI が失敗・タイムアウトしてエスカレーションになった場合は、この手順には来ないため、2g 手順7 のとおり
   エスカレーションの行の備考に同じ書式で書く。
   自動マージした場合は、あわせて手順8 の結果を `worktree・ブランチ: 削除済み` / `worktree・ブランチ: 削除失敗（<残ったものと理由>）`
   と書く（例: `worktree・ブランチ: 削除失敗（ブランチ 12-refactor/x が残った。Branch: KEPT: ...）`。削除処理の pane を残した
   場合は「副指揮役モード」5 と同じく `削除処理の pane を残した（<pane ID>）` も書く）。
   削除に失敗した場合は、Step 3 の「人間への依頼」の「マージ後の後片付け」にも issue 番号・残ったもの・理由・手で片付ける方法を書く
   （pane を残した場合は、その pane で `wt-rm.sh` が終わったのを確かめてから片付ける旨を添える。worktree が残っていれば通常は
   `scripts/wt-rm.sh <番号> --delete-branch` で、未コミットの変更がある場合は内容を確認してから実行する旨を添える。registry に
   行が無いなど `wt-rm.sh` が使えない場合は `git worktree remove <worktree パス>`。ブランチだけが残った場合は
   `git branch -D <ブランチ名>`）。
   次の issue へ進む

並列実行（`/auto-loop-parallel`）では、他の系統が先にマージすると main が進むため、後から 2h に
到達した PR は手順4 の追従と CI の再確認を経ることが多くなり、追従でのコンフリクトも起きやすくなる
（下の「main への追従で起きたコンフリクトの解消」で解消する）。手順5 の確認から手順6 のマージまでの
わずかな間に他の系統がマージした場合は検出できない（残るリスクとして受け入れている）。

#### main への追従で起きたコンフリクトの解消

2h 手順4 の追従が `CONFLICT` になったときの手順。コンフリクトを解消した merge コミットを PR ブランチに push し、
自動マージの判定を続ける（線引きの理由は定義表「自動マージの条件」の冒頭）。rebase・force push は使わない（2h 手順4 と同じ理由）。
解消した差分は一次レビュー（2f）をやり直さずに、2g の CI チェックと 2h 手順5 の M2 の判定し直しで検証する。

コンフリクトの解消（ファイルの編集）は、新しく起動した opus のセッションに行わせ、merge コミットの作成と push は
指揮役が pane のシェルで行う。環境を変更する操作は pane の中で行い、指揮役の Bash では読み取りだけを行う
（2a と同じ理由）。コミットと push を解消のセッションに任せないのは、push の前にコンフリクトマーカーと
未コミットの変更を指揮役が確かめるため。
コンフリクトしたファイルのパスは、`pane run` で送る文字列に埋め込まない（ファイルベースルーティングの
`$id.tsx` のように `$` を含むファイル名がありうり、シェルに変数として展開されるため）。

途中で失敗した場合（下の各手順で「失敗」とするもの）は、手順7 で記録して 2h 手順9 へ進む（M3 を満たさない）。

1. **コンフリクトしたファイルを控える**（指揮役の Bash。読み取りのみ）:
   ```
   git -C <worktree パス> diff --name-only --diff-filter=U
   ```
   出力の各行がコンフリクトしたファイルのパスで、自動マージの記録コメント（2h 手順7）と Step 3 サマリーの備考
   （2h 手順9）に載せる。コマンドが失敗した場合と、出力が空の場合は、失敗（理由: コンフリクトしたファイルを
   特定できなかった）とする。
   パスを含むコメントの本文（2h 手順7 の記録コメント・2g 手順7 の理由コメント）を一時ファイルに書き出すときは、
   Write ツールか、区切り文字をクォートしたヒアドキュメント（`<<'EOF'`）を使う。パスに含まれる `$` が
   変数として展開されて消えるのを防ぐため
2. **解消用の pane で claude を起動し、解消を指示する**。2f のレビュー pane と同じ要領で、opus の新しいセッションを起動する
   （split の要領は 2a 手順1 と同じ）:
   ```
   herdr pane split --pane "$HERDR_PANE_ID" --direction <向き> --no-focus --cwd <プロジェクトルート>
   herdr pane rename <解消 pane-id> "resolve-<番号>"
   herdr pane run <解消 pane-id> "cd <worktree パス> && claude --permission-mode auto --model opus"
   herdr wait agent-status <解消 pane-id> --status idle --timeout 60000
   herdr pane get <解消 pane-id>
   ```
   `pane get` の応答から `result.pane.agent_session.value`（解消paneのセッションID）を控える（「実行記録の投稿」の
   トークン消費量集計で使う）。opus で起動するのは、解消した差分が一次レビューを通らずに自動マージされうるため、
   差分を作る側を弱いモデルにしないためである。

   起動を確認したら、2f と同じく対話ダイアログを使わない制約を単独で送り、`idle` を待ってから解消を指示する
   （`pane run` に渡す文字列に改行を含めない）:
   ```
   herdr pane run <解消 pane-id> "このセッションでは、質問・確認・判断の相談を AskUserQuestion などの対話ダイアログで出さず、必ず通常のテキスト応答で行ってください（指揮役が pane 経由のテキストで応答するため）。了解したら次の指示を待ってください"
   herdr wait agent-status <解消 pane-id> --status idle --timeout 60000
   herdr pane run <解消 pane-id> "この worktree は、issue #<番号> の PR #<PR番号> のブランチに origin/<baseRefName> を merge している途中で、コンフリクトしています。コンフリクトしたファイルは git diff --name-only --diff-filter=U で確認できます。PR の変更の意図（gh pr view <PR番号> と gh issue view <番号> で確認できます）と <baseRefName> 側の変更の両方を残す形でコンフリクトを解消し、解消したファイルごとに git add してください。コンフリクトしたファイル以外は編集しないでください。git commit・git merge --abort・git push・git reset・git stash・git rebase とブランチを切り替える操作は実行しないでください（コミットと push は指揮役が行います）。解消できないファイルがあれば、そのファイルは git add せずに、解消できなかったファイルと理由を答えてください"
   ```
3. **解消の完了を待つ**。2c 手順1〜2 と同じ要領で、`working` から抜けるのを待つ:
   - `idle` / `done` → `herdr pane read <解消 pane-id> --source recent-unwrapped --lines 200` で報告を読み、要点を記録する。
     報告に解消できなかったファイルがあると書かれていれば、失敗（理由: コンフリクトを解消できなかった。解消できなかった
     ファイルと理由を添える）とする
   - `blocked` → 2c 手順3 と同じくダイアログに応答せず、`herdr pane read <解消 pane-id> --source visible --lines 60` で
     内容を読んで記録し、失敗（理由: 解消のセッションが blocked になった）とする
   - 解消の指示を送ってから合計 1,800,000ms（30分）を超えても `working` のまま → `pane read` で表示を読んで記録し、
     失敗（理由: 解消の wait がタイムアウトした）とする

   どの場合も、読み終えたら `herdr pane close <解消 pane-id>` で解消 pane を閉じる
4. **未解消のファイルが残っていないことを確かめる**（指揮役の Bash。読み取りのみ）。手順1 のコマンドを実行し直し、
   出力が空であることを確認する。出力が空でない場合は失敗（理由: コンフリクトを解消できなかった。未解消のファイルを添える）、
   コマンドが失敗した場合も失敗（理由: 未解消のファイルを確かめられなかった）とする
5. **merge コミットを作り、確かめる**。2a 手順1 の要領で pane を新しく split し、その中でコミットする:
   ```
   herdr pane run <pane-id> 'bash -c "cd <worktree パス> && git commit --no-edit && echo RESOLVE""_COMMIT=OK || echo RESOLVE""_COMMIT=FAILED"'
   herdr wait output <pane-id> --match "RESOLVE_COMMIT=" --timeout 300000
   herdr pane read <pane-id> --source recent-unwrapped --lines 40
   ```
   `--no-edit` にすると、2h 手順4 の `git merge -m` に渡したメッセージ（`#<番号> <baseRefName> を取り込む`）で
   merge コミットができる。`FAILED` と wait のタイムアウトは、失敗（理由: merge コミットを作れなかった。
   読み取った出力の要点を添える）とする。

   `OK` なら、pane は閉じずに、指揮役の Bash で merge コミットを確かめる（読み取りのみ）:
   ```
   git -C <worktree パス> grep -I -n -E '^(<<<<<<<|=======|>>>>>>>)' HEAD
   git -C <worktree パス> status --porcelain
   ```
   - `git grep` は、行頭のコンフリクトマーカーが merge コミットのどれかのファイルにあると終了コード 0 でその行を出力し、
     無いと終了コード 1 で何も出力しない。終了コード 0 なら、push せずに失敗（理由: コンフリクトを解消できなかった。
     コンフリクトマーカーが残っているファイルと行を添える）とする。0・1 以外（照会の失敗）も、マーカーが無いことを
     確かめられないため失敗とする。コンフリクトしたファイルに限らず merge コミットのすべてのファイルを対象にするのは、
     解消のセッションがコンフリクトしたファイル以外を編集していても見逃さないため。`-I` でバイナリファイルを除くのは、
     git はバイナリファイルにコンフリクトマーカーを書かず、画像などのバイト列がマーカーと同じ並びを含むと誤って一致するため
   - `status --porcelain` の出力が空でない場合（コミットに含まれない変更が残っている）と、コマンドが失敗した場合は、
     push せずに失敗（理由: 解消後に未コミットの変更が残っている。出力を添える）とする。コミットされていない
     解消の変更は、M6 と同じく 2g の CI チェックと M2 の検出の対象にならないため
6. **push する**。手順5 と同じ pane で次を実行する:
   ```
   herdr pane run <pane-id> 'bash -c "cd <worktree パス> && git push origin HEAD && echo RESOLVE""_PUSH=OK || echo RESOLVE""_PUSH=FAILED"'
   herdr wait output <pane-id> --match "RESOLVE_PUSH=" --timeout 300000
   herdr pane read <pane-id> --source recent-unwrapped --lines 40
   ```
   マーカーを分割しているのは 2a 手順5 と同じ理由。手順5 と別のマーカーにしているのは、同じ pane の画面に残っている
   手順5 の出力に wait が一致しないようにするため。読み取ったら pane を閉じ、結果で分岐する:
   - `OK` → コンフリクトを解消したことと、手順1 で控えたファイルのパスを記録する。2h 手順4 の `PUSHED` と同じく、
     2g を手順1から再実行し、解消後のコミットで CI チェックを確認する（CI の失敗・タイムアウトは 2g 手順7 の
     エスカレーションになる）。2g が「完了」になったら 2h 手順5 へ（M2 の判定し直しも 2h 手順5 で行う）
   - `FAILED`・wait のタイムアウト → 失敗（理由: 解消した merge コミットを push できなかった。読み取った出力の要点を添える）
7. **失敗したときの記録**。M3 を満たさない（理由は各手順で失敗としたもの）として記録する。worktree は元に戻さない
   （`git merge --abort` もしない。人間が解消の途中から引き継げるようにするため）。開いたままの pane があれば閉じてから、
   指揮役の Bash で worktree の状態を確かめる（読み取りのみ）:
   ```
   git -C <worktree パス> rev-parse -q --verify MERGE_HEAD
   git -C <worktree パス> status --porcelain
   git -C <worktree パス> rev-parse HEAD
   git ls-remote --heads origin <ブランチ名>
   ```
   次を M3 の理由に添えて記録し、2h 手順9 へ進む:
   - 解消途中の変更が残っているか: `MERGE_HEAD` を解決できた（merge の途中である）場合と、`status --porcelain` の出力が
     空でない場合は、「解消途中の変更が残っている」と、どちらに当たったか・出力の要点を書く
   - 未 push のコミットが残っているか: worktree の HEAD とリモートのブランチ先端が異なる場合は、「未 push の merge コミットが
     残っている（<HEAD>）」と書く。`ls-remote` が失敗した場合と出力が空の場合は、比べられなかったことを書く
   - worktree のパス（`<worktree パス>`）と、手順1 で控えたコンフリクトしたファイルのパス（控えられた場合）

#### worktree・ブランチの削除手順

2h 手順8（自動マージした PR）と「エスカレーション時の後片付け」手順3（成果ゼロの worktree。対象外終了も同じ）で
共通の手順。削除してよいかの判定は呼び出し側で済ませてから行う。

環境を変更する操作なので、指揮役の Bash ではなく必ず pane 内で実行する。実行する pane の cwd は
**本体チェックアウトのプロジェクトルート**であること（削除対象の worktree の中から実行しない）。
pane を新しく split する場合の要領は 2a 手順1 と同じ（`--cwd` にプロジェクトルート・`--no-focus`）。

1. **削除を実行する**:
   ```
   herdr pane run <pane-id> 'bash -c "scripts/wt-rm.sh <番号> --delete-branch && echo WT""RM_RESULT=OK || echo WT""RM_RESULT=NG"'
   herdr wait output <pane-id> --match "WTRM_RESULT=" --timeout 600000
   herdr pane read <pane-id> --source recent-unwrapped --lines 40
   ```
   マーカーを分割しているのは 2a 手順5 と同じ理由（入力エコーへの誤マッチ防止）。マーカーは `wt-rm.sh` が終わったことを
   知らせるだけで、何を削除できたかは手順2 で判定する（`wt-rm.sh` は worktree を削除したうえでブランチの処理が
   `FAILED` / `UNKNOWN` になった場合も終了コードが 1 になるため、`NG` は worktree が残っていることを意味しない）。
   - ディレクトリを直接削除してはいけない。`.worktree-registry` の更新を伴うため
     （エントリが残ると次回の `wt-new.sh` が `Error: issue N already exists in registry` で失敗する）
   - worktree の中から実行しない。cwd が削除対象ごと消えるためだけでなく、worktree 側の
     `scripts/wt-rm.sh` を実行すると registry と worktree の基準ディレクトリが worktree 側に
     解決され、別の worktree を消しにいくおそれがあるため（`wt-rm.sh` は `git rev-parse --git-common-dir` で
     本体チェックアウトを解決するガードを持つ前提だが、cwd は揃えておく）
   - `--delete-branch` はローカル・リモート両方のブランチを削除する。削除するのはブランチのコミットが `origin/main` か
     マージ済み PR の head に含まれる場合だけで、どちらにも含まれないコミットがあると削除せず `KEPT: ...` になる。
     既定ブランチ（`main`）も削除対象にしない（`KEPT: refusing to delete the default branch`）
   - 未コミットの変更がある worktree は削除確認プロンプトで止まり、60 秒応答がなければ中断する（`NG` になる）
2. **wait が成功したら結果を判定する**。指揮役の Bash で実態を確認する（pane 出力だけを信用しない）:
   - worktree: 2a 手順3 のコマンドの出力が空なら削除済み
   - ブランチ: `git branch --list <ブランチ名>` と `git ls-remote --heads origin <ブランチ名>` がどちらも空なら削除済み
     （`ls-remote` は通信できないときも空を返すため、空を「削除済み」と即断せず、完了バナーの `Branch:` 行と突き合わせる）

   ブランチの処理結果は完了バナーの `Branch:` 行に出る（`local: deleted / remote: deleted` /
   `local: deleted / remote: not found` / `KEPT: ...` / `SKIPPED: ...` / `FAILED` や `UNKNOWN` を含む形。
   マージ済み PR を根拠に削除した場合は `[merged via PR #<番号>]` が付く）。**成功バナーが出ていてもブランチは
   残っていることがある**ため、`Branch:` 行まで読んでから結果を記録する。worktree は消えてブランチだけが残った場合は、
   まとめて「削除できなかった」と扱わず、何が残ったかを分けて記録する（事実と逆の記録が残るため）。
   判定を終えたら pane を閉じる
3. **wait がタイムアウトしたら pane を閉じない**。マーカーは `wt-rm.sh` の成否にかかわらず終了時に必ず出るため、
   タイムアウトは `wt-rm.sh` がまだ動いていることを意味する。ここで pane を閉じると、worktree の削除や
   `.worktree-registry` の更新が途中で止まり、`wt-rm.sh` でも片付けにくい状態が残る。
   `herdr pane read <pane-id> --source recent-unwrapped --lines 40` で止まっている箇所を読み、
   worktree・ブランチを削除できなかったものとして扱う。記録には pane を残したこと（pane ID）と、
   読み取った出力の要点を含める。削除の失敗で呼び出し側の処理（2h の記録・エスカレーション処理）は止めない

### エスカレーション（issue 単位の保留）

定義表「エスカレーション条件」（共通 + そのワークフローの固有条件）のいずれかに該当したら、
その issue の処理を保留して人間に引き継ぎ、次の issue へ進む。

エスカレーション時の動作（この順に行う）:

1. `gh issue edit <番号> --add-label "auto-loop:escalated"` でラベルを付け、
   `gh issue view <番号> --json labels` で付与を確認する
2. 後片付けの**判定だけ**を行う（後述「エスカレーション時の後片付け」の手順1）。
   読み取りのみで環境は変えない
3. 保留理由を issue コメントとして投稿する（後述「エスカレーション理由コメント」）。
   worktree を削除するか残すかは手順2の判定結果をそのまま書く。
   投稿後は `gh issue view <番号> --json comments` で実在を確認する
4. 後片付けを**実行**する（同「手順2」「手順3」）
5. 実行結果が手順2の判定と食い違った場合（削除するはずのものが残った等）だけ、
   訂正を追加コメントとして投稿する
6. 何をどこまで判断して保留したかを指揮役の出力に記録する
7. 次の issue の処理に進む

**判定と実行を分け、その間にコメント投稿を挟む**のは、ラベルだけが付いて理由が GitHub 側に
残らない状態を最短にするためである。後片付けの実行は pane の閉鎖・`wt-rm.sh`・最大 600 秒の
待機を含み、ここで指揮役のターンが落ちると理由不明のまま `auto-loop:escalated` だけが
残った issue ができる。判定は読み取りのみで先に確定できるので、コメントの内容は実行の完了を
待たずに書ける。並列モードではメタ指揮役がコメントの欠落を補填するが（`auto-loop-parallel`
の「完了回収」3）、単体実行には補填役がいないためこの順序が効いてくる。

#### エスカレーション時の後片付け

保留理由は issue コメントとして残るため（次項）、理由を読むために pane を残す必要はない。
判断が決まった後は**新しいセッションで再実行すればよく、保留時の会話文脈は引き継がなくてよい**
（内側ワークフローは issue コメントの進捗マーカーから再開ポイントを判定するため）。むしろ
中身のない pane が残り続けると、pane 一覧が実際の稼働状況を表さなくなる。成果ゼロの
worktree も、判断待ちの間に main が進むと古い分岐点のまま陳腐化するため残さない。

**1. worktree・ブランチの削除可否を判定する**

次の2条件を**両方**満たすときだけ削除する。片方でも満たさなければ worktree・ブランチとも
残す（作業成果を失わないため）:

1. `git -C <worktree パス> status --porcelain` が空（未コミット変更なし）
2. `git fetch origin main --quiet` に成功したうえで
   `git -C <worktree パス> log origin/main..HEAD --oneline` が空（コミットなし）

判定は読み取りと remote-tracking ref の更新だけなので指揮役の Bash で実行してよい
（2d の完了検証と同じ）。

比較対象が `main` ではなく **`origin/main`** なのは、ブランチの分岐点がリモートの main 先端
だからである（`wt-new.sh` は `gh issue develop --base main` でブランチを作る前提。「worktree スクリプトの前提」）。ローカルの
`main` はこのフローの誰も最新化しないため、人間が GitHub 上で PR をマージすると容易に古くなり、
`main..HEAD` は成果ゼロの worktree でも「コミットあり」を返す。それを条件にすると、
後片付けがこの機能を最も必要とする場面で黙って不発になる。`git fetch` が失敗した場合
（オフライン等）は `origin/main` も古い可能性があるため、条件2を満たさない扱いにして
worktree を残す（安全側に倒す）。

判定材料を **git の状態だけで完結させている**のは、指揮役の会話文脈に依存させないためである。
「この実行で作成した worktree か」を記憶で判定すると、長いループの途中で記録が失われたときに
後片付けが黙って効かなくなる。2a 手順3 で既存 worktree を再利用していた場合も、上の2条件を
満たすなら失われるのはセットアップ時間（依存インストール・DB マイグレーション）だけで、
作業成果は失われない。

**2. 子 pane を閉じる**

- 子 pane がまだ無い（2b 手順0〈前処理〉を 2a より先に済ませていて、そこで保留した場合）→
  閉じる対象は無い。手順1の判定で削除するものがあれば、後片付け用の pane を新しく
  split して使い、実行後に閉じる（split の要領は 2a 手順1と同じ）
- 子 claude が未起動（2a 段階、または 2a 実施後の 2b 手順0〈前処理〉での保留）→ 子 pane はシェルのままで cwd もプロジェクトルート
  なので、下の手順3にそのまま使い、実行後に閉じる
- 子 claude が起動済み → `herdr pane close <pane-id>` で閉じる。claude に `/exit` や
  Ctrl-C を送って抜けようとしない（送信キーでの操作はしない）。手順3で削除するものが
  あれば、後片付け用の pane を新しく split して使い、実行後に閉じる
  （split の要領は 2a 手順1と同じ。`--cwd` にプロジェクトルート・`--no-focus`）。
  この pane を使い回さないのは、2b で `cd` した結果 cwd が削除対象の worktree 内に
  なっているため
- 2f でのエスカレーション（一次レビューの修正後にテストが green に戻らない等）→ 実装用の
  子 pane は 2f 冒頭で閉じているため、閉じる対象はレビュー pane になる
- 2g でのエスカレーション（CI失敗・タイムアウト）→ 実装用の子 pane は 2f 冒頭で、
  レビュー pane は 2f 末尾で既に閉じているため、閉じる対象の pane は無い（2h 手順4 から 2g を再実行した場合も、
  追従・コンフリクトの解消に使った pane は 2g の再実行前に閉じている）

閉じるのは自分が作った pane だけ。**指揮役自身の pane は閉じない**（副指揮役モードでは
タブも閉じない。タブの閉鎖はメタ指揮役が完了回収で行う）。手順3 に使った pane を「実行後に閉じる」のは、
削除手順の wait がタイムアウトしなかった場合だけ（「worktree・ブランチの削除手順」手順3）。

**3. worktree・ブランチを削除する**

手順1の2条件を満たさなかった場合はこの手順を行わない（worktree・ブランチとも残す）。

「worktree・ブランチの削除手順」で削除する。ブランチまで削除するのは、残すと `wt-new.sh` が再開時に
残ったブランチを as-is で再利用し、古い分岐点のままやり直すことになるため。
手順1の条件2を満たしていれば `Branch:` 行が `KEPT: has commits not contained in ...` になることはない。
なった場合はブランチを残したまま進め、理由コメントに明記する。

削除手順で削除できなかったもの（wait のタイムアウトで pane を残した場合を含む）があれば、残した事実と
読み取ったエラーを「エスカレーション時の動作」の5（訂正コメント）とサマリーに書く。
後片付けの失敗でエスカレーション処理自体を止めない。
`Branch:` 行に `FAILED` / `UNKNOWN` が含まれていた場合は、**worktree は削除済み・ブランチの状態だけが不定**
なので、`Branch:` 行の内容をそのまま訂正コメントに転記する。リモートブランチが残ったまま再開すると
`wt-new.sh` がそれを as-is で再利用するため、この事実は必ず残す。

#### エスカレーション理由コメント

ラベルだけでは「止まったこと」しか GitHub 側に残らず、セッションを閉じた後や別の人が issue を
見たときに「なぜ止まったのか」が分からない。エスカレーションは子の内側ワークフローが終端マーカーを
残す前に指揮役が止める判断であるため、指揮役が書かなければ理由はどこにも残らない。

見出しマーカーには `## /auto-loop エスカレーション` を使う（後から grep で拾うための
固定文字列。**変更しない**）。この文字列は終端マーカー表のどのマーカーとも、内側ワークフローの
再開判定マーカー（`## 確認済み不明点` と、定義表の「計画コメントの名称」「実装完了マーカー」
「修正試行カウンタ見出し」の各列）とも部分文字列として重ならないため、
双方の grep が互いに誤マッチしない。Step 1 の除外判定はラベル `auto-loop:escalated` と
終端マーカーで行い、このマーカーは記録専用で除外判定には使わない。

旧名 `## /refactor-loop エスカレーション` が付いた既存コメントは書き換えない（記録専用で
除外判定に使っていないため、運用への影響がない）。過去分を検索するときだけ両方の文字列で grep する。

本文は一時ファイルに書き出して `gh issue comment <番号> --body-file <一時ファイル>` で投稿する
（改行を含むため `--body` の直接指定はしない）:

```
## /auto-loop エスカレーション

- 保留者: 指揮役（/auto-loop）
- 対象ワークフロー: <refactor / bug>
- 該当したエスカレーション条件: <定義表のどの条件に該当したか>

### 調査で判明した事実

- <調査でわかったこと。issue の前提（制約・実現可能性）と実態が食い違っていた場合は必ず明記する>

### 人間に判断してほしいこと

- <判断してほしい論点。実行可能な代替案があれば選択肢として併記する>

### 判断が決まった後にすること

- <再実行するなら「`auto-loop:escalated` ラベルを外してから `/auto-loop <番号>` を
  再実行する」。issue 本文の修正など、再実行の前に必要な作業があればそれも書く>
- <子が終端マーカー（結果分類「エスカレーション」）を投稿済みの場合のみ:
  そのコメントも削除しないと Step 1 の除外判定でスキップされる旨。
  ラベルを外すだけでは再実行できない>
- <worktree を残す判定になった場合のみ: <worktree パス> を残している
  （理由: 未コミット変更がある / コミットがある / origin/main を fetch できなかった）>
```

Step 1 の除外はラベルと終端マーカーの**両方**で行うため（Step 1 参照）、子が終端マーカーを
残してからのエスカレーション（`## /refactor-auto — 自動修正できませんでした` 等）では、
ラベルを外すだけでは `/auto-loop` の対象に戻らない。指揮役が子より先に止めた場合は
マーカーが無いのでラベルを外すだけでよい。どちらなのかを判定して書き分ける。

保留した pane は後片付けで閉じており、再開は新しいセッションで行う（内側ワークフローは
issue コメントの進捗マーカーから再開ポイントを判定するため、保留時の会話文脈は不要）。
そのため pane 名・セッション ID のような「保留時のセッションへ戻るための情報」は書かない。
worktree・ブランチも削除が既定なので、**残す判定になった場合だけ**その事実と理由を書く。

このコメントは後片付けの**判定後・実行前**に投稿する（「エスカレーション時の動作」参照）
ため、書く内容は判定結果であって実行結果ではない。実行が判定どおりに終わらなかった場合は、
次の形式の追加コメントで訂正する（見出しは検索用の固定文字列。**変更しない**）:

```
## /auto-loop 後片付け訂正

- <予定と実際の差分。例: worktree は削除したが、リモートブランチ <ブランチ名> が残っている>
- <`wt-rm.sh` の完了バナー `Branch:` 行の内容、または読み取ったエラーの要点>
- <人間が手で片付ける必要があるコマンド。例: git push origin --delete <ブランチ名>>
```

auto mode の分類器に `gh issue comment` をブロックされた場合でも、エスカレーション処理自体は
止めない（ラベル付与・後片付け・次 issue への進行は行う）。投稿できなかったコメント本文は
Step 3 の「人間への依頼」に全文を含め、人間が投稿できるようにする。

**ループ全体を停止する**のは次の場合に限る: gh・herdr 自体が使えなくなったとき、
またはエスカレーションが3 issue 連続で発生したとき（原因が対象 issue ではなく
指揮役側・環境側にある可能性が高いため、続行せず人間の点検を仰ぐ）。
「対象外」で終わった issue はこの連続カウントを加算もリセットもせず透過させる
（指揮役の判断や環境の異常を示す事象ではないため）。

### 対象外終了（issue 単位の正常終了）

子が結果分類「対象外」の終端マーカーを投稿した場合の扱い。bug ワークフローで
完了条件が人間確認（見た目・主観判断）に該当したときの終端であり、
**エスカレーションではなく正常終了**として処理する。

1. `gh issue view <番号> --json comments` で対象外マーカーの実在を確認する
   （pane 出力だけを信用しない）。マーカーが無ければ子の報告と実態が食い違っているので、
   完了検証の失敗と同じくエスカレーションに切り替える
2. **`auto-loop:escalated` ラベルは付けない**。人間の判断待ちではなく、このワークフローの
   守備範囲外だと判定できたという結論だからである。ラベルを付けると「指揮役が止まった issue」と
   混ざり、判断待ちの棚卸しが濁る
3. **理由コメントは指揮役から投稿しない**。子が投稿した対象外マーカーのコメントに
   判定の根拠・調査サマリー・再実行の手順が既に含まれているため、重複させない
4. **PR 工程（2e〜2h）はスキップする**。完了条件を自動判定できないと結論した以上、
   レビュー待ちの PR を人間に積むべきではない
5. 後片付けは「エスカレーション時の後片付け」の手順1〜3と同じ判定・手順で行う
   （子 pane を閉じ、成果ゼロなら worktree とブランチを削除する）。
   探索段階（内側ワークフローの Step 1・2）で対象外と判定された場合はコミットが無いので
   削除され、レビュー段階（同 Step 6〜8）で判明した場合は実装コミットが積まれているため
   worktree・ブランチとも残る。
   **残す判定になった場合は、ブランチ名と worktree パスを必ずサマリー（手順7）に書く**。
   対象外では PR を作らず（手順4）指揮役から理由コメントも投稿しない（手順3）ため、
   コミットの所在を示す記録がサマリーしかない。PR 未作成のブランチは push されていない
   ことがあり、その場合はローカルの worktree だけが成果物の置き場になる
6. 全体停止のエスカレーション連続カウントには含めない（加算もリセットもしない）
7. Step 3 のサマリーに結果「対象外」として記録し、「人間への依頼」に次を書く:
   - 「issue の期待動作を検証可能な形に具体化して再実行するか、手動で対応するか」の判断依頼。
     **再実行するには子が投稿した対象外マーカーのコメント（と、レビュー段階の場合は
     `## 承認済み修正計画` / `## バグ修正実装完了`）を削除する必要がある**ことも添える
     （残っている限り Step 1 の除外判定でスキップされ続ける）
   - 対象外マーカーのコメントの「経緯として参照する他 issue/PR との食い違い」が「なし」以外
     だった場合は、その内容と**再実行の前に issue 本文の前提を直す必要がある**ことも書く
     （エスカレーション条件の同項目は対象外では発火せず、指揮役から理由コメントも
     投稿しない〈手順3〉ため、ここに書かないと食い違いが人間に届かない）
   - 後片付けの結果。worktree・ブランチを残した場合は**ブランチ名と worktree パス**まで書く
8. 次の issue の処理に進む

対象外マーカーは終端マーカー表に載っているため、次回以降の実行では Step 1 の除外判定で
自動的に処理対象から外れる（同じ issue を繰り返し掘り返さない）。

### Step 3: サマリー報告

ループ終了時（全件完了・件数上限（`--limit`）到達・エスカレーションのいずれでも）、以下の形式で報告する。
結果「完了」の行の備考には、2g で判定した CI 結果（`CI: 成功` / `CI: 対象外`）と、2h の自動マージの結果
（`自動マージ: 済み` / `自動マージ: 未実施（<満たさなかった条件>）` / `自動マージ: 失敗（<エラーの要点>）`）を含める。
自動マージした場合は、2h 手順9 で記録した worktree・ブランチの削除結果も含める。
2h 手順4 でコンフリクトを解消して push した issue は、自動マージしたかどうかにかかわらず、2h 手順9 の書式で
コンフリクトの解消の記録（`コンフリクト解消: <パス>`）も含める（push した後の 2g でエスカレーションになった場合は、
エスカレーションの行に含める）。
この報告を出力する前に「実行記録の投稿」の実行順序を完了させる（副指揮役モードでは「副指揮役モード」6 のとおり
手順1〜3だけを行い、記録本文を `### 実行記録ブロック` として出力する）:

## 実行記録の投稿

auto-loop / auto-loop-parallel 共通の正とする。実行ごとに、ラベル `auto-loop:log` を付けた
固定のトラッキング issue（人間が事前に1件用意する。用意手順は下記）に、
`## /auto-loop 実行記録`（auto-loop-parallel は `## /auto-loop-parallel 実行記録`）の
固定見出しでコメントを1件追記する。`gh issue create` は指揮役からは使わない
（既存の `gh issue comment` の延長で完結させる）。

**実行順序（重要）**: 投稿に失敗した場合も投稿できなかった記録の本文が終了サマリーに含まれる
ようにするため、記録の投稿と実在確認を Step 3 の終了サマリー出力**より前**に完了させる:

1. 終了日時を確定する（`date -u +%Y-%m-%dT%H:%M:%SZ`）
2. トークン消費量を集計する
3. 記録本文を組み立てる
4. トラッキング issue を特定する
5. 特定できた場合のみ、記録本文を一時ファイルに書き出して
   `gh issue comment <トラッキング番号> --body-file <一時ファイル>` で投稿を試みる
6. 投稿できた場合は、今回の記録が実在することを確認する。トラッキング issue のコメントはすべて同じ
   固定見出しを持つため、見出しの有無で確認すると過去の実行のコメントに一致してしまい、投稿の失敗を
   検出できない。今回の開始日時の行で照合する（出力が1以上なら実在）:
   ```
   gh issue view <トラッキング番号> --json comments --jq '[.comments[].body | select(contains("- 開始日時: <今回の開始日時>"))] | length'
   ```
7. 4で特定できなかった、5で投稿に失敗した（auto mode の分類器によるブロックを含む）、
   または6で実在確認できなかった場合、ループの処理・Step 3 の終了サマリー出力は止めない。
   この場合、Step 3 の終了サマリーの「人間への依頼」に `- 実行記録: <本文全文>` を含めて出力する。
   **あわせて、失敗の理由（トラッキング issue が0件・2件以上／投稿の失敗〈分類器のブロックを含む〉／
   実在確認できず）も併記する**（0件のときに人間が事前準備のコマンドを実行すべきだと分かるように
   するため）。6まで成功した場合は「人間への依頼」への追加は不要

**トラッキング issue の特定方法**: `gh issue list --label "auto-loop:log" --state open --json number,title`。
ちょうど1件→採用。0件、または2件以上（一意に定まらない）→「トラッキング issue が見つからない」として
手順5を試行せず手順7のフォールバックへ（closed の issue は `--state open` で除外され、0件の扱いに合流する）。
「人間への依頼」には件数に応じた依頼も添える:
- 0件: 下記「トラッキング issue の事前準備」の2コマンドを全文で示し、実行を依頼する
- 2件以上: 該当した issue 番号を列挙し、1件だけを残して他を close するかラベル `auto-loop:log` を外すよう
  依頼する（事前準備のコマンドを案内すると記録用 issue がさらに増えるため、案内しない）

**トラッキング issue の事前準備（人間が一度だけ実行する。エージェントは実行しない）**:

```
gh label create "auto-loop:log" --description "auto-loop/auto-loop-parallel の実行記録を蓄積するissue" --color "0E8A16"
gh issue create --title "auto-loop 実行記録" --body "このissueは auto-loop / auto-loop-parallel の実行記録をコメントとして蓄積するためのトラッキングissueです。人間が作業対象として使わないでください。" --label "auto-loop:log"
```

**記録テンプレート**（`## /auto-loop 実行記録` 固定見出し。auto-loop-parallel は
`## /auto-loop-parallel 実行記録` で並列度の行を追加する）:

```
## /auto-loop 実行記録

- 開始日時: <ISO8601 UTC>
- 終了日時: <ISO8601 UTC>
- 上限件数: <N>（`--limit`。省略時は既定の5）
- トークン消費量: input=<合計> / output=<合計> / cache_creation=<合計> / cache_read=<合計>
  （一部取得できず: <どのセッション>・<理由>／全て取得できない場合は「取得できません（理由: …）」のみ）

### 対象 issue
| issue | ワークフロー | 結果 | PR番号 | 計画承認の差し戻し回数 | 一次レビュー指摘件数 | 一次レビュー修正の有無 |
|---|---|---|---|---|---|---|
| #12 | refactor | 完了 | #101 | 0 | 0 | 無 |

### エスカレーション条件の該当要約
- #34: <該当したエスカレーション条件の要約（1行）。該当 issue が無ければ「該当なし」>
```

`- 上限件数:` を残すのは、ループが「候補を処理し切って終わった」のか「上限に当たって
打ち切った」のかを、後から記録だけで区別できるようにするためである（Step 3 はこの2つを
別々の終了理由として扱うが、対象 issue の件数だけでは見分けられない）。

結果が「エスカレーション」「対象外」「スキップ」「未処理（上限）」「未着手」の行は、PR工程未実施のため該当する
範囲だけ埋め、それ以外は「—」とする（auto-loop-parallel はメタエスカレーション等 Step 3 の
処理結果表の区分も含む。詳細は auto-loop-parallel の Step 3 を参照）。
結果が「完了」でも値を記録できなかった欄（2f で一次レビューの指摘件数を読み取れなかった場合など）は
「不明」とし、工程未実施の「—」と区別する。

**トークン消費量の集計手順**: 同一 `message.id` の assistant 応答が複数行に記録されることがある。
メインセッションの記録では重複行同士の `message.usage` は同じ値だが、サブエージェントの記録
（`subagents/agent-*.jsonl`）ではストリーミング途中の行が混ざり、先に書かれた行ほど `output_tokens` が
小さい（最後の行が最終値）。行単位で合算すると過大計上になり、先の行の値を採ると `output_tokens` を
過少計上するため、**`message.id` で重複排除し、最後に書かれた行の値を採ってから合算する**。
集計する4フィールド（`input_tokens`・`output_tokens`・`cache_creation_input_tokens`・`cache_read_input_tokens`）は
1つの合計値に足し合わせず、**フィールドごとに別々の数値として記録する**。

対象セッション範囲:
- auto-loop: 指揮役自身のセッション、issueごとの子paneセッション（2b）、issueごとのレビューpane
  セッション（2f）、コンフリクトを解消した issue の解消paneセッション（2h「main への追従で起きたコンフリクトの解消」）、
  およびそれぞれのサブエージェント（Task）記録
- auto-loop-parallel: メタ指揮役自身のセッション、および各副指揮役が算出した小計（副指揮役の
  小計には副指揮役自身・その子pane・そのレビューpane・その解消pane・各サブエージェントの分が含まれる）

セッションIDの取得タイミング（pane が閉じる前に控える。取得できなかった場合は理由とともに記録し
集計対象から除外する）:
- 指揮役自身／メタ指揮役自身: **Step 0の末尾で、開始日時の確定（`date -u +%Y-%m-%dT%H:%M:%SZ`）と
  あわせて** `herdr pane get "$HERDR_PANE_ID"` を実行し `result.pane.agent_session.value` を控える
  （`herdr pane current --current` は使わない。理由は Step 0 を参照）
- 子pane: 2b手順2で起動完了（idle）を待った後に `herdr pane get <pane-id>` を実行し控える
- レビューpane: 2fで起動完了（idle）を待った後に同様に控える
- 解消pane: 2h「main への追従で起きたコンフリクトの解消」の手順2で起動完了（idle）を待った後に同様に控える
- 副指揮役（auto-loop-parallel）: 「系統の起動」手順3の起動完了後に `herdr pane get <pane-id>` で
  控える（メタ指揮役の監査ログ用の補助情報。トークン集計自体は副指揮役が自分の小計として
  算出したものをそのまま使い、メタ指揮役が二重に集計しない）

集計コマンド（読み取り専用。指揮役／メタ指揮役のBashで直接実行してよい）。控えたセッションIDを引数に並べて渡す。
トランスクリプトは `~/.claude/projects/<プロジェクトスラッグ>/<セッションID>.jsonl` と
`<セッションID>/subagents/agent-*.jsonl` に保存されるが、スラッグは組み立てず、セッションID（UUID で一意）で
`~/.claude/projects/` 配下の全プロジェクトディレクトリから探す（スラッグは cwd の `/` 以外の記号も `-` に
置換した文字列であり、pane の cwd の取り違えや置換規則のずれがあるとファイルを見失うため）:

```js
node -e '
const fs = require("fs");
const path = require("path");
const root = path.join(require("os").homedir(), ".claude", "projects");
const projectDirs = fs.readdirSync(root, { withFileTypes: true })
  .filter((d) => d.isDirectory())
  .map((d) => path.join(root, d.name));
// message.id -> usage。サブエージェントの記録では同一 message.id の行に途中値（output_tokens が小さい）が
// 含まれるため、最後に書かれた行（最終値）で上書きする
const seen = new Map();
const missing = [];
for (const sessionId of process.argv.slice(1)) {
  const files = [];
  for (const dir of projectDirs) {
    const main = path.join(dir, sessionId + ".jsonl");
    if (!fs.existsSync(main)) continue;
    files.push(main);
    const sub = path.join(dir, sessionId, "subagents");
    if (!fs.existsSync(sub)) continue;
    for (const name of fs.readdirSync(sub)) {
      if (name.startsWith("agent-") && name.endsWith(".jsonl")) files.push(path.join(sub, name));
    }
  }
  if (files.length === 0) {
    missing.push(sessionId);
    continue;
  }
  for (const f of files) {
    for (const line of fs.readFileSync(f, "utf8").split("\n")) {
      if (!line.trim()) continue;
      let entry;
      try { entry = JSON.parse(line); } catch { continue; }
      if (entry.type !== "assistant") continue;
      const msg = entry.message;
      if (!msg || !msg.usage || !msg.id) continue;
      seen.set(msg.id, msg.usage);
    }
  }
}
const t = { input_tokens: 0, output_tokens: 0, cache_creation_input_tokens: 0, cache_read_input_tokens: 0 };
for (const u of seen.values()) {
  t.input_tokens += u.input_tokens || 0;
  t.output_tokens += u.output_tokens || 0;
  t.cache_creation_input_tokens += u.cache_creation_input_tokens || 0;
  t.cache_read_input_tokens += u.cache_read_input_tokens || 0;
}
console.log(JSON.stringify({ ...t, missing }));
' <セッションID> [<セッションID> ...]
```

出力の `missing` には、トランスクリプトが見つからなかったセッションIDが入る（集計からは除かれている）。
`missing` が空でない場合と、セッションIDを控えられなかったセッションがある場合は、除いた分だけで合算した
値に「一部取得できず（<どのセッション>・<理由>）」と明記する。1件も取得できなければ「取得できません（理由: …）」のみを書く。

## タッチポイントへの応答基準

### 不明点質問（内側ワークフローの Step 2）への回答

- issue 本文・リポジトリの規約（CLAUDE.md・`.claude/rules/`・`docs/architecture/`・`docs/adr/` とデザイン規約〈あれば〉）・
  既存コードの慣例から根拠を持って答えられるものだけ回答する
- 判断の根拠を回答に含める（子がその根拠ごと issue に記録するため）
- スコープの質問は保守的に答える: 迷ったら「issue に明記された範囲のみ。それ以外はスコープ外」
- ただし、内側ワークフローから issue 本文が経緯・前提として参照する他 issue/PR の状態が
  実際の state と食い違うと報告された質問は、根拠を示せる場合であっても指揮役が
  自ら回答せずエスカレーションする（エスカレーション条件に該当するため）
- bug ワークフローで「どうなれば直ったと言えるか」を問われた場合は、issue の機能要件に
  書かれた期待動作を根拠に、**検証可能な形**（入力と出力・状態遷移・具体的な文言・数値閾値・
  一意に特定できる規約への参照）で答える。issue にその根拠が無く、指揮役の裁量で期待動作を
  決めることになる場合は回答せずエスカレーションする（判定方式の分類を左右する回答であり、
  `.claude/skills/bugfix-auto/judgment-criteria.md` の Q1 が人間に確認するよう定めている問いだから）
- 1問でもエスカレーション条件に該当したら、他の質問に答えず停止する

### 計画承認依頼（内側ワークフローの Step 4）への応答

定義表「計画の承認基準」に従う。

## 注意事項

- pane の ID は必ず herdr の JSON 応答から読み取る。推測やサイドバーの順序から組み立てない
- 自分が作った pane 以外を閉じない・操作しない
- `pane run` を送る前に `pane get` で子の状態を確認する（`working` 中に送らない）
- gh での副作用（ラベルの作成・改名・付与、エスカレーション理由コメントの投稿、自動マージ、
  自動マージの記録コメント・見送った指摘のコメントの投稿、実行記録の投稿）は、実行後に別の読み取りコマンドで実在確認する
- 指揮役は issue へのコメント投稿を**原則として**自分では行わない（進捗記録は子の内側ワークフローが
  担う。指揮役の判断ログはサマリー報告に残す）。**例外はエスカレーション理由コメント**
  （`## /auto-loop エスカレーション`）と**実行記録**（`## /auto-loop 実行記録`）——
  エスカレーションは子が終端マーカーを残す前に指揮役が止める判断であり、指揮役が投稿しなければ
  GitHub 側に理由が残らないため。実行記録は処理対象の issue ではなく別のトラッキング issue
  （ラベル `auto-loop:log`）に指揮役自身が投稿するものであり、issue ごとに閉じて動く子の
  内側ワークフローには担えないため（詳細は「実行記録の投稿」）。
  対象外終了は子が理由を含むコメントを残しているので、指揮役からは投稿しない
- PR への自動マージの記録コメント（2h 手順7）と見送った指摘のコメント（2f「見送った指摘の記録」）は issue コメントでは
  ないが、それぞれ自動マージの判断と一次レビューで見送った指摘を GitHub 側に残す唯一の記録なので、指揮役が投稿する
- ワークフロー固有の値（対象ラベル・補助ラベル・投入コマンド・終端マーカー・ブランチ名・承認基準・
  エスカレーション条件の差分）は**必ず定義表から引く**。手順本文にワークフロー名を直接
  書き足さない（ワークフローを追加するたびに手順本文を書き換える羽目になり、
  refactor と bug で機構の挙動が非対称にずれる原因になる）
- 1回の実行で処理する issue は最大 N 件（`--limit N`。省略時は5）。同一 issue の再試行はしない
- **マージしてよいのは、2h で自動マージの条件（M1〜M6）をすべて満たした PR だけ**（かつ CLAUDE.md が
  `/auto-loop` による自動マージを許可している場合に限る）。それ以外の PR は
  マージしない（人間の PR レビューとマージが最後の独立した検証層）。条件は GitHub 側で強制されない
  ため、判定を省略したり推測で済ませたりしない。PR 作成・一次レビューは人間の承認を待たずに行ってよい
- 完了した issue の worktree は、原則として指揮役では削除しない（PR のマージ後に人間が
  `scripts/wt-rm.sh <番号>` で削除する）。**例外は次の2つ**:
  - **2h で自動マージした場合**——マージ直後に `scripts/wt-rm.sh <番号> --delete-branch` で worktree とブランチを
    削除する（2h 手順8）。自動マージした PR には人間が関わらず、ここで削除しないと誰も片付けないため
  - **エスカレーション・対象外終了時の後片付け**——worktree に作業成果（未コミット変更・`origin/main` に無いコミット）が
    まったくない場合に限り、`scripts/wt-rm.sh <番号> --delete-branch` で worktree とブランチを削除する
    （残すと再開時に古い分岐点のブランチが as-is で再利用されるため）
- worktree 内では bwrap サンドボックスの既知バグで `ls`/`find` が失敗することがある。
  回避策（`git ls-files` で代替）は `.claude/rules/core.md` に記載済みで、
  worktree 内の子セッションにも同ルールが読み込まれる
- **環境を変更する操作（worktree 作成・依存インストール・テスト実行）は子 pane で行い、
  指揮役の Bash では行わない**。指揮役のサンドボックスはプロジェクトルート外への書き込み等を
  遮断しており、`excludedCommands` はトップレベルコマンドのみに効く（スクリプト内部の
  git / gh はサンドボックス内で動く）。サンドボックス起因の失敗を切り分けるときも
  この非対称に注意する（トップレベルの git が成功しても、スクリプト内の git が
  同じ操作に成功するとは限らない）
- **pane の対話シェルは環境依存**（ユーザーのログインシェルが開く。bash とは限らない）。
  pane に送るコマンドは `$?` などシェル固有の構文に依存させず、`bash -c "…"` でラップする。
  `herdr wait output --match` は入力エコーにもマッチするため、待ち受けるマーカーは
  プログラム自身の出力を使うか、文字列連結で分割してコマンド行に現れないようにする
- 構文エラー等で pane の入力バッファに残骸が残った場合は、送信キーでの修復を試みず
  その pane を閉じて作り直す（自分が作った pane に限る）
