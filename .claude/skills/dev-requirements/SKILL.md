## 概要

実行可能仕様駆動開発ワークフロー（`docs/workflow/executable-spec-driven-workflow.md`）のステップ2「要件定義」を実行する。
具体的な実行可能仕様を通じて人間との合意形成を取ることがゴール。

## 引数

- `<issue番号>`（必須）: 要件定義を行うGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /dev-requirements 42」と伝えて終了する

## エージェント構成

```
メインスキル（オーケストレーター）
├── Step1: Issue確認（メイン）
├── Step2: コードベース調査＋ブラインドスポット・パス
│   ├── 2-a: 既存パターン調査（Explore）
│   └── 2-b: ブラインドスポット・パス（盲点探索・メイン）
│             ↓ 調査サマリー＋未知の未知の候補を受け取る
├── Step3: 合意対象の判定と仕様生成
│   ├── 3-a: 合意対象の判定（メイン）
│   └── 3-b: 仕様生成 → general-purpose エージェント
│             ↓ 生成ファイル一覧を受け取る
├── Step4: 横断インデックスの更新（メイン）
└── Step5: 人間確認・合意（メイン）
```

## 手順

### Step 1: Issue確認

1. `gh issue view <番号>` でissue内容を取得する
2. 機能要件・制約の不明点を洗い出す
3. 不明点があれば **1回にまとめて** ユーザーに確認する（複数回に分けない）
4. ユーザーから回答を得たら、以下の形式で `gh issue comment` でissueに記録する:
   ```
   ## 不明点と回答

   ### 確認内容
   - <質問1>
   - <質問2>

   ### 回答
   - <質問1への回答>
   - <質問2への回答>
   ```
   - 不明点がなかった場合はこの記録をスキップする

### Step 2: コードベース調査とブラインドスポット・パス

#### Step 2-a: コードベース調査（Explore エージェント）

以下を調査させ、調査サマリーをメインに返させる:

- `docs/specs/` 配下の現状（存在する場合 — 画面一覧・ER図等の既存内容を把握）
- `docs/architecture/` のアーキテクチャ定義（ディレクトリ構造・命名規則・使用技術）
- issueに関連する既存コードのパターン・ディレクトリ構造
- 使用しているバックエンドフレームワークと API 契約の既存形式（`docs/specs/openapi.yaml` を使っているか、コードファーストのスキーマ定義＋ルート定義を使っているか。既存のスキーマ定義・ルート定義のパターンを含む。Step3 での API 契約の生成方針（下記「API 契約の形式」）の判断と、生成の参考に使う）

Exploreエージェントへの指示例:
```
以下を調査してサマリーを返してください:
1. docs/specs/ の現状（存在すれば各ファイルの内容）
2. docs/architecture/ のアーキテクチャ定義
3. issue内容「<issueタイトルと概要>」に関連する既存コード
4. バックエンドフレームワーク（package.json, requirements.txt, composer.json等から判断）と API 契約の既存形式（docs/specs/openapi.yaml か、コードファーストのスキーマ定義＋ルート定義か。後者なら既存のスキーマ定義・ルート定義のパターン）
5. ブラインドスポット・パス（blindspot pass）: 上記1〜4に加え、関連コード・ドキュメント・テスト・ログ・実例・公開情報を検索し、この issue の実装で見落としやすい『未知の未知（unknown unknowns）』の候補と、各候補の解決に必要な証拠を列挙する

返却フォーマット: 上記1〜4の調査サマリーに加え、ブラインドスポット・パスの結果（『未知の未知の候補』と『各候補の解決に必要な証拠』の一覧）を返す
```

#### Step 2-b: ブラインドスポット・パス（盲点探索の整理・メイン）

Step 2-a が返した『未知の未知の候補』を整理し、不明点として扱う。以下の3フィルタで機械的に絞る:

1. 証拠が既に見つかっている候補（＝実は既知に転じたもの）は落とす
2. Step 1 で確認済みの不明点と重複するものは除外する
3. 設計を左右するものだけ残す

残った不明点は Step 1 と同じ要領で **1回にまとめて** ユーザーに確認してから Step 3 へ進む（Step 1 で確認済みの場合は差分のみ確認する）。件数のハード上限は設けないが、「設計を左右するか」で機械的に絞り、羅列を避ける。

> 影響度ラベル・選択肢・推奨案（自動フローの改善）は手動フローには適用しない。ここでは既存 Step 1 スタイルの素朴な列挙のままとする。

### Step 3: 合意対象の判定と仕様生成

「実行可能仕様駆動」のゴールは、人間が**目で見て手で触れる仕様**を素材にして合意することにある。
このステップでは issue から「**合意したいもの**」を判定し、それぞれに対応する実行可能仕様を生成する。

#### Step 3-a: 合意対象の判定（メイン）

issue 内容と Step 2 の調査サマリーをもとに、以下のうち合意したいものをすべて判定する。
「シンプル/複雑」のような主観基準では選ばず、**合意したい対象が存在するか**で機械的に判定する。
排他ではないため、複数該当する場合はすべて選ぶ（例: フォーム追加なら「各状態の見た目」と「ページレイアウト」を両方選ぶ）。

**フロントエンド（画面）**

| 合意したいもの | 判定基準 | 成果物 |
|---|---|---|
| 各状態の見た目 | 状態が 2 つ以上ある（成功 / 失敗 / 空 / ローディング / バリデーションエラー 等） | presentationalコンポーネント + Story（状態ごとに1つ） |
| ページのレイアウト・要素配置 | 新規ページの追加 or 既存ページの構成変更 | ページコンポーネントに静的UIを実装（ロジックは書かない）。機能要件を伴う場合は下記「機能要件を伴うページの Container 配線方針」に従う |
| 画面間の遷移 | 2 画面以上の間の遷移が追加・変更される | `docs/specs/screen-transition.md` 更新 + 関連ページの静的実装 |
| 操作の意図（押下・送信で何が変わるか） | インタラクションを伴うUIが追加される | Story の `play` 関数で操作を示す、または該当箇所にコメントで意図を記述。機能要件を伴う操作（送信→API呼び出し→画面遷移等）の場合は下記「機能要件を伴うページの Container 配線方針」に従う |

#### 機能要件を伴うページの Container 配線方針

issue の機能要件（「ユーザーは〜できる」という記述）に UI から到達する必要があるページ（例: フォーム送信で投稿が作成される）は、Presentational コンポーネントの静的描画だけで合意しない。以下のいずれかを確定仕様に明記する:

- (a) このフェーズでルートを Container（静的画面〈Presentational コンポーネント等〉を実データ・API に接続する層。具体的な配置・呼び方は `docs/architecture/frontend/directory-structure.md` に従う）に配線する
- (b) 配線は実装フェーズ（dev-impl）で行う旨と、配線が必要であること自体を明記する（「静的UIのみ」として暗黙に確定しない）

判定基準: 「シンプル/複雑」ではなく、**issue の機能要件がこのページの操作から実際に到達可能である必要があるか**で機械的に判定する。見た目確認のみが目的の合意（例: エラー表示パターンのみを確認したい場合）はこの方針の対象外。

記録先: ページコンポーネントファイル内のコメント、または Step 5 の確定仕様コメントの該当行に一言添える（例:「Container配線: 実装フェーズで実施」）。

この方針が明記されたページの受け入れテスト（対象ルート/ページの統合テスト）には、実装準備フェーズ（`dev-impl-prep` / `dev-auto-test-plan`）で「実際の送信→API呼び出し→画面遷移」のハッピーパスを1本含めるよう申し送る（Container 未配線を実装前の RED として早期検知するため）。

**(a) を選んだ場合の後続フェーズへの申し送り**: このフェーズ（要件定義）で Container 配線＝業務ロジックの実装まで完了するため、後続フェーズでは通常の TDD 順序（RED → GREEN）が成立しない。これは実装漏れではなく (a) を選んだ結果として想定される挙動であり、以下のとおり扱う（申し送り先: `dev-impl-prep` / `dev-auto-test-impl` / `dev-auto-test-reviewer` / `dev-impl` / `dev-auto-impl`）:
- テスト実装フェーズ: 上記のハッピーパステストは実装済みコードに対して最初から GREEN になりうる。当該テストに限り「実装未着手を理由に失敗すること（RED）」の確認を必須とせず、代わりに「確定仕様どおりに GREEN であること」を確認する（検証扱い）。他の未配線箇所のテストは通常どおり RED を確認する
- 実装フェーズ: 当該ページについては追加実装が不要（変更ファイルなし）になりうる。これは実装漏れではなく、この場合はテストが確定仕様どおりに動作することの確認（検証）のみを行う

(b) を選んだ場合はこの申し送りは不要（通常どおり RED → GREEN の順序が成立する）。

#### ストレッチドリンク（オーバーレイ型クリック領域拡張）採用時の前面要素の列挙

カード全体を透明な全面リンクでクリック可能にし、内側の独立クリック要素（ボタン・リンク等）を `relative z-10` 等で前面に上げる「ストレッチドリンク」パターンを採用する場合、「前面に上げる要素」をブロック単位ではなく要素単位で列挙して確定仕様に明記する。以下を確認する:

- 前面に上げるべきなのは「独自のクリック挙動を持つ要素そのもの」（ボタン・リンク本体）だけか
- その要素を含む**親ブロック**（本文テキスト等）ごと持ち上げていないか（テキスト全体が巻き添えで不可視のクリック障壁になり、カード本体のクリックで遷移しなくなっていないか）
- 結果として「カードのどの領域をクリックすると遷移するか」を面積ベースで説明できるか

記録先: 生成するコンポーネント実装またはStoryのコメントに、前面に上げた要素の一覧を明記する。

**バックエンド・データ**

| 合意したいもの | 判定基準 | 成果物 |
|---|---|---|
| API のリクエスト・レスポンス形状 | APIエンドポイントの追加・変更 | 既定: `docs/specs/openapi.yaml`（スキーマのみ・処理は書かない）。コードファーストのスタックでは、スキーマ定義＋ルートのスタブ定義（定型レスポンスを返すだけでロジックは書かない）。下記「API 契約の形式」参照 |
| DB スキーマ | DB 構造の変更 | マイグレーションファイル（カラム定義のみ） |
| ログ出力 | 新規ログ出力 | `docs/specs/log-spec.md`（ログ形式・出力条件） |
| 非同期メッセージ・イベント | イベント・キューの追加・変更 | `docs/specs/events.md`（イベント・メッセージスキーマ） |

#### API 契約の形式（openapi.yaml／コードファーストのスキーマ＋ルートスタブ）

API のリクエスト・レスポンス形状は、次のいずれかの形式で「API 契約」として書き、その成果物を人間がレビューして合意する。どちらを採るかは Step 2 で調査したバックエンドフレームワークと既存の API 契約の形式（`docs/architecture/` に定めがあればそれ）に従う。

- **既定: `docs/specs/openapi.yaml`（OpenAPI 定義）** — スキーマのみを書き、処理は書かない。合意レビューの対象は `openapi.yaml` の diff。
- **コードファースト: スキーマ定義＋ルートのスタブ定義（schema-first / stub-first）** — スキーマ定義から型・OpenAPI が生成される構成（例: スキーマバリデーションライブラリの定義から型付きクライアントを推論する TypeScript のルーター、FastAPI + Pydantic 等）では、API の形状を独立したドキュメントに二重記載せず、要件定義フェーズで「スキーマ定義＋ルートのスタブ」をコードとして書き、その diff を人間がレビューして合意する。この場合、**形状の正はコード**としてよい。合意した時点で API の型（型付きクライアントの型・生成される OpenAPI 等）が確定するため、frontend はその型に対して即座に型チェック・並行開発できる。実装フェーズ（dev-impl）ではスタブの返り値型を変えずに中身（ロジック）を実装する。
  - 入力: その処理（usecase・ハンドラ等）の入力スキーマを定義・export する（合意そのもの）。配置は `docs/architecture/backend/` のディレクトリ設計・既存パターンに従う
  - 出力: ハンドラの返り値の型を固定する（型注釈・`satisfies` 等、言語の仕組みで返り値がレスポンス型に一致することを保証する）。レスポンス型は既存慣例どおりの型定義でよく、必要ならスキーマ定義から導出してもよい
  - スタブはビルド・型チェック・CI 相当チェック（`docs/specs/technical-environment.md` の `## 実行コマンド`）を通す必要があるが DB には触れない（定型値を返すだけ）。統合テストは実装フェーズで書く

コードファーストの記法例（言語非依存の擬似コード）:

```
# <スキーマ定義ファイル> — その処理自身の入力（と必要なら出力）をスキーマ／型で先に定義（合意対象）
FollowCreateInput = { followeeId: string (min length 1) }
FollowResponse    = { id: string, followerId: string, followeeId: string, createdAt: string }

# <ルート定義ファイル> — ルート＋定型（スタブ）。入力スキーマでバリデーションし、返り値をレスポンス型に固定する。ロジックは dev-impl で実装する
POST /follows  (body validated by FollowCreateInput)
  -> 201, return { id: "", followerId: "", followeeId: "", createdAt: "" } as FollowResponse
```

コードファーストの場合、人間の合意レビュー対象は「スキーマ定義＋ルートスタブの diff」（＝コード）であり、ドキュメントではない。

複数の合意対象が同じ成果物を要求する場合（例: 新規ページ追加で「ページのレイアウト」と「画面遷移」が両方ヒット）、成果物のファイルは 1 つにまとめてよい。Step 5 では複数の項目から同じファイルを参照する形になる。

判定が完了したら、以下の形式で `gh issue comment` で issue に記録する（合意前の判定速報。確定版は Step 5 で記録する）:
```
## 合意対象判定（合意前の判定速報）

### 合意対象 → 成果物
- 各状態の見た目 → `<Storyファイル一覧>`
- API のリクエスト・レスポンス形状 → `docs/specs/openapi.yaml`（コードファーストの場合は `<スキーマ定義ファイル>`＋`<ルートスタブファイル>`）
- ...
```

このコメントは Step 5 で確認対象ファイル一覧を提示する際の原本として参照する。会話メモリだけに保持せず、必ず記録する。

#### Step 3-b: 仕様生成（general-purpose エージェント）

Step 3-a で判定した合意対象と対応する成果物の一覧を渡し、即時ファイル保存させる。
実装コード（処理ロジック）は書かない。

**生成物のフォーマット・lint 検証（このステップの完了条件）**: 生成・変更したファイルをプロジェクトで設定済みのフォーマッタ・linter で整形し、CI と同じ検証が green になることを確認してから完了とする（ワークフローの手順として指示された整形であり、自己判断での整形ではない）。委任先だけでなく、このステップを自分で実行する場合（`/dev-auto` 経由の `dev-auto-spec-gen`）にも適用する。

- 整形: 設定済みフォーマッタ・linter の自動修正（format + lint の safe fix + import 整列等）を、自フェーズで生成・変更したファイルだけを対象に適用する（コマンドは `docs/specs/technical-environment.md` の `## 実行コマンド` とフォーマッタの設定に従う。複数パッケージ構成ならパスは対象パッケージ起点で指定する）
- 検証: `docs/specs/technical-environment.md` の `## 実行コマンド` に記載の「CI 相当チェック」のコマンド（CI と同一条件で検証するもの。複数パッケージ構成なら全パッケージに対して実行し、1 つ目が red でも残りを検証する）が green であること。format:check / lint だけでは CI の検証項目（import 整列等）を網羅しない場合があるため、これだけで CI 相当の検証を済ませたとみなさない（根拠: `.claude/agents/dev-auto-impl.md`）
- フォーマッタ・linter の適用範囲外（例: フォーマッタの対象が特定ディレクトリ・特定拡張子に限られ、`docs/specs/` の Markdown・マイグレーションの SQL 等を含まない場合）は実行対象とせず、適用範囲外である旨を報告する。自フェーズの生成物でない既存の崩れは巻き込んで直さない（`.claude/agents/dev-auto-spec-gen.md` の既存事象判定に従う）

general-purposeエージェントへの指示例:
```
以下の合意対象に対応する実行可能仕様を生成してください。
合意形成のための素材であり、実装コード（処理ロジック）は書きません。

[Step 2 の調査サマリー]
[Step 3-a で判定した「合意対象 → 成果物」のリスト]
[issue内容]

- 各合意対象に対応する成果物を、ファイルとして即時保存する
- 既存のディレクトリ構造・命名規則に従う
- ストレッチドリンク（透明な全面リンク + 内側要素の前面化）を使う場合、前面に上げる要素を「独自のクリック挙動を持つ要素そのもの」に限定し、それを含む親ブロックごと持ち上げない（上記「ストレッチドリンク採用時の前面要素の列挙」参照）
- API の追加・変更がある場合、成果物は API 契約とする: 既定は `docs/specs/openapi.yaml`（スキーマのみ・処理は書かない）。コードファーストのスタックでは、スキーマ定義（処理自身の入力として定義・export する）＋ ルートのスタブ定義（定型レスポンスを返り値の型を固定して返すだけ。DB アクセス・ロジックは書かない）とする（上記「API 契約の形式」参照）
- スタブを書いた場合は、ビルド・型チェック（コマンドは `docs/specs/technical-environment.md` の `## 実行コマンド` を参照）を通ること。api-list.md への一覧行追記は行わない（Step 4 の担当）
- 自フェーズで生成・変更したファイルに設定済みフォーマッタ・linter の自動修正を適用し、`docs/specs/technical-environment.md` の「CI 相当チェック」のコマンドが green であることを確認すること（フォーマッタ・linter の適用範囲外のファイルは対象外。上記「生成物のフォーマット・lint 検証」参照）。フォーマット・import 整列の崩れを残したまま完了報告しない
- 完了後、生成したファイル一覧を「どの合意対象に対応するか」を明示して返してください。あわせて、実行した整形・検証コマンドとその結果（green か、残存エラーがある場合はその内容と扱い）を返してください
```

### Step 4: 横断インデックスの更新（メイン）

Step 3-b で生成しない「リポジトリ横断のインデックス・サマリ系ドキュメント」だけをここで更新する。
Step 3-a の 成果物 列に挙がっているファイル（API 契約〈`docs/specs/openapi.yaml`、またはコードファーストのスキーマ定義＋ルートスタブ〉・`docs/specs/screen-transition.md`・マイグレーション・各種コンポーネント等）は Step 3-b で生成済みのため、このステップでは触らない。**責務境界: API の形状（契約）＝ Step 3-b、api-list.md のエンドポイント一覧行の追記＝ Step 4。**

以下を即時ファイル保存する。変更がない項目はスキップ。
`docs/specs/` のファイルが存在しない場合は `docs/template/` からコピーして新規作成する。

| ファイル | 内容 | 更新条件 |
|---|---|---|
| `docs/specs/screen-list.md` | 新規画面を行として追記 | 画面の追加・変更がある場合 |
| `docs/specs/er-diagram.md` | テーブル・カラムをmermaid erDiagramに追記・修正 | DB構造の変更がある場合 |
| `docs/specs/api-list.md` | 新規エンドポイントを行として追記（概要一覧） | REST APIエンドポイント（JSONレスポンスを返すもの）の追加・変更がある場合（画面を返すルートは対象外） |

> `api-list.md` は REST API（JSONレスポンスを返すエンドポイント）のメソッド・パス・説明・認証を一覧するのみ。リクエスト/レスポンス形状の正は Step 3-b で生成した API 契約（`openapi.yaml` はその機械可読の完全仕様。コードファーストの場合はスキーマ定義＋ルート定義のコード）が担い、api-list.md に形状は書かない。画面ルートは `screen-list.md` に記載し `api-list.md` には含めない。

### Step 5: 人間への確認・合意（メイン）

Step 3-a で判定した合意対象ごとに、確認対象ファイルを一覧で提示する。
ユーザーがファイルを見て「OK」または修正指示を返したら合意とみなす。
API の形状については、確認対象は API 契約の diff である（既定は `openapi.yaml`。コードファーストの場合はドキュメントではなく「スキーマ定義＋ルートスタブの diff」（コード）であり、合意時点で API の型が確定し、frontend はその型で型チェックできる）。ユーザーはこの diff を見て合意する。

1. Step 3-a で判定した合意対象だけを抜き出し、以下の形式で提示する（判定対象外の項目は提示しない）。
   雛形中の `<...>` プレースホルダは Step 3-b で実際に生成したファイルパスに置換すること（リテラルのまま出さない）。
   ```
   以下のファイルを生成・更新しました。確認してフィードバックをください。
   修正したい点があれば指示してください。問題なければ「OK」と返してください。

   - 各状態の見た目: `<Storyファイル一覧>`
   - API のリクエスト・レスポンス形状: `docs/specs/openapi.yaml`（コードファーストの場合は `<スキーマ定義ファイル>`＋`<ルートスタブファイル>`）／一覧行: `docs/specs/api-list.md`
   - ...
   ```
2. フィードバックを受けて修正する（複数回対応）。ユーザーが「OK」を返したら確定とみなす
3. ユーザーが確定したら、以下の形式で `gh issue comment` でissueに記録する。これがフェーズの確定版であり、後続フェーズ（`dev-impl-prep` / `dev-impl`）はこのコメントを参照する:
   ```
   ## 確定した合意済み仕様

   ### 合意対象 → 確定ファイル
   - 各状態の見た目: `<Storyファイル一覧>`
   - API のリクエスト・レスポンス形状: `docs/specs/openapi.yaml`（コードファーストの場合は `<スキーマ定義ファイル>`＋`<ルートスタブファイル>`）／一覧行: `docs/specs/api-list.md`
   - ...

   ### フィードバック履歴
   - <何をどう変えたか>
   ```
4. コミット前に Step 3-b の「生成物のフォーマット・lint 検証」を再実行し、green であることを確認する（手順 2 のフィードバック修正でフォーマット・import 整列が崩れうるため）
5. 生成・更新したファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）
6. 「要件定義フェーズが完了しました」と伝え、次のコマンドを案内する:
   ```
   次のフェーズへ進む場合は以下を実行してください:
   /dev-impl-prep <issue番号>
   ```

## 注意事項

- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- アーキテクチャ定義（`docs/architecture/`）を必ず参照し、既存コードの命名規則・ディレクトリ構造に従う
- 変更が不要なドキュメントは更新しない（空振りの更新をしない）
- issueに記録するコメントは日本語で書く
