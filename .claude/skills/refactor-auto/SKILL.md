  - 「/refactor-auto <番号>」と呼び出されたとき

## 概要

リファクタリング専用の自律ループワークフロー。
機能追加とは異なり、「既存コードを別のコード・コンポーネントに置き換える」パターンに特化する。

探索フェーズで「何をどう変えるか」を明確にし、質問→計画→承認のサイクルで人間と合意してから実装する。
実装後はレビュー（最大3回）→修正（最大2回）を繰り返し、通らなければ人間に報告して終了する。
なお、ワークフロー開始時に issue へのコメント投稿許可を Step 0 で1回確認する。

## 引数

- `<issue番号>`（必須）: リファクタリング対象のGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /refactor-auto 42」と伝えて終了する

## エージェント構成

```
メインスキル（オーケストレーター）
├── Step0: mainブランチガード・進捗確認・再開ポイント判定（メイン）
├── Step1: 探索 → Explore エージェント
│             ↓ 調査結果・変更パターン候補・不明点リストを受け取る
├── Step2: 質問フェーズ（メイン）← タッチポイント① ※不明点がなければスキップ
├── Step3: 計画立案 → Plan エージェント
│             ↓ 変更計画書を受け取る
├── Step4: 計画承認フェーズ（メイン）← タッチポイント②
├── Step5: 実装 → general-purpose エージェント（実装完了時にコミットし、続けて `## リファクタ実装完了` を投稿）
│             ↓ 変更ファイル一覧を受け取る
│             ※ 新規依存の install がサンドボックスでブロックされた場合は、
│               install 依頼以降（検証・修正・コミット・完了コメント投稿）をメインが引き取る
├── Step6〜8: レビュー → 修正ループ（レビュー最大3回・修正最大2回）
│   ├── [refactor-auto-reviewer] レビュー
│   └── [general-purpose] 修正（問題ありの場合。修正後はメインが追加コミット）
└── Step9: 完了マーカー投稿（ふりかえり同梱）・PR 作成・完了報告・改善issue起票確認（メイン）
```

## 手順

### Step 0: mainブランチガード・コメント投稿許可・再開ポイントの判定

> **集約先ファイルとの対応関係**: 本 Step 0 の「main ブランチガード / 開始時ガード（ブランチ突合・未コミット差分確認）/ コメント投稿許可」は、`dev-auto`・`bugfix-auto` の Step 0 と共通のロジックとして `.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」に集約されている。この共通部分を変更する場合は集約先ファイルのその節を更新すること（3スキルに自動的に反映される）。スキル固有の差分（コマンド名・再開表の内容・再開ポイントのステップ番号）は本ファイルに残す。

`.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」を Read し、`<コマンド名>` を `/refactor-auto`、`<進捗コメント項目一覧（説明文）>` を `確認済み不明点・承認済みリファクタ計画・実装完了・完了マーカー等`、`<進捗コメント項目一覧（確認文言）>` を `確認済み不明点・承認済みリファクタ計画・各フェーズの完了マーカー等` に置き換えて、その内容のとおりに実行する。同ファイルを Read できない、または該当節が見つからない場合は、開始時ガードとコメント投稿許可を省略して先へ進まず、その旨をユーザーに伝えて終了する。

続いて `gh issue view <番号> --json comments` でissueコメントを取得し、以下の表に従って再開ポイントを決定する（`--comments` は auto mode の環境で空出力になる既知事象があり、空出力を「コメントなし（初回）」と誤判定して完了済み issue をやり直してしまうため使わない。/auto-loop 配下の子は auto mode で起動されるので必ず該当する）。

| issueコメントの状態 | 再開ポイント |
|---|---|
| コメントなし（初回） | Step 1 から実行 |
| `## 確認済み不明点` のコメントあり（スキップした場合を含む） | Step 3 から実行 |
| `## 承認済みリファクタ計画` のコメントあり | Step 5 から実行 |
| `## リファクタ実装完了` のコメントあり | Step 6 から実行 |
| `## /refactor-auto — 自動修正できませんでした` のコメントあり | Step 6 から再開（手動修正後の再実行を想定し、レビュー・修正ループの回数はリセットする） |
| `## /refactor-auto 完了` のコメントあり | 完了済みと報告して終了 |

複数の行に該当する場合は、最も進んだ（表の下の）行を採用する。

再開ポイントが Step 1 以外の場合は、ユーザーに以下を伝えてから該当 Step に進む:

```
issue #<番号> の進捗を確認しました。<X> まで完了しているため、Step <N> から再開します。
```

### Step 1: 探索（Explore エージェント）

`subagent_type: "Explore"`・`model: "sonnet"` でエージェントを起動する。以下を調査させ、結果をメインに返させる:

- issueのタイトル・本文（`gh issue view <番号>` で取得）
- 経緯として参照している他 issue/PR の状態の検証（issue 本文の記載と実際の state が食い違っていないか）
- リファクタ対象と思われるファイル・ディレクトリ
- 置き換え前のパターン（現在のコード）と、置き換え後のパターン（新コンポーネント・新APIなど）の候補
- 変更対象ファイルの一覧（`git grep`・ファイル検索で特定）
- 確定事項とMaterial Ambiguityの区別
  - **確定事項**: プロジェクト内ドキュメント（`docs/` 配下・`.claude/rules/` 等）を調べれば一意に決まるもの。質問候補にはせず、根拠となるドキュメント名・節名・該当記述の引用を添えて返す
  - **Material Ambiguity（実装方向が変わりうる曖昧点）**: ドキュメントを調べても決まらず、人間の判断が必要なもののみ
    - スコープ: どのディレクトリ・ファイルまで変更するか
    - 例外: 変更しないファイル・ケースがあるか
    - 変換ルール: 複数のパターンがある場合の優先度や使い分け
    - ユーザーに見える動作が変わりうる点
    - 経緯として参照する他 issue/PR の状態が食い違っている点
    - 経緯として参照する他 issue/PR の参照先番号が解決できなかった点（検証コマンドが終了コード0以外で失敗した場合）
  - 判断に迷う場合は Material Ambiguity 側に倒す（確定事項への誤分類は人間の判断機会の喪失につながるため）

Exploreエージェントへの指示例:
```
issue番号 <番号> のリファクタリングを自律実行するために、以下を調査してください。

1. `gh issue view <番号>` でissueの内容を取得する
2. issue 本文が他 issue/PR 番号を経緯として参照している場合（前提として他 issue/PR の状態に言及している箇所。単なる関連リンクの列挙は対象外）、参照先ごとに状態を検証し、記載内容と食い違っていれば 6. の Material Ambiguity に含めること。経緯として参照しているかの判断に迷う場合は検証する側（安全側）に倒すこと
   - `gh issue view <参照先の番号> --json state,stateReason,closedAt` を1回実行する（`<参照先の番号>` は調査対象の issue 番号ではなく参照先の番号を指す）。`gh issue view` は PR 番号も解決し、PR の場合は `state` が `MERGED` / `CLOSED` / `OPEN` で返るため、番号の種別を事前に判別する必要はない（`gh pr view` との2段フォールバックは不要）
   - `owner/repo#<番号>` の形で他リポジトリを指す参照には `--repo owner/repo` を付けること。付けないと現在のリポジトリの同じ番号を見に行き、その番号が存在しなければ実在する参照を「解決できなかった参照先」として誤報告し、存在すれば無関係な issue/PR の state を検証結果にしてしまう
   - 検証の成否はコマンドの終了コードで判定する（gh の直後で終了コードを確認すること。`gh ... | jq ...` のようにパイプでつなぐと末尾コマンドの終了コードになり gh の失敗を取りこぼす）
   - 終了コード0以外（番号が存在しない・認証切れ・レート制限など理由を問わない）の場合、その参照先番号を「解決できなかった参照先」として 6. の Material Ambiguity に含めること
3. 変更対象と思われるファイル・ディレクトリを特定する（`git grep` や `git ls-files` を使う）
   - リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
4. 置き換え前のコードパターンと置き換え後のパターン候補を具体的に示す
5. 変更が必要なファイルの一覧を作成する
6. 曖昧点を洗い出し、以下の2つに区別する:
   - **確定事項**: プロジェクト内ドキュメント（`docs/` 配下・`.claude/rules/` 等）を調べれば一意に決まるもの。質問候補にはしない。根拠となるドキュメント名・節名・該当記述の引用を添えて返す
   - **Material Ambiguity（実装方向に影響する曖昧点）**: ドキュメントを調べても決まらず、人間の判断が必要なもののみ。以下の観点で洗い出す:
     - 変更スコープ（どこまで変えるか）
     - 例外ケース（変えないファイル・パターンがあるか）
     - 変換ルールが複数ある場合の使い分け
     - ユーザーに見える動作が変わりうる点
     - 経緯として参照する他 issue/PR の状態が、2. で検証した実際の状態と食い違っている点
     - 経緯として参照する他 issue/PR の参照先番号が解決できなかった点（検証コマンドが終了コード0以外で失敗した場合）
   - 判断に迷う場合は Material Ambiguity 側に倒すこと（確定事項への誤分類は人間の判断機会の喪失につながる）
7. （3.〜6. のすべてに適用される制約）main との差分・分岐点算出（マージベースの特定等）を扱う場合は、比較対象を `main` ではなく `origin/main` にすること。ローカル `main` は worktree 作成スクリプト（例: `scripts/wt-new.sh`。`gh issue develop --base main` で作業ブランチを作る）のフローで最新化されないため、ローカル `main` を基準にすると分岐点を誤って古く算出しうる（根拠: `.claude/skills/auto-loop/SKILL.md`「エスカレーション時の後片付け」節）。また、`origin/main` を参照する前に `git fetch origin main` を実行し、**終了コードで成否を判定する**こと（worktree 作成スクリプトは作業ブランチしか fetch しないことがあり、worktree の `origin/main` 自体が古いことがある）。fetch に失敗した場合は `origin/main` も古い可能性があるため分岐点を確定させず、その旨を明記すること（同節の「`git fetch` が失敗した場合は `origin/main` も古い可能性がある」の扱いに合わせ、安全側に倒す）。使用した比較対象と `git fetch` の成否は調査サマリーに残すこと（Step 3・Step 4 で基準を突き合わせられるようにするため）

以下を返してください:
- 調査サマリー（対象ファイル一覧・現在のパターン・置き換えパターン）
- 経緯として参照している他 issue/PR の検証結果（参照先の番号と state。解決できなかった参照先は `#<番号>: 解決できず` の形で明記する。参照が無ければ「なし」）
- 確定事項の一覧（引用付き。なければ「なし」）
- Material Ambiguityの一覧（なければ「なし」）
- main との差分・分岐点を扱った場合の比較対象と `git fetch origin main` の成否（扱っていなければ「該当なし」）
```

### Step 2: 質問フェーズ（メイン）← タッチポイント①

Explore エージェントから Material Ambiguity の一覧を受け取る。

記録するコメントには Step 1 の探索結果サマリーを必ず同梱する。
別セッションで Step 3 から再開しても、Plan エージェントに探索結果を渡せるようにするため。

**不明点がない場合**: このステップをスキップし、以下の内容でissueに記録してStep 3へ進む:
```
## 確認済み不明点

不明点なし。探索フェーズで変更計画を立てる十分な情報が得られました。

### 探索結果サマリー
- 対象ファイル一覧: <一覧>
- 現在のパターン: <置き換え前のパターン>
- 置き換えパターン: <置き換え後のパターン>
- 経緯として参照している他 issue/PR の検証結果: <参照先の番号と state（例: #12: MERGED）。解決できなかった参照先は `#<番号>: 解決できず` の形で明記する。参照が無ければ「なし」>
```

**不明点がある場合**: 不明点を **1回にまとめて** ユーザーに質問する（複数回に分けない）。
質問は通常のテキスト応答として提示し、AskUserQuestion 等の対話ダイアログは使わない
（/auto-loop の指揮役が pane 経由で応答できるようにするため）。
回答を得たら、以下の形式で `gh issue comment` でissueに記録する:
```
## 確認済み不明点

### 質問
- <質問1>
- <質問2>

### 回答
- <質問1への回答>
- <質問2への回答>

### 探索結果サマリー
- 対象ファイル一覧: <一覧>
- 現在のパターン: <置き換え前のパターン>
- 置き換えパターン: <置き換え後のパターン>
- 経緯として参照している他 issue/PR の検証結果: <参照先の番号と state（例: #12: MERGED）。解決できなかった参照先は `#<番号>: 解決できず` の形で明記する。参照が無ければ「なし」>
```

### Step 3: 計画立案（Plan エージェント）

> **集約先ファイルとの対応関係**: 本 Step 3 の Plan エージェント指示のうち、`origin/main` 基準の段落・`git grep` の使用指示は、`.claude/skills/_shared/orchestrator-common.md`「Step 3 Plan 指示: origin/main 基準の段落」「Step 3 Plan 指示: git grep 使用指示」に集約されている（`bugfix-auto` の Step 3 も同じ集約先を参照するため、変更すれば両スキルに自動的に反映される）。変更する場合は集約先ファイルの該当節を更新すること。自己チェックの「変更対象ファイル内の並行記述」2項目は、`bugfix-auto` の Step 3 の対応する2項目と対象範囲・検索コマンドが実際に異なる（本スキルは検索対象を変更対象ファイル内に限定するが、`bugfix-auto` は変更対象ファイルの内外に拡張し検索範囲もリポジトリ全体にする）ため集約せず、各スキルにスキル固有の記述として残す。上記2節の集約対象以外の Plan エージェント指示（計画の項番号・計画コメント名 `## 承認済みリファクタ計画` を含む）は本ファイルに残る。

`subagent_type: "Plan"`・`model: "sonnet"` でエージェントを起動する。
以下を渡し、具体的な変更計画書を作成させる:

```
以下のリファクタリングの変更計画を作成してください。

[issue番号: <番号>]
※ issueの詳細は `gh issue view <番号>` で取得すること

[探索結果サマリー]
<Step 1 の調査サマリー（経緯として参照している他 issue/PR の検証結果を含む）>

[不明点への回答]
<`gh issue view <番号> --json comments --jq '.comments[].body'` で生テキストとして取得した、最後の `## 確認済み不明点` コメントの「### 回答」セクションを、要約せずそのまま貼り付けること（スキップした場合は「不明点なし」）>

[前提の優先順位]
issue 本文の記載と、[探索結果サマリー] の「経緯として参照している他 issue/PR の検証結果」が食い違う場合は、[不明点への回答] で別の結論が示されていない限り、検証結果を優先して計画に反映すること。

変更計画には以下を含めること:
1. リファクタリングの目的・ゴール（1〜2行）
2. 変換ルール（置き換え前のパターン → 置き換え後のパターンを具体的なコード例付きで）
   - 既存の記述を削除するのではなく**置換する**パターンについては、方針の説明だけで済ませず、対象ファイルを実際に Read したうえで **Before / After の逐語（実文面）を提示する**こと
   - 置換によって元の記述が持っていた意味が失われないことの根拠を1〜2行で添えること
   - 検討したが採用しなかった置換案がある場合は、その理由も残すこと（レビュー時に判断を再現できるようにするため）
   - 複数の Before/After ブロック（同一ファイル内の import・型定義・本体処理等に限らず、ファイルをまたぐものも含む）が互いに矛盾しないことを自己チェックしてから返すこと（例: ある箇所の After で削除した import を、別箇所の After で参照していないか。あるファイルの After で削除したエクスポートを、別ファイルの After が import したままにしていないか）
   - 新規に追加するコメント/ドキュメントコメントが、他の関数・変数・判定ロジックとの役割分担や処理順序を主張する場合は、方針の説明だけで済ませず、その説明対象のコード（呼び出し元・別の判定ロジック等）を実際に Read し、記述内容が実装と一致することを確認してから計画に記載すること（対象コードを読まずに役割分担・処理順序を推測で記述しない。追加するコメント案が除外処理の主体や呼び出し元を実装と取り違え、差し戻しになりうるため）
3. 変更対象ファイル一覧（ファイルパスと変更内容の概要）
   - 削除・移動するファイルがある場合は、そのファイルの参照元を `git grep` で網羅的に洗い出し、判明した参照元をすべて「編集」対象としてこの一覧に含めること（削除・移動対象のファイル名・エクスポート名で広めに検索してから絞り込むこと。狭い検索条件では参照元を取りこぼす）
     - <`.claude/skills/_shared/orchestrator-common.md`「Step 3 Plan 指示: git grep 使用指示」の本文を要約せずこの位置に貼り付ける>
   - `git grep` の対象は次を**最低限**とし、これ以外の参照形式も見つけ次第一覧に含めること（列挙は網羅の上限ではない）:
     - コード: 使用言語のモジュール参照構文すべて（例: JS/TS なら `import ... from`・re-export（`export * from` / `export { ... } from`）・`import type`・動的 import（`await import("...")`）。他言語なら `require` / `use` / `from ... import` 等）
     - テスト: テストファイル中のモック対象のパス指定（例: `vi.mock` / `jest.mock` / `unittest.mock.patch` の文字列引数）。モックのパス指定は型チェックや依存関係の機械検証の対象外になりやすいため `git grep -n <pattern> -- <テストファイルの pathspec>` で洗い出さないと見落とされる。テストファイルの拡張子・命名パターンはプロジェクトで使われているものすべてを対象にし、一部の拡張子に絞らない
     - 設定・機械検証のベースライン: ファイルパスを直書きしている設定ファイル（例: 依存関係検証ツールの既知違反ベースライン。移動すると陳腐化して CI が落ちる）・テストランナーの共有設定ファイル（例: `vitest.config.ts` / `jest.config.js` / `pytest.ini`）等のパス指定
     - ドキュメント: `docs/` 配下・`CLAUDE.md`・`.claude/` 配下のパス記述（型チェック・テスト・依存関係の機械検証のいずれでも検出されない）
   - 使用した `git grep` パターンとヒット一覧（一覧に含めたもの・含めなかったものとその理由）を計画に残すこと（実装時とレビュー時に網羅性を再現できるようにするため）
4. 変更しないファイル・スコープ外の明示
5. 注意点（変換時に気をつけるべき例外・エッジケース）
   - 新規に定数・関数を export（公開）するモジュールがある場合は、そのモジュールのファイル名（拡張子なしのベース名）でテストファイル中のモック指定行（例: `vi.mock(` / `jest.mock(`）を広めに `git grep` し、パスエイリアス表記・相対パス表記の両方の記述を拾ってから対象を絞り込むこと（狭い検索条件では参照元を取りこぼす。項目3と同じ理由）。既存テストを対象とする
   - ヒットしたモックが、モジュールの戻り値をファクトリで全指定するフルモックか、元の実装を取り込んだうえで一部だけ差し替える部分モック（例: Vitest の `importOriginal` / Jest の `jest.requireActual` を経由するもの）かを1件ずつ判定すること
   - フルモックが1件でもあれば、「新規 export がモック上で未定義になるため部分モック化が必要」という旨をこの注意点に明記し、該当テストファイルの実行コマンドを7.の検証手順にも含めること
   - 使用した `git grep` パターンとヒット一覧（フル/部分モックの判定を含む）を計画に残すこと
6. 新規依存の追加有無（追加が必要な場合はパッケージ名・バージョン・用途・追加先（複数パッケージ構成ならワークスペース・パッケージ名）を明記。不要なら「なし」）
7. 検証手順（変更後に実行する確認コマンドと期待結果）
   - 検証コマンドは**削除対象に限定したパターン**で書くこと。スコープ外として意図的に残す記述にヒットしないよう、パターンを絞るか対象範囲（行・節）を限定する
   - 絞り込めない場合は「0件であること」ではなく、**期待ヒット数とその内訳（どの行がなぜ残るか）**を明記すること
   - 削除・移動を伴う場合は、3. で使った参照元 `git grep` の再実行を検証手順に含めること（期待は0件、または残る行とその理由）。計画時の洗い出し漏れを実装後に機械的に検出するため
     - `git grep` は追跡済みファイルのみを走査する。実装で新規作成したファイルが未コミット（未追跡）のままだと走査対象外になり「0件」が偽陰性になりうるため、再実行は `--untracked` を付けるか、先にコミットしてから行うこと
   - 検証手順に期待テストファイル数・テスト数を明記する場合、削除・移動・新規作成の対象ファイル（テストファイル自身とは限らない。例: 表示コンポーネントの本体ファイル）が、ディレクトリの走査結果やソース側の配列・定数からテストケースを動的に生成する既存テストの生成対象に含まれることがある。次の手順で増減を見積もりに反映すること（パラメタライズドテストの構文（例: `it.each` / `test.each` / `pytest.mark.parametrize`）そのもので検索すると静的な配列を回すだけの実装まで多数ヒットし絞り込めないため使わない）
     - ディレクトリ走査型の動的生成を洗い出す: 使用言語のファイル列挙 API を `git grep -n --untracked -E` で検索する（例: JS/TS なら `"readdirSync|readdir\(|import\.meta\.glob|globSync|globby|fast-glob"`、Python なら `"os\.listdir|os\.walk|glob\.glob|Path\([^)]*\)\.(r?glob|iterdir)"`。このパターンは**最低限**であり、列挙は網羅の上限ではない）
     - データ駆動型の動的生成を洗い出す: ソース側の配列・定数をパラメタライズドテストに流し込むテスト（例: シードデータの配列を1件ずつ検証するテスト）は上のパターンに掛からないため、削除・移動対象がエクスポートする配列・定数名でも `git grep -n --untracked` する
     - ヒットしたテストは「走査範囲・import 範囲に入っているか」ではなく「そのテストがケースを生成する条件に合致するか」で判定する（例: ソースディレクトリ全体を走査するが、ケースを生成するのは特定ディレクトリ配下の特定ファイル名に限るテスト。走査範囲だけで判定すると、生成対象外のファイルの削除にまで増減を計上してしまう）
     - 期待テストファイル数・テスト数には、削除・移動対象自身のテスト件数の増減（パラメタライズドテストを含むテストファイルを削除する場合はテスト定義の出現数ではなく展開後のケース数で数える）に加え、該当した動的生成テストの増減も含める。期待値は算術だけで組み立てず、変更前に実行したテストの実測値をベースラインとして併記し、期待値をその差分として示すこと
     - 使用した `git grep` パターンとヒット一覧（動的生成に該当したもの・しなかったものとその理由）を計画に残すこと（項目3・5と同じ理由）

<`.claude/skills/_shared/orchestrator-common.md`「Step 3 Plan 指示: origin/main 基準の段落」の本文を、`<扱った計画項目の列挙>` を `3. の変更対象ファイル一覧・4. のスコープ外・5. の注意点・7. の検証手順` に置き換えて、要約せずこの位置に貼り付ける>

返す前に、計画書全体（2. の複数の Before/After・3. の変更対象ファイル一覧・4. のスコープ外・5. の注意点・7. の検証手順を含む）を横断して読み直し、記述どうしが矛盾していないか、および変更対象ファイル内に同一内容・同一構造を並行して保持する他の記述箇所への追随漏れがないかを自己チェックすること。少なくとも次は必ず確認する:

- 3. の変更対象ファイル一覧に挙げたファイル（またはその配下）を、4. のスコープ外でも指定していないか（実装エージェントはスコープ外を優先して一切触らないため、二重記載のファイルは変換されないまま残り、レビューでもスコープ外扱いで見逃される）
- 7. の検証手順の期待結果が、2.・3.・4. で「残す」と決めた記述と食い違っていないか（スコープ外として意図的に残す記述に検証コマンドがヒットしないか）
- 2. の変換ルールが対象とする変更対象ファイル内に、変更箇所と同一内容・同一構造を並行して保持している他の記述箇所がないか確認したか（例: 同一の観点リストや対応表が複数箇所に重複して存在し、一方を変更すればもう一方にも追随が必要な構造。ファイル内の他の節・ブロックも対象に含める。同じリストが地の文と指示例のコードブロックの両方に置かれているケースを見落としやすい）。確認は記憶や部分的な検索結果で済ませず、変更対象ファイルを通しで読むか `git grep -n --untracked '<変更箇所から引用した文言>' -- <変更対象ファイル>` で並行箇所を洗い出して行う。洗い出した結果（見つからなければ「並行記述なし」）を計画に明記すること（明記が無いと、Step 4 で確認漏れと「確認したうえで無し」を見分けられないため）
- 上記の並行記述が見つかった場合、その記述箇所を見出し・項番号・引用した文言など一意で陳腐化しにくい目印で特定したうえで（行番号だけで指定しない）、そこへの変更を 2. の変換ルールと 3. の変更対象ファイル一覧の「変更内容の概要」に、同一ファイル内の別箇所として1件ずつ書き出しているか（Step 5 の実装エージェントは `## 承認済みリファクタ計画` コメントしか読まないため、ファイルパスが一覧にあるだけでは並行箇所の存在も位置も伝わらない）。変更の趣旨が並行箇所には当てはまらず変更しない場合は、その理由を 5. の注意点に明記すること（4. のスコープ外には書かない。3. に挙げた変更対象ファイルを 4. にも挙げると、実装エージェントがスコープ外を優先してそのファイルを一切触らなくなるため。「移植元・参照元に対応物が無い」のように、並行箇所そのものを見ていない理由だけで変更対象から外さない）
- 2. で新規に追加したコメント/ドキュメントコメントが他の関数・変数・判定ロジックとの役割分担や処理順序を主張している場合、その説明対象のコードを実際に Read し、記述内容が実装と一致することを確認したか（確認せずに記述した場合は、対象コードを Read したうえで記述を実装に合わせて修正してから返すこと）

矛盾が見つかった場合、および上記のいずれかを満たさない場合は、該当する記述を修正・加筆してから計画書を返すこと。

計画書を返してください（ファイルへの保存は不要）。最終回答は要約や「詳細な章立ては本文に記載済みです」のような言及で済ませず、1. の目的・ゴール・2. の複数の Before/After・3. の変更対象ファイル一覧・4. のスコープ外・5. の注意点・6. の新規依存の追加有無・7. の検証手順を含む計画書全文を省略せずそのままこの回答に出力すること。
```

### Step 5: 実装（general-purpose エージェント）

`subagent_type: "general-purpose"`・`model: "sonnet"` でエージェントを起動する。
承認済みリファクタ計画を渡し、変更を実装させる:

```
以下の承認済みリファクタ計画に従って、コードを変更してください。

[issue番号: <番号>]
※ 承認済みリファクタ計画の詳細は `gh issue view <番号> --json comments --jq '.comments[].body'` で取得すること
  （`## 承認済みリファクタ計画` のコメントを参照）

実装方針:
- 承認済みリファクタ計画の変換ルールに厳密に従う
- スコープ外のファイルは絶対に触らない
- リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
- **計画のファイル一覧に無いファイルの修正が必要になった場合**（例: 削除・移動したファイルへの import が計画の `git grep` 網羅から漏れていた場合）:
  - 対象は「変更対象ファイル」にも「スコープ外」にも記載が無いファイルに限る。**「スコープ外」に該当するファイルは、ファイル名で明示列挙されていてもディレクトリ・範囲で指定されていても対象外であり、引き続き一切触らない**
  - 実施してよいのは、削除・移動対象ファイルの参照元に対する**機械的な import パス変更（re-export・型のみの import の付け替えを含む）にとどまる場合のみ**
  - 実施した場合は「変更したファイルの一覧」と `## リファクタ実装完了` コメントの「計画外の変更」欄に、どの削除・移動対象ファイルの参照元だったかを添えて必ず記録する（レビュアーは承認済み計画の「変更対象ファイル」「スコープ外」欄と実差分を突合するため、指摘された際にメインが計画外変更の妥当性を追跡・判断できる記録として残す）
  - それ以外（ロジック変更・シグネチャ変更など機械的でない修正が必要）の場合は実施せず、対象ファイル・必要になった理由・機械的でない理由を報告して戻る（計画の更新と再承認はメインが Step 3〜4 に戻って行う）
- 機能の変更は行わない（リファクタリングのみ）
- CLAUDE.md・.claude/rules/core.md のコーディング規約に従う
- フォーマットは設定済みのフォーマッタで行い、独自判断で手整形しない（フォーマッタを実行するかどうかは `.claude/rules/core.md`「フォーマット・コード整形」に従う。実行する場合はその適用範囲に含まれる変更に対して実行する）
- 変更完了後、既存テストをすべて実行して通ることを確認する（テストコマンドは docs/specs/technical-environment.md の `## 実行コマンド` を参照）
- テスト・フォーマッタの適用範囲外（Markdown・ドキュメントのみの変更等）の部分は実行対象とせず、対象ツールの設定範囲を判断根拠として報告する（例: フォーマッタの対象が特定ディレクトリ・特定拡張子に限られ Markdown を含まない場合、Markdown 向け lint/format ツールがリポジトリに無い場合）。適用範囲外であること自体は問題ではない
- **新規依存の追加が必要な場合（承認範囲）**: 追加してよいのは、承認済みリファクタ計画の「新規依存」に記載があるパッケージだけ。新規ライブラリの追加はユーザー承認が必須であり（`.claude/rules/core.md`「ライブラリのインストール」）、Step 4 の承認がその承認にあたる。計画に記載のない依存が必要になった場合は追加せず、必要になった理由・候補パッケージ・代替案の有無を報告して戻る（計画の更新と再承認はメインが Step 3〜4 に戻って行う）
- **新規依存の追加が必要な場合（install）**: 依存定義ファイル（例: `package.json` / `pyproject.toml` / `composer.json`）の編集までを行う。パッケージマネージャの依存追加・install コマンドはサンドボックス制約で失敗しうる（パッケージキャッシュ・ストアが read-only / パッケージレジストリへの到達がブロックされる等）。失敗してもサンドボックスは無効化せず（`.claude/rules/core.md`）、install は人間に依頼する必要がある旨を報告して戻る。install が未完了では型チェック・テストを実行できないため、**テスト・コミット・`## リファクタ実装完了` の投稿は行わない**（コード変更は未コミットのまま残す）
- 型解決の可否など「実際に型チェックを回さないと確定できない判断」が残る場合は、候補と判断待ちの理由を報告に含める（確定は install 後にオーケストレータが行う）
- 最後に変更したファイルをコミットする（コミット規約は .claude/rules/core.md を参照。`git add` で対象ファイルを個別指定する）
- コミットに続けて、`gh issue comment` で以下の形式で投稿する:
  ```
  ## リファクタ実装完了

  変更したファイル:
  - `<ファイルパス>`: <変更内容の概要>
  - ...

  計画外の変更（機械的な import パス変更のみ）:
  - `<ファイルパス>`: <どの削除・移動対象ファイルの参照元か>
  - ...（なければ「なし」）

  変換できなかった箇所: <なければ「なし」>
  ```

完了後に以下を返してください:
- 変更したファイルの一覧（ファイルパスと変更内容の概要）
- 変換できなかったファイル・箇所があれば一覧と理由
- 既存テストの実行結果（テストが適用範囲外の場合はその旨と判断根拠）
- 新規依存の追加有無。install がブロックされて戻る場合は、インストールが必要なパッケージ名とバージョン・編集済みの依存定義ファイルのパス・型チェック待ちで未確定の判断
- 承認済み計画の「新規依存」に記載のない依存が必要になった場合は、そのパッケージ名・必要になった理由・代替案の有無（この場合は依存を追加せずに戻る）
- 計画のファイル一覧に無いファイルを機械的な import パス変更で修正した場合は、そのファイルパスと変更理由（`## リファクタ実装完了` の「計画外の変更」欄に記録済みであることの確認を兼ねる）。機械的でない修正が必要で実施を見送った場合は、そのファイルパス・理由・戻る旨
```

完了後、まず実装エージェントの報告に **install がサンドボックスでブロックされた** 旨が含まれるかを確認し、分岐する:

- **含まれる場合**: この時点で `## リファクタ実装完了` が未投稿なのは想定どおりの状態である。代理投稿も Step 6 への進行も行わず、下記「新規依存の install がブロックされた場合のフォールバック」に従う
- **含まれない場合**: `## リファクタ実装完了` コメントを投稿済みであることを `gh issue view <番号> --json comments` で確認する。投稿が確認できた場合はそのまま Step 6 のレビューへ進む。（万一未投稿の場合のみ、返された変更ファイル一覧をもとにメインが同形式で投稿するフォールバックを行う。）

#### 新規依存の install がブロックされた場合のフォールバック（メイン）

実装エージェントが「install がサンドボックスでブロックされた」と報告して戻った場合、Step 5 の残りの責務（install 依頼・検証・修正・コミット・完了コメント投稿）はメインが引き取る。
実装エージェントを再起動しても同じ制約で止まるため、再起動はしない。

1. `git status --porcelain` で依存定義ファイルを含むコード変更が未コミットで残っていることを確認する。何も残っていない場合は実装自体が行われていないため、Step 5 の実装エージェントから実行し直す
2. install を人間に依頼する。サンドボックスは無効化せず、メインが install を代行しようともしない（`.claude/rules/core.md` の「サンドボックスの取り扱い」）:
   ```
   新規依存 <パッケージ名@バージョン> の追加が必要ですが、サンドボックス制約で
   インストールを実行できません（パッケージキャッシュが read-only / パッケージレジストリがブロック 等）。
   <依存定義ファイル> は編集済みです。お手元のターミナル（Claude Code のサンドボックス外）で
   以下を実行し、完了したら「完了」と返してください。

     <依存を install するコマンド（docs/specs/technical-environment.md 等に記載のもの）>
   ```
3. install 完了の応答を受けたら、メインが型チェック・テストを実行する（コマンドは `docs/specs/technical-environment.md` の `## 実行コマンド` を参照）
4. 失敗があれば、**承認済みリファクタ計画のスコープ内に収まる軽微な修正**をメインが行い、3. を再実行する。ここで確定させてよいのは、実装エージェントが判断待ちにした事項（型解決のフォールバック選択など、型チェックを実際に回さないと確定できないもの）と install 後にしか現れないエラーに限る。計画のスコープを超える修正が必要になった場合は自動修正せず、人間に報告して終了する
5. 通ったら、メインが変更ファイルをコミットし（コミット規約は `.claude/rules/core.md` を参照。`git add` で対象ファイルを個別指定する）、続けて `gh issue comment` で `## リファクタ実装完了` を上記と同じ形式で投稿する。「変換できなかった箇所」欄には、人間が install を実行したことと追加した依存を記録する
   - **コミット対象には依存定義ファイルと併せてロックファイル（例: `package-lock.json` / `pnpm-lock.yaml` / `poetry.lock` / `composer.lock`）を必ず含める**。人間の install でロックファイルが更新されるため、`git add` の個別指定から漏らすと、ロックファイル固定で install する worktree 作成スクリプト（例: `scripts/wt-new.sh`）や CI が壊れる
6. Step 6 のレビューへ進む

install 待ちで中断し別セッションから再開した場合は、`## リファクタ実装完了` が未投稿のため Step 0 の再開表では Step 5 に戻る。
このとき 1. の確認で依存定義ファイルを含む未コミット変更が残っていれば、実装エージェントは起動せずフォールバックの 2. から続ける。
なお再開時は Step 0 の開始時ガードで「未コミットの変更があります」と警告が出るが、これは install 待ちで意図的に残した想定内の差分である。
差分の内容が依存定義ファイルと計画のスコープ内ファイルに限られることを確認したうえで続行し、stash・破棄はしない。

**/auto-loop 配下で動いている場合**: 指揮役は install を代行せず、エスカレーションする。
理由はサンドボックス制約ではなく（子 pane 内なら install 自体は実行しうる）、
新規ライブラリの追加がユーザー承認を要する判断だからで、
`.claude/skills/auto-loop/SKILL.md`「エスカレーション条件」の共通条件「新規ライブラリの導入」に該当する。
本来この条件は Step 4 の計画承認時（計画の「新規依存」欄）で判定され、依存追加を伴う issue は
Step 5 に到達しないのが正規の経路である。実装中に依存追加が判明して本フォールバックに入った場合は
終端マーカーが投稿されないため、指揮役は 2c 手順4 の「判断できない出力」経路でエスカレーションに倒す。
このとき未コミット差分が残っているため、「エスカレーション時の後片付け」の削除条件1（未コミット変更なし）を
満たさず worktree は保持される（実装成果は失われず、install 後に新しいセッションで Step 5 から再開できる）。

### Step 6〜8: レビュー → 修正ループ（レビュー最大3回・修正最大2回）

#### 各ループの流れ

1. `subagent_type: "refactor-auto-reviewer"` でレビュアーエージェントを起動する。渡すプロンプト:
   ```
   issue番号: <番号>
   実装ファイル一覧: <Step 5 または前回の修正で変更したファイル一覧>
   ```

   Step 6 から再開した場合など、手元に実装ファイル一覧がない場合は
   `## リファクタ実装完了` コメントから取得して渡す。

2. 結果を受けて（**判定の確定は「レビュアー判定の確定手順（Step 6〜8 共通）」に従う**）:
   - **`判定: 承認`**: Step 9へ進む
   - **`判定: 問題あり`**: `subagent_type: "general-purpose"`・`model: "sonnet"` で修正エージェントを以下のプロンプトで起動する:
     ```
     issue番号: <番号>

     以下のレビュー指摘を修正してください。
     <refactor-auto-reviewer が返した問題リスト>

     制約:
     - `## 承認済みリファクタ計画`（`gh issue view <番号> --json comments --jq '.comments[].body'` で取得）の変換ルール・スコープに厳密に従う
     - スコープ外のファイルは絶対に触らない
     - リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
     - 計画の「変更対象ファイル」にも「スコープ外」にも記載が無いファイルの修正が必要になった場合は Step 5 と同じ裁量境界に従う（削除・移動対象ファイルの参照元に対する機械的な import パス変更のみ実施し、対象ファイルと参照元だった削除・移動対象ファイルを報告に含める。それ以外は実施せず理由を報告して戻る）
     - 機能の変更は行わない（リファクタリングのみ）
     - 修正後に既存テストをすべて実行して通ることを確認する（テストコマンドは docs/specs/technical-environment.md の `## 実行コマンド` を参照）。適用範囲外（Markdown・ドキュメントのみ等）の場合は対象ツールの設定範囲を判断根拠として報告する
     ```
     - 修正試行時に `gh issue comment` で試行カウンタを投稿する:
       ```
       ## リファクタ修正試行 <N>/2

       ### レビュー結果（<N> 回目のレビュー指摘）
       <問題リスト>

       ### 修正内容
       - <変更したファイルと変更内容>

       ### 計画外の変更（機械的な import パス変更のみ）
       - `<ファイルパス>`: <どの削除・移動対象ファイルの参照元か>
       - ...（なければ「なし」）
       ```
     - 「計画外の変更」欄には、修正エージェントが報告した計画外のファイルへの import パス変更をすべて書く。無い場合も欄を省略せず「なし」と書く（`/auto-loop` の自動マージの条件 M5 がこの欄を読み、欄が無いと条件を満たさない扱いになるため）
     - 修正完了後、メインが修正ファイルをコミットしてから（amend・rebase・reset は使わず必ず追加コミット。コミット規約は `.claude/rules/core.md` を参照）、次のレビューに進む

3. レビュアーの返答に `## 参考指摘`（判定に影響しない指摘）が含まれる場合、その内容は修正エージェントに渡さない（`判定: 承認` なら参考指摘の有無にかかわらず Step 9 へ進む）。内容は保持し、Step 9 の完了コメントの `### スキルふりかえり` に転記する。

#### レビュアー判定の確定手順（Step 6〜8 共通）

> **集約先ファイルとの対応関係**: 本節は、`dev-auto`「レビュアー判定の確定手順（Step 4 / Step 9 共通）」と共通のロジックとして `.claude/skills/_shared/orchestrator-common.md`「レビュアー判定の確定手順」に集約されている。この共通部分を変更する場合は集約先ファイルのその節を更新すること（両スキルに自動的に反映される）。

`.claude/skills/_shared/orchestrator-common.md`「レビュアー判定の確定手順」を Read し、`<レビュアーサブエージェント名>` を `refactor-auto-reviewer`、`<エージェント定義ファイルパス>` を `.claude/agents/refactor-auto-reviewer.md`、`<妥当な判定値の列挙>` を `` `判定: 承認` / `判定: 問題あり` ``、`<独立検証の観点一覧>` を `承認済みリファクタ計画・スコープ・ビルド/型チェック/テスト結果等の実状態` に置き換えて、その内容のとおりに適用する。同ファイルを Read できない、または該当節が見つからない場合は、判定を推測で確定せず、その旨をユーザーに伝えて終了する。

#### ループ回数の管理

- レビューは最大3回（Step6・Step7・Step8）、修正は最大2回
- 3回目のレビューで `判定: 問題あり` が返ってきた場合: **自動修正を打ち切り**、人間に報告して終了する
- Step 6 に再開した際は `## リファクタ修正試行 N/2` コメントの最大 N を数え、修正回数=N・レビュー回数=N+1（初回レビュー分）として残り budget を算出し、上限（レビュー3・修正2）判定に使う。ただし失敗マーカー（`## /refactor-auto — 自動修正できませんでした`）から再開した場合は回数を意図的にリセットする（下記「意図的リセット」参照）。`## リファクタ修正試行` は budget 復元専用の試行カウンタであり、Step 0 再開表のマーカーには加えない

3回のレビューで解消できなかった場合の報告:
```
## /refactor-auto — 自動修正できませんでした

3回のレビュー・2回の修正試行で以下の問題が解消できませんでした:

### 未解決の問題
<問題リスト>

### 試行履歴
- 修正1: <変更したファイルと変更内容>
- 修正2: <変更したファイルと変更内容>

手動での確認・修正をお願いします。
```

`gh issue comment` でissueにも同内容を記録し、終了する。

#### 意図的リセット

以下の場合はループ回数を意図的にリセットする（過去の試行カウンタコメントは budget 復元に使わない）:
- 失敗マーカー（`## /dev-auto — 自動修正できませんでした` / `## /refactor-auto — 自動修正できませんでした`）からの再開（手動修正後の再実行を想定）
- フェーズ再実行を伴う再開（dev-auto Step 3 からのテスト計画再生成、test-reviewer の再起動）

これは Step 0 再開表の「`## /refactor-auto — 自動修正できませんでした` あり → レビュー・修正ループの回数はリセットする」と整合する。

### Step 9: 完了マーカー投稿・PR 作成・完了報告（メイン）

1. `gh issue comment` で以下をissueに記録する（再開判定の終端マーカー。本文に「スキルふりかえり」を同梱する）:

   ```
   ## /refactor-auto 完了

   ### スキルふりかえり
   - <スキルの指示が曖昧で迷った点・レビュー→修正ループが余計に回った原因などを1〜2行で記録>
   ```

   ふりかえりで特に気づきが無い場合は `- なし` と記録する（`### スキルふりかえり` の見出し自体は必ず入れる）。

   レビュアーが返した `## 参考指摘` がある場合は、`- 参考指摘（<エージェント名>）: <内容>` の形でこの節に転記する。

2. `/create-pr` skill を実行して PR を作成する（ユーザー・指揮役への確認は不要。PR の作成だけでは既存のコードに影響が出ないため、PR 作成に人間の承認はいらない運用とする。プロジェクトの CLAUDE.md が PR 作成に承認を求めている場合はそれに従い、作成せずに完了報告で `/create-pr` の実行を案内する）。作成された PR の URL を 3. の完了報告に含める。マージは行わない。

   PR 作成に失敗した場合は中断せず、失敗理由を完了報告の「PR」欄に記録して 3. へ進む（リファクタ自体は完了しているため）。

3. 以下の形式でユーザーに完了を報告する:

```
## /refactor-auto 完了 (#<番号>)

### 実行したフェーズ
1. 探索（変更対象・パターンの特定）
2. 質問フェーズ（<スキップ / N件の不明点を確認>）
3. 計画立案
4. 計画承認
5. 実装
6. レビュー・修正（<N回で承認>）

### 成果物
- 変更ファイル: <一覧>
- レビュー結果: <承認 / N回の修正後承認>

### スキルふりかえり
- <1. で issue に記録したふりかえりと同じ内容（無い場合は「- なし」）>

### PR
- <作成した PR の URL / 作成に失敗した場合はその理由>

レビューとマージをお願いします（マージは行っていません）。
```

4. ふりかえりに「なし」以外の気づきがあり、スキル定義（SKILL.md・エージェント定義）の編集に値する場合は、完了報告に続けて起票の確認を行う:

   ```
   スキルふりかえりに以下の気づきがありました。スキル改善 issue として起票しますか？（はい / いいえ）
   - <気づき1>
   - <気づき2>
   ```

   ユーザーが許可した場合のみ、気づき1件につき1つの issue を作成する（1つの気づき = 1 issue）。
   起票とラベル付与は分けて実行する:

   1. `gh issue create --title "refactor-auto: <気づきの要約>" --body "<本文>" --assignee @me`（`--label` は付けない）
   2. `gh issue edit <作成した issue 番号> --add-label skill-improvement`

   - issue 本文には「対象スキル」「気づきの内容と改善案」「発生した実行（元 issue #<番号>）」を含める
   - ユーザーが拒否した場合・気づきが「なし」の場合は起票せず終了する（ふりかえり自体は 1. のコメントに記録済み）
   - SKILL.md・エージェント定義をこの場で直接編集しない（スキル編集は issue → PR → 人間のマージ承認のゲートを必ず通す）

## 注意事項

- 人間・指揮役への質問・承認依頼（Step 2・Step 4）は通常のテキスト応答で行い、
  AskUserQuestion 等の対話ダイアログは使わない（/auto-loop の指揮役が
  pane 経由のテキストで応答するため。ダイアログはオーケストレータから操作できない）
- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- 実装フェーズでは「機能変更なし・リファクタのみ」を実装エージェントに明示すること
- レビュアーには承認済みリファクタ計画のissueコメントを必ず参照させる
- issueに記録するコメントは日本語で書く
- コミットはフェーズ単位で実行する: Step 5（実装エージェント、実装完了時。実装エージェントはコミットに続けて `## リファクタ実装完了` を投稿する）・Step 6〜8 の修正ループ（メイン、修正のたびに追加コミット）。Step 9 ではコミットしない
  - 例外: 新規依存の install がサンドボックスでブロックされた場合、Step 5 のコミットと `## リファクタ実装完了` の投稿はメインが行う（Step 5 の「新規依存の install がブロックされた場合のフォールバック」を参照）
- 依存追加を伴うリファクタでは、install がサンドボックスで失敗する前提で進める。実装エージェントに完結させようとせず、install 以降をメインが引き取る分岐（Step 5 のフォールバック）に乗せる
- 新規ライブラリの追加はユーザー承認が必須（`.claude/rules/core.md`）。承認は Step 4 の計画承認で取り、承認済み計画の「新規依存」欄に記載のないパッケージは追加しない
- 修正時のコミットは amend・rebase・reset を使わず必ず追加コミットにする
- コミット対象は変更したファイルのみ。意図しないファイルを混入させない（`git add .` / `git add -A` は使わない）
- **ツール結果の捏造に気づいたら再開運用に乗せる**（汎用ルールは `.claude/rules/core.md` の「ツール結果の捏造禁止」を参照）:
  - 捏造に気づいたら続行せず、`/clear` → `/refactor-auto <番号>` を再実行 → Step 0 で issue コメントから再開ポイントを判定する
  - **再開前に汚染区間を検証する**: 汚染セッション中に投稿された issue コメント（Step 0 再開表のマーカー: `## 確認済み不明点` / `## 承認済みリファクタ計画` / `## リファクタ実装完了` / `## /refactor-auto — 自動修正できませんでした` / `## /refactor-auto 完了`）と、その間のコミット差分が捏造情報に基づいていないかを確認する。疑わしいコメント・差分は、再開ポイント判定の根拠にする前に人間が精査し、必要なら破棄する
- 終端マーカーコメントには `### スキルふりかえり` を同梱するが、再開判定・汚染区間検証は見出し行 `## /refactor-auto 完了` の有無で行う（マーカー見出しの文字列は変更しない）
- ふりかえりコメントの投稿は Step 0 で得たコメント投稿許可の範囲内で行う（追加の許可フローは設けない）。一方、スキル改善 issue の起票はこの許可の範囲外のため、必ず完了報告時にユーザーの許可（はい）を得てから実行する。自動起票はしない
- `skill-improvement` ラベルはリポジトリに作成済みであることを前提とする（存在せず `gh issue edit --add-label` がエラーになった場合は、エラーをそのままユーザーに伝える）
- **実行モデルはエージェント定義と Agent 呼び出しで決まる（skill frontmatter に `model:` は置かない）**:
  skill frontmatter の `model:` は公式仕様上「起動したターンの残りにだけ適用され、次のプロンプトでセッションモデルに戻る」。
  /refactor-auto は Step 0 の開始時ガードとコメント投稿許可でユーザーの応答を待つため、最初のターンはそこで切れる
  （さらに Step 2 の質問は不明点がなければスキップされるため、以降のターン境界の位置は実行ごとに変わる）。
  つまり frontmatter に `model:` を書いても効くのは Step 0 の同意プロンプトを出すまでで、Step 1 以降の
  オーケストレーターはセッションモデルで動く。「この skill は sonnet で走っている」という誤解を生むだけなので、
  この skill の frontmatter には `model:` を置かない。各フェーズの実行モデルはこれに影響されない——
  Step 1（Explore）・Step 3（Plan）・Step 5（実装）・Step 6〜8（修正）は Agent 呼び出しの `model` 引数で、
  レビュアーは `.claude/agents/refactor-auto-reviewer.md` の `model:` で、いずれも sonnet に固定されるため
  （承認済み計画に従う機械的変換であり、opus を要する工程がない）。オーケストレーター自身のモデルを固定したい場合は、
  セッション側（`/model`・`claude --model`）で指定する（/auto-loop の 2b はこれを行っている）
