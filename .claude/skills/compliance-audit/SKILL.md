## 概要

文章でしか書かれていない規約・ADR・仕様の逸脱は CI で検出できず、`/auto-loop` の自動マージを
導入した後は PR ごとに人間が確認しなくなる。
このスキルは、その逸脱を人間が決めたタイミングで調査し、issue として起票するところまでを担う。

調査の観点は A〜E に固定され、観点ごとに「読む規約ファイル」「重点観点」「対象外」が
このファイルに明記されている。**規約・ADR・仕様の中身はここに書き写さず、参照先だけを固定する**
（規約とスキル定義の二重管理を避けるため）。

- 調査対象はコードベース全体とする（前回の調査以降の差分には絞らない）
- 実行のタイミングは人間が決める。定期的な自動起動は行わない
- 見つかった違反の修正はこのスキルでは行わない（起票した issue を `/auto-loop` 等で処理する）

## 引数

- `<観点>`（省略可）: `A`〜`E` を空白区切りで1つ以上指定する（例: `/compliance-audit A C`）
- 省略時: 5観点すべてを調査する
- `A`〜`E` 以外が指定された場合: 「観点は A〜E から指定してください。例: /compliance-audit A C」と伝えて終了する

## 観点の定義

| 記号 | 観点 | 読む規約 | 重点観点 | 対象外 |
|---|---|---|---|---|
| A | バックエンドのアーキテクチャ・規約 | `docs/architecture/backend/` 配下（`directory-structure.md`・`naming-conventions.md` 等）・`.claude/rules/` 配下のうちバックエンドに適用される規約ファイル（コーディング・テスト・コメント規約など）・関連する ADR | 入口層（ルーティング・コントローラ等）の責務（薄い入口・業務エラーの網羅的な扱い） / 処理の置き場所（業務判断がユースケース層等の所定の層にあるか、スケジュール実行の入口やミドルウェアに漏れていないか、型・定数の定義場所） / モジュールの境界（`docs/architecture/backend/` でモジュール境界が定義されている場合、他モジュールのテーブルの JOIN・更新、FK がモジュールの中に閉じているか、公開 API 経由の呼び出しになっているか） / 環境変数・設定値に触れてよい層 / モジュールをまたぐ重複実装 | 依存関係の検証ツール（lint ルール・依存グラフ検査など）で CI が機械的に検査している範囲 |
| B | フロントエンドのアーキテクチャ・規約 | `docs/architecture/frontend/` 配下（`directory-structure.md`・`naming-conventions.md` 等）・`.claude/rules/` 配下のうちフロントエンドに適用される規約ファイル（コーディング・テスト・コンポーネントカタログ・コメント規約など） | ディレクトリ設計で定めた単位（共通コンポーネント / 機能単位 / hooks 等）の使い分けと機能単位間の依存 / 表示コンポーネント（Presentational 等）と接続層（Container 等）の責務（副作用や状態の混入） / レンダリング方式（SSR・CSR 等）の指定とドキュメントの記述の一致 / API 層の入出力の型を API 契約（OpenAPI 定義や型生成元）から派生させているか / コメント・ドキュメントコメント / テストと story の書き方（命名・モックの範囲・AAA・argTypes） | lint・フォーマッタ・既存の規約検査テストで CI が機械的に検査している範囲 |
| C | デザインシステム | デザインシステムの定義（例: `DESIGN.md`・デザイン原則のドキュメント）・`.claude/rules/` 配下のデザイントークンに関する規約・デザインシステムに関する ADR・トークンを定義しているスタイルファイル | トークン外の色・スペーシング・タイポグラフィ・角丸・ボーダー / アイコン（採用しているアイコンセットか、サイズ） / アクセシビリティ（コントラスト比・タッチ領域・フォーカス表示・色だけで状態を表していないか） | なし |
| D | セキュリティ | 認証・セキュリティに関わる ADR・`docs/specs/technical-environment.md` の「セキュリティ方針」・非機能要件の仕様（`docs/specs/` 配下にあれば） | **バックエンド**: 公開されているルートと認証の掛かり方 / トークンの受け渡し / ユースケース層での認可（誰のデータを操作できるか） / レスポンスでの情報の出しすぎ / HTTP 以外の入口（スケジュール実行・キューの消費者・WebSocket 等） / 未認証・権限不足（401 / 403）のテスト / 入力検証（API の入口での型・長さ・件数の上限、生の SQL の組み立て） / 秘密情報（ログ・レスポンスへの混入、環境変数の扱い、CORS の設定）<br>**フロントエンド**: 認証が必要な画面がガードの内側にあるか / 認証ライブラリ・IdP の設定（許可するオリジン・リダイレクト先など） / CSRF / ログアウト時のキャッシュ破棄 / ストリーミング接続（SSE・WebSocket）でのトークンの受け渡し / XSS（ユーザーが入力した内容の表示でエスケープを迂回していないか） / 秘密情報のクライアントバンドルへの混入 | コードから確認できない外部サービス（IdP の管理画面など）の設定、コードで管理していない配信・インフラの設定（CSP ヘッダーなど）、本番デプロイの構成 |
| E | ADR・仕様と実装の整合 | `docs/adr/` の各 ADR の決定内容・`docs/specs/` 配下の仕様（`api-list.md`・`screen-list.md`・`screen-transition.md`・`er-diagram.md`・`openapi.yaml`・ログ定義・非機能要件など、存在するもの） | ADR の決定が実装に反映されているか / ADR・仕様が廃止済みの方式や古い構成を参照していないか / API・画面・テーブル・ログの一覧と実装の食い違い / 非機能要件に反する実装 | API 契約の正をコード（スキーマ定義）に置くコードファーストの構成の場合、API の入出力の形状（正はコード） |

**重点観点は照らし合わせる記述を示す例であり、重点観点に挙げていない違反も調査の対象に含める。**

**「読む規約」はプロジェクトの実ファイルに具体化して固定することを推奨する。** 上の表はどの技術スタックでも
使えるよう `.claude/rules/` 配下・`docs/architecture/` 配下などの置き場所で書いている。このままでは実行ごとに
サブエージェントが選ぶファイルがぶれうるため、導入したプロジェクトでは「読む規約」を実際のファイルパスの列挙に
書き換え、「対象外」も CI で実際に検査している内容（ツール名・検査テスト名）に書き換える。書き換えるまでは、
サブエージェントが実際に読んだファイルを Step 5 の「調査範囲」で必ず報告させ、前回との比較に使う。

プロジェクトに該当する規約ファイルが1つも無い観点（例: デザインシステムの定義を持たないプロジェクトの観点 C）は、
推測で規約を補わずに「確認できなかった点」に「規約ファイルが存在しない」と報告し、違反の起票は行わない。

観点 A の「関連する ADR」と観点 C・D の「〜に関わる ADR」は、ADR の一覧（`docs/adr/README.md` 等の索引があればそれ、
無ければ `git ls-files docs/adr/` で列挙したファイルのタイトル）から該当するものを選ぶ。
ADR 番号をこのファイルに列挙しないのは、ADR が追加されたときに追従漏れが起きるため。

**ADR を読む前に各 ADR のステータス（索引の Status 欄、または各 ADR のステータス節）を確認し、現在有効な決定だけを調査の根拠にする**
（ADR 全体を読む観点 E も同じ）。

- 置き換え済み・非推奨・却下（`Superseded` / `Deprecated` / `非推奨` / `却下` 等）: 置き換え済みなら後継 ADR を読む。元の ADR の決定は根拠にしない
- 有効（`Accepted` / `承認済み` 等）でも、決定の一部が後続の ADR に外された・改められたことが
  ステータスの備考や本文に書かれている場合がある（例: ある ADR は有効だが、その決定の条件の一部を後続の ADR が
  外している）。備考がある場合は指されている ADR も読み、残っている決定だけを根拠にする

無効になった決定を根拠にすると、偽陽性を `bug` / `refactoring` で起票することになり、
`/auto-loop` がそれを自動で実装してマージする。

## 起票のラベル

検出した違反は、観点と修正対象に応じて次のラベルで起票する。

| 観点 | 修正対象 | ラベル | 処理者 |
|---|---|---|---|
| A・B・C・E | コード | `refactoring` | `/auto-loop` |
| D | コード | `bug` | `/auto-loop` |
| A〜E | ドキュメント（規約・ADR・仕様） | `documentation` | 人間 |

- **修正対象がドキュメントなら、観点によらず `documentation` を付ける。** Step 2 の分類
  「コードとドキュメントのどちらを直すべきか判断が必要」はどの観点でも発生するため、E 以外でも
  ドキュメントを直す結論になりうる（例: 観点 A で `docs/architecture/backend/directory-structure.md`
  が実装と乖離していて、Step 3 で人間がドキュメントを直すと判断した場合）
- **`/auto-loop` の対象ラベル（`refactoring`・`bug`）は必ず1つだけ付ける。** 2つ以上付いた issue は
  `/auto-loop` の振り分けで処理対象から外れる（`.claude/skills/auto-loop/SKILL.md` の Step 1 手順2）
- `skill-improvement` は `/auto-loop` の**補助ラベル**であり、対象ラベルが付いていれば併用されても
  無視される（同 Step 1 手順2）。このスキルでは付けない
- `documentation` は `/auto-loop` の対象ラベルでも補助ラベルでもないため、ループには拾われず
  人間が処理する

## エージェント構成

```
メインスキル（オーケストレーター）
├── Step0: 引数の解釈・起票許可の確認（メイン）
├── Step1: 観点ごとの調査 → general-purpose エージェント（観点1つにつき1エージェント・同時3まで）
│             ↓ 違反候補・調査した項目・探索方法・調査範囲・確認できなかった点を受け取る
├── Step2: 検出結果の分類（メイン）
├── Step3: 人間への確認（メイン）← タッチポイント（確認事項が0件ならスキップ）
├── Step4: 重複チェックと起票 → /create-issue skill（メイン）
└── Step5: 報告（メイン）
```

## 手順

### Step 0: 引数の解釈・起票許可の確認

引数から調査する観点を決める（省略時は A〜E すべて）。決まった観点をユーザーに表示する。

このスキルは**ファイルの編集・git の状態変更を一切行わない**（ブランチの切り替え・コミット・
stash をしない）ため、ブランチガードと未コミット差分の確認は行わない。main ブランチ上でも実行してよい。

行う副作用は issue の起票だけなので、開始前にユーザーへ次を伝え、明示的な同意を得る:

```
この調査で検出した明確な違反は、GitHub issue として起票します（観点: <観点の一覧>）。
起票を許可して進めてよいですか？（はい / いいえ）
```

- 許可された場合のみ続行する。この同意をもって Step 4 の起票を実行する
- 拒否された場合: 起票せずに調査と報告だけを行うか、中止するかをユーザーに確認し、その選択に従う
  - 「中止」: その場で終了する
  - 「調査と報告だけ」: **報告のみモード**として続行する。Step 1・2・5 は同じだが、
    **Step 3 では起票の可否を尋ねず、Step 4 の起票は一切行わない**（各 Step の
    「報告のみモードのとき」の記述に従う）

このモードの判定は Step 3・4 で参照するため、どちらで続行しているかを最後まで保持する。

### Step 1: 観点ごとの調査

調査する観点の数だけ general-purpose エージェントを起動する（**1観点 = 1エージェント**）。
同時起動は最大3までとし、4観点以上を調査する場合は3件ずつのバッチに分けて、
1バッチ分の呼び出しを1メッセージ内にまとめて発行する（`.claude/rules/core.md`「サブエージェントへの委任」）。

サブエージェントは親の会話履歴を引き継がないため、次の内容を自己完結でプロンプトに含める。

- **担当観点**: 「観点の定義」の該当行（記号・観点名・読む規約・重点観点・対象外）をそのまま貼る
- **手順**:
  1. 「読む規約」に該当するファイルを `git ls-files` で特定し、すべて読む（ADR は ADR の一覧から該当するものを選び、ステータスを確認してから読む）
  2. 規約の各記述について、コードベース全体から違反していないかを確認する
  3. 重点観点に挙がっていない記述も対象にする
- **探索方法**（`.claude/rules/core.md` の既知の制限に合わせる）:
  - テキスト検索は `grep -r` ではなく `git grep -n <pattern> -- <pathspec>` を使う
  - ファイル一覧は `ls` / `find` ではなく `git ls-files <path>` を使う
  - 機械的に絞り込める記述は `git grep` の条件で候補を出し、該当箇所を読んで判定する
- **禁止事項**:
  - ファイルの編集・git の状態変更を行わない
  - issue を起票しない（重複チェックと起票は親がまとめて行う）
  - 規約・ADR・仕様の中身を推測で補わない。読めなかったファイル・存在しなかった規約は読めなかった・存在しなかったと報告する
  - 確認しきれなかった記述を「問題なし」に含めない。「確認できなかった点」に書く
- **出力形式**:

```
## 観点 <記号>: <観点名>

### 調査範囲
- 読んだ規約ファイル: <実際に読んだファイルの一覧（ADR は番号とファイルパス）>
- 調査したディレクトリ: <探索の対象にしたディレクトリ・pathspec の一覧>

### 調査した項目
| 規約の記述（ファイル:行） | 探索方法（git grep の条件・読んだファイル） | 結果（問題なし / 違反あり） |
|---|---|---|

### 検出した違反候補
候補ごとに次を書く。
- 分類: 明確な違反 / 解釈が割れる / コードとドキュメントのどちらを直すべきか判断が必要
- 違反している規約の記述: <ファイル:行>
- 該当箇所: <ファイル:行> の一覧（すべて挙げる）
- 根拠: 規約の記述と実装がどう食い違っているか
- 分類の理由: 「明確な違反」以外にした場合は、何が一意に決まらないかを書く

### 確認できなかった点
次のいずれかに当たるものを、理由とともにすべて書く。なければ「なし」と書く。
- 読めなかったファイル（「読む規約」に挙がっているが存在しない・読めなかったもの）
- 規約の記述のうち、照合できなかったもの（照合の手段が無い・該当箇所を特定しきれない・
  対象が多く全件を確認しきれなかった など）と、どこまで確認したか
```

「調査した項目」は Step 5 の報告でそのまま「問題がないと確認した項目」として使うため、
**何をどう調べて問題なしと判断したかが再現できる粒度**で書かせる。
「調査範囲」と「確認できなかった点」は、違反を起票しなかった観点について「調べて違反が無かった」のか
「調べられなかった・照合できなかった」のかを Step 5 の報告で区別するために使う。

### Step 2: 検出結果の分類

全エージェントの結果を受け取り、違反候補を分類する。

| サブエージェントの分類 | 扱い |
|---|---|
| 明確な違反 | Step 4 で起票する |
| 解釈が割れる | Step 3 で人間に確認する |
| コードとドキュメントのどちらを直すべきか判断が必要 | Step 3 で人間に確認する |

**起票の単位は規約の記述単位とする。** 同じ規約の記述に違反している箇所は、ファイルや機能単位が
異なっても1つの issue にまとめ、該当箇所は issue の「制約」に列挙する。
異なる規約の記述に対する違反は別の issue に分ける。

サブエージェントの分類は親がそのまま採用せず、根拠（規約の記述と該当箇所）を読んで確認する。
根拠が示されていない候補・該当箇所が実在しない候補は破棄し、その旨を Step 5 で報告する。

### Step 3: 人間への確認

Step 2 で人間に確認する扱いになった候補を、**観点をまたいでまとめて1回**提示する。
観点ごとに都度聞かない。確認事項が0件の場合はこの Step をスキップして Step 4 に進む。

候補ごとに次を示し、起票するかどうか（食い違いの場合はコードとドキュメントのどちらを直すか）を尋ねる。

- 違反している規約の記述（ファイル:行）
- 該当箇所（ファイル:行）
- 一意に決まらない点

回答を反映し、「起票する」となったものを Step 4 の対象に加える。
「起票しない」となったものは理由とともに Step 5 で報告する。

**報告のみモードのとき**は起票の可否を尋ねない。候補は提示したうえで「一意に決まらない点」への
判断だけを尋ね（食い違いの場合はコードとドキュメントのどちらを直すべきか）、回答は Step 5 の
「人間に確認した事項と回答」に載せる。確認する候補が0件ならこの Step をスキップする。

### Step 4: 重複チェックと起票

**報告のみモードのときは Step 4 全体を行わず、Step 5 に進む**（重複チェックも起票もしない）。

**1. 重複チェック**

```bash
gh issue list --state open --limit 100 --json number,title,labels,body
```

起票候補ごとに、**同じ規約の記述に対する違反を扱っている open issue** があるかを確認する。
- ある場合: 起票せず、既存の issue 番号を Step 5 で報告する
- ない場合: 起票する

**closed issue は確認しない。** そのため、過去に起票して「対応しない」と判断して閉じた違反は
再度起票される。この割り切りを前提に運用する。

**2. 起票**

起票は `/create-issue` skill に委譲する（テンプレート準拠と機能要件の検証可能性チェックを
再実装しないため）。呼び出す前に、候補ごとに次を組み立てておく。

- **タイトル**: 「〜を〜の規約に揃える」のように、直す対象と揃える先の規約がわかる形にする
- **概要**: 規約が何を定めているか / 実装がどう食い違っているか / 放置すると何が起きるか
- **機能要件**: `.claude/skills/create-issue/SKILL.md` のステップ4-1の検証可能性の基準（入力と出力 /
  状態遷移 / 具体的な文言 / 数値閾値 / 一意に特定できる規約の参照先）と、ステップ4-2の
  実装非依存性の基準（必須性 / 実装非依存性）を満たす形で書く。
  機械的に検証できるものは `git grep` の条件とヒット件数で書く
- **制約**: 該当箇所を `ファイル:行` で列挙する。スコープ外を明記する
- **ラベル**: 「起票のラベル」の表から1つだけ選ぶ

`/create-issue` には上記を渡し、**ラベルはこちらで決めた1つを使うよう明示する**
（`/create-issue` のステップ5のラベル選択には任せない。対象ラベルが2つ以上付くと `/auto-loop` の
処理対象から外れるため）。`/create-issue` は実行中にユーザーへ確認せず、基準を満たさない機能要件を
書き直すか外して起票する（ステップ4-2・4-3）。起票後に機能要件が意図から変わらないよう、
上記の基準を満たす形で渡す。

起票した issue の番号と URL を記録し、次の候補に進む。

### Step 5: 報告

調査した観点ごとに、次の6項目を報告する。

```
## 観点 <記号>: <観点名>

### 調査範囲
- 読んだ規約ファイル: <ファイルの一覧>
- 調査したディレクトリ: <ディレクトリ・pathspec の一覧>

### 確認できなかった点
| 対象（ファイル / 規約の記述） | 理由・どこまで確認したか |
|---|---|

### 問題がないと確認した項目
| 規約の記述 | 探索方法 |
|---|---|

### 起票した issue
| issue | タイトル | ラベル | 該当箇所の件数 |
|---|---|---|---|

### 人間に確認した事項と回答
| 確認した内容 | 回答 |
|---|---|

### 起票しなかったものとその理由
| 違反候補 | 理由（既存 issue #NN と重複 / 人間が起票不要と判断 / 根拠が確認できず破棄） |
|---|---|
```

該当がない項目は「なし」と書く（「確認できなかった点」も、該当が無ければ省略せず「なし」と書く）。
「調査範囲」「確認できなかった点」はサブエージェントの出力から転記する。サブエージェントが結果を返さなかった
観点・出力にこの2項目が無かった観点は、推測で埋めずに「確認できなかった点」に「サブエージェントの結果を
取得できなかった（観点全体が未確認）」または「調査範囲の報告が無い」と書く。
最後に、調査した観点・起票した issue の総数・人間への確認件数を
1行でまとめる。

報告のみモードのときは「起票した issue」を「なし（報告のみモード）」とし、起票の対象になっていた
違反候補を「起票しなかったものとその理由」に理由「報告のみモード」で列挙する。

**この報告はファイルにも issue コメントにも残さない。** 調査結果を永続化しない運用のため、
次回の調査は前回の結果を参照せず、毎回ゼロから同じ観点で調べ直す。

## 注意事項

- 調査中はファイルの編集・git の状態変更を行わない。行う副作用は issue の起票だけ
- 重点観点は照らし合わせる記述を示す例であり、重点観点に挙げていない違反も調査の対象に含める
- 規約・ADR・仕様の中身をこのファイルに書き写さない。固定するのは「読む規約ファイル」「重点観点」「対象外」だけ
- 規約ファイルが移動・改名されていて読めない場合は、推測で代替を探さずに読めなかったことを報告する
  （観点の定義の参照先が古くなっているサインであり、このファイルの更新が必要になる）
- 対象外に挙げたものは、CI や既存のテストが検査しているため調査しない（重複した指摘を避ける）
