# オーケストレーター共通ロジック

`refactor-auto`・`bugfix-auto`・`dev-auto` の SKILL.md オーケストレーターが共有するロジックの集約先。
このファイルは `SKILL.md` という名前を持たないため、スキルとしては起動できない
（`.claude/skills/bugfix-auto/judgment-criteria.md` と同じ扱いの補助ファイル）。
各 SKILL.md からは明示パスでの `Read` により参照する。

このファイル自身の内容を変更する場合は、参照している全 SKILL.md（下記の各節の「参照元」に列挙）
の挙動が連動して変わることを踏まえ、変更後にそれぞれの SKILL.md 側の記述（プレースホルダの値・
見出し名・貼り付け先の体裁）と矛盾しないかを確認すること。

## Step 0 開始時ガード

参照元: `refactor-auto`・`bugfix-auto`・`dev-auto` の Step 0（「main ブランチガード / 開始時ガード
（ブランチ突合・未コミット差分確認）/ コメント投稿許可」の部分。issue コメントを読んで再開ポイントを
決定する部分〈表を含む〉は各 SKILL.md 側にスキル固有の記述として残る）。

呼び出し側は `<コマンド名>`・`<進捗コメント項目一覧（説明文）>`・`<進捗コメント項目一覧（確認文言）>`
を自分の値に置き換えて、以下をそのまま実行する（説明文用と確認文言用でプレースホルダ名が異なる
ことに注意。値が同じ場合でも両方のプレースホルダに明示的に代入すること）。

---

Step 0 の最初に `git branch --show-current` で現在のブランチを確認する。
結果が `main` の場合は、以下のメッセージを表示して終了する（ブランチの自動作成は行わない）:

```
main ブランチ上では <コマンド名> を実行できません。
作業ブランチを作成してから再実行してください。例:
gh issue develop <issue番号> --name <ブランチ名>
```

main 以外であれば、次に **対象 issue とブランチの対応** を確認する:
- 現在のブランチ名が命名規約 `<issue番号>-<type>/<name>`（`.claude/rules/core.md` 参照）の番号プレフィックスを持つ場合、その番号と引数の `<issue番号>` を突合する
  - 一致: そのまま続行する
  - 不一致: 次のように警告し、続行可否をユーザーに確認する（自動でのブランチ作成・切り替えはしない）:
    ```
    現在のブランチ `<ブランチ名>` は issue #<ブランチの番号> に紐づく名前ですが、
    引数の issue 番号は #<引数の番号> です。このまま続行しますか？（はい / いいえ）
    ```
  - ブランチ名に番号プレフィックスがない場合: 突合できない旨を警告し、`git branch --show-current` の結果を提示して続行可否をユーザーに確認する

続いて **未コミット差分** を確認する:
- `git status --porcelain`（未追跡ファイルを含む）を実行し、差分がある場合は次のように警告して続行可否をユーザーに確認する（自動での stash・コミットはしない。判断は人間に委ねる）:
    ```
    未コミットの変更があります（未追跡ファイルを含む）。このまま続行しますか？（はい / いいえ）
    <git status の要約>
    ```
- ユーザーが「いいえ」を選んだ場合はワークフローを中断して終了する

上記の開始時ガードを通過したら、次に **issue コメント投稿の許可** をユーザーに求める。

このワークフローは各フェーズの進捗（<進捗コメント項目一覧（説明文）>）を `gh issue comment` で issue #<番号> に記録しながら進める。これは別セッションからの再開とサブエージェント間のデータ受け渡しに使う設計上の中核動作。ワークフロー開始前にユーザーへ次を伝え、明示的な同意を得る:

```
このワークフローは進捗を issue #<番号> にコメントとして投稿しながら進めます
（<進捗コメント項目一覧（確認文言）>）。
issue へのコメント投稿を許可して進めてよいですか？（はい / いいえ）
```

- ユーザーが許可した場合のみ続行する。この明示的な同意をもって、以降の全ステップで `gh issue comment` を実行する。
- ユーザーが拒否した場合: 進捗コメントを投稿しない前提では再開・フェーズ間のデータ受け渡しが成立しないため、その旨を伝えて終了する。
- この許可取得は再開時（Step 1 以外から始める場合）も含め、ワークフローの最初に毎回行う。

## レビュアー判定の確定手順

参照元: `refactor-auto`「レビュアー判定の確定手順（Step 6〜8 共通）」・`dev-auto`「レビュアー判定の確定手順（Step 4 / Step 9 共通）」。

呼び出し側は `<レビュアーサブエージェント名>`・`<エージェント定義ファイルパス>`・`<妥当な判定値の列挙>`・
`<独立検証の観点一覧>` を自分の値に置き換えて、以下をそのまま実行する。

---

レビュアーサブエージェント（<レビュアーサブエージェント名>）の返答から判定を確定する際は、以下の手順に従う。

1. **判定行の走査**: 返答1行目に限定せず、返答全体を走査して `判定:` で始まる行をすべて抽出する。エージェント定義（`<エージェント定義ファイルパス>`）は「返答1行目に固定形式で判定を書く」ことを指示しているが、実際にはその指示どおりに返らない場合がある（判定行が末尾付近に置かれる、無関係なメッセージが混入する等）ため、オーケストレーター側は判定行の位置に依存しない。
2. **単一・一致**: 抽出した判定行が1件のみ、または複数件あっても値がすべて一致する場合は、その値を分岐の根拠とする。
3. **複数・矛盾 / 判定不能**: 以下のいずれかに該当する場合、レビュアーの結論をそのまま分岐根拠にせず、**オーケストレーター自身が独立検証を行って判定を確定する**:
   - 判定行が複数件あり、値が矛盾している（例: 1通目 `判定: 問題あり`、2通目 `判定: 承認`）
   - 判定行が1件も見つからない、または定義された値（<妥当な判定値の列挙>）以外の不正な文字列である
   - 独立検証は、レビュアーが確認すべきだった観点（<独立検証の観点一覧>）を、オーケストレーター自身がコード・テスト・実行結果に照らして再確認する形で行う。**レビュアーの文面上の結論そのものは根拠にしない**
   - 独立検証の結果、問題ありと判断した場合は通常の修正ループへ、問題なしと判断した場合は次のステップへ進む
   - 独立検証で判定を確定した場合は、その旨と根拠（何を検証してどう判断したか）をレビュー履歴・試行カウンタコメント等の記録に残す

## Step 3 Plan 指示: origin/main 基準の段落

参照元: `refactor-auto`・`bugfix-auto` の Step 3（計画立案・Plan エージェントへのプロンプト）。
Plan エージェントに渡すプロンプトの一部としてサブエージェントへ渡る内容のため、呼び出し側
（オーケストレーター）は `<扱った計画項目の列挙>` を自分の値に置き換えたうえで、以下の本文を
**要約せずそのまま** Plan エージェント向けプロンプト内の貼り付けマーカーの位置に貼り付けること。

---

計画のいずれかの項目（<扱った計画項目の列挙>を含む）で main との差分・分岐点算出（マージベースの特定等）を扱う場合は、比較対象を `main` ではなく `origin/main` にすること。ローカル `main` は worktree 作成スクリプト（例: `scripts/wt-new.sh`。`gh issue develop --base main` で作業ブランチを作る。参考実装は `docs/examples/scripts/wt-new.sh`）のフローで最新化されないため、ローカル `main` を基準にすると分岐点を誤って古く算出しうる（根拠: `.claude/skills/auto-loop/SKILL.md`「エスカレーション時の後片付け」節）。また、`origin/main` を参照する前に `git fetch origin main` を実行し、**終了コードで成否を判定する**こと（worktree 作成スクリプトは作業ブランチしか fetch しないことがあり、worktree の `origin/main` 自体が古いことがある）。fetch に失敗した場合は `origin/main` も古い可能性があるため分岐点を確定させず、その旨を明記すること（同節の「`git fetch` が失敗した場合は `origin/main` も古い可能性がある」の扱いに合わせ、安全側に倒す）。どの項目で main との差分・分岐点を扱ったか（扱っていなければ「該当なし」）・使用した比較対象・`git fetch` の成否を計画に明記すること（Step 4 で基準を突き合わせて差し戻せるようにするため。明記が無いと、ローカル `main` を基準にした計画を見分けられない）。

---

## Step 3 Plan 指示: git grep 使用指示

参照元: `refactor-auto`・`bugfix-auto` の Step 3（計画立案・Plan エージェントへのプロンプト）。
Plan エージェントに渡すプロンプトの一部のため、呼び出し側は以下の本文を**要約せずそのまま**
Plan エージェント向けプロンプト内の貼り付けマーカーの位置に貼り付けること（プレースホルダはない）。
以下の本文自体には箇条書きの接頭辞「- 」やインデントを含めない。貼り付け先の体裁（箇条書きの
入れ子か独立した段落か、インデント量）は各 SKILL.md 側がそれぞれ独自に定める（refactor-auto は
項目3の入れ子の箇条書きとして5スペースインデント＋「- 」を付けて貼り付ける。bugfix-auto は
独立した段落としてそのまま貼り付ける。付け方は各 SKILL.md の貼り付けマーカーの位置に従う）。

---

リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
