## 概要

/auto-loop は並列度1で複数 issue を順次処理するため、issue 数に比例して総所要時間が
延びる。かといって指揮役1セッションが複数の子 pane を直接多重監視するフラット構成は、
issue 間の文脈混線・pane 誤爆・二重応答のリスクがある。本 skill はその解決として
**メタ指揮役 + 副指揮役の階層構成**を取る:

- **副指揮役** = /auto-loop の単一 issue 実行。ワークフローの振り分け（ラベル判定）・
  タッチポイント応答・計画承認・エスカレーション判定を、既存 /auto-loop の基準のまま・
  常に 1 issue の文脈に閉じて行う
- **メタ指揮役**（本 skill）= 系統の起動・多重監視・回収だけを行う。issue の内容判断はしない
  （ラベルとコメントによる機械的な判定は行う。Step 1・完了回収を参照）

検証の多層構造（指揮役レビュー → 内側ワークフロー内蔵の reviewer → テスト・型チェック →
PR 一次レビュー → CI チェック確認 → 自動マージの条件判定 → 条件を満たさない PR についての
人間の PR レビューとマージ）は /auto-loop と同一である。自動マージの条件判定とマージは
副指揮役が /auto-loop の 2h に従って行い、**メタ指揮役はマージしない**。

役割分担:

| 判断 | 担当 |
|---|---|
| 計画の承認・タッチポイント応答・エスカレーション判定 | 副指揮役（/auto-loop の基準のまま。本 skill では変更しない） |
| PR 作成 | 副指揮役（人間の承認は不要） |
| 系統の起動順・セットアップ直列化・並列度・全体停止 | メタ指揮役 |
| 自動マージの条件判定・マージ・マージした PR の worktree とブランチの削除 | 副指揮役（/auto-loop の 2h の基準のまま。条件をすべて満たした PR のみ。CLAUDE.md が自動マージを許可していることが前提） |
| 自動マージの条件を満たさない PR のレビュー・マージ | 人間（最終ゲート） |

## 引数

- `<issue番号...>`（省略可）: 処理対象の issue 番号を空白区切りで複数指定できる。指定順に起動する
- `--parallel N`（省略可）: 同時に稼働させる系統数の上限。1〜5 の整数。**省略時は 4**。
  `--parallel` の直後の値は並列度であり、issue 番号として扱わない
  （`/auto-loop-parallel --parallel 2 12 34` の `2` は issue #2 ではなく並列度）
- `--limit N`（省略可）: 1回の実行で処理する issue 数の上限。1以上の整数（上限値は設けない）。
  **省略時は 5**。`--limit` の直後の値は件数であり、issue 番号として扱わない
  （`/auto-loop-parallel --limit 2 12 34` の `2` は issue #2 ではなく件数）。
  件数の適用規則は `.claude/skills/auto-loop/SKILL.md` の Step 1 手順3が正
- **両オプションの値の検証**（不正な指定の判定・エラーの伝え方・検証を行うタイミング）は
  `.claude/skills/auto-loop/SKILL.md` の「引数」節 `--limit N` が正であり、本 skill で
  重複定義・変更しない（`--parallel` は範囲が 1〜5 である点だけが異なる）。検証は同節のとおり
  **Step 0 の前提チェック・ラベル準備より前**に行うため、候補収集にも系統の起動にも先立つ
- issue 番号省略時: /auto-loop の「ワークフロー定義表」の対象ラベル・補助ラベル
  （`refactoring` / `bug` / `skill-improvement`）が付いた open issue からメタ指揮役が
  選定する（最大 N 件。N は `--limit` の値、省略時は5）

## 前提条件（満たさなければ即終了）

**実行モデルの前提（機械的に検証できないため即終了条件には含めない）**: メタ指揮役は多重監視の
イベントループを取りこぼしなく回す必要があり、起動する副指揮役（/auto-loop）は「人間の代理」を
担うため opus 以上を前提とする。このスキル自身も **opus 以上のセッションで実行する**ことを前提とし、
副指揮役の pane には「系統の起動」で `--model opus` を明示的に渡してこの前提を保証する。
Step 0 の前提チェック時にこの前提をユーザーへ明示する（skill frontmatter の `model:` は「起動したターンの
残りにだけ適用され、次のプロンプトでセッションモデルに戻る」仕様のため、複数ターンにまたがる
メタ指揮役では使わずセッション側で指定する）。

/auto-loop の前提条件4点（Herdr 内であること・herdr デーモンに接続できること・
gh が使えること・`scripts/wt-new.sh` と `scripts/wt-rm.sh` があること）に加えて:

5. **herdr の tab コマンドが使えること**: `herdr tab list` がエラーなく JSON を返すこと
   （系統ごとの専用タブ作成に使う）

前提チェックは上記の順に、ラベル作成など副作用のある操作より先に行う。

worktree スクリプトに求める振る舞い（特に並列実行で必要になる `.worktree-registry` の書き換えの排他制御）と、
本 skill で使う `<worktree パス>` の表記は、`.claude/skills/auto-loop/SKILL.md` の「worktree スクリプトの前提」が正である。

herdr CLI の正確な構文はインストール済みバイナリが正である。操作前に `herdr pane` /
`herdr tab` / `herdr wait` などコマンドグループ名だけを実行してヘルプを確認する
（引数なしの `herdr` は TUI が起動するため実行しない）。
制御系コマンド（tab create / split / get / wait 等）は JSON を返すが、**`pane read` は
プレーンテキストを返す**——JSON としてパースしない。

## 構成

```
メタ指揮役（この skill を実行するセッション、Herdr の1 pane）
├── Step 0: 前提チェック・エスカレーションラベル準備
├── Step 1: 対象 issue と並列度の決定・ワークフローの振り分け・処理計画の表示
├── Step 2: 系統の起動と多重監視（イベントループ）
│   │ 系統 = issue 1件の処理単位（専用タブ + 副指揮役 pane + 子 pane）
│   │ セットアップは直列（同時にセットアップ中の系統は最大1つ）・稼働は最大〈並列度〉
│   ├── タブ al-<番号>
│   │   ├── 副指揮役 pane（claude + /auto-loop <番号> 副指揮役モード）
│   │   └── 子 pane（副指揮役が split で作成。claude + 内側ワークフロー）
│   ├── タブ al-<番号> …（並列度の数まで）
│   └── 多重監視: バックグラウンド herdr wait + herdr pane list の一括状態確認
└── Step 3: 全体サマリー報告（副指揮役サマリーの回収・エスカレーション集計）
```

worktree は /auto-loop と同じ **1 issue = 1 worktree**（`<worktree パス>`、
作成は副指揮役が子 pane 内で `scripts/wt-new.sh` により行う）。`wt-new.sh` がポート割当まで worktree
単位で分離するため稼働中の系統同士は衝突しないが、**セットアップ（worktree 作成・
依存インストール・ベースラインテスト）は CPU 競合による偽エスカレーション
（テストのタイムアウト等）を避けるため直列に行う**。この直列化は「副指揮役の
セットアップ完了マーカーを待ってから次の系統を起動する」ことで実現する
（マーカーの定義は `.claude/skills/auto-loop/SKILL.md` の「副指揮役モード」が正）。

## 手順

### Step 0: 前提チェック・ラベル準備

**まず引数（`--parallel`・`--limit`）を検証する**（規則は「引数」節）。不正なら以降の操作を
一切行わずに終了する。ラベル準備はリポジトリに対する副作用のある操作であり、不正な引数のまま
実行しないため、検証は前提チェックよりも前に置く。

前提条件5点を確認する。次に `auto-loop:escalated` ラベルを準備する。手順は
`.claude/skills/auto-loop/SKILL.md` の Step 0「ラベル準備」が正であり、本 skill で
重複定義・変更しない（旧名 `refactor-loop:escalated` からの改名による移行を含むため、
「なければ作成する」だけで済ませると付与済み issue が旧ラベルに取り残される）。
メタ指揮役が先に済ませておくことで、並列起動された副指揮役同士のラベル操作の競合も防げる。

開始日時を確定し（`date -u +%Y-%m-%dT%H:%M:%SZ`）、続けて `herdr pane get "$HERDR_PANE_ID"` を実行して
`result.pane.agent_session.value`（メタ指揮役自身のセッションID）を控える（`--current` を使わない理由は
/auto-loop の Step 0 と同じ）。どちらも
`.claude/skills/auto-loop/SKILL.md`「実行記録の投稿」のトークン消費量集計・記録テンプレートの
開始日時で使う。

PR 作成の承認確認は行わない（PR 作成は人間の承認なしで進めてよい）。
CLAUDE.md が `/auto-loop` による自動マージを許可していない場合の告知文の読み替えは、/auto-loop の Step 0 と同じ。
以下をユーザーへ伝えてから Step 1 へ進む（確認待ちはしない。表示は監査用のログ）:

```
このループは最大<並列度>並列で複数 issue を処理し、完了した issue ごとに
PR 作成と一次レビュー・修正（1周）・CI チェックの確認まで自動で進めます。自動マージの条件を
すべて満たした PR は副指揮役がマージし、満たさない PR は満たさなかった条件を添えて引き渡します。
自動マージの前に PR へ main を取り込んでコンフリクトした場合は、副指揮役がコンフリクトを解消した merge コミットを
PR ブランチに push します（解消できなければマージせずに引き渡します）。
一次レビューで修正せずに見送った指摘がある PR には、副指揮役がその指摘を PR にコメントとして投稿します
（自動マージの可否には影響しません）。
エスカレーション（人間の判断待ち）にした issue には、ラベル付与とあわせて保留理由を
issue コメントとして投稿します。実行終了時には、この実行の記録（開始/終了日時・並列度・処理結果・
トークン消費量等）をトラッキング issue（ラベル `auto-loop:log`）にコメントとして投稿します。

副指揮役は opus で起動します。メタ指揮役（このセッション）も opus 以上で実行する前提です。
セッションモデルはこちらから確認できないため、opus 未満で動いている場合は
`/model opus` に切り替えてから再実行してください。
```

### Step 1: 対象 issue と並列度の決定・ワークフローの振り分け

**対象 issue の選定基準・除外条件・ワークフローの振り分け表は
`.claude/skills/auto-loop/SKILL.md` の Step 1 と「ワークフロー定義表」が正**であり、
本 skill で重複定義・変更しない。副指揮役も起動後に同じ判定を行うが、除外対象をここで
落としておかないと、タブ・pane・系統枠を消費したうえで副指揮役が即スキップして終わる。

**除外と起動順の決定を先に適用し、そのうえで最大 N 件（`--limit N`。省略時5。適用規則は
`.claude/skills/auto-loop/SKILL.md` の Step 1 手順3が正）を取る**（除外対象や優先度の低い issue が
枠を消費して、実処理が N 件未満になったり優先度の高い issue が漏れたりするのを防ぐため）:

1. 候補を集める。引数で番号が指定された場合は各番号を
   `gh issue view <番号> --json number,title,state,labels` で実在確認する。省略時は
   定義表の対象ラベル・補助ラベルごとに
   `gh issue list --label <ラベル> --state open --json number,title,labels` を実行し、
   結果の和集合を候補とする
2. 各候補のラベルでワークフローを振り分ける（判定の正は auto-loop の Step 1 の振り分け表）。
   対象ラベルがちょうど1つ付いていればそのワークフロー、対象ラベルが1つも付いておらず
   補助ラベルがちょうど1つ付いていればその補助ラベルの列のワークフロー、**それ以外
   （対象ラベルが2つ以上・補助ラベルだけが2つ以上・どちらも付いていない）は処理対象から外す**
   （どちらのワークフローで扱うかは issue の分類そのものの問題で、人間が決めるべきものだから）
3. 以下に該当する issue も対象から外す。外した issue は理由とともに Step 3 の報告に含める
   （結果欄は「スキップ」）:
   - `state` が `CLOSED`（引数指定時のみ発生する）
   - `auto-loop:escalated` ラベルが付いている（人間の判断待ち）
   - issue コメントに、**振り分け先ワークフローの終端マーカー**（定義表「終端マーカー表」の
     該当ワークフローの全行。完了・エスカレーション・対象外のいずれも）がある。
     bug ワークフローでは `## /bugfix-auto — 対象外（人間確認が必要）` も除外対象に含まれる
     （対象外は正常終了であり、同じ issue を掘り返さないため）
4. 残った候補の起動順を決めてから最大 N 件を取る（起動順の決め方は、引数指定時の扱いも含めて
   `.claude/skills/auto-loop/SKILL.md` の Step 1 手順3が正。本 skill では重複定義しない）

振り分け結果（issue ごとのワークフロー種別）は系統の状態として記録しておく。完了回収の
裏取りマーカーと Step 3 の報告で使う。メタ指揮役が持つのはこのラベル由来の機械的な判定結果
だけで、issue の内容判断（どう直すか・その計画が妥当か）は行わない。

コメントの確認には `gh issue view <番号> --json comments` を使う（`--comments` は
auto mode の環境で空出力になる既知事象があり、空出力を「マーカーなし」と誤判定して
処理済み issue を再処理してしまうため）。

並列度は引数 `--parallel N` から決める（省略時4）。起動待ちキューは手順4 で上限件数（`--limit N`。省略時5）
まで絞られており、issue 1件につき系統は1つで再試行もしないため、同時に稼働する系統数
（セットアップ中と稼働中の合計）は min(並列度, 上限件数) を超えない。`--limit` が `--parallel` より小さいときは
上限件数が同時稼働数の上限になるが、表示・記録する並列度は指定値のままとし、実効値には置き換えない
（並列度だけを見て同時稼働数を読み違えないよう、実行記録には上限件数も並べて残す。Step 3「実行記録の投稿」を参照）。
対象 issue・振り分け先ワークフロー・起動順・並列度・適用された上限件数をユーザーに表示してからループを開始する
（確認待ちはしない。表示は監査用のログ）。

### Step 2: 系統の起動と多重監視（イベントループ）

メタ指揮役は以下の状態を管理し、変化のたびに自分の出力へ記録する（監査ログ）:

- 起動待ちキュー（起動順）
- セットアップ中の系統（**常に最大1つ**）
- 稼働中の系統（issue 番号・振り分け先ワークフロー・tab_id・副指揮役の pane_id）
- 終了した系統（完了 / エスカレーション / 対象外 / 未着手）
- エスカレーション合計件数（「対象外」で終わった系統は加算しない）

ループは次の繰り返しで進める:

1. **起動判定**: セットアップ中の系統がなく、起動待ちキューが空でなく、
   （セットアップ中 + 稼働中）の系統数が並列度未満で、エスカレーション合計が3件未満なら、
   キュー先頭の issue で「系統の起動」を行う
2. **待機**: バックグラウンド wait の完了通知を待ち、通知が来たら「イベント処理」を行う。
   どの系統の wait かは、完了したコマンドに含まれる pane_id で識別する
3. 全系統が終了し（起動待ちが空、または全体停止で未着手確定）、稼働中・セットアップ中が
   なくなったら Step 3 へ

#### 系統の起動

1. `git rev-parse --show-toplevel` でプロジェクトルートの絶対パスを取得し、専用タブを作る:
   ```
   herdr tab create --no-focus --label "al-<番号>" --cwd <プロジェクトルート>
   ```
   応答 JSON から tab_id を読み取る。初期 pane の pane_id が応答に含まれない場合は
   `herdr pane list` で該当 tab_id の pane を特定する（ID を推測で組み立てない）。
   タブ名にワークフロー種別を入れないのは、系統の識別は issue 番号で足り、
   ワークフローの対応づけは Step 3 の報告で示すためである
2. `herdr pane rename <pane-id> "al-sub-<番号>"` で副指揮役 pane に名前を付ける
3. 副指揮役の claude を auto mode の対話モードで起動し、起動完了を待つ:
   ```
   herdr pane run <pane-id> "claude --permission-mode auto --model opus"
   herdr wait agent-status <pane-id> --status idle --timeout 60000
   ```
   起動完了を待った後に `herdr pane get <pane-id>` を実行し、`result.pane.agent_session.value`
   （副指揮役のセッションID）を監査ログに記録する（トークン消費量の集計には使わない。副指揮役が
   自分の小計として算出するため。/auto-loop の「実行記録の投稿」を参照）。
   `--model opus` を渡すのは、副指揮役が計画承認・タッチポイント応答という「人間の代理」を
   担うため（/auto-loop の「前提条件」の実行モデル前提を、起動側から保証する）。
   副指揮役がさらに起動する子（内側ワークフロー）のモデルは /auto-loop の 2b が指定するため、
   ここでの指定は副指揮役自身のセッションにのみ効く
4. 副指揮役モードで /auto-loop を投入する（改行を含めず1行で送る）。
   **wait で待ち受けるマーカーの完成形をプロンプトに書かない**（pane に表示された
   プロンプト自体に `herdr wait output` が誤マッチするため。マーカーの定義・分割表記の
   指示は auto-loop 側の「副指揮役モード」が正で、副指揮役はそれを読んで完成形を
   自分の出力として書く）:
   ```
   herdr pane run <pane-id> "/auto-loop <番号> 副指揮役モード: (1) 質問・確認・承認依頼は対話ダイアログを使わず通常のテキスト出力で行ってください。(2) セットアップ完了・失敗マーカーと終了サマリーは auto-loop skill の「副指揮役モード」の定義に従って出力してください"
   ```
5. `herdr wait agent-status <pane-id> --status working --timeout 60000` で作業開始を確認する
6. セットアップ監視を **Bash ツールの run_in_background** で開始する
   （フォアグラウンドで待たない。待っている間に他系統の監視が止まるため）。
   マーカー監視と idle 監視の2本を並行して張り、先に完了した方のイベントで分岐する
   （副指揮役が前提条件エラー・対象 issue の除外などで**マーカーを出さずに**ターンを
   終えた場合に、マーカー監視のタイムアウトまで直列化がブロックされるのを防ぐ）:
   ```
   herdr wait output <pane-id> --match "SETUP_(DONE|FAIL)_<番号>" --regex --source recent-unwrapped --timeout 600000
   herdr wait agent-status <pane-id> --status idle --timeout 600000
   ```
   この系統を「セットアップ中」として記録する。セットアップ中の系統がある間は、
   並列枠が空いていても次の系統を起動しない（セットアップの直列化）

#### イベント処理: セットアップ監視の完了

セットアップ監視は2本（マーカー監視・idle 監視）あるため、先に完了した方で分岐する。
分岐の結果、系統が「稼働中」に昇格したら idle 監視はそのまま稼働中の idle 監視（後述）
として引き継ぎ、監視を張り直す場合は2本とも張り直す:

- **`SETUP_DONE_<番号>` にマッチ**: 系統を「稼働中」に昇格する。ループ先頭へ（次の起動判定）
- **`SETUP_FAIL_<番号>` にマッチ**: エスカレーション合計に1加算する（理由: セットアップ失敗。
  ラベル付与・issue の保留は副指揮役が通常のエスカレーション処理として行う）。系統は
  終了サマリー待ちとして「稼働中」扱いにする。ループ先頭へ
- **idle 監視が先に完了した**（マーカーなしでターンが終わっている。前提条件エラー・
  対象 issue の除外・想定外の質問など）:
  `herdr pane read <pane-id> --source recent-unwrapped --lines 200` で内容を読む。
  質問なら「メタ指揮役の応答基準」で応答し、作業再開を確認してからセットアップ監視を
  張り直す。終了サマリー（`## /auto-loop 終了`）が出ていれば「完了回収」へ回し
  （タブの扱いはそこの判断表に従う）、サマリーのないエラー報告なら系統を終了として
  記録する（処理されないまま終わった issue はメタエスカレーション）。
  いずれもセットアップ枠を解放してループ先頭へ
- **両方タイムアウト**: `herdr pane get <pane-id>` と
  `herdr pane read <pane-id> --source visible --lines 60` で状況を確認する:
  - `working` で画面が進んでいる → セットアップ監視を張り直す
  - `blocked`、または表示が前回のタイムアウト時から進んでいない（ハング疑い） →
    メタエスカレーション（後述）。セットアップ枠が解放されるのでループ先頭へ

#### イベント処理: 稼働中の系統の idle 監視

稼働中の各系統には、次を run_in_background で張っておく:

```
herdr wait agent-status <pane-id> --status idle --timeout 600000
```

- **idle で返った**（副指揮役のターンが終了。終了サマリー・質問のいずれか）:
  `herdr pane read <pane-id> --source recent-unwrapped --lines 200` で最終出力を読み分岐する:
  - **`## /auto-loop 終了` を含む** → 「完了回収」へ
  - **質問・確認** → 「メタ指揮役の応答基準」に従って応答を `pane run` で送り、
    `herdr wait agent-status <pane-id> --status working --timeout 60000` で作業再開を
    確認してから idle 監視を張り直す
  - **判断できない出力** → 1回だけ「現在の状況と次に必要な入力を教えてください」と
    `pane run` で問い合わせる。それでも判断できなければメタエスカレーション
- **タイムアウト**: `herdr pane list` で全系統の agent_status を一括確認する
  （wait は単一 pane しか待てないため、この一括確認が blocked 検出と監視漏れの補完を兼ねる）:
  - 該当 pane が `working` → 監視を張り直す。ただし `pane read --source visible` の表示が
    数回連続で進んでいない場合はハングを疑い、内容を確認してメタエスカレーションを検討する
  - 該当 pane が `blocked`（permission ダイアログ等） → 内容を確認する。
    **ダイアログへの自動応答はしない**（現行 /auto-loop と同じ扱い）。
    メタエスカレーションへ
  - 一括確認で**他の系統**の異常（blocked・pane 消失など）に気づいたら、その系統の
    イベントとして同様に処理する

#### 完了回収

1. 終了サマリー（`## /auto-loop 終了`）から結果（完了 / エスカレーション / 対象外・PR 番号・
   自動マージと worktree・ブランチの削除の結果・main への追従で解消したコンフリクト（`コンフリクト解消: <パス>`）・
   一次レビューで見送った指摘のコメント（PR 番号・URL。
   投稿できなかった場合はその本文全文と失敗の理由）・判断ログ・開始/終了日時・計画承認の差し戻し回数・
   一次レビュー指摘件数と修正の有無・エスカレーション条件の該当要約・トークン消費量小計
   〈フィールド別〉）を読み取り、記録する（実行記録ブロックの詳細は `.claude/skills/auto-loop/SKILL.md`
   「副指揮役モード」項目6・「実行記録の投稿」を参照）
2. 裏取りする（pane 出力だけを信用しない）。**確認するマーカーはその系統の振り分け先
   ワークフローの行を定義表「終端マーカー表」から引く**（`## /refactor-auto 完了` /
   `## /bugfix-auto 完了` のようにワークフローごとに文字列が異なるため、種別を取り違えると
   完了しているのに裏取りに失敗する）:
   - **完了**とされた issue: `gh issue view <番号> --json comments` に**完了マーカー**が
     あること。さらに PR 作成済みとされた場合はサマリーの PR 番号で
     `gh pr view <PR番号> --json headRefName,url,state` を実行し、PR が実在して head ブランチが
     `<issue番号>-` プレフィックスであることを確認する（メタ指揮役はブランチ名を直接は
     知らないため、PR 番号ベースで確認する）。あわせて、サマリーの自動マージの結果と PR の
     `state` が一致すること（`自動マージ: 済み` なら `MERGED`、`未実施`・`失敗` なら `OPEN`）を確認する。
     `自動マージ: 済み` の場合は、worktree・ブランチが実際に削除されたかも確認する。worktree は /auto-loop の
     2a 手順3 のコマンド（パスの末尾まで照合する）、ローカルブランチは `git branch --list <headRefName>` で確認する。
     Step 3 の報告には、サマリーの削除結果ではなくここで確認した実態を書く。サマリーの削除結果と実態が
     食い違っていた場合（削除済みとあるのに残っている／削除失敗とあるのに消えている）は、その食い違いも判断ログに書く
     （削除処理の pane を残した系統では、サマリーを出した後に削除が終わって食い違うことがある）。
     残っていた場合も下の「相違」には含めず（PR はマージ済みで、残るのはローカルの worktree・ブランチだけのため）、
     Step 3 の「マージ後の後片付け」に issue 番号・残っているもの・手で片付ける方法を書く
   - **対象外**とされた issue: 同じく `--json comments` に**対象外マーカー**があること。
     PR は作られないため PR の確認はしない

   相違があればその系統をメタエスカレーションに切り替える
3. サマリーでエスカレーションが報告されていた場合: `gh issue view <番号> --json labels,comments` で
   `auto-loop:escalated` ラベルと `## /auto-loop エスカレーション` コメントの両方が
   残っていることを確認し、欠けているものをメタ指揮役が補って再確認する
   （コメントは副指揮役の終了サマリーに書かれた保留理由をそのまま転記する。副指揮役が
   分類器に投稿をブロックされた場合の埋め合わせ）。
   エスカレーション合計に1加算する（`SETUP_FAIL` で加算済みの系統は二重加算しない）
4. サマリーで**対象外**が報告されていた場合: **ラベルは付けず、エスカレーション合計にも
   加算しない**（「対象外」はエスカレーションではなく正常終了。扱いの正は定義表の
   「結果分類ごとの扱い」）。理由コメントは内側ワークフローが投稿済みなので、
   メタ指揮役からは投稿しない。副指揮役サマリーに書かれた後片付けの結果
   （worktree・ブランチを残した場合はそのパスとブランチ名）は Step 3 の報告へ転記する
   ——対象外では PR を作らないため、コミットの所在を示す記録がサマリーにしかない
5. 後片付け: `herdr pane list` でそのタブに残っている pane が自分の系統のものだけで
   あることを確認してから `herdr tab close <tab-id>` で閉じる。**完了・エスカレーション・
   対象外のいずれでもタブを閉じる**（下表）。ただし手順2でメタエスカレーションに切り替えた系統
   （裏取りの相違）はこの手順を行わない——タブを残すのがメタエスカレーションの要件のため。
   副指揮役サマリーが削除処理の pane を残したと報告している系統（書式・理由は /auto-loop の「副指揮役モード」5）も
   タブを閉じない——閉じると実行中の `wt-rm.sh` が途中で止まるため。その系統はタブ名と pane ID を Step 3 の
   「人間への依頼」（自動マージした issue は「マージ後の後片付け」、それ以外はその結果分類の欄）に書く。
   worktree はメタ指揮役では削除しない
   （自動マージした issue の worktree・ブランチの削除〈/auto-loop の 2h 手順8〉と、エスカレーション・対象外終了時の
   成果ゼロ worktree の削除は、副指揮役が終了サマリーを出す前に済ませている。削除の結果を Step 3 の報告へ転記する。
   自動マージした issue は手順2 で確認した実態を書く）
6. ループ先頭へ（起動待ちが残っていれば次の系統を起動）

タブを閉じるかどうかの判断:

| ケース | pane にしかない情報 | 方針 |
|---|---|---|
| 完了（裏取りOK） | なし | タブを閉じる |
| 対象外（裏取りOK） | なし | タブを閉じる |
| セットアップ前の保留（子 pane 未起動） | なし | タブを閉じる |
| 子 pane 起動済み・作業途中の保留 | 会話文脈のみ（再開時は引き継がなくてよい） | タブを閉じる |
| 削除処理の pane を残した（結果分類を問わない） | 実行中の `wt-rm.sh`（閉じると削除が途中で止まる） | **タブを残す** |
| メタエスカレーション（blocked / ハング / 応答不能 / 裏取りの相違） | 画面そのものが診断材料 | **タブを残す**（後述） |

エスカレーション・対象外でもタブを閉じられるのは、その理由が issue コメント
（`## /auto-loop エスカレーション` / 内側ワークフローの対象外マーカー）として自己完結しており、
判断が決まった後は新しいセッションで再実行すればよいためである（内側ワークフローは issue
コメントの進捗マーカーから再開ポイントを判定する）。中身のないタブが保留のたびに増えると、
タブ一覧が実際の稼働状況を表さなくなる。

#### メタ指揮役の応答基準

メタ指揮役は issue 個別の文脈を持たない。副指揮役から入力を求められたら:

- **進行上の事務的な確認**（auto-loop の手順に定義がある確認事項）→ その定義に沿って応答する
- **issue の内容判断**（計画・スコープ・技術判断）を求められた → それは副指揮役の担当範囲
  なので、1回だけ「それはあなたの判断範囲です。/auto-loop の承認基準・応答基準に
  従って判断してください」と差し戻す。それでも内容判断を求められたらメタエスカレーション
  （メタ指揮役が代わりに判断すると、判断を 1 issue の文脈に閉じるという本構成の前提が崩れる）

応答・差し戻しの内容は、その都度メタ指揮役自身の出力にも記録する（監査ログ）。

#### メタエスカレーション（系統単位の保留）

副指揮役自体が機能不全のとき（blocked・ハング・応答不能・完了裏取りの相違）に、
メタ指揮役が系統ごと保留して人間に引き継ぐ:

1. `gh issue edit <番号> --add-label "auto-loop:escalated"` でラベルを付け、
   `gh issue view <番号> --json labels` で付与を確認する
2. ラベル付与に続けて、保留理由を issue コメントとして投稿し、
   `gh issue view <番号> --json comments` で実在を確認する。見出しマーカー
   （`## /auto-loop エスカレーション`）・本文の形式・分類器にブロックされた場合の扱いは
   `.claude/skills/auto-loop/SKILL.md` の「エスカレーション理由コメント」が正であり、
   本 skill で重複定義・変更しない。差分は次の2点だけ:
   - `- 保留者:` は「メタ指揮役（/auto-loop-parallel）」とする
   - 「判断が決まった後にすること」には、タブ `al-<番号>`・副指揮役 pane `al-sub-<番号>`・
     worktree パスを残していることを書く（メタエスカレーションはタブ・worktree を
     閉じない／削除しないため、通常のエスカレーションと違って残置物の場所が要る）

   メタ指揮役は issue の内容判断をしないため、理由には**副指揮役が機能不全になった状況**
   （blocked・ハング・応答不能・完了裏取りの相違）と、その時点で `pane read` から読み取れた
   副指揮役の最終出力の要点を書く（issue の技術的な是非を判断して書かない）
3. **タブ・副指揮役 pane・子 pane・worktree はそのまま残す**（副指揮役自体が機能不全に
   なったという保留であり、画面に表示されているエラー・ダイアログそのものが原因究明の
   手がかりになるため。通常のエスカレーションではタブを閉じる——「完了回収」の判断表を参照）。
   副指揮役が機能不全なので後片付け（子 pane の閉鎖・成果ゼロ worktree の削除）は
   実施されない。メタ指揮役が肩代わりもしない
4. 何をどこまで判断して保留したかをメタ指揮役の出力に記録する
5. エスカレーション合計に1加算し、その系統のバックグラウンド wait は張り直さない（監視終了）

#### 全体停止

- **エスカレーション合計が3件に達したら、新規系統の起動を停止する**（/auto-loop の
  「3 issue 連続」ルールの並列版。原因が個別 issue ではなくメタ指揮役側・環境側にある
  可能性が高いため）。起動待ちの issue は「未着手」として Step 3 で報告する。
  稼働中の系統は強制終了せず、監視を続けて回収してから Step 3 へ進む。
  「対象外」で終わった系統はこの合計に含めない（定義表「結果分類ごとの扱い」に従う）。
  なお bug ワークフローは refactor に比べてエスカレーションに倒れやすいため
  （理由は /auto-loop の「エスカレーション条件」）、全体停止に達したときは
  メタ指揮役側・環境側の異常だと決めつけず、対象 issue 群の書き方も点検の対象に含める
- gh・herdr 自体が使えなくなったときは即時停止し、その時点の状態を Step 3 で報告する

### Step 3: 全体サマリー報告

ループ終了時（全件回収・全体停止のいずれでも）、以下の形式で報告する。
結果「完了」の行の備考には、副指揮役の終了サマリーに書かれた CI 結果（`CI: 成功` / `CI: 対象外`）と
自動マージの結果（`自動マージ: 済み` / `自動マージ: 未実施（<満たさなかった条件>）` / `自動マージ: 失敗（<エラーの要点>）`）を転記する。
自動マージした場合は、完了回収の手順2 で確認した worktree・ブランチの削除の実態も書く（書式は /auto-loop の 2h 手順9 が正）。
副指揮役の終了サマリーの備考にコンフリクトの解消の記録（`コンフリクト解消: <パス>`。書式は /auto-loop の 2h 手順9 が正）が
あれば、自動マージしたかどうかにかかわらず、その issue の行の備考にそのまま転記する（エスカレーションの行でも同じ）。

**実行記録の投稿**: 手順（実行順序）・記録テンプレートは `.claude/skills/auto-loop/SKILL.md`「実行記録の投稿」が
正であり、本 skill で重複定義・変更しない。この報告を出力する前に、同節の実行順序どおり投稿と実在確認まで
完了させる。差分は次の3点だけ:

- 見出しは `## /auto-loop-parallel 実行記録`
- 記録テンプレートに並列度の行（`- 並列度: <N>`）を追加する
- 投稿はメタ指揮役が実行1回につき1件だけ行う（副指揮役は終了サマリーの `### 実行記録ブロック` に出力するが
  投稿はしない。詳細は /auto-loop の「副指揮役モード」項目6）。トークン消費量は
  メタ指揮役自身のトークン消費量と各副指揮役が報告した小計をフィールドごとに合算する

副指揮役の小計に「一部取得できず」の注記が付いていた場合は、その注記（どのセッション・理由）を
issue 番号を添えて全体のトークン消費量の注記に引き継ぐ（落とすと、欠けた合計が完全な値に見える）。
副指揮役の終了サマリー（実行記録ブロック）を回収できなかった系統（メタエスカレーション等）は、
記録テンプレートの「対象 issue」テーブルでその issue の行の取得できない値を「—」とし、
トークン消費量に「一部取得できず（#<番号> の副指揮役・終了サマリーを回収できなかった）」と書く。
結果列は下記「処理結果」表と同じ区分（メタエスカレーションを含む）を使う。

```
## /auto-loop-parallel 終了

並列度: 4 / 上限件数: 5 / エスカレーション合計: 3件

### 処理結果
```

## 注意事項

- pane・tab の ID は必ず herdr の JSON 応答から読み取る。推測やサイドバーの順序から
  組み立てない
- 自分が作ったタブ・pane 以外を閉じない・操作しない
- `pane run` を送る前に `pane get` で相手の状態を確認する（`working` 中に送らない）
- gh での副作用（ラベル作成・付与・エスカレーション理由コメントの投稿、実行記録の投稿）は、実行後に別の
  読み取りコマンドで実在確認する
- メタ指揮役は issue へのコメント投稿を**原則として**自分では行わない（進捗記録は子の
  内側ワークフローが担う。メタ指揮役の判断ログはサマリー報告に残す）。**例外はエスカレーション
  理由コメント**（メタエスカレーション時と、副指揮役がエスカレーションしたのにコメントが
  残っていない場合の埋め合わせ。理由がラベルだけになって失われるのを防ぐため）と**実行記録**
  （`## /auto-loop-parallel 実行記録`。メタ指揮役の実行1回につき1件、トラッキング issue に
  投稿する。副指揮役はStep3で実行記録ブロックを出力するが投稿はしない）。
  対象外終了の理由コメントは内側ワークフローが投稿済みなので、メタ指揮役からは投稿しない
- 環境を変更する操作（worktree 作成・依存インストール・テスト実行・claude 起動）は
  すべて pane 内で行い、メタ指揮役の Bash では行わない。メタ指揮役の Bash で使うのは
  herdr の制御系・git / gh の読み取り系と、例外としてラベル操作
  （`gh label create` / `gh label edit`（Step 0 の旧名からの改名移行）/
  `gh issue edit --add-label`）、エスカレーション理由コメントと実行記録の投稿
  （`gh issue comment`）、およびトークン消費量集計に使うトランスクリプトファイルの読み取り
  （`~/.claude/projects/**`、読み取り専用）のみ
  （サンドボックスの制約と非対称性は /auto-loop の注意事項と同じ）
- `pane run` で送るプロンプトに、wait で待ち受けるマーカーの完成形を書かない
  （入力エコーへの誤マッチ防止）。マーカー・終了サマリーの定義は
  `.claude/skills/auto-loop/SKILL.md` の「副指揮役モード」が正であり、
  本 skill で重複定義・変更しない
- 副指揮役の判断品質に関わる基準（計画の承認基準・タッチポイントへの応答基準・
  エスカレーション条件）は /auto-loop が正。メタ指揮役が代行・上書きしない
- 監視の wait は必ず run_in_background で行い、フォアグラウンドの wait で代替しない
  （1つの pane を待つ間、他系統の異常検出が止まるため）。通知が来ない系統も
  タイムアウト（600000ms）ごとに `herdr pane list` の一括確認で拾う
- 1回の実行で処理する issue は最大 N 件（`--limit N`。省略時は5）。同一 issue の再試行はしない
- 並列度の既定は4（上限は5）
- **メタ指揮役はマージしない**。自動マージは、副指揮役が /auto-loop の 2h の条件をすべて満たした PR に
  だけ行う（条件を満たさない PR は、人間の PR レビューとマージが最後の独立した検証層）。
  並列実行では他の系統のマージで main が進むため、後から 2h に到達した PR は main への追従と
  CI の再確認を経ることが多くなり、追従でのコンフリクトも起きやすくなる（コンフリクトは副指揮役が
  /auto-loop の 2h「main への追従で起きたコンフリクトの解消」に従って解消する）
- worktree はメタ指揮役では削除しない（完了した issue の worktree は PR のマージ後に人間が
  `scripts/wt-rm.sh` で削除する）。**例外は自動マージした issue の worktree・ブランチの削除
  （/auto-loop の 2h 手順8 が正）と、エスカレーション・対象外終了時の成果ゼロ worktree の
  削除だが、どちらも行うのは副指揮役**（後者は /auto-loop の「エスカレーション時の後片付け」が正）で
  あり、メタ指揮役は肩代わりしない。副指揮役が削除できなかった worktree はそのまま残し、
  Step 3 の「人間への依頼」に記載する
- タブを閉じるのは完了・エスカレーション・対象外のいずれでも行う（判断表は「完了回収」を参照）。
  タブを残すのはメタエスカレーションと、副指揮役が削除処理の pane を残した系統だけ
- ワークフロー固有の値（対象ラベル・補助ラベル・終端マーカー・結果分類ごとの扱い・振り分け表）は
  **必ず /auto-loop の「ワークフロー定義表」から引き、本 skill に独自の対応表を持たない**
  （メタ指揮役が別表を持つと、ワークフローを追加するたびに2箇所を同期する羽目になり、
  副指揮役との判定のずれも検出できなくなる）。本文でマーカーを例示している箇所も
  参照先を示すための例示であって、定義そのものではない
- blocked（permission ダイアログ等）への自動応答は行わない（現行 /auto-loop と同じく
  エスカレーションとして扱う。自動応答は本 skill のスコープ外）
