  - 「/dev-auto <番号>」と呼び出されたとき

## 概要

各フェーズをサブエージェントとして実行し、コンテキストの汚染を防ぎながら自律的に開発を進める。
人間が介入するのは要件定義フェーズの仕様合意の1回のみ。

それ以外のタッチポイントは、各スキルに「スキップ指示」を渡すのではなく、サブエージェントが確認要求を返してきた時点で別のレビュアーサブエージェントが仕様と照合して代理判断する。

- テスト計画承認（dev-impl-prep Step4 の人間確認）→ **dev-auto-plan-reviewer** が仕様照合で承認判断
- 動作確認（dev-impl Step5 の人間確認）→ **dev-auto-impl-reviewer** が承認判断する。ランタイムで動く成果物（CLI スクリプト・サーバ起動・バッチ等）については、仕様準拠確認に加え、レビュアー自身による安全経路でのスモーク起動の観測（実装者の自己申告に依存せず独立に実行）を承認条件に含める（静的な仕様照合だけに縮小しない）。コミットは各フェーズのサブエージェント・修正ループで実行する

## 引数

- `<issue番号>`（必須）: 開発対象のGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /dev-auto 42」と伝えて終了する

## フロー

```
/dev-auto <issue番号>
  ├── [メイン] mainブランチガード・進捗確認（issueコメントを読んで再開ポイントを判定）
  │       ↓ 再開ポイントへジャンプ
  ├── [dev-auto-spec-gen] 仕様生成（dev-requirementsのStep1〜4相当）
  │       ↓ 生成ファイル一覧とサマリーを返す
  ├── [メイン] 人間に仕様提示・合意 ← 唯一の人間タッチポイント
  │       ↓ issueに確定仕様を記録・コミット
  ├── [dev-auto-test-plan] テスト計画作成（dev-impl-prepのStep1〜3）
  │       ↓ テスト計画（箇条書き）とコードベース調査サマリーを返す
  ├── [dev-auto-plan-reviewer] テスト計画レビュー（仕様照合・承認判断）
  │       ↓ 承認 or 修正リスト（最大1回フィードバックループ。修正はdev-auto-test-planの修正モード再起動で行う）
  ├── [メイン] 承認済みテスト計画（調査サマリー同梱）をissueに記録
  ├── [dev-auto-test-impl] テスト実装（承認済みテスト計画をテストコードとして実装・コミット）
  │       ↓ テストファイル一覧を返す（`## テスト実装完了` を投稿）
  ├── [dev-auto-test-reviewer] テストセルフレビュー・修正（仕様との照合。修正発生時は修正コミット）
  │       ↓ レビュー結果と修正ファイル一覧を返す（`## テストレビュー完了` を投稿）
  ├── [dev-auto-impl] 実装・補助テスト・セルフレビュー（dev-implのStep1〜4。セルフレビュー後にコミット）
  │       ↓ 実装ファイル一覧とセルフレビュー結果を返す（`## 実装完了`・`## セルフレビュー完了` を投稿）
  ├── [dev-auto-impl-reviewer] 実装レビュー（仕様準拠確認・承認判断）
  │       ↓ 承認 or 問題リスト（最大1回再修正ループ。修正発生時はメインが修正ファイルをコミットしてから再レビュー）
  └── [メイン] 完了コメント記録・完了報告
```

## 手順

### Step 0: メイン — mainブランチガードと再開ポイントの判定

Step 0 の最初に `git branch --show-current` で現在のブランチを確認する。
結果が `main` の場合は、以下のメッセージを表示して終了する（ブランチの自動作成は行わない）:

```
main ブランチ上では /dev-auto を実行できません。
作業ブランチを作成してから再実行してください。例:
gh issue develop <issue番号> --name <ブランチ名>
```

次に `gh issue view <番号> --comments` でissueコメントを取得し、以下の表に従って再開ポイントを決定する。

| issueコメントの状態 | 再開ポイント |
|---|---|
| コメントなし（初回） | Step 1 から実行 |
| `## 確定した合意済み仕様` あり | Step 3 から実行 |
| `## 承認済みテスト計画` あり | Step 6 から実行 |
| `## テスト実装完了` あり | Step 7 から実行 |
| `## テストレビュー完了` あり | Step 8 から実行 |
| `## セルフレビュー完了` あり | Step 9 から実行 |
| `## /dev-auto 完了` あり | 完了済みと報告して終了 |

複数の行に該当する場合は、最も進んだ（表の下の）行を採用する。

再開ポイントが Step 1 以外の場合は、ユーザーに以下を伝えてから該当 Step に進む:

```
issue #<番号> の進捗を確認しました。<X> まで完了しているため、Step <N> から再開します。
```

### Step 1: dev-auto-spec-gen — 仕様生成

`subagent_type: "dev-auto-spec-gen"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: 生成・更新したファイルの一覧・各ファイルの内容サマリー・不明点一覧

### Step 2: メイン — 人間への仕様確認（唯一のタッチポイント）

dev-auto-spec-genから受け取った情報をもとに、ユーザーに提示する:

1. 不明点があった場合は最初に共有する:
   ```
   仕様生成中に以下の不明点がありましたが、issueに記録して先に進みました:
   - <不明点1>
   ```

2. 生成ファイルを一覧で提示する:
   ```
   以下のファイルを生成・更新しました。確認してフィードバックをください。
   修正したい点があれば指示してください。問題なければ「OK」と返してください。

   - <合意対象>: `<ファイルパス>`
   - ...
   ```

3. フィードバックを受けて修正する（複数回対応）。「OK」が返ってきたら:
   - 以下の形式で `gh issue comment` でissueに記録する:
     ```
     ## 確定した合意済み仕様

     ### 合意対象 → 確定ファイル
     - <合意対象>: `<ファイルパス>`
     - ...

     ### フィードバック履歴
     - <何をどう変えたか（変更がなければ「修正なし」）>
     ```
   - 生成・更新したファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）

### Step 3: dev-auto-test-plan — テスト計画作成

`subagent_type: "dev-auto-test-plan"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: テスト計画（箇条書き、カテゴリ別）・コードベース調査サマリー

### Step 4: dev-auto-plan-reviewer — テスト計画レビュー

`subagent_type: "dev-auto-plan-reviewer"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>

レビュー対象のテスト計画:
<dev-auto-test-planが返したテスト計画をそのまま貼り付ける>
```

結果を受けて:
- **「承認」**: Step 5へ進む
- **「修正が必要」**: dev-auto-test-planを修正モードで再起動する（最大1回）。コードベース調査（Explore）は再実行させない。渡すプロンプト:

  ```
  issue番号: <番号>

  レビューフィードバック:
  <dev-auto-plan-reviewerが返した修正リスト>

  前回のテスト計画:
  <前回のテスト計画>

  前回のコードベース調査サマリー:
  <前回の調査サマリー>
  ```

  修正済みテスト計画を受け取ったら、dev-auto-plan-reviewerを再起動して再レビューする
  - 2回目でも「修正が必要」: ユーザーに状況とフィードバック内容を伝えて手動確認を依頼し、終了する

### Step 5: メイン — 承認済みテスト計画をissueに記録

以下の形式で `gh issue comment` でissueに記録する（コードベース調査サマリーを末尾に同梱する）:

```
## 承認済みテスト計画

### APIテスト
- <テストケース1>
- <テストケース2>

### UIコンポーネントテスト
- <テストケース1>

### その他
- <テストケース1>

### コードベース調査サマリー
- テストフレームワーク: <名称>
- 命名規則: <規則>
- テストファイルの保存場所: <パス規則>
```

### Step 6: dev-auto-test-impl — テスト実装

`subagent_type: "dev-auto-test-impl"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

（テスト計画と調査サマリーは `## 承認済みテスト計画` コメントから取得させる）

受け取るもの: 実装したテストファイルの一覧

### Step 7: dev-auto-test-reviewer — テストのセルフレビュー・修正

dev-auto-test-implの完了を確認してから起動する。

`subagent_type: "dev-auto-test-reviewer"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: レビュー結果・修正ファイル一覧・未解消問題

修正が発生した場合の修正テストファイルのコミットと、レビュー完了後の `## テストレビュー完了` コメント（レビュー結果＋修正ファイル一覧）の投稿は、dev-auto-test-reviewer自身が行う。

dev-auto-test-reviewerが解消できなかった問題を報告した場合は、その内容をユーザーに伝えて手動対応を依頼し、終了する。

### Step 8: dev-auto-impl — 実装

dev-auto-test-reviewerの完了を確認してから起動する。

`subagent_type: "dev-auto-impl"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: 作成・変更したファイルの一覧・セルフレビュー結果・未解消問題

`## 実装完了`（実装完了時）・`## セルフレビュー完了`（セルフレビュー完了・コミット後）のコメント投稿と、セルフレビュー後のコミットは、dev-auto-impl自身が行う。

dev-auto-implがセルフレビューで解消できなかった問題を報告した場合は、その内容をユーザーに伝えて手動対応を依頼し、終了する（この場合 `## セルフレビュー完了` は投稿されない）。

### Step 9: dev-auto-impl-reviewer — 実装レビュー

`subagent_type: "dev-auto-impl-reviewer"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
実装ファイル一覧: <dev-auto-implが返したファイル一覧>
セルフレビュー結果: <dev-auto-implが返したセルフレビュー結果>
テストファイル一覧: <dev-auto-test-implが返したテストファイル一覧>
```

再開などで手元にこれらのデータがない場合は、issueコメントから取得して渡す:
- 実装ファイル一覧・セルフレビュー結果: `## 実装完了`・`## セルフレビュー完了` コメント
- テストファイル一覧: `## テスト実装完了` コメント

結果を受けて:
- **「承認」**: Step 10へ進む
- **「問題あり」**: general-purposeエージェントに問題リストを渡して修正させる（最大1回）
  - 修正後、メインが修正ファイルをコミットしてから（amend・巻き戻しは使わず必ず追加コミット。コミット規約は `.claude/rules/core.md` を参照）、dev-auto-impl-reviewerを再起動して再レビュー
  - 再度「問題あり」: ユーザーに問題リストを伝えて手動対応を依頼し、終了する

### Step 10: メイン — 完了コメント記録・完了報告

1. `gh issue comment` で以下をissueに記録する（再開判定の終端マーカー）:

   ```
   ## /dev-auto 完了
   ```

2. 以下の形式でユーザーに完了を報告する:

```
## /dev-auto 完了 (#<番号>)

### 実行したフェーズ
1. 要件定義（仕様生成 + 仕様合意）
2. テスト計画作成（レビュアーによる自動承認）
3. テスト実装・セルフレビュー（自動）
4. 実装・セルフレビュー（自動）
5. 実装レビュー（レビュアーによる自動承認）

### 成果物
- 仕様ファイル: <一覧>
- テストファイル: <一覧>
- 実装ファイル: <一覧>
- テスト計画レビュー: <承認 / 修正後承認>
- 実装レビュー: <承認 / 修正後承認>

PRを作成する場合は以下を実行してください:
/create-pr
```

## 注意事項

- 起動順序: dev-auto-test-plan → dev-auto-plan-reviewer → (メインで記録) → dev-auto-test-impl → dev-auto-test-reviewer → dev-auto-impl → dev-auto-impl-reviewer の順番で起動する（前のエージェントの完了を確認してから次を起動）
- 各エージェントはそれぞれ独立したコンテキストで動くため、issueコメントが各フェーズ間の主要な情報受け渡し手段になる
- コミットはフェーズ単位で実行する: Step 2（メイン）・Step 6（dev-auto-test-impl）・Step 7（dev-auto-test-reviewer、修正発生時）・Step 8（dev-auto-impl、セルフレビュー後）・Step 9 の修正ループ（メイン）。Step 10 ではコミットしない
- 修正時のコミットは amend・rebase・reset を使わず必ず追加コミットにする
- `## 実装完了` は Step 8 の途中状態を示すマーカーであり、再開判定表の行にはしない（再開は `## テストレビュー完了`→Step 8 / `## セルフレビュー完了`→Step 9 で判定する）
- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- issueに記録するコメントは日本語で書く
- **ツール結果の捏造に気づいたら再開運用に乗せる**（汎用ルールは `.claude/rules/core.md` の「ツール結果の捏造禁止」を参照）:
  - 捏造に気づいたら続行せず、`/clear` → `/dev-auto <番号>` を再実行 → Step 0 で issue コメントから再開ポイントを判定する
  - **再開前に汚染区間を検証する**: 汚染セッション中に投稿された issue コメント（Step 0 再開表のマーカー: `## 確定した合意済み仕様` / `## 承認済みテスト計画` / `## テスト実装完了` / `## テストレビュー完了` / `## セルフレビュー完了` / `## /dev-auto 完了`。加えて途中状態マーカー `## 実装完了`）と、その間のコミット差分が捏造情報に基づいていないかを確認する。疑わしいコメント・差分は、再開ポイント判定の根拠にする前に人間が精査し、必要なら破棄する
