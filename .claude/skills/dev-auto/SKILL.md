---
name: dev-auto
description: >
  実行可能仕様駆動開発ワークフローを自律ループで実行するオーケストレーター。
  「/dev-auto <issue番号>」で呼び出す。issue番号は必須引数。

  人間のタッチポイントは要件定義フェーズの仕様合意1回のみ。各フェーズをサブエージェントとして
  実行することでコンテキストの蓄積を防ぎ、フェーズ間で自律的に連鎖する。

  以下の場面で必ずこのskillを使うこと:
  - 「/dev-auto <番号>」と呼び出されたとき
  - 「issue #NNを自律的に実装して」「タッチポイント1回で進めて」と言われたとき
---

## 概要

各フェーズをサブエージェントとして実行し、コンテキストの汚染を防ぎながら自律的に開発を進める。
人間が介入するのは要件定義フェーズの仕様合意の1回のみ（加えて、ワークフロー開始時に issue へのコメント投稿許可を Step 0 で1回確認する）。

それ以外のタッチポイントは、各スキルに「スキップ指示」を渡すのではなく、サブエージェントが確認要求を返してきた時点で別のレビュアーサブエージェントが仕様と照合して代理判断する。

- テスト計画承認（dev-impl-prep Step4 の人間確認）→ **dev-auto-plan-reviewer** が仕様照合で承認判断
- 動作確認（dev-impl Step5 の人間確認）→ **dev-auto-impl-reviewer** が承認判断する。ランタイムで動く成果物（CLI スクリプト・サーバ起動・バッチ等）については、仕様準拠確認に加え、レビュアー自身による安全経路でのスモーク起動の観測（実装者の自己申告に依存せず独立に実行）を承認条件に含める（静的な仕様照合だけに縮小しない）。加えて、テストスイートの全通過・ビルド・型チェック・フォーマットチェックをレビュアー自身が独立に実行することも承認条件に含める（適用範囲外のツールは対象ツールの設定範囲を判断根拠に「適用範囲外」と扱い、それ自体は問題としない）。コミットは各フェーズのサブエージェント・修正ループで実行する

## 引数

- `<issue番号>`（必須）: 開発対象のGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /dev-auto 42」と伝えて終了する

## フロー

```
/dev-auto <issue番号>
  ├── [メイン] mainブランチガード・進捗確認（issueコメントを読んで再開ポイントを判定）
  │       ↓ 再開ポイントへジャンプ
  ├── [dev-auto-spec-gen] 仕様生成（dev-requirementsのStep1〜4相当）
  │       ↓ 生成ファイル一覧とサマリーを返す
  ├── [メイン] 人間に仕様提示・合意 ← 唯一の人間タッチポイント
  │       ↓ issueに確定仕様を記録・コミット
  ├── [dev-auto-test-plan] テスト計画作成（dev-impl-prepのStep1〜3）
  │       ↓ テスト計画（箇条書き）とコードベース調査サマリーを返す
  ├── [dev-auto-plan-reviewer] テスト計画レビュー（仕様照合・承認判断）
  │       ↓ 承認 or 修正リスト（最大1回フィードバックループ。修正はdev-auto-test-planの修正モード再起動で行う）
  ├── [メイン] 承認済みテスト計画（調査サマリー同梱）をissueに記録
  ├── [dev-auto-test-impl] テスト実装（承認済みテスト計画をテストコードとして実装・コミット）
  │       ↓ テストファイル一覧を返す（`## テスト実装完了` を投稿）
  ├── [dev-auto-test-reviewer] テストセルフレビュー・修正（仕様との照合。修正発生時は修正コミット）
  │       ↓ レビュー結果と修正ファイル一覧を返す（`## テストレビュー完了` を投稿）
  ├── [dev-auto-impl] 実装・補助テスト・セルフレビュー（dev-implのStep1〜4。セルフレビュー後にコミット）
  │       ↓ 実装ファイル一覧とセルフレビュー結果を返す（`## 実装ノート`（逸脱時）・`## 実装完了`・`## セルフレビュー完了` を投稿。未解消問題をメインが実測してテストファイル側の不備と判定した場合は Step 7 に戻り再実行 → 本 Step を再実行。最大1回）
  ├── [dev-auto-impl-reviewer] 実装レビュー（仕様準拠確認・承認判断）
  │       ↓ 承認 or 問題リスト（最大1回再修正ループ。修正発生時はメインが修正ファイルをコミットしてから再レビュー）
  └── [メイン] PR 作成・完了コメント記録（push / PR の状態・ふりかえり同梱）・完了報告・改善issue起票確認
```

## 手順

### Step 0: メイン — mainブランチガード・コメント投稿許可・再開ポイントの判定

> **集約先ファイルとの対応関係**: 本 Step 0 の「main ブランチガード / 開始時ガード（ブランチ突合・未コミット差分確認）/ コメント投稿許可」は、`refactor-auto`・`bugfix-auto` の Step 0 と共通のロジックとして `.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」に集約されている。この共通部分を変更する場合は集約先ファイルのその節を更新すること（3スキルに自動的に反映される）。スキル固有の差分（コマンド名・再開表の内容・再開ポイントのステップ番号）は本ファイルに残す。

`.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」を Read し、`<コマンド名>` を `/dev-auto`、`<進捗コメント項目一覧（説明文）>` を `確定仕様・承認済みテスト計画・各フェーズの完了マーカー等`、`<進捗コメント項目一覧（確認文言）>` を `確定仕様・承認済みテスト計画・各フェーズの完了マーカー等` に置き換えて、その内容のとおりに実行する。同ファイルを Read できない、または該当節が見つからない場合は、開始時ガードとコメント投稿許可を省略して先へ進まず、その旨をユーザーに伝えて終了する。

続いて `gh issue view <番号> --json comments` でissueコメントを取得し、以下の表に従って再開ポイントを決定する（`--comments` は auto mode の環境で空出力になる既知事象があり、空出力を「コメントなし（初回）」と誤判定して完了済み issue をやり直してしまうため使わない。子は auto mode で起動されるので必ず該当する）。

| issueコメントの状態 | 再開ポイント |
|---|---|
| コメントなし（初回） | Step 1 から実行 |
| `## 合意対象判定` あり（`## 確定した合意済み仕様` 未投稿で中断した場合） | 「合意対象 → 成果物」のファイル実在を確認し、生成済みなら提示して Step 2（仕様合意）、未生成なら Step 1（dev-auto-spec-gen）を再実行 |
| `## 確定した合意済み仕様` あり | Step 3 から実行 |
| `## 承認済みテスト計画` あり | Step 6 から実行 |
| `## テスト実装完了` あり | Step 7 から実行 |
| `## テストレビュー完了` あり | Step 8 から実行 |
| `## セルフレビュー完了` あり | Step 9 から実行 |
| `## /dev-auto — 自動修正できませんでした` あり | 記録された「打ち切ったステップ」から再開（手動修正後の再実行を想定し、レビュー・修正ループの回数はリセットする） |
| `## /dev-auto 完了` あり（`### push / PR` に `push: 未` または `PR: 未作成` と記録されている） | Step 10 から再開する（実装は完了しているため前段のフェーズは再実行しない） |
| `## /dev-auto 完了` あり（`### push / PR` が push 済み・PR 作成済み） | 完了済みと報告して終了 |

複数の行に該当する場合は、最も進んだ（表の下の）行を採用する。

`## /dev-auto 完了` に `### push / PR` の節が無い場合（この節を導入する前の実行）は、push と PR の状態をコメントから読み取れないため実状態で判定する。`gh pr list --head <ブランチ名> --state all --json number,url` で PR の実在を確認し、PR があれば完了済みと報告して終了、無ければ Step 10 から再開する。

Step 10 から再開する場合は、既存の `## /dev-auto 完了` コメントの `### スキルふりかえり` の内容をそのまま引き継いで再投稿する（再開したセッションではふりかえりの元になった経緯を持っていないため、書き直さない）。

例外: `## セルフレビュー完了` と `## テストレビュー完了` が併存し、`createdAt` で `## テストレビュー完了` の方が新しい場合は Step 8 から再開する（Step 8 の「テストファイル側の不備」分岐がコミット済みケースで Step 7 を再起動した途中で中断した状態であり、Step 8 の再実行が未了のため。詳細は Step 8 参照）。

`## 合意対象判定` で再開する場合は、まずそのコメントの「合意対象 → 成果物」に列挙されたファイルの実在・内容を確認する（`## 合意対象判定` コメント投稿直後・成果物ファイル生成前に中断したセッションでは、列挙されたファイルが基底状態のまま＝未生成の場合がある）。

- 列挙されたファイルがすべて生成済みの場合: そのファイルを提示し、Step 2 の仕様合意から再開する（Step 1 の仕様再生成は行わない）
- 一部でも未生成（基底状態のまま）の場合: Step 1（dev-auto-spec-gen）を再実行して実際に生成し直してから Step 2 に進む

再開ポイントが Step 1 以外の場合は、ユーザーに以下を伝えてから該当 Step に進む:

```
issue #<番号> の進捗を確認しました。<X> まで完了しているため、Step <N> から再開します。
```

### Step 1: dev-auto-spec-gen — 仕様生成

`subagent_type: "dev-auto-spec-gen"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: 生成・更新したファイルの一覧（API の追加・変更がある場合は API 契約＝`docs/specs/openapi.yaml`（既定）／コードファーストのスタックではスキーマ定義＋ルートのスタブ定義を含む）・各ファイルの内容サマリー・不明点一覧・フォーマッタ/lint/型チェックの残存エラーがあった場合はその判定と裏取りの結果（既存事象と判定した根拠・自フェーズと判定して修正した内容・「裏取り不能」の有無・自フェーズの生成物でない差分の申し送り）・「要件定義フェーズ完結ケース」に該当すると判定した合意対象の一覧（速報。Step 2 で判定し直す）

### Step 2: メイン — 人間への仕様確認（唯一のタッチポイント）

dev-auto-spec-genから受け取った情報をもとに、ユーザーに提示する:

1. 不明点があった場合は最初に共有する。設計への影響度が高い順（高 → 中 → 低）に並べ、
   各不明点へ影響度ラベル・選択肢・推奨案（一言理由）を添える（spec-gen が返した構造を
   そのまま提示する。件数のハード上限は設けず簡潔に）:
   ```
   仕様生成中に以下の不明点がありました（issueに記録済み。設計への影響度が高い順）。
   確認いただけると仕様の確度が上がります:

   1. [影響度: 高] <不明点>
      - 選択肢: A) <案A> / B) <案B>
      - 推奨: A（<一言理由>）
   2. [影響度: 中] <不明点>
      - 選択肢: A) <案A> / B) <案B>
      - 推奨: B（<一言理由>）
   ```

2. 生成ファイルを一覧で提示する（API の形状については、確認対象は API 契約の diff である。既定は `openapi.yaml`、コードファーストの場合は「スキーマ定義＋ルートスタブの diff」〈コード〉。`dev-requirements` スキルの「API 契約の形式」参照）:
   ```
   以下のファイルを生成・更新しました。確認してフィードバックをください。
   修正したい点があれば指示してください。問題なければ「OK」と返してください。

   - <合意対象>: `<ファイルパス>`
   - ...

   要件定義フェーズ完結ケース（実装フェーズで本番コードを追加変更しない前提で後続フェーズを進める合意対象。速報）:
   - <合意対象>（該当がなければ「なし」）
   ```

3. フィードバックを受けて修正する（複数回対応）。**フィードバックが挙動・可視範囲（誰に何を見せるか等）・データ形状に関わる変更を含む場合**、修正対象ファイルを直すだけで終わらせず、横断インデックス3種（`docs/specs/screen-list.md` / `docs/specs/api-list.md` / `docs/specs/screen-transition.md`）に同じ内容を記載した記述がないか `git grep` 等で洗い出し、記述の整合を確認・修正してから次に進む（例:「自分の投稿を含めない → 含める」のような可視範囲の変更を1ファイルにのみ反映すると、同じ挙動を記載した別インデックスの記述が古いまま残り、確定仕様の内部矛盾が実装レビューまで持ち越される）。

   dev-auto-spec-gen が返した「要件定義フェーズ完結ケース」の判定（該当合意対象一覧）は Step 1 時点の速報であり、そのまま機械的に転記せず、ユーザーが「OK」を返した時点の最終的な合意成果物を基準に、合意対象ごとに判定し直す（Step 2 のフィードバックループで成果物〈本番コード〉が変更され、実装フェーズに追加の本番コード変更が残る状態に変わることがあるため。該当するのは、その合意対象に対応する本番コードの変更が要件定義フェーズのコミット〈本 Step 末尾でコミットする成果物〉で完結しており、実装フェーズで追加する本番コード変更が残っていない場合に限る。「機能要件を伴うページの Container 配線方針」(a) に該当する合意対象は対象外）。spec-gen の判定一覧が手元にない場合（`## 合意対象判定` から Step 2 に再開した場合など）も、同じ基準で合意対象ごとに判定する。再判定の結果が 2. で提示した速報と異なる場合は、記録の前にその差分をユーザーに提示して確認を得る（該当合意対象は実装フェーズで本番コードを追加変更しない前提で後続フェーズが進むため、人間の合意を経ずに記録しない）。

   「OK」が返ってきたら:
   - 以下の形式で `gh issue comment` でissueに記録する:
     ```
     ## 確定した合意済み仕様

     ### 合意対象 → 確定ファイル
     - <合意対象>: `<ファイルパス>`
     - ...

     ### フィードバック履歴
     - <何をどう変えたか（変更がなければ「修正なし」）>
     ```
     上記の再判定で「要件定義フェーズ完結ケース」に該当すると判定した合意対象がある場合、その行に `（要件定義フェーズで本番コードの変更まで完結。実装フェーズでの追加の本番コード変更なし）` を付記する。
   - 生成・更新したファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）

### Step 3: dev-auto-test-plan — テスト計画作成

`subagent_type: "dev-auto-test-plan"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>
```

受け取るもの: テスト計画（箇条書き、カテゴリ別）・コードベース調査サマリー

### Step 4: dev-auto-plan-reviewer — テスト計画レビュー

`subagent_type: "dev-auto-plan-reviewer"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>

レビュー対象のテスト計画:
<dev-auto-test-planが返したテスト計画をそのまま貼り付ける>
```

結果を受けて（**判定の確定は「レビュアー判定の確定手順（Step 4 / Step 9 共通）」に従う**）:
- **`判定: 承認`**: Step 5へ進む
- **`判定: 修正が必要`**: dev-auto-test-planを修正モードで再起動する（最大1回）。コードベース調査（Explore）は再実行させない。渡すプロンプト:

  ```
  issue番号: <番号>

  レビューフィードバック:
  <dev-auto-plan-reviewerが返した修正リスト>

  前回のテスト計画:
  <前回のテスト計画>

  前回のコードベース調査サマリー:
  <前回の調査サマリー>
  ```

  修正済みテスト計画を受け取ったら、dev-auto-plan-reviewerを再起動して再レビューする
  - 2回目でも `判定: 修正が必要`: 失敗マーカー（`## /dev-auto — 自動修正できませんでした`。下記「自動修正の打ち切りマーカー」参照。打ち切ったステップ: Step 4、試行履歴: 1回目/2回目のレビューフィードバック）を投稿してから、ユーザーに状況とフィードバック内容を伝えて手動確認を依頼し、終了する

### Step 5: メイン — 承認済みテスト計画をissueに記録

以下の形式で `gh issue comment` でissueに記録する（コードベース調査サマリーを末尾に同梱する）:

```
## 承認済みテスト計画

### APIテスト
- <テストケース1>
- <テストケース2>

### UIコンポーネントテスト
- <テストケース1>

### その他
- <テストケース1>

### コードベース調査サマリー
- テストフレームワーク: <名称>
- 命名規則: <規則>
- テストファイルの保存場所: <パス規則>

### レビュー履歴
- <承認 / 1回修正後承認>
```

（`### レビュー履歴` は Step 4 のテスト計画レビュー結果を記録する。このループは完了マーカー `## 承認済みテスト計画` の内側で完結するため、中断時は `## 確定した合意済み仕様` から Step 3 に戻ってテスト計画を再生成し、回数は自然に 0 から再開する（意図的リセット。下記「自動修正の打ち切りマーカー」直後の注記を参照）。）

### Step 6: dev-auto-test-impl — テスト実装

`subagent_type: "dev-auto-test-impl"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>

（参考）作業ツリーに 0 バイトの未追跡ファイルが複数、ほぼ同時刻に存在し、かつそのファイル名が
サンドボックスの書き込み禁止パス相当のシステム/設定パス（例: `.bashrc`・`.gitconfig`・`.mcp.json`・
`.vscode`・`.claude/hooks`・`.git/config.lock` など。限定列挙ではない）である場合、それらは
サンドボックスがマウント/保護のために生成したものであり、今回のタスクの成果物とは無関係です。
ステージ・削除の対象にしたり、未解消の問題として報告したり、作業ツリーが clean かどうかの判定
（ミューテーション検証後の復元確認を含む）に含めたりしないでください。一方、`src/`・`docs/` 配下
などタスクの成果物になりうるパスのファイルは、0 バイトであってもこの除外の対象にせず、従来どおり
扱ってください（自分が作成したはずのファイルが空になっている場合は必ず報告してください）。
```

（テスト計画と調査サマリーは `## 承認済みテスト計画` コメントから取得させる）

受け取るもの: 実装したテストファイルの一覧

### Step 7: dev-auto-test-reviewer — テストのセルフレビュー・修正

起動前に、dev-auto-test-impl の成果物を「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」に従って裏取りする（`## テスト実装完了` マーカーの実在と、報告されたコミットの実在・内容を確認する）。不一致を検知した場合は Step 6（dev-auto-test-impl）を同一セッション内で再実行してから、本 Step に進む。

`subagent_type: "dev-auto-test-reviewer"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>

（参考）作業ツリーに 0 バイトの未追跡ファイルが複数、ほぼ同時刻に存在し、かつそのファイル名が
サンドボックスの書き込み禁止パス相当のシステム/設定パス（例: `.bashrc`・`.gitconfig`・`.mcp.json`・
`.vscode`・`.claude/hooks`・`.git/config.lock` など。限定列挙ではない）である場合、それらは
サンドボックスがマウント/保護のために生成したものであり、今回のタスクの成果物とは無関係です。
ステージ・削除の対象にしたり、未解消の問題として報告したり、作業ツリーが clean かどうかの判定
（ミューテーション検証後の復元確認を含む）に含めたりしないでください。一方、`src/`・`docs/` 配下
などタスクの成果物になりうるパスのファイルは、0 バイトであってもこの除外の対象にせず、従来どおり
扱ってください（自分が作成したはずのファイルが空になっている場合は必ず報告してください）。
```

受け取るもの: レビュー結果・修正ファイル一覧・未解消問題・修正回数（判定導出には使わない補助情報）

修正が発生した場合の修正テストファイルのコミットと、レビュー完了後の `## テストレビュー完了` コメント（レビュー結果＋修正ファイル一覧）の投稿は、dev-auto-test-reviewer自身が行う。

判定の確定は「Step 7 判定の確定手順」に従う。確定した判定が `判定: 問題あり`（未解消の問題が残っている場合。2回修正しても未解消のケースに限らない）の場合は、失敗マーカー（`## /dev-auto — 自動修正できませんでした`。下記「自動修正の打ち切りマーカー」参照。打ち切ったステップ: Step 7、試行履歴: reviewer の修正試行）を投稿してから、その内容をユーザーに伝えて手動対応を依頼し、終了する。

返答に `## 参考指摘`（判定に影響しない指摘）が含まれる場合、その内容は修正ループに渡さない（確定した判定が `判定: 問題なし` なら、参考指摘の有無にかかわらず「Step 7 判定の確定手順」6. に従って先へ進む）。内容は保持し、Step 10 の完了コメントの `### スキルふりかえり` に転記する。

### Step 7 判定の確定手順

dev-auto-test-reviewer の返答から判定を確定する際は、以下の手順に従う（Step 8 の再修正分岐（「3. Step 7の結果で分岐する」）で Step 7 を再起動した場合も同じ手順を適用する）。

「レビュアー判定の確定手順（Step 4 / Step 9 共通）」は流用しない（同節は判定値を `判定: 承認` / `判定: 修正が必要` / `判定: 問題あり` と定義しており Step 7 の2値 `判定: 問題なし` / `判定: 問題あり` と一致しないうえ、単一・妥当な値の判定行を本文と突き合わせずに採用するため、判定行が返答本文や実際のコメント内容と食い違うケースを検知できない）。

1. **判定行の走査**: 返答全体から `判定:` で始まる行をすべて抽出する。
2. **`## テストレビュー完了` コメントの特定**: 今回の起動（Step 8 経由の再起動を含む）で dev-auto-test-reviewer を起動した後に投稿された `## テストレビュー完了` のうち、`createdAt` が最も新しい1件を対象とする（「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」3. と同じ考え方）。特定できない場合は、下記3.〜5.（妥当性確認・整合確認・独立検証）には進まず、同節に従って dev-auto-test-reviewer を同一セッション内で即時再実行する。再実行時は直前の起動と同じプロンプトを渡す（Step 8 の再修正分岐経由の起動であれば、同分岐 2. の「作業ツリーの前提」を含むプロンプトを使い、通常の Step 7 のプロンプトに差し替えない）。
3. **判定行の妥当性確認**: 以下のいずれかに該当する場合は、4.（整合確認）を行わず 5.（独立検証）へ進む:
   - 判定行が1件も見つからない、または定義された値（`判定: 問題なし` / `判定: 問題あり`）以外の不正な文字列である
   - 判定行が複数件あり、値が矛盾している
4. **未解消問題の有無との整合確認（主基準）**: 判定行の値（複数件ある場合は一致した値）を、返答本文の未解消の問題の記載と、2. で特定したコメントの `### レビュー結果` の記載の両方と突き合わせる。以下のいずれかに該当すれば矛盾として 5. へ進み、該当しなければその値で判定を確定する:
   - `判定: 問題あり` なのに、返答本文にもコメントにも未解消の問題の記載が無い
   - `判定: 問題なし` なのに、返答本文またはコメントに未解消の問題が列挙されている
   - `### 修正回数` は補助情報として参照してよいが、単独では矛盾の根拠にしない（`dev-auto-test-reviewer.md` の観点6・7により、観点7で修正ループに投入しなかったため修正回数が 0/2・1/2 のままの `判定: 問題あり` や、`### レビュー結果` に本ワークフロー対象外の red の記載がある `判定: 問題なし` は正当なケースであり、修正回数だけを基準にすると誤検知する）
5. **矛盾・判定不能時の独立検証**: 3. または 4. から進んだ場合、dev-auto-test-reviewer の文面上の結論をそのまま分岐根拠にせず、**オーケストレーター自身が独立検証を行って判定を確定する**。
   - 独立検証は、`.claude/agents/dev-auto-test-reviewer.md` のレビュー観点1〜7を、オーケストレーター自身がコード・テスト・issue の実際のコメント内容に照らして再確認する形で行う（レビュアーの文面上の結論そのものは根拠にしない）
   - コマンドは allowlist（`.claude/settings.json` の `permissions.allow`）の範囲で実行する。観点6 のコマンド（`docs/specs/technical-environment.md` の `## 実行コマンド` の「型チェック」「CI 相当チェック」）のうち allowlist 内のものは実行する。allowlist 外のものは実行せず、Step 8「1. 実測」の CI 相当チェック失敗の場合と同じ手順（allowlist 内で実行できる lint 系コマンド → 原因ファイルの静的確認 → それでも判断が付かない場合に限り `## テストレビュー完了` に記録された実行結果を代替根拠にする）で代替し、代替根拠を用いた事実は 7. の記録に残す
   - Step 8 の再修正分岐経由の起動では、同分岐 2. のプロンプトに書いた「作業ツリーの前提」を独立検証にも適用する（観点4 は適用しない。観点5 のミューテーション検証で壊した実装の復元先は HEAD ではなく検証開始時点の作業ツリーの内容とし、未コミットの実装差分を破棄しない）
6. **確定後の分岐**:
   - `判定: 問題あり` で確定した場合: dev-auto-test-reviewer 内部の修正試行回数（`### 修正回数`）にかかわらず、上記の失敗マーカー分岐に一本化する（外側からの差し戻しは新設しない）
   - `判定: 問題なし` で確定した場合: 通常の Step 7 起動からであれば Step 8 へ進む。Step 8 の再修正分岐（「3. Step 7の結果で分岐する」）経由の再起動であれば、同分岐の該当ケース（修正コミットが発生した／発生しなかった）へ進む
7. **記録**: 独立検証で判定を確定した場合は、その旨と根拠（何を検証してどう判断したか）を記録する。`判定: 問題あり` で失敗マーカーを投稿する場合は同マーカーの `### 試行履歴` に記録する。`判定: 問題なし` で先へ進む場合は内容を保持し、以降で最初に投稿する終端マーカー（Step 10 完了コメントの `### スキルふりかえり`、または途中の Step で打ち切る場合は失敗マーカーの `### 試行履歴`）に記録する。

### Step 8: dev-auto-impl — 実装

起動前に、dev-auto-test-reviewer の成果物を「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」に従って裏取りする（`## テストレビュー完了` マーカーの実在と、修正が発生した場合はその修正コミットの実在・内容を確認する）。不一致を検知した場合は Step 7（dev-auto-test-reviewer）を同一セッション内で再実行してから、本 Step に進む。

`subagent_type: "dev-auto-impl"` でエージェントを起動する。渡すプロンプト:

```
issue番号: <番号>

（参考）作業ツリーに 0 バイトの未追跡ファイルが複数、ほぼ同時刻に存在し、かつそのファイル名が
サンドボックスの書き込み禁止パス相当のシステム/設定パス（例: `.bashrc`・`.gitconfig`・`.mcp.json`・
`.vscode`・`.claude/hooks`・`.git/config.lock` など。限定列挙ではない）である場合、それらは
サンドボックスがマウント/保護のために生成したものであり、今回のタスクの成果物とは無関係です。
ステージ・削除の対象にしたり、未解消の問題として報告したり、作業ツリーが clean かどうかの判定
（ミューテーション検証後の復元確認を含む）に含めたりしないでください。一方、`src/`・`docs/` 配下
などタスクの成果物になりうるパスのファイルは、0 バイトであってもこの除外の対象にせず、従来どおり
扱ってください（自分が作成したはずのファイルが空になっている場合は必ず報告してください）。
```

受け取るもの: 作成・変更したファイルの一覧・セルフレビュー結果・未解消問題・テストファイル起因の red 報告（あれば）・`## 実装ノート` として投稿した逸脱の要約（あれば）・実装をコミットしたか（コミット済みならそのハッシュ）

`## 実装ノート`（逸脱時、任意件数）・`## 実装完了`（実装完了時）・`## セルフレビュー完了`（セルフレビュー完了・コミット後）のコメント投稿と、セルフレビュー後のコミットは、dev-auto-impl自身が行う。

dev-auto-implが、テスト起因で「テストを GREEN にできない」「確定した合意済み仕様」「アーキテクチャ文書」「CI 相当チェック」のいずれかを満たせない問題を、(a) セルフレビューで解消できなかった問題として報告した場合、(b) `.claude/agents/dev-auto-impl.md`「フォーマット/lint検証の範囲」節の red 報告（**テストファイルが原因の red** に限る。同節の「自分のワークフロー起因でない red」は本分岐の対象ではない）として報告した場合、(c) `## 実装ノート` による逸脱報告として報告した場合のいずれかで報告したとき、直ちに失敗マーカーを投稿せず、まず未解消問題の原因を判定する。(b)・(c) は通常コミット・`## セルフレビュー完了` の投稿まで完了している非ブロッキング経路だが、(c) は実装途中に投稿されるため (a) と同時に成立して未コミットのまま終わることもある。本分岐は実装がコミット済みか未コミットかを問わず対象にし、どちらのケースとして扱うかは報告経路ではなく下記 1. で確認した git の実状態で決める（この判定は、本 Step の冒頭で dev-auto-impl 起動前に行う「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」の裏取りとはトリガー・タイミングが異なる別処理である）。

(b)・(c) は dev-auto-impl の返答だけでは把握できないことがあるため、dev-auto-impl が終了した直後（本分岐のトリガー判定より前）に `gh issue view <番号> --json comments` を実行し、**当該フェーズ中に投稿された `## 実装ノート` の有無・内容**を確認して、返答に含まれる red 報告・逸脱報告と合わせてトリガー判定に使う（Step 9 起動前に行う Step 8 の成果物検証とは別の、それより前のタイミングでの確認である）。

1. **実測**: オーケストレーター自身が判定対象を実行・確認し、失敗内容を実測する（dev-auto-impl の自己申告に依存しない）。実行は allowlist（`.claude/settings.json` の `permissions.allow`）範囲のコマンドのみで行う（コマンドの実体は `docs/specs/technical-environment.md` の `## 実行コマンド` を参照し、そのうち allowlist 内のものだけを使う）。実測方法は判定対象ごとに書き分ける:
   - **テスト失敗の場合**: 対象テストを実行し、失敗内容を実測する。
     - 複数パッケージ構成（モノレポ等）で、ルートのテストコマンドが全パッケージに再帰実行される場合、ルートのコマンドに対象ファイルのパスを渡すとファイル名フィルタが全パッケージに転送され、**対象外のパッケージが「該当テストなし」で非ゼロ終了する**ことがある（テストランナーが該当テストなしを失敗扱いにする設定の場合）。この exit code を実装の失敗と読み違えないこと
     - したがって判定に使うのは、**対象ファイルを持つパッケージの実行結果（failed/passed 件数・失敗したテストケース名）だけ**とする。切り分けが付かない場合は引数なしでテストコマンドを実行し、全体の結果から対象テストの行を読む
   - **CI 相当チェック失敗の場合**: まず allowlist 内で完結する lint 系コマンド（`.claude/agents/dev-auto-impl.md`「フォーマット/lint検証の範囲」節が切り分け用に挙げている「フォーマットチェック」「Lint」のコマンドのうち allowlist 内で実行できるもの）を実行し、red の原因がこれで再現・特定できるか試す。dev-auto-impl が報告する「CI 相当チェック」はフォーマットや import 整列等も検証するため、lint 単体では再現しない red がありうる（**lint が green でも red を否定できない**）。再現しない場合は、報告された原因ファイルを自分で読み、報告された red の内容（import 順序・未使用 import・整形崩れなど）が実在するかを静的に確認する（`Read` は allowlist 内であり、この静的確認も実測に含める）。**allowlist 内のコマンドと上記の静的確認でも判断が付かない場合に限り**、dev-auto-impl の報告内容（実行したコマンドと出力）を実測の代替根拠とする。これは本項冒頭の「オーケストレーター自身が実測する／dev-auto-impl の自己申告に依存しない」という原則の例外であり、無条件に自己申告を採用してよいわけではない。代替根拠を用いた場合は、その事実自体（allowlist 内で完結せず自己申告を代替根拠にしたこと）を次の「判定」の記録に残す
   - **確定仕様・アーキテクチャ文書からの逸脱の場合**: テスト実行では実測できないため、`## 実装ノート` に記載された逸脱箇所と、対応する確定仕様（`## 確定した合意済み仕様` コメント）・アーキテクチャ文書（`docs/architecture/` 配下）の該当箇所を、オーケストレーター自身が読み比べて実測結果とする
2. **判定**: 実測結果と、判定対象に応じた根拠資料（テスト失敗: 対象テストファイルの記述〈モックの既定値・`beforeEach` 等のセットアップ・フィクスチャ〉と共有テスト設定〈テストランナーの共有設定ファイルのモックの自動リセット設定等〉。CI 相当チェック失敗: 原因テストファイルの import 順序・未使用 import・整形。逸脱: `## 実装ノート` の該当箇所と確定仕様・アーキテクチャ文書）を確認し、「テストファイル側の不備」か「実装側の不備／判別不能」かを判定する。「テストファイル側の不備」の定義例は判定対象ごとに異なる:
   - **テスト失敗の場合**: モックの既定値欠落・フィクスチャの不整合など、実装をどう書いても両立不可能なもの
   - **CI 相当チェック失敗の場合**: テストファイル自身の import 順序・未使用 import など、テストファイルを直さない限り CI 相当チェックの red が解消できないもの
   - **確定仕様・アーキテクチャ文書からの逸脱の場合**: テストファイルの前提（期待するレスポンス形状・呼び出し方など）が確定仕様・アーキテクチャ文書と矛盾しており、実装側をどう変更してもテストと確定仕様/アーキ文書の両方を満たせないもの

判定結果を受けて:
- **テストファイル側の不備と判定し、かつ本分岐を本セッションでまだ使っていない場合（最大1回）**: 失敗マーカーを投稿せず、以下の 1〜3 の順で進める。

  1. **実装のコミット状態を確認し、未コミット分・コミットを控える**: `git status --porcelain` を実行し、**報告経路ではなく実状態で**以下のいずれかに振り分ける（(c) の逸脱報告は実装途中に投稿されるためコミット済みとは限らず、(a) と併存して未コミットで終わることもある）。両方に該当する場合（コミット済みだが未コミットの差分も残っている場合）は両方の扱いを併用する。
     - **未コミットケース（従来どおり）**: Step 8 の実装差分が**未コミットのまま作業ツリーに残っている**場合（(a) セルフレビュー未解決報告の経路では、dev-auto-impl は未解消問題を報告した場合コミットしないため〈`.claude/agents/dev-auto-impl.md`〉、通常こちらになる）。`git status --porcelain` の一覧を控える。この差分は破棄も先行コミットもしない（Step 8 の再実行が同じ作業ツリー上で続きを行うため。「各フェーズ後の実状態検証」の不一致検知による即時再実行と同じ扱い）。
     - **コミット済みケース**: 実装が既にコミットされ `## セルフレビュー完了` の投稿まで完了している場合（(b) red 報告・(c) `## 実装ノート` の逸脱報告の経路では通常こちらになる）。dev-auto-impl が報告したコミットハッシュを `git log --oneline -1 <hash>` で実在確認してから控える（「各フェーズ後の実状態検証」1 と同じ手順。報告にハッシュがない場合は `git log --oneline -1` で HEAD を確認して控える）。このコミットは破棄・巻き戻しの対象にしない（Step 8 の再実行はこのコミットの上に続きを行う）。

  2. **Step 7（`dev-auto-test-reviewer`）を再起動する**。通常の Step 7 起動と作業ツリーの前提が異なるため、その差分をプロンプトに明記する。渡すプロンプト:

  ```
  issue番号: <番号>

  Step 8（dev-auto-impl）で、テスト起因の問題（テスト失敗 / CI 相当チェックの red /
  確定仕様・アーキテクチャ文書からの逸脱）が解消できませんでした。オーケストレーターが実測した結果、
  テストファイル側の不備（実装側では両立不可能）と判定したため、テストコードの修正をお願いします。

  実測結果:
  <実行したコマンドと結果。テスト失敗なら failed/passed件数・失敗したテストケース名。

> - **未コミットケース（現状のまま）**: この分岐を取った場合も `## セルフレビュー完了` は投稿されず、失敗した Step 8 の `## 実装完了` は issue に残ったままになる。
> - **コミット済みケース**: 本分岐が発生した時点（red 報告または `## 実装ノート` の逸脱報告の時点）で既にコミット・`## セルフレビュー完了` の投稿が完了している（2件目の扱いは上記「マーカーの2件目」参照）。そのため本分岐の途中（Step 7 の再起動後）でセッションが分断されると、issue には分岐前の `## セルフレビュー完了` と分岐中に投稿された `## テストレビュー完了` が併存する。Step 0 の再開表は行の位置で「最も進んだ行」を選ぶため素直に読むと Step 9 になるが、`createdAt` で `## テストレビュー完了` が `## セルフレビュー完了` より新しい場合は本分岐の Step 8 再実行が未了であることを意味するため、**Step 8 から再開する**（この順序のときだけ表より createdAt を優先する）。

Step 9 を起動する前に、Step 8 の成果物（`## 実装完了`・`## セルフレビュー完了` マーカーの実在と、実装コミットの実在・内容）を「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」に従って裏取りする。不一致を検知した場合は Step 8（dev-auto-impl）を同一セッション内で再実行する。

### Step 9: dev-auto-impl-reviewer — 実装レビュー

> Step 9 はコミットもマーカーコメントの投稿もメイン自身が行うため、「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」の対象ではない（サブエージェントの自己申告を裏取りする Step 6/7/8 とは性質が異なる）。直前の Step 8 の成果物は、本 Step を起動する前に同節に従って検証済みである。

`subagent_type: "dev-auto-impl-reviewer"` でエージェントを起動する。渡すプロンプト:

```

セルフレビュー結果: <dev-auto-implが返したセルフレビュー結果>
テストファイル一覧: <dev-auto-test-implが返したテストファイル一覧>
```

再開などで手元にこれらのデータがない場合は、issueコメントから取得して渡す:
- 実装ファイル一覧・セルフレビュー結果: `## 実装完了`・`## セルフレビュー完了` コメント（Step 8 が再実行されると `## 実装完了` は複数件になるため、**必ず最新の1件**を採用する）
- テストファイル一覧: `## テスト実装完了` コメント（Step 6 が再実行されると複数件になるため、**必ず最新の1件**を採用する）

Step 8 が「各フェーズ後の実状態検証」の「要件定義フェーズ完結ケース（新ケース）」（「担当範囲に両ケースが混在する場合」を含む）でコミットなしに終わった場合は、「実装ファイル一覧」に「なし」だけを渡さない。同節の「要件定義コミットの実装差分の確認手順」で特定した要件定義コミットと確定ファイルを「実装は要件定義コミット `<hash>` に含まれる: <確定ファイル一覧>」の形で渡す（実装レビュアーがレビュー対象の実装差分を特定できるようにするため）。

結果を受けて（**判定の確定は「レビュアー判定の確定手順（Step 4 / Step 9 共通）」に従う**）:
- **`判定: 承認`**: Step 10へ進む
- **`判定: 問題あり`**: general-purposeエージェントを **`model: "opus"` を明示して**起動し、以下のプロンプトで修正させる（最大1回）。opus で書かれた実装の修正を同格のモデルで行うため、セッションモデルへの暗黙の継承に任せない:

  ```

### 各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）

Step 6・7・8 のサブエージェント（dev-auto-test-impl / dev-auto-test-reviewer / dev-auto-impl）は「コミット作成」「マーカーコメント投稿」を自己申告で返す。オーケストレーター（メイン）は、これらの自己申告を鵜呑みにせず、**次フェーズを起動する前に必ず git/gh の実状態で裏取りする**。

検証は **allowlist（`.claude/settings.json` の `permissions.allow`）に登録済みのコマンドだけ** で行う（`git show`・`git cat-file` は登録しない前提のため使わない）:

1. **コミット実在**: `git log --oneline -1 <hash>`（該当コミットが無ければ unknown revision で失敗する＝捏造を検知できる）
2. **コミット内容**: `git log --oneline --stat -1 <hash>`（または `git diff <hash>~1..<hash> --stat`）で報告されたファイルが実際に含まれるかを確認し、`git status` で取りこぼし（未コミットの差分）が無いかを確認する
3. **マーカー実在**: `gh issue view <番号> --json comments` で該当する完了マーカー見出しが実在するかを確認する
   - Step 6 → `## テスト実装完了`
   - Step 7 → `## テストレビュー完了`
   - Step 8 → `## 実装完了` と `## セルフレビュー完了`
   - **再実行では同じ見出しのコメントが複数件になる**（マーカー見出しは固定文字列であり、再実行かどうかを見出しでは区別しない）。したがって「実在」は単なる有無ではなく、**当該フェーズのサブエージェントを起動した後に投稿された最新の1件があるか**で判定する（`--json comments` の `createdAt` で判別する）。過去の実行が残した同じ見出しのコメントを実在の根拠にしない

> **サンドボックス由来の空ファイルの除外**:
> - 主基準（以下の3条件をすべて満たす場合のみ除外対象とする）: (a) 0バイトである (b) 複数の未追跡ファイルがほぼ同一タイムスタンプで一括生成されている (c) ファイル名がサンドボックスの書き込み禁止パス相当のシステム/設定パスである
> - 参考例（列挙に限定しない）: `.bashrc`・`.gitconfig`・`.mcp.json`・`.vscode`・`.claude/hooks`・`.git/config.lock` など。これらは `git status` の未追跡ファイル一覧に現れるものと現れないもの（`.git/config.lock` は `.git/` 配下のため通常は現れない）が混在する参考例であり、名前の網羅的な一覧ではない
> - 3条件のいずれかを満たさない未追跡ファイルは、従来どおり取りこぼしとして扱う（既存挙動を維持）

上記のいずれかが確認できない場合（報告と実状態が不一致の場合）は、サブエージェントによる捏造とみなし、**同一セッション内で当該フェーズのサブエージェントを即時再実行する**（`/clear`・停止はしない）。再実行に伴うループ回数の管理は下記「意図的リセット」に接続する。

> **Step 8 でコミットが発生しない場合の扱い**: 確定仕様に「機能要件を伴うページの Container 配線方針」で (a)（要件定義フェーズで配線済み）が明記されているページのみが担当範囲で、追加実装が不要だった場合（`dev-auto-impl` 参照）、Step 8 では変更ファイルがなくコミットが発生しない。この場合は 1（コミット実在）と 2 のうちコミット内容の検証を省略してよいが、2 の `git status` による取りこぼし（未コミットの差分）確認は省略しない（「変更ファイルなし」の申告は、作業ツリーに Step 8 由来の未コミット差分が無いことで裏取りする）。あわせて `## 実装完了` に「作成・変更したファイル: なし（Container配線済みのため追加実装不要。検証のみ実施）」の理由が明記されていることと、3（マーカー実在: `## 実装完了` と `## セルフレビュー完了`）は通常どおり確認する。理由の記載がないままコミットが見つからない場合は、通常どおり捏造とみなして即時再実行する。Step 8 の「テストファイル側の不備」分岐の再実行でコミットが発生しない場合は、同分岐に書かれた条件（理由の記載）を満たせば、本段落と同じ範囲で検証を省略する（本段落・下記の各ケースの理由文言には該当しなくてよい）。

> **要件定義フェーズ完結ケース（新ケース）**: 確定仕様の該当合意対象の行に条件ア（`（要件定義フェーズで本番コードの変更まで完結。実装フェーズでの追加の本番コード変更なし）`）が明記されている合意対象のみが担当範囲で、実装フェーズで追加する本番コード変更が残っていなかった場合、Step 8 では変更ファイルがなくコミットが発生しない。この場合は 1（コミット実在）と 2 のうちコミット内容の検証を省略してよいが、2 の `git status` による取りこぼし（未コミットの差分）確認は省略しない（変更ファイルなしと申告しながら本番コードの差分が未コミットで残っている状態を受理しないため）。あわせて `## 実装完了` に条件イ（`作成・変更したファイル: なし（要件定義フェーズで本番コード変更完了のため追加実装不要。要件定義フェーズ完結ケース。検証のみ実施）`）の理由が明記されていることと、3（マーカー実在: `## 実装完了` と `## セルフレビュー完了`）は通常どおり確認する。さらに、条件アの付いた合意対象の確定ファイルへの実装差分が要件定義コミットに実際に含まれていることを、下記「要件定義コミットの実装差分の確認手順」で確認する（条件ア・イはいずれも記載の有無であり、実装が要件定義コミットに入っていることは git の履歴で裏取りする）。Step 8 のオーケストレーターとして、上記の条件ア・イの両方の存在と要件定義コミットの実装差分を確認したうえで最終的に受理する（最終ゲート）。理由の記載がないままコミットが見つからない場合、または要件定義コミットの実装差分を確認できない場合は、通常どおり捏造とみなして即時再実行する。

> **担当範囲に両ケースが混在する場合**: 担当範囲に (a) と要件定義フェーズ完結ケースが混在する場合、担当範囲の**すべて**の項目がそれぞれ (a) か要件定義フェーズ完結ケースのどちらかに該当するときに限り、Step 8 のコミット不発生を受理する。受理の前に、理由の内訳の各項目について、(a) 該当分は確定仕様に (a)（要件定義フェーズで配線済み）が明記されていること、要件定義フェーズ完結ケース該当分は確定仕様の該当合意対象の行に条件アが明記されていることと、下記「要件定義コミットの実装差分の確認手順」で要件定義コミットに当該確定ファイルの実装差分が含まれていることをオーケストレーター自身が確認する（確認できない項目がある場合は、理由の記載がない場合と同じく捏造とみなす）。受理する場合も 2 の `git status` による取りこぼし（未コミットの差分）確認は省略しない。この場合も `## 実装完了` の一覧行は単独ケースと同じ「作成・変更したファイル: なし（複数ケース該当のため理由の内訳を参照）」の1行のみを維持し（`dev-auto-impl` の「一覧行の形式は崩さず補足は一覧の下に書く」規定に従う）、一覧行の下に「理由の内訳:」として、(a) 該当分・要件定義フェーズ完結ケース該当分それぞれの理由を、ファイルパスを行頭の箇条書き要素にしない形式で列挙する（テンプレートは `dev-auto-impl` 参照）。担当範囲の一部でもどちらのケースにも該当しない場合は、通常どおり 1・2（コミット実在・内容）を検証する。理由の記載がないままコミットが見つからない場合は、通常どおり捏造とみなして即時再実行する。

> **要件定義コミットの実装差分の確認手順**（要件定義フェーズ完結ケース、および両ケース混在時の要件定義フェーズ完結ケース該当分で使う）: `## 確定した合意済み仕様` コメント自体にはコミットハッシュが記録されないため、本節冒頭の allowlist 制約（`git show`・`git cat-file` は使わない）に従い、次の手順で git の履歴から確認する。いずれかを満たさない場合は、要件定義コミットの実装差分を確認できないものとして扱う:
> 1. `git log --oneline origin/main..HEAD -- <確定ファイル1> <確定ファイル2> ...`（条件アの付いた合意対象の確定ファイル）で、本ブランチ上で確定ファイルを変更したコミットを特定する。範囲指定（`origin/main..HEAD`）は省略しない（省略すると main 側の過去のコミットが候補に混ざり、そのコミットは必ず確定ファイルを変更しているため、要件定義コミットが確定ファイルを変更していなくても検証が通ってしまう）。出力が空の場合は満たさない
> 2. 特定したコミットのメッセージが本 issue の番号（`#<番号>`）で始まることを確認する（`origin/main` が分岐点より古い場合に混ざる main 側のコミットを除外するため）
> 3. `git diff <hash>~1..<hash> -- <確定ファイル>` で差分の中身を読み、issue の実装要求を満たす変更であることを確認する（`--stat` はファイル名と行数しか示さず、実装差分かどうかを判定できないため、`--stat` だけで済ませない）
>
> ここで特定した要件定義コミットと確定ファイルは、Step 9 で実装レビュアーに渡す（Step 9 参照）。

> **既存の捏造対策との役割分担**:
> - **フック `.claude/detect-fabrication.mjs`**（Stop / SubagentStop で走る）は、機械的なセーフティネットであり警告を出すのみ・非ブロッキングである。本節の実状態検証は、そのフックとは別に、オーケストレーターが次フェーズ起動前に必ず実施する **必須の事前検証** として役割を分担する。
> - **core.md「ツール結果の捏造禁止」** は、**自セッションが捏造した**場合に `/clear` して停止する運用を定める。本節はこれと性質が異なり、**サブエージェントの自己申告の捏造をオーケストレーターが検知する**ケースを扱う。この場合は停止・`/clear` はせず、当該フェーズを同一セッション内で再実行する。

### 自動修正の打ち切りマーカー（Step 4 / 7 / 8 / 9 共通）

Step 4・7・8・9 で自動修正を打ち切る場合は、`gh issue comment` で以下の失敗マーカーを投稿してから、ユーザーに状況を伝えて手動対応を依頼し終了する（refactor-auto の `## /refactor-auto — 自動修正できませんでした` と対をなす）:

```
## /dev-auto — 自動修正できませんでした

<打ち切ったステップ>で以下の問題が解消できませんでした:

### 未解決の問題
<問題リスト / レビューフィードバック>

### 試行履歴
- <試行1: 実施内容 / レビュー結果>
- <試行2: 実施内容 / レビュー結果>

### 打ち切ったステップ
- Step <N>: <ステップ名>

手動での確認・修正をお願いします。
```

このマーカーは Step 0 再開表のマーカーであり、投稿後の再開では記録された「打ち切ったステップ」から再実行する（手動修正後の再実行を想定し、レビュー・修正ループの回数はリセットする）。

#### 意図的リセット

以下の場合はループ回数を意図的にリセットする（過去の試行カウンタコメントは budget 復元に使わない）:
- 失敗マーカー（`## /dev-auto — 自動修正できませんでした` / `## /refactor-auto — 自動修正できませんでした`）からの再開（手動修正後の再実行を想定）
- フェーズ再実行を伴う再開（dev-auto Step 3 からのテスト計画再生成、test-reviewer の再起動）
- 「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」の不一致検知による Step 6/7/8 の同一セッション内即時再実行
- Step 8 の未解消問題がテストファイル側の不備と判定された場合の Step 7 → Step 8 再実行（この再実行でリセットされるのは Step 6〜8 のレビュー・修正ループ回数であり、**Step 8 の当該分岐自体の「最大1回」の上限はリセット対象に含めない**）

### Step 10: メイン — PR 作成・完了コメント記録・完了報告

1. `/create-pr` skill を実行して PR を作成する（ユーザーへの確認は不要。PR を作成しただけでは既存のコードに影響が出ないため）。マージは行わない。

   PR 作成に失敗した場合は中断せず、**push の成否と PR の有無を切り分けて**控えてから 2. へ進む（実装自体は完了しているため）:
   - push: push の成否（push 後にリモートのブランチ先端がローカル HEAD と一致したか）。create-pr が push 前に中止した場合は push 未実行のため「未」
   - PR: 作成できた PR の URL、作成できなかった場合は create-pr が返したエラーの要約

2. `gh issue comment` で以下をissueに記録する（再開判定の終端マーカー。本文に push / PR の状態と「スキルふりかえり」を同梱する）:

   ```
   ## /dev-auto 完了

   ### push / PR
   - ブランチ: <ブランチ名>
   - push: <済み / 未（理由: <エラーの要約>）>
   - PR: <PR の URL / 未作成（理由: <エラーの要約>）>

   ### スキルふりかえり
   - <スキルの指示が曖昧で迷った点・レビュー→修正ループが余計に回った原因などを1〜2行で記録>
   ```

   `### push / PR` の3行は省略しない（Step 0 の再開判定がこの節を読んで、未 push・PR 未作成のまま終わった実行を Step 10 から再開するため）。push・PR が「済み」でない場合は、理由に create-pr が返したエラーの要約を必ず添える。

   ふりかえりで特に気づきが無い場合は `- なし` と記録する（`### スキルふりかえり` の見出し自体は必ず入れる）。

   レビュアーが返した `## 参考指摘` がある場合は、`- 参考指摘（<エージェント名>）: <内容>` の形でこの節に転記する。

3. 以下の形式でユーザーに完了を報告する（これはユーザーへの報告であり issue コメントではない。issue に記録する終端マーカーは 2. の `## /dev-auto 完了` であり、下の `(#<番号>)` 付き見出しをそのまま issue に投稿しない）。

   `### 残作業` は push または PR が未了の場合のみ記載する（どちらも済んでいる場合はこの節ごと省く）。未 push で終わる場合はコミットがローカルにしか無く、この報告が成果物の所在を伝える唯一の経路になるため、ブランチ名・ディレクトリのパス・人間が実行する操作を省略しない。

```
## /dev-auto 完了 (#<番号>)

### 実行したフェーズ
1. 要件定義（仕様生成 + 仕様合意）
2. テスト計画作成（レビュアーによる自動承認）
3. テスト実装・セルフレビュー（自動）
4. 実装・セルフレビュー（自動）
5. 実装レビュー（レビュアーによる自動承認）

### 成果物
- 仕様ファイル: <一覧>
- テストファイル: <一覧>
- 実装ファイル: <一覧>
- テスト計画レビュー: <承認 / 修正後承認>
- 実装レビュー: <承認 / 修正後承認>

### スキルふりかえり
- <2. で issue に記録したふりかえりと同じ内容（無い場合は「- なし」）>

### push / PR
- ブランチ: `<ブランチ名>`
- push: <済み / 未（理由: <エラーの要約>）>
- PR: <作成した PR の URL / 未作成（理由: <エラーの要約>）>

### 残作業
- worktree: `<worktree のパス>`（worktree を使っていない場合は作業ディレクトリのパス）
- 人間が実行する操作: 上記ディレクトリで `git push -u origin HEAD` を**他のコマンドと連結せず単独で**実行し、成功したら `/create-pr` で PR を作成する

<PR を作成できた場合: レビューとマージをお願いします（マージは行っていません）。
push または PR が未了の場合: 上記の残作業をお願いします（コミットはローカルにのみ存在します）。>
```

4. ふりかえりに「なし」以外の気づきがあり、スキル定義（SKILL.md・エージェント定義）の編集に値する場合は、完了報告に続けて起票の確認を行う:

   ```
   スキルふりかえりに以下の気づきがありました。スキル改善 issue として起票しますか？（はい / いいえ）
   - <気づき1>
   - <気づき2>
   ```

   ユーザーが許可した場合のみ、気づき1件につき1つの issue を作成する（1つの気づき = 1 issue）。
   起票とラベル付与は分けて実行する:

   1. `gh issue create --title "dev-auto: <気づきの要約>" --body "<本文>" --assignee @me`（`--label` は付けない）
   2. `gh issue edit <作成した issue 番号> --add-label skill-improvement`

   - issue 本文には「対象スキル」「気づきの内容と改善案」「発生した実行（元 issue #<番号>）」を含める
   - ユーザーが拒否した場合・気づきが「なし」の場合は起票せず終了する（ふりかえり自体は 2. のコメントに記録済み）
   - SKILL.md・エージェント定義をこの場で直接編集しない（スキル編集は issue → PR → 人間のマージ承認のゲートを必ず通す）

## 注意事項

- 起動順序: dev-auto-test-plan → dev-auto-plan-reviewer → (メインで記録) → dev-auto-test-impl → dev-auto-test-reviewer → dev-auto-impl → dev-auto-impl-reviewer の順番で起動する（前のエージェントの完了を確認してから次を起動する。特に Step 6/7/8 では「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」で git/gh の実状態を裏取りしてから次を起動する）
- 各エージェントはそれぞれ独立したコンテキストで動くため、issueコメントが各フェーズ間の主要な情報受け渡し手段になる
- コミットはフェーズ単位で実行する: Step 2（メイン）・Step 6（dev-auto-test-impl）・Step 7（dev-auto-test-reviewer、修正発生時）・Step 8（dev-auto-impl、セルフレビュー後）・Step 9 の修正ループ（メイン）。Step 10 ではコミットしない（PR 作成に伴う push は行う）
- 修正時のコミットは amend・rebase・reset を使わず必ず追加コミットにする
- `## 実装完了` は Step 8 の途中状態を示すマーカーであり、再開判定表の行にはしない（再開は `## テストレビュー完了`→Step 8 / `## セルフレビュー完了`→Step 9 で判定する）。`## 実装ノート` も記録専用のコメントであり、再開判定には使わない（再開判定表の行にもしない）
- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- issueに記録するコメントは日本語で書く
- **ツール結果の捏造に気づいたら再開運用に乗せる**（汎用ルールは `.claude/rules/core.md` の「ツール結果の捏造禁止」を参照）:
  - 捏造に気づいたら続行せず、`/clear` → `/dev-auto <番号>` を再実行 → Step 0 で issue コメントから再開ポイントを判定する
  - ただし**サブエージェントの自己申告の捏造をオーケストレーターが検知した**場合は、停止せず「各フェーズ後の実状態検証（Step 6 / 7 / 8 共通）」に従って当該フェーズを同一セッション内で再実行する（`/clear` はしない。自セッションが捏造した上記のケースとは分岐が異なる）
  - **再開前に汚染区間を検証する**: 汚染セッション中に投稿された issue コメント（Step 0 再開表のマーカー: `## 合意対象判定` / `## 確定した合意済み仕様` / `## 承認済みテスト計画` / `## テスト実装完了` / `## テストレビュー完了` / `## セルフレビュー完了` / `## /dev-auto — 自動修正できませんでした` / `## /dev-auto 完了`。加えて途中状態マーカー `## 実装完了` / `## 実装ノート`）と、その間のコミット差分が捏造情報に基づいていないかを確認する。疑わしいコメント・差分は、再開ポイント判定の根拠にする前に人間が精査し、必要なら破棄する
- **マーカー見出しの文字列は変更しない**: dev-auto が issue コメントとして投稿する見出しは検索用の固定文字列であり、次のすべてが対象——再開判定表の各マーカー（`## 合意対象判定` / `## 確定した合意済み仕様` / `## 承認済みテスト計画` / `## テスト実装完了` / `## テストレビュー完了` / `## セルフレビュー完了`。再開判定・汚染区間検証・情報受け渡しで検索する）、終端マーカー（`## /dev-auto 完了`）、失敗マーカー（`## /dev-auto — 自動修正できませんでした`）、途中状態マーカー（`## 実装完了` / `## 実装ノート`。再開判定表には加えず、汚染区間検証・情報受け渡しで検索する）、試行カウンタマーカー（`## 実装修正試行 <N>/1`。`<N>` 以外の文字列は固定。再開判定表には加えず、試行回数カウントに使う）。
  - 判定・検索はいずれも**見出し行の有無**で行うため、本文に節を足しても判定は壊れない（終端マーカーコメントに `### スキルふりかえり` を同梱できるのはこのため）
  - 今回が再実行・修正であることを示したい場合も見出しには手を加えず、本文の**既定セクション内**に書く（例: 見出しはそのまま `## テストレビュー完了` とし、`### レビュー結果` に「Step 7 再実行」と記載する）。テンプレートに `###` セクションがないマーカー（`## 実装完了` 等）は、パースされる一覧行の形式を崩さないよう一覧の下に書く。テンプレートにない `###` セクションを新設しない
  - 再実行では**同じ見出しのコメントが複数件**になる（見出しでは再実行かどうかを区別しないため）。参照・検証はつねに**最新の1件**を採用する
- ふりかえりコメントの投稿は Step 0 で得たコメント投稿許可の範囲内で行う（追加の許可フローは設けない）。一方、スキル改善 issue の起票はこの許可の範囲外のため、必ず完了報告時にユーザーの許可（はい）を得てから実行する。自動起票はしない
- `skill-improvement` ラベルはリポジトリに作成済みであることを前提とする（存在せず `gh issue edit --add-label` がエラーになった場合は、エラーをそのままユーザーに伝える）
- **実行モデルはエージェント定義と Agent 呼び出しで決まる（skill frontmatter に `model:` は置かない）**:
  skill frontmatter の `model:` は公式仕様上「起動したターンの残りにだけ適用され、次のプロンプトでセッションモデルに戻る」。
  /dev-auto は Step 0 のコメント投稿許可でユーザーの応答を待つため、最初のターンはそこで切れる。
  つまり frontmatter に `model:` を書いても効くのは Step 0 の同意プロンプトを出すまでで、Step 1 以降の
  オーケストレーターはセッションモデルで動く。「この skill は sonnet で走っている」という誤解を生むだけなので、
  この skill の frontmatter には `model:` を置かない。各フェーズの実行モデルはこれに影響されない——
  サブエージェントは `.claude/agents/*.md` の `model:`（spec-gen・test-plan・plan-reviewer・test-impl・test-reviewer = sonnet、
  impl・impl-reviewer = opus）、Step 9 の修正エージェントは Agent 呼び出しの `model` 引数で明示的に決まるため。
  オーケストレーター自身のモデルを固定したい場合は、セッション側（`/model`・`claude --model`）で指定する
