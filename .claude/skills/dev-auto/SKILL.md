---
name: dev-auto
description: >
  実行可能仕様駆動開発ワークフローを自律ループで実行するオーケストレーター。
  「/dev-auto <issue番号>」で呼び出す。issue番号は必須引数。

  人間のタッチポイントは要件定義フェーズの仕様合意1回のみ。各フェーズをサブエージェントとして
  実行することでコンテキストの蓄積を防ぎ、フェーズ間で自律的に連鎖する。

  以下の場面で必ずこのskillを使うこと:
  - 「/dev-auto <番号>」と呼び出されたとき
  - 「issue #NNを自律的に実装して」「タッチポイント1回で進めて」と言われたとき
model: sonnet
---

## 概要

各フェーズをサブエージェントとして実行し、コンテキストの汚染を防ぎながら自律的に開発を進める。
人間が介入するのは要件定義フェーズの仕様合意の1回のみ。

それ以外のタッチポイントは、各スキルに「スキップ指示」を渡すのではなく、サブエージェントが確認要求を返してきた時点で別のレビュアーサブエージェントが仕様と照合して代理判断する。

- テスト計画承認（dev-impl-prep Step4 の人間確認）→ **subagent E** が仕様照合で承認判断
- 動作確認（dev-impl Step5 の人間確認）→ **subagent F** が仕様準拠確認で承認判断し、コミットはメインが実行

## 引数

- `<issue番号>`（必須）: 開発対象のGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /dev-auto 42」と伝えて終了する

## フロー

```
/dev-auto <issue番号>
  ├── [subagent A] 仕様生成（dev-requirementsのStep1〜4相当）
  │       ↓ 生成ファイル一覧とサマリーを返す
  ├── [メイン] 人間に仕様提示・合意 ← 唯一の人間タッチポイント
  │       ↓ issueに確定仕様を記録・コミット
  ├── [subagent B] テスト計画作成（dev-impl-prepのStep1〜3）
  │       ↓ テスト計画（箇条書き）とコードベース調査サマリーを返す
  ├── [subagent E] テスト計画レビュー（仕様照合・承認判断）
  │       ↓ 承認 or 修正リスト（最大1回フィードバックループ）
  ├── [メイン] 承認済みテスト計画をissueに記録
  ├── [subagent B2] テスト実装（dev-impl-prepのStep5相当）
  │       ↓ テストファイル一覧を返す
  ├── [subagent D] テストセルフレビュー・修正（仕様との照合）
  │       ↓ レビュー結果と修正ファイル一覧を返す
  ├── [subagent C] 実装・補助テスト・セルフレビュー（dev-implのStep1〜4）
  │       ↓ 実装ファイル一覧とセルフレビュー結果を返す
  ├── [subagent F] 実装レビュー（仕様準拠確認・承認判断）
  │       ↓ 承認 or 問題リスト（最大1回再修正ループ）
  └── [メイン] コミット・完了報告
```

## 手順

### Step 1: subagent A — 仕様生成

general-purposeエージェントに以下を指示して起動する:

```
あなたは実行可能仕様駆動開発の「要件定義フェーズ（仕様生成）」を担当します。
ワークフロー定義: `docs/workflow/executable-spec-driven-workflow.md`
詳細手順: `.claude/skills/dev-requirements/SKILL.md`

issue番号: <番号>

**実行する手順（SKILL.mdのStep1〜4に対応）:**

Step1 — Issue確認:
- `gh issue view <番号>` でissue内容を確認する
- 不明点がある場合は以下の形式で `gh issue comment` に記録する（人間への確認は行わず記録だけして先に進む）:
  ## 不明点の記録（自律実行のため確認省略）
  - <不明点1>
  - <不明点2>

Step2 — コードベース調査（Exploreエージェントを使う）:
- `docs/specs/` 配下の現状
- `docs/architecture/` のアーキテクチャ定義
- issueに関連する既存コードのパターン
- バックエンドフレームワーク

Step3 — 合意対象の判定と仕様生成:
- SKILL.mdのStep3-aに従い合意対象を判定する
- 判定結果を `gh issue comment` に「合意対象判定（合意前の判定速報）」として記録する
- SKILL.mdのStep3-bに従い仕様ファイルを生成・保存する（実装コードは書かない）

Step4 — 横断インデックスの更新:
- SKILL.mdのStep4に従い `docs/specs/screen-list.md`, `er-diagram.md`, `api-list.md` を更新する

**返すもの（親に渡す情報）:**
- 生成・更新したファイルの一覧（合意対象ごとにファイルパスを明示）
- 各ファイルの内容サマリー（人間が確認しやすい形で）
- 不明点があればその一覧

**実行しないこと:**
- 人間への確認・合意（SKILL.mdのStep5）は行わない
- `## 確定した合意済み仕様` のissueコメントは書かない（親が書く）
```

### Step 2: メイン — 人間への仕様確認（唯一のタッチポイント）

subagent Aから受け取った情報をもとに、ユーザーに提示する:

1. 不明点があった場合は最初に共有する:
   ```
   仕様生成中に以下の不明点がありましたが、issueに記録して先に進みました:
   - <不明点1>
   ```

2. 生成ファイルを一覧で提示する:
   ```
   以下のファイルを生成・更新しました。確認してフィードバックをください。
   修正したい点があれば指示してください。問題なければ「OK」と返してください。

   - <合意対象>: `<ファイルパス>`
   - ...
   ```

3. フィードバックを受けて修正する（複数回対応）。「OK」が返ってきたら:
   - 以下の形式で `gh issue comment` でissueに記録する:
     ```
     ## 確定した合意済み仕様

     ### 合意対象 → 確定ファイル
     - <合意対象>: `<ファイルパス>`
     - ...

     ### フィードバック履歴
     - <何をどう変えたか（変更がなければ「修正なし」）>
     ```
   - 生成・更新したファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）

### Step 3: subagent B — テスト計画作成

general-purposeエージェントに以下を指示して起動する:

```
あなたは実行可能仕様駆動開発の「テスト計画作成」を担当します。

issue番号: <番号>

以下を順番に実行してください:

Step1 — Issue確認:
- `gh issue view <番号> --comments` でissueの内容とコメントを取得する
- `## 確定した合意済み仕様` コメントを確認し、確定ファイル一覧を把握する
- `docs/specs/` 配下の関連ファイルを読み、確定済み仕様を把握する

Step2 — コードベース調査（Exploreエージェントを使う）:
- 既存テストのディレクトリ構造と命名規則
- 使用しているテストフレームワーク（package.json等から判断）
- 既存テストファイルの書き方のパターン（describe/it/expect の構成等）
- テストファイルの保存場所の規則

Step3 — テスト計画（箇条書き）:
- 確定仕様をもとにテストケースをカテゴリ別に箇条書きで列挙する（コードは書かない）
- カテゴリ: APIテスト / UIコンポーネントテスト / その他（変更がないカテゴリは省略）

**返すもの（親に渡す情報）:**
- テスト計画（箇条書き、カテゴリ別）
- コードベース調査サマリー（テストフレームワーク・命名規則・ファイル保存場所）
```

### Step 4: subagent E — テスト計画レビュー

subagent Bが返したテスト計画を、確定仕様と照合してレビューする。

general-purposeエージェントに以下を指示して起動する:

```
あなたは「テスト計画レビュアー」です。提示されたテスト計画が確定仕様を適切にカバーしているかを判断してください。

issue番号: <番号>
レビュー対象のテスト計画:
<subagent Bが返したテスト計画をそのまま貼り付ける>

以下を実行してください:
1. `gh issue view <番号> --comments` で `## 確定した合意済み仕様` を確認する
2. `docs/specs/` 配下の確定仕様ファイル（openapi.yaml・screen-list.md等）を読む
3. テスト計画と確定仕様を照合し、以下を確認する:
   - すべてのAPIエンドポイントが正常系・異常系・バリデーションでカバーされているか
   - すべての画面・コンポーネントがカバーされているか
   - 重要なビジネスルール・バリデーションがカバーされているか
   - 仕様変更のないカテゴリが含まれていないか（余分なカバレッジは指摘不要）

**返すもの（親に渡す情報）:**
- 判断: 「承認」または「修正が必要」
- 修正が必要な場合: 追加・修正すべきテストケースの具体的なリスト
```

subagent Eの結果を受けて:
- **「承認」**: Step 5へ進む
- **「修正が必要」**: メインがフィードバックをもとにテスト計画を修正し、subagent Eを再起動（最大1回）
  - 2回目でも「修正が必要」: ユーザーに状況とフィードバック内容を伝えて手動確認を依頼し、終了する

### Step 5: メイン — 承認済みテスト計画をissueに記録

以下の形式で `gh issue comment` でissueに記録する:

```
## 承認済みテスト計画

### APIテスト
- <テストケース1>
- <テストケース2>

### UIコンポーネントテスト
- <テストケース1>

### その他
- <テストケース1>
```

### Step 6: subagent B2 — テスト実装

general-purposeエージェントに以下を指示して起動する:

```
あなたは実行可能仕様駆動開発の「テスト実装」を担当します。

issue番号: <番号>
コードベース調査サマリー: <subagent Bが返した調査サマリー>

以下を実行してください:
- `gh issue view <番号> --comments` で `## 承認済みテスト計画` を確認する
- 調査サマリーに記載のパターン・命名規則に従い、承認済みテスト計画をすべてテストコードとして実装する
- ビジネスロジックは実装しない（テストコードのみ）
- 完了後に `gh issue comment` で以下を記録する:
  ## テスト実装完了
  実装したテストファイル:
  - `<ファイルパス1>`
  - `<ファイルパス2>`
- 実装したテストファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）

**返すもの（親に渡す情報）:**
- 実装したテストファイルの一覧
```

### Step 7: subagent D — テストのセルフレビュー・修正

subagent B2の完了を確認してから起動する。

general-purposeエージェントに以下を指示して起動する:

```
あなたは実行可能仕様駆動開発の「テストセルフレビュー」を担当します。

issue番号: <番号>

以下の手順でテストファイルをレビューし、問題があれば修正してください。

**レビュー対象の取得:**
- `gh issue view <番号> --comments` でissueの以下のコメントを確認する:
  - `## 確定した合意済み仕様`（確定ファイル一覧）
  - `## 承認済みテスト計画`（期待するテストケース一覧）
  - `## テスト実装完了`（実装されたテストファイル一覧）
- `docs/specs/` 配下の確定仕様ファイルを読む

**レビューの観点（コード品質ではなく仕様準拠に絞る）:**
1. 承認済みテスト計画の各項目がテストコードに実装されているか
2. 確定仕様と照合し、仕様を正しくテストしているか
3. テストが存在しない仕様上の重要な項目がないか

**修正が必要な場合:**
- 問題リストを作成し、general-purposeエージェントに修正させる（最大2回）
- 2回で解消できなかった問題は返答に含める

**返すもの（親に渡す情報）:**
- レビュー結果（問題なし or 修正した内容の概要）
- 修正したテストファイルの一覧（修正がある場合）
- 2回修正しても解消できなかった問題（あれば）
```

subagent Dが解消できなかった問題を報告した場合は、その内容をユーザーに伝えて手動対応を依頼し、終了する。

### Step 8: subagent C — 実装

subagent Dの完了を確認してから起動する。

general-purposeエージェントに以下を指示して起動する:

```
あなたは実行可能仕様駆動開発の「実装フェーズ」を担当します。
ワークフロー定義: `docs/workflow/executable-spec-driven-workflow.md`
詳細手順: `.claude/skills/dev-impl/SKILL.md`

issue番号: <番号>

SKILL.mdのStep1〜4を実行してください。
- Step5（人間による動作確認・コミット）は実行しない。親エージェントが別のレビュアーで確認後にコミットする。

**返すもの（親に渡す情報）:**
- 作成・変更したファイルの一覧
- セルフレビュー結果（問題なし or 修正した内容）
- セルフレビューで2回修正しても解消できなかった問題（あれば）
```

subagent Cがセルフレビューで解消できなかった問題を報告した場合は、その内容をユーザーに伝えて手動対応を依頼し、終了する。

### Step 9: subagent F — 実装レビュー

subagent Cから受け取った結果をもとに、仕様準拠を確認する。

general-purposeエージェントに以下を指示して起動する:

```
あなたは「実装レビュアー」です。実装が確定仕様に準拠しているかを判断してください。

issue番号: <番号>
実装ファイル一覧: <subagent Cが返したファイル一覧>
セルフレビュー結果: <subagent Cが返したセルフレビュー結果>

以下を実行してください:
1. `gh issue view <番号> --comments` で確定仕様・承認済みテスト計画を確認する
2. `docs/specs/` 配下の確定仕様ファイル（openapi.yaml・api-list.md・screen-list.md等）を読む
3. `docs/architecture/` を参照し、ディレクトリ構造・命名規則を確認する
4. 実装ファイルを読み、以下を確認する:
   - APIエンドポイントが openapi.yaml / api-list.md の仕様と一致しているか（メソッド・パス・リクエスト/レスポンス形式）
   - UIコンポーネントが screen-list.md の仕様と一致しているか
   - アーキテクチャ定義のディレクトリ構造・命名規則に従っているか
   - セルフレビューが「問題なし」または「修正済み」で完了しているか

**返すもの（親に渡す情報）:**
- 判断: 「承認」または「問題あり」
- 問題ありの場合: 仕様との差異・違反の具体的なリスト
```

subagent Fの結果を受けて:
- **「承認」**: Step 10へ進む
- **「問題あり」**: general-purposeエージェントに問題リストを渡して修正させる（最大1回）
  - 修正後、subagent Fを再起動して再レビュー
  - 再度「問題あり」: ユーザーに問題リストを伝えて手動対応を依頼し、終了する

### Step 10: メイン — コミット・完了報告

1. subagent Cが作成・変更したファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）
2. 以下の形式でユーザーに完了を報告する:

```
## /dev-auto 完了 (#<番号>)

### 実行したフェーズ
1. 要件定義（仕様生成 + 仕様合意）
2. テスト計画作成（レビュアーによる自動承認）
3. テスト実装・セルフレビュー（自動）
4. 実装・セルフレビュー（自動）
5. 実装レビュー（レビュアーによる自動承認）・コミット

### 成果物
- 仕様ファイル: <一覧>
- テストファイル: <一覧>
- 実装ファイル: <一覧>
- テスト計画レビュー: <承認 / 修正後承認>
- 実装レビュー: <承認 / 修正後承認>

PRを作成する場合は以下を実行してください:
/create-pr
```

## 注意事項

- 起動順序: B → E → (メインで記録) → B2 → D → C → F の順番で起動する（前のサブエージェントの完了を確認してから次を起動）
- 各サブエージェントはそれぞれ独立したコンテキストで動くため、issueコメントが各フェーズ間の主要な情報受け渡し手段になる
- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- issueに記録するコメントは日本語で書く
