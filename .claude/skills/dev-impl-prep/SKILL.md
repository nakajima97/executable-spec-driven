## 概要

実行可能仕様駆動開発ワークフロー（`docs/workflow/executable-spec-driven-workflow.md`）のステップ3「実装準備」を実行する。
要件定義フェーズで確定した仕様（API仕様・UI仕様・DBスキーマ等）を守るためのテストを、
まず箇条書きで計画し、人間の承認を得てから実装することがゴール。

## 引数

- `<issue番号>`（必須）: 実装準備を行うGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /dev-impl-prep 42」と伝えて終了する

## エージェント構成

```
メインスキル（オーケストレーター）
├── Step1: Issue確認（メイン）
├── Step2: コードベース調査 → Explore エージェント
│             ↓ 調査サマリーを受け取る
├── Step3: テスト計画（箇条書き）（メイン）
├── Step4: 人間確認・合意（メイン）
└── Step5: テスト実装 → general-purpose エージェント
```

## 手順

### Step 1: Issue確認

1. issueの内容とコメントを取得する
   - `gh issue view <番号>` でissue本文を取得する
   - `gh issue view <番号> --json comments --jq '.comments[].body'` でコメントを取得する
   - 要件定義フェーズの確定版コメント `## 確定した合意済み仕様` を必ず確認する
   - 見当たらない場合は要件定義フェーズが未完了の可能性があるため、その旨をユーザーに伝えて終了する
2. `docs/specs/` 配下の関連ファイルと確定した API 契約を読み、確定済み仕様を把握する
   - 対象例: `api-list.md`（一覧）, API 契約（`openapi.yaml`（既定）／コードファーストのスタックではスキーマ定義＋ルートのスタブ定義 = API 形状の正。`dev-requirements` スキルの「API 契約の形式」参照）, `screen-list.md`, `er-diagram.md`
3. テスト対象となる仕様を整理する（APIエンドポイント・UIコンポーネント・DBスキーマ等）

### Step 2: コードベース調査（Explore エージェント）

以下を調査させ、調査サマリーをメインに返させる:

- 既存テストのディレクトリ構造とファイル命名規則
- 使用しているテストフレームワーク（フロントはVitest、バックエンドは任意）
- 既存テストファイルの書き方（describe/it/expect の構成パターン等）
- テストファイルの保存場所の規則（`__tests__` ディレクトリ、`.test.ts` サフィックス等）

Exploreエージェントへの指示例:
```
以下を調査してサマリーを返してください:
1. 既存テストファイルのディレクトリ構造と命名規則
2. 使用しているテストフレームワーク（package.json, requirements.txt等から判断）
3. 既存テストファイルの書き方のパターン（describe/it/test の構成）
4. テストファイルの保存場所の規則
```

### Step 3: テスト計画（箇条書き）（メイン）

Step1・Step2の情報をもとに、テストケースを箇条書きで列挙する。**コードは書かない。**

以下のカテゴリでテストケースを整理する:

**APIテスト**（APIエンドポイントの追加・変更がある場合）:
- 各エンドポイントごとに正常系・異常系・バリデーションのテストケースを列挙

**UIコンポーネントテスト**（画面の追加・変更がある場合）:
- 各コンポーネントごとにレンダリング・props・インタラクションのテストケースを列挙
- 確定仕様に「機能要件を伴うページの Container 配線方針」（`dev-requirements` スキル参照）が明記されているページは、対象ルート/ページの受け入れテスト（統合テスト）に「実際の送信→API呼び出し→画面遷移」のハッピーパスを1本含める（静的UIのレンダリング確認だけで済ませない。Container 未配線を実装前の RED として検知するため）
- 統合テスト（複数層を結合して検証するテスト。例: フロントエンドの `*.int.test.tsx`）を計画する場合は、プロジェクトのテスト規約（`.claude/rules/` 配下や `docs/architecture/` に統合テストの対象範囲の定めがあればそれ）を Read し、統合テストのケースごとに、それが「単体テストで担保が難しい振る舞い」のどれに当たるかをケースの行に併記する（上記の受け入れテストも対象。Step 4 で人間が照合できるようにするため）。規約に例の一覧があればそれを正とし、この計画に書き写さない。規約が無い場合の既定: 単体テストで担保が難しい振る舞いとは、複数層の連携・ルーティング/画面遷移・非同期の実データフロー等を指す。例に当たらないケース（ロジックを純粋関数・表示コンポーネント（Presentational）に切り出せば単体テストで書ける振る舞い、または計画内・既存テストの他の層（hook / Container / ページ等）で同じ振る舞いを検証しているもの）は統合テストとして計画しない（前者は単体テストとして計画し、後者は1つの層にまとめる）

**その他**（DB変更がある場合など）:
- スキーマ検証・マイグレーション検証等のテストケースを列挙

### Step 4: 人間への確認・フィードバック反映（メイン）

1. テスト計画（箇条書き）をユーザーに提示する
2. フィードバックを受けて修正する（複数回対応）
3. ユーザーが承認したら、以下の形式で `gh issue comment` でissueに記録する:
   ```
   ## 承認済みテスト計画

   ### APIテスト
   - <テストケース1>
   - <テストケース2>

   ### UIコンポーネントテスト
   - <テストケース1>

   ### その他
   - <テストケース1>
   ```
4. Step5へ進む

### Step 5: テスト実装（general-purpose エージェント）

Step4で承認されたテスト計画と、Step2のコードベース調査サマリーをコンテキストとして渡し、
テストコードを実装させる。

general-purposeエージェントへの指示例:
```
以下の調査サマリーと承認済みテスト計画をもとに、テストコードを実装してください。
[調査サマリー]
[承認済みテスト計画]

- ビジネスロジックは実装しない（テストコードのみ）
- 既存テストのパターン・命名規則に従う
- 実装したテストを実行し、RED を確認する（テストコマンドは `docs/specs/technical-environment.md` の `## 実行コマンド` を参照）:
  - (1) 構文・import エラーなく実行可能であること
  - (2) 対応する実装が存在しないことを理由に失敗すること（RED。実装前の失敗は正常）
  - 例外: 確定仕様に「機能要件を伴うページの Container 配線方針」で (a)（このフェーズで配線）が明記されているページの受け入れテストは、実装済みコードに対して最初から GREEN になりうる（`dev-requirements` スキル参照）。この場合は (2) の RED 確認を必須とせず、代わりに「確定仕様どおりに GREEN であること」を確認する
  - 実装未着手以外の理由（テスト設定エラー等）で失敗する場合は修正してから完了報告する
- 実装したテストファイルの一覧と、RED 確認結果（実行コマンド・想定どおり失敗した旨。上記例外に該当するテストがあれば GREEN であった旨とその理由）を返してください
```

完了後:
1. 実装したテストファイルの一覧をユーザーに提示する
2. 以下の形式で `gh issue comment` でissueに記録する:
   ```
   ## テスト実装完了
   実装したテストファイル:
   - `<ファイルパス1>`
   - `<ファイルパス2>`

   ### RED 確認
   - 実行コマンド: `<実行したテストコマンド>`
   - 結果: 構文・import エラーなく実行可能。実装未実装により想定どおり失敗（RED 確認済み）
   ```
3. 実装したテストファイルをコミットする（コミット規約は `.claude/rules/core.md` を参照）
4. 「実装準備フェーズが完了しました」と伝え、次のコマンドを案内する:
   ```
   次のフェーズへ進む場合は以下を実行してください:
   /dev-impl <issue番号>
   ```

## 注意事項

- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- テスト計画（箇条書き）は人間が承認するまでテストコードを書かない
- 既存テストのパターン・命名規則に必ず従う
- issueに記録するコメントは日本語で書く
- 変更が不要なカテゴリのテストは計画に含めない（APIの変更がなければAPIテストは不要）
