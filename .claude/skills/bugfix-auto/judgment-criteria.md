# 完了条件の判定方式 — 判断基準

`/bugfix-auto` の「完了条件の判定方式」（回帰テスト / AI照合 / 人間確認）を **誰が判定しても同じ結論になる** ようにするための共有リファレンス。

判定方式そのものの定義とワークフローでの扱いは `.claude/skills/bugfix-auto/SKILL.md` の「概要」を参照する。本ドキュメントは「どう分類を決めるか」の手順・集約ルール・境界ケースだけを定義する。

## 参照者と使い方

| 参照者 | 使い方 |
|---|---|
| Step 1: Explore エージェント | 本ドキュメントの判定手順に従って分類を決め、根拠とともに返す |
| Step 2: 質問フェーズ（メイン） | 「検証可能性の不足」「分類への確信のなさ」を Material Ambiguity として人間に確認し、分類を確定させる |
| Step 6〜8: bugfix-auto-reviewer | 承認済み修正計画の判定方式が本基準に照らして妥当かを確認したうえで、その方式で完了を判定する。人間確認相当の項目が含まれると判明した場合は `判定: 人間確認が必要` を返す（修正ループでは解消できないため「問題あり」にしない） |

いずれの参照者も、分類の根拠は本ドキュメントの問い（後述の Q1〜Q4）のどこで決まったかで説明する。

## 判定手順

### 0. 検証項目に分解する

issue の「機能要件」の各項目（および概要に書かれた期待動作）を、**独立に検証できる単位** に分解する。1 つの箇条書きに複数の期待動作が含まれる場合は分けて扱う。

以降の Q1〜Q4 は **項目ごとに** 適用し、最後に「集約ルール」で issue 全体の分類を決める。

### Q1. 期待動作が検証可能な形で書かれているか

期待動作が次のいずれかの形で issue に書かれているかを確認する:

- 入力と出力（リクエスト → レスポンス、引数 → 戻り値）
- 状態遷移（操作前後の DB・UI・ストアの状態）
- 具体的な文言（表示テキストの全文または一部）
- 数値閾値（件数・時間・サイズ・コントラスト比など）
- 参照先が一意に特定できる規約（デザインシステム定義（例: `DESIGN.md`）のトークン名、ADR の決定事項、`docs/specs/` の記述など）

**書かれていない場合、人間確認に直行しない。** 「検証可能性の不足」を Material Ambiguity として洗い出し、質問フェーズで「どうなれば直ったと言えるか」を人間に確認して要件の具体化を試みる。

- 具体化できた場合: Q2 から判定をやり直す
- 具体化を試みてもなお人間の知覚・主観に依存する場合のみ: 人間確認（Q4）

**この再判定は Step 2（人間への質問と回答）を経て行う。** Step 1 の Explore は人間に質問できないため、Q1 を満たさない項目は Material Ambiguity として返すところまでが担当範囲であり、自問自答で具体化したことにして分類を断定しない。

書かれている場合は Q2 へ進む。

### Q2. 既存テスト基盤で決定的にアサートできるか

次をすべて満たすなら **回帰テスト**。

- 既存のテスト基盤で書ける（テストフレームワーク・対象範囲は `docs/specs/technical-environment.md` の `## テスト`、テストの種類・命名・置き場所の方針は `.claude/rules/` 配下や `docs/architecture/` のテスト規約、実行方法は `docs/specs/technical-environment.md` の `## 実行コマンド` を参照）
- 修正前に必ず失敗し、修正後に必ず通る（red → green が決定的）
- 実行環境に依存する不安定要素（時刻・乱数・ネットワーク・実ブラウザの描画結果）を含まないか、固定化できる

満たさない典型:

- テストは書けるが結果が毎回同じにならない（flaky）
- テスト基盤が対象をカバーしていない（実ブラウザでの視覚的な描画結果、E2E 基盤が無いなど）
- Storybook 等のコンポーネントカタログでしか確認できない（カタログは人間が目視するための基盤であり、自動アサートの基盤ではない。story の**定義**が規約どおりかは Q3 の突合対象になるが、story の**見え方**は Q2 を満たさない）

**回帰テストと AI照合の両方で判定できる場合は回帰テストを選ぶ**（SKILL.md の「原則こちらを優先」と整合）。満たさない場合は Q3 へ進む。

### Q3. 静的なコード実態との突合で判定できるか

次のような **静的に読める実態** と機能要件の突合で完了を判定できるなら **AI照合**。

- ルート定義・エクスポート・関数シグネチャ・型定義・スキーマ定義（バリデーションスキーマ・OpenAPI 定義など）
- 設定値（ビルド設定・lint 設定・環境変数の参照箇所など）
- ファイル配置・命名規約への準拠
- ドキュメント同士の整合（`docs/specs/` ・ADR・README・スキル定義の記述）
- デザインシステム定義（例: `DESIGN.md`）のトークン準拠（コード上のトークン参照と定義の一致）
- コンポーネントカタログの story 定義の規約準拠（プロジェクトの story 規約（あれば `.claude/rules/` 配下）の title・argTypes・作成する story ケースと story ファイルの突合）

条件は **「何と何を突き合わせれば充足と言えるか」が事前に一意に決まること**。突合対象が事前に決まらない・読む人によって変わる場合は AI照合ではない。

満たさない場合は Q4 へ進む。

### Q4. 判定に人間の知覚・主観が本質的に必要か

次に該当するなら **人間確認**。

- 実際の描画結果を目で見ないと判断できない（余白のバランス・要素の重なり・折り返しの見え方）
- 良し悪しの評価が主観に属する（読みやすい・使いやすい・自然な日本語）
- 再現が非決定的で、原因も特定できず、直ったことを機械的にも静的にも確認できない

Q4 に到達した場合、**Q1 に戻って要件を具体化できないかを一度検討する**。人間確認は `/bugfix-auto` の対象外（ワークフロー終了）を意味するため、要件の書き方の問題を分類の問題として扱わない。

この検討で「人間に聞けば具体化できそう」と判断した場合、Step 1 の時点では人間確認と断定せず、Material Ambiguity として Step 2 に回す（Q1 と同じ扱い）。Q1 ↔ Q4 を自分の中で往復させて結論を出さない。

## 集約ルール

項目ごとの分類を、次の順で issue 全体の分類に集約する。

1. **1 項目でも人間確認があれば、issue 全体を人間確認とする**（対象外マーカーを投稿して終了。判明した時点が Step 1・Step 2・Step 6〜8 のいずれでも同じ扱い）
2. 回帰テストと AI照合が混在する場合は、**回帰テストを主判定とする**
3. 全項目が AI照合なら AI照合

補足:

- 2 の場合、AI照合でしか確認できない項目は承認済み修正計画の「照合内容」に必ず書き残す。レビュアーは回帰テストの確認に加えてその照合も行う（回帰テストが主判定であることは、AI照合項目を省いてよいことを意味しない）
- 1 で終了する場合、対象外マーカーの「判定の根拠」に **どの検証項目が人間確認なのか** を明記する。人間が issue を分割・具体化して再実行できるようにするため

## 境界ケースの判定例

分類が割れやすいパターンの既定の判定。実際の issue はこの表に当てはめたうえで Q1〜Q4 を辿って確定させる。

| パターン | 分類 | 判断のポイント |
|---|---|---|
| 「表示が崩れる」— 崩れの原因が DOM 構造・条件分岐・クラス指定に帰着し、期待する構造が一意に決まる | 回帰テスト | コンポーネントテストのライブラリ（例: React Testing Library）で要素の存在・属性・階層をアサートする |
| 「表示が崩れる」— 期待状態が「バランスが悪い」程度でしか言語化されていない | Q1 へ戻す → 具体化できなければ人間確認 | 「どの要素がどうなっていれば正しいか」を質問フェーズで確定させる。コンポーネントカタログで見えることは自動判定できることを意味しない |
| 「文言がおかしい」— 修正後の文言が issue に明記されている | 回帰テスト（表示箇所がテスト基盤の対象外なら AI照合） | 文言そのものをアサート／定義箇所の文字列を突合する |
| 「文言がおかしい」— 「もっと自然な表現に」など修正後の文言が未確定 | Q1 へ戻す → 確定すれば回帰テスト / AI照合 | 文言が確定すれば主観判断は残らない |
| 「色がデザイントークンと違う」— デザインシステム定義のトークン名が一意に決まる | AI照合 | コード上のトークン参照とデザインシステム定義のトークン一覧を突合する |
| 「色がデザイントークンと違う」— コントラスト比が論点で、数値基準（例: WCAG AA: 通常テキスト 4.5:1 / 大テキスト・UI 3:1）に照らせる | 回帰テスト（計算をアサートできる場合）／ AI照合 | 数値基準がある時点で主観判断ではない |
| 「色がデザイントークンと違う」— 実際の見え方の良し悪しが論点 | 人間確認 | 基準が数値化されていない色の印象は知覚に依存する |
| 「遅い」— 数値閾値と測定方法が issue にある | 回帰テスト（実行環境の影響を固定化できる場合）／ 固定化できなければ Q1 へ戻す | 実行時間の直接測定は flaky になりやすい。閾値があること自体は Q2 の充足を意味しないため、固定化できるかを Q2 で判断する |
| 「遅い」— 原因が N+1 クエリ・不要な再レンダリング等に特定でき、呼び出し回数をアサートできる | 回帰テスト | 実時間ではなく **回数** をアサートすれば決定的になる |
| 「遅い」— 「体感が遅い」だけで閾値が無い | Q1 へ戻す → 閾値が決まらなければ人間確認 | 閾値が決まればほぼ回帰テストに落ちる |
| 「非決定的に再現するバグ」— 非決定性の原因（競合状態・時刻依存・順序依存）が特定でき、原因を固定化した条件で決定的に再現できる | 回帰テスト | 固定化した条件で red → green が再現することが条件 |
| 「非決定的に再現するバグ」— 原因（メカニズム）は特定できたが、非決定性が実行環境側（CPU 競合・実時間スケジューリング等）に起因し、テストコード側で固定化できないため決定的に red を再現できない | AI照合 | 原因を構造的に除去したことをコード実態との突合で判定する（例: 実時間デッドラインに依存する待機が残っていないか）。突合対象のファイル・箇所は計画時に一意に特定しておく（Q3 の条件）。実行結果は flaky のため単独では判定根拠にならず、補助的な確認にとどめる（既存アサーションの削除・緩和で見かけ上 green にしたものは未充足とする） |
| 「非決定的に再現するバグ」— 原因が特定できず再現条件も不明 | 人間確認 | Step 1 の調査サマリーに「再現できなかった」事実を残す |
| ドキュメント・設定の記述が実装と食い違う | AI照合 | Markdown はテスト基盤・フォーマッタの対象外であることが多い。記述と実態の突合で判定する |
| アクセシビリティ — aria 属性・フォーカス順・キーボード操作が一意に決まる | 回帰テスト | 属性・フォーカス遷移はアサートできる |
| アクセシビリティ — スクリーンリーダーの読み上げの自然さ | 人間確認 | 読み上げ結果の良し悪しは知覚・主観に属する |
| コンポーネントカタログの story が規約どおりに存在しない・title が配置と食い違う | AI照合 | プロジェクトの story 規約と story ファイルの定義を突合する（story の見え方ではなく定義が対象） |
| 特定のブラウザ・端末でのみ再現し、既存基盤の実行環境では再現しない | 人間確認 | テスト基盤も静的な突合も再現条件をカバーできない |

## 迷った場合の扱い

**分類に確信が持てないこと自体を Material Ambiguity に含め、質問フェーズ（Step 2）へ回す。**

- Step 1 では **人間確認と断定せず**、候補のうち自動判定できる方（回帰テスト / AI照合）を暫定分類として返し、Material Ambiguity に確信が持てない旨を書く
  - 例: 「機能要件 3 の判定方式は回帰テスト（○○をアサート）と AI照合（○○の定義を突合）のどちらが適切か確信が持てない」
- 明らかに人間確認だと判断できる場合のみ、質問フェーズを経ずに対象外として報告・終了してよい（SKILL.md Step 1 の既定動作）
- 質問フェーズの回答で人間確認が必要と確定した場合は、Step 1 と同じ対象外マーカーを投稿して終了する
- レビュー（Step 6〜8）で人間確認相当と判明した場合も、修正ループに入れずに対象外マーカーを投稿して終了する。修正エージェントは承認済み修正計画の判定方式を変えられないため、「問題あり」として差し戻しても解消せず、レビュー上限まで空回りするだけになる

Material Ambiguity に書く際は、次を含めて人間が判断できる形にする:

- 対象の検証項目（機能要件のどれか）
- 候補となる分類と、それぞれの場合の確認方法
- 迷っている理由（どの問い Q1〜Q4 で判断がつかないか）
