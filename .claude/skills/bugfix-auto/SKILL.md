## 概要

バグ修正専用の自律ループワークフロー。
リファクタリング（機能変更なし）とは異なり、「issue に記録された期待動作（機能要件）と現在の挙動の乖離を解消する」パターンに特化する。

探索フェーズで再現・原因分析を行い、**完了条件の判定方式**を次の3つに分類する:

| 判定方式 | 内容 | ワークフローでの扱い |
|---|---|---|
| 回帰テスト | 修正前に失敗し修正後に通るテストで機械的に判定できる | red → green の TDD ループで修正する（原則こちらを優先） |
| AI照合 | テストは書きにくいが、コード実態と issue の機能要件の突合で AI が判定できる | レビュアーが機能要件との突合で完了を判定する |
| 人間確認 | 見た目・主観判断が必要で、AI 判定では完了を保証できない | ワークフロー対象外として報告・終了する |

**どの方式に分類するかの判断基準は `.claude/skills/bugfix-auto/judgment-criteria.md` を正とする**（判定手順・集約ルール・境界ケース・迷った場合の扱い）。判定に関わる各所（Step 1 の Explore・Step 2 の質問フェーズ・レビュアー）は同ファイルを参照し、基準を重複定義しない。

質問→計画→承認のサイクルで人間と合意してから実装する。
実装後はレビュー（最大3回）→修正（最大2回）を繰り返し、通らなければ人間に報告して終了する。
なお、ワークフロー開始時に issue へのコメント投稿許可を Step 0 で1回確認する。

## 引数

- `<issue番号>`（必須）: 修正対象のGitHub issueの番号
- 未指定の場合: 「issue番号を指定してください。例: /bugfix-auto 42」と伝えて終了する

## エージェント構成

```
メインスキル（オーケストレーター）
├── Step0: mainブランチガード・進捗確認・再開ポイント判定（メイン）
├── Step1: 再現・原因分析 → Explore エージェント
│             ↓ 原因分析・修正方向候補・完了条件の判定方式・不明点リストを受け取る
│             ↓ 判定方式が「人間確認」なら対象外マーカーを投稿して終了
├── Step2: 質問フェーズ（メイン）← タッチポイント① ※不明点がなければスキップ
│             ↓ 回答で判定方式が「人間確認」に確定したら対象外マーカーを投稿して終了
├── Step3: 修正計画立案 → Plan エージェント
│             ↓ 修正計画書を受け取る
├── Step4: 計画承認フェーズ（メイン）← タッチポイント②
├── Step5: 実装 → general-purpose エージェント（回帰テスト先行。実装完了時にコミットし、続けて `## バグ修正実装完了` を投稿）
│             ↓ 変更ファイル一覧を受け取る
├── Step6〜8: レビュー → 修正ループ（レビュー最大3回・修正最大2回）
│   ├── [bugfix-auto-reviewer] レビュー（機能要件の充足判定・判定方式の妥当性チェック）
│   │             ↓ 「人間確認が必要」判定なら対象外マーカーを投稿して終了（修正ループに入らない）
│   └── [general-purpose] 修正（問題ありの場合。修正後はメインが追加コミット）
└── Step9: 完了マーカー投稿（ふりかえり同梱）・PR 作成・完了報告・改善issue起票確認（メイン）
```

## 手順

### Step 0: mainブランチガード・コメント投稿許可・再開ポイントの判定

> **集約先ファイルとの対応関係**: 本 Step 0 の「main ブランチガード / 開始時ガード（ブランチ突合・未コミット差分確認）/ コメント投稿許可」は、`dev-auto`・`refactor-auto` の Step 0 と共通のロジックとして `.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」に集約されている。この共通部分を変更する場合は集約先ファイルのその節を更新すること（3スキルに自動的に反映される）。スキル固有の差分（コマンド名・再開表の内容・再開ポイントのステップ番号）は本ファイルに残す。

`.claude/skills/_shared/orchestrator-common.md`「Step 0 開始時ガード」を Read し、`<コマンド名>` を `/bugfix-auto`、`<進捗コメント項目一覧（説明文）>` を `確認済み不明点・承認済み修正計画・実装完了・完了マーカー等`、`<進捗コメント項目一覧（確認文言）>` を `確認済み不明点・承認済み修正計画・各フェーズの完了マーカー等` に置き換えて、その内容のとおりに実行する。同ファイルを Read できない、または該当節が見つからない場合は、開始時ガードとコメント投稿許可を省略して先へ進まず、その旨をユーザーに伝えて終了する。

続いて `gh issue view <番号> --json comments` でissueコメントを取得し、以下の表に従って再開ポイントを決定する（`--comments` は auto mode の環境で空出力になる既知事象があり、空出力を「コメントなし（初回）」と誤判定して完了済み issue をやり直してしまうため使わない。/auto-loop 配下の子は auto mode で起動されるので必ず該当する）。

| issueコメントの状態 | 再開ポイント |
|---|---|
| コメントなし（初回） | Step 1 から実行 |
| `## /auto-loop エスカレーション` のコメントがあり、それ以降に「人間の回答コメント」（`.claude/skills/auto-loop/SKILL.md` 2b 手順0の定義を参照）が投稿されているが、bugfix-auto標準マーカー（本表の他の行）がまだ無い | Step 1 から実行（エスカレーション回答の扱いは下記「エスカレーション回答の読み込み」を参照） |
| `## /bugfix-auto — 対象外（人間確認が必要）` のコメントあり | 対象外と判定済みであることを報告して終了 |
| `## 確認済み不明点` のコメントあり（スキップした場合を含む） | Step 3 から実行 |
| `## 承認済み修正計画` のコメントあり | Step 5 から実行 |
| `## バグ修正実装完了` のコメントあり | Step 6 から実行 |
| `## /bugfix-auto — 自動修正できませんでした` のコメントあり | Step 6 から再開（手動修正後の再実行を想定し、レビュー・修正ループの回数はリセットする） |
| `## /bugfix-auto 完了` のコメントあり | 完了済みと報告して終了 |

複数の行に該当する場合は、最も進んだ（表の下の）行を採用する。
（`## /bugfix-auto — 対象外（人間確認が必要）` は例外的に最優先で終了判定とする。人間が issue を修正して再実行したい場合は、当該コメントを削除してから再実行する）

**エスカレーション回答の読み込み（再開ポイントに関わらず行う）**: `## /auto-loop エスカレーション` コメントがあり、それ以降に「人間の回答コメント」（`.claude/skills/auto-loop/SKILL.md` 2b 手順0 の定義を参照。複数回のやり取りがあれば最新のものを含む全体）が投稿されている場合は、**上表のどの行で再開したかに関わらず**、その回答を追加の前提条件として以降の各フェーズ（Step 1 の Explore・Step 3 の Plan・Step 5 の実装・Step 6〜8 の修正）へのプロンプトに必ず含める。エスカレーションは計画承認・レビュー段階でも発生し、その場合は bugfix-auto 標準マーカーが既にあって Step 3 以降から再開するため、Step 1 の指示にだけ書くと回答が読まれないまま処理が進む。回答に前処理指示（別issueへの切り出し等）が含まれていても、その実行は指揮役（`/auto-loop`）の責務であり bugfix-auto 側では実行しない（「注意事項」参照）。

再開ポイントが Step 1 以外の場合は、ユーザーに以下を伝えてから該当 Step に進む:

```
issue #<番号> の進捗を確認しました。<X> まで完了しているため、Step <N> から再開します。
```

### Step 1: 再現・原因分析（Explore エージェント）

`subagent_type: "Explore"`・`model: "sonnet"` でエージェントを起動する。以下を調査させ、結果をメインに返させる:

- issueのタイトル・本文（`gh issue view <番号>` で取得）
- **経緯として参照している他 issue/PR の状態の検証**（issue 本文・前提として読み込んだコメントの記載と実際の state が食い違っていないか）
- バグの再現条件と原因箇所（ファイル・行・データフロー）
- 修正方向の候補（issue 本文に候補が書かれていればその妥当性も検証する）
- **完了条件の判定方式の分類**（回帰テスト / AI照合 / 人間確認）
- **Material Ambiguity（修正方向が変わりうる曖昧点）の洗い出し**

Exploreエージェントへの指示例:
```
issue番号 <番号> のバグ修正を自律実行するために、以下を調査してください。

1. `gh issue view <番号>` でissueの内容（概要・機能要件・制約）を取得する
2. `gh issue view <番号> --json comments` でissueコメントを確認し、`## /auto-loop エスカレーション` コメントがあれば、それ以降に投稿された「人間の回答コメント」（Step 0 の「エスカレーション回答の読み込み」の定義を参照。複数回のやり取りがあれば最新のものを含む全体）を追加の前提条件として読み込むこと。回答に前処理指示（別issueへの切り出し等）が含まれていても、その実行は指揮役（`/auto-loop`）の責務であり、Explore・以降のどのフェーズでも前処理を実行しないこと（参考情報として読むのみ）
3. issue 本文（および 2. で前提条件として読み込んだ回答コメント）が他 issue/PR 番号を経緯として参照している場合（前提として他 issue/PR の状態に言及している箇所。単なる関連リンクの列挙は対象外）、参照先ごとに状態を検証し、記載内容と食い違っていれば 8. の Material Ambiguity に含めること。経緯として参照しているかの判断に迷う場合は検証する側（安全側）に倒すこと
   - `gh issue view <参照先の番号> --json state,stateReason,closedAt` を1回実行する（`<参照先の番号>` は調査対象の issue 番号ではなく参照先の番号を指す）。`gh issue view` は PR 番号も解決し、PR の場合は `state` が `MERGED` / `CLOSED` / `OPEN` で返るため、番号の種別を事前に判別する必要はない（`gh pr view` との2段フォールバックは不要）
   - `owner/repo#<番号>` の形で他リポジトリを指す参照には `--repo owner/repo` を付けること。付けないと現在のリポジトリの同じ番号を見に行き、その番号が存在しなければ実在する参照を「解決できなかった参照先」として誤報告し、存在すれば無関係な issue/PR の state を検証結果にしてしまう
   - 検証の成否はコマンドの終了コードで判定する（gh の直後で終了コードを確認すること。`gh ... | jq ...` のようにパイプでつなぐと末尾コマンドの終了コードになり gh の失敗を取りこぼす）
   - 終了コード0以外（番号が存在しない・認証切れ・レート制限など理由を問わない）の場合、その参照先番号を「解決できなかった参照先」として 8. の Material Ambiguity に含めること
4. バグの原因箇所を特定する（`git grep` や `git ls-files` でファイルを特定し、コードを読んで原因を分析する）
   - リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
5. 再現条件を整理する（どの操作・どのデータ・どの状態で発生するか）
6. 修正方向の候補を具体的に示す（issue 本文に修正方向の候補があればその妥当性も検証する）
7. 完了条件の判定方式（回帰テスト / AI照合 / 人間確認）を1つ選び、根拠とともに示す
   - **判断基準は `.claude/skills/bugfix-auto/judgment-criteria.md` を必ず読み、その判定手順（検証項目への分解 → Q1〜Q4）・集約ルール・境界ケースの判定例に従うこと**
   - 根拠には「どの検証項目が、どの問い（Q1〜Q4）で、なぜその分類になったか」を含める
   - 分類に確信が持てない場合は人間確認と断定せず、同ファイルの「迷った場合の扱い」に従って暫定分類を返し、8. の Material Ambiguity に含める
8. 以下の観点で「Material Ambiguity（修正方向に影響する曖昧点）」を洗い出す:
   - 修正スコープ（どこまで直すか。周辺の類似バグを含めるか）
   - 期待動作の解釈が分かれる点（issue の機能要件だけでは一意に決まらない挙動）
   - 修正方向の候補が複数あり優劣が判断できない点
   - 既存の挙動・API仕様に影響が出うる点
   - 期待動作が検証可能な形で書かれていない点（judgment-criteria.md の Q1）・判定方式の分類に確信が持てない点
   - 経緯として参照する他 issue/PR の状態が、3. で検証した実際の状態と食い違っている点
   - 経緯として参照する他 issue/PR の参照先番号が解決できなかった点（検証コマンドが終了コード0以外で失敗した場合）
9. （4.〜8. のすべてに適用される制約）main との差分・分岐点算出（マージベースの特定等）を扱う場合は、比較対象を `main` ではなく `origin/main` にすること。ローカル `main` は worktree 作成スクリプト（例: `scripts/wt-new.sh`。`gh issue develop --base main` で作業ブランチを作る）のフローで最新化されないため、ローカル `main` を基準にすると分岐点を誤って古く算出しうる（根拠: `.claude/skills/auto-loop/SKILL.md`「エスカレーション時の後片付け」節）。また、`origin/main` を参照する前に `git fetch origin main` を実行し、**終了コードで成否を判定する**こと（worktree 作成スクリプトは作業ブランチしか fetch しないことがあり、worktree の `origin/main` 自体が古いことがある）。fetch に失敗した場合は `origin/main` も古い可能性があるため分岐点を確定させず、その旨を明記すること（同節の「`git fetch` が失敗した場合は `origin/main` も古い可能性がある」の扱いに合わせ、安全側に倒す）。使用した比較対象と `git fetch` の成否は調査サマリーに残すこと（Step 3・Step 4 で基準を突き合わせられるようにするため）

以下を返してください:
- 調査サマリー（原因箇所・再現条件・修正方向の候補）
- 経緯として参照している他 issue/PR の検証結果（参照先の番号と state。解決できなかった参照先は `#<番号>: 解決できず` の形で明記する。参照が無ければ「なし」）
- 完了条件の判定方式（回帰テスト / AI照合 / 人間確認）と根拠
- Material Ambiguity の一覧（なければ「なし」）
- main との差分・分岐点を扱った場合の比較対象と `git fetch origin main` の成否（扱っていなければ「該当なし」）
```

**判定方式が「人間確認」だった場合**: 以下を `gh issue comment` でissueに記録し、同内容をユーザーに報告して終了する（Step 2 以降へ進まない）:

```
## /bugfix-auto — 対象外（人間確認が必要）

この issue の完了条件は見た目・主観判断を含むため、/bugfix-auto の自動判定では完了を保証できません。

### 判定の根拠
<Explore エージェントが返した根拠>

### 調査サマリー（手動修正の参考情報）
- 原因箇所: <原因箇所>
- 再現条件: <再現条件>
- 修正方向の候補: <候補>
- 経緯として参照する他 issue/PR との食い違い: <食い違いの内容。なければ「なし」>

### 再実行するには
issue の期待動作を検証可能な形に具体化したうえで、**このコメントを削除してから**再実行すると、
再現・原因分析（Step 1）からやり直せます。このコメントが残っている限り、`/bugfix-auto` は
Step 0 の再開判定で対象外と報告して終了し、`/auto-loop` も Step 1 の除外判定でこの issue を
処理対象から外します。
```

**再実行手順をコメント本文に含めるのは省略しない**。このコメントは指揮役（`/auto-loop`）から
実行された場合の唯一の GitHub 側の記録であり、削除が再実行の前提だと書かれていないと、
issue を具体化して再実行しても除外判定で黙ってスキップされ続ける。

### Step 2: 質問フェーズ（メイン）← タッチポイント①

Explore エージェントから Material Ambiguity の一覧を受け取る。

Material Ambiguity に「期待動作が検証可能な形で書かれていない」「判定方式の分類に確信が持てない」が含まれる場合は、質問に **「どうなれば直ったと言えるか」を確定させる問い** を必ず含める（判断基準は `.claude/skills/bugfix-auto/judgment-criteria.md` を参照）。回答を得たら同ファイルの判定手順で判定方式を確定し、確定後の分類に応じて次のように分岐する:

- **回帰テスト / AI照合に確定した場合**: `## 確認済み不明点` コメントの「完了条件の判定方式」に確定後の分類と根拠を記録して Step 3 へ進む
- **人間確認に確定した場合**: `## 確認済み不明点` は投稿せず（Step 3 から再開されると人間確認のまま計画立案に進んでしまうため）、Step 1 と同じ `## /bugfix-auto — 対象外（人間確認が必要）` のコメントのみを投稿して終了する（「判定の根拠」には質問と回答を踏まえた根拠を書き、「調査サマリー」は Step 1 の探索結果を同梱する）

記録するコメントには Step 1 の探索結果サマリーを必ず同梱する。
別セッションで Step 3 から再開しても、Plan エージェントに探索結果を渡せるようにするため。

**不明点がない場合**: このステップをスキップし、以下の内容でissueに記録してStep 3へ進む:
```
## 確認済み不明点

不明点なし。探索フェーズで修正計画を立てる十分な情報が得られました。

### 探索結果サマリー
- 原因箇所: <原因箇所>
- 再現条件: <再現条件>
- 修正方向の候補: <候補>
- 完了条件の判定方式: <回帰テスト / AI照合>（根拠: <根拠>）

- 2. の修正方針が対象とする変更対象ファイルの内外（他ファイルを含む）に、変更箇所と同一内容・同一構造を並行して保持している他の記述箇所がないか確認したか（例: 同一の観点リストや対応表が複数箇所に重複して存在し、一方を変更すればもう一方にも追随が必要な構造。ファイル内の他の節・ブロックだけでなく他ファイルも対象に含める。同じリストが地の文と指示例のコードブロックの両方に置かれているケースを見落としやすい）。確認は記憶や部分的な検索結果で済ませず、`git grep -nF '<変更箇所から引用した文言>'`（検索対象パスを変更対象ファイルに固定せず、内外を横断して検索する。引用した文言に `*` `.` `[` などの正規表現メタ文字が含まれると、既定の正規表現検索では意図せずヒットしない・エラーになるため `-F` を付ける）で他ファイルを含む並行箇所を洗い出したうえで、変更対象ファイル自身も通しで読んで確認する（変更対象ファイルを通しで読むだけで済ませない。ファイル内の確認はファイル横断の確認の代わりにならない）。検索語は変更する具体的な文言・見出し・シンボル名に限定し、ヒットが複数ある場合はヒット箇所が変更箇所と同じ役割（同じ観点リスト・同じ手順・同じ処理や定数定義・同じ注記が指す対応節）を担っているかで並行記述かどうかを判断する。洗い出した結果（見つからなければ「並行記述なし」）を計画に明記すること（明記が無いと、Step 4 で確認漏れと「確認したうえで無し」を見分けられないため）
- `.claude/skills/_shared/orchestrator-common.md` の節そのもの、または同ファイルの節を参照・貼り付けしている節（各 SKILL.md 内で `> **集約先ファイルとの対応関係**` の注記が付いている節。またはその内部）に変更を加える場合は、grep のヒットに頼らず、参照・貼り付け元である `.claude/skills/_shared/orchestrator-common.md` の該当節、および同じ節を参照・貼り付けしているすべてのスキルファイルの対応節（変更箇所自身を除く）を実際に Read して確認したか（スキルごとに言い回しが書き換わっており、変更する具体的な文言がそのまま他ファイルに現れず grep でヒットしないことがあるため）。Read した対応節と確認結果（同期が必要か・不要か）を計画に明記すること（明記が無いと、Step 4 で確認漏れと「確認したうえで同期不要」を見分けられないため）。同期が必要と判明した対応節は、下記の並行記述と同じ扱いで（対象ファイルごとではなく対応節ごとに1件ずつ）書き出す。各節が定めるプレースホルダの値・スキル固有の記述のみの変更など、同期が不要と判断した場合はその理由を 5. に明記すること
- 上記2項目で並行記述（注記を起点に見つかった他スキルファイルの対応節を含む）が見つかった場合、その記述箇所を見出し・対象ファイルに実在する項番号（例: 対象ファイル内に `1.` `2.` … と番号が印字された項目の「2.」）・シンボル名・引用した文言など一意で陳腐化しにくい目印で特定したうえで（行番号だけで指定しない。対象ファイルに番号の無い箇条書き・段落・表の行などを数えて作った序数（例:「既存6番目」）は目印として使わない。引用文言を併記していても、序数表現自体を残してはならない）、そこへの変更を 2. の修正方針と 4. の変更対象ファイル一覧の「変更内容の概要」に、同一ファイル内の箇所であれば同一ファイル内の別箇所として、他ファイルの箇所であれば当該ファイルを 4. の変更対象ファイル一覧に追加したうえで、箇所ごとに1件ずつ書き出しているか（Step 5 の実装エージェントは `## 承認済み修正計画` コメントしか読まないため、ファイルパスが一覧にあるだけでは並行箇所の存在も位置も伝わらない）。変更の趣旨が並行箇所には当てはまらずスコープ外とする場合は、その理由を 5. に明記すること（「移植元・参照元に対応物が無い」のように、並行箇所そのものを見ていない理由だけでスコープ外に置かない）
- 番号付きの箇条書き・手順（項番）の項目を追加・削除・並べ替える変更が計画に含まれる場合（後続の項番が繰り下がる・繰り上がる変更を含む。計画本文が「繰り下げ」に言及していなくても対象）、ずれる番号・消える番号を指した既存の参照（例:「7. の◯◯に含める」のような番号での参照）が残らないかを確認したか。参照の洗い出しは変更するブロック内で終えず、変更対象ファイル全体と他ファイル（例: `.claude/agents/*.md` がスキルの Step 番号を指す記述）を `git grep -n '<番号を含む参照文言>'` で検索して行う
- 上記で参照が見つかった場合、「どのファイルのどの記述を、どの番号に更新するか（削除する項目への参照は参照先ごと書き換える）」を1件ずつ計画に明記しているか（「後続項目はそのまま繰り下げる」のような一括記述だけで済ませない。一括記述は個々の参照の更新漏れを隠すため）

上記のいずれかを満たさない場合は、該当する記述を実態に合わせて修正・加筆してから計画書を返すこと。

計画書を返してください（ファイルへの保存は不要）。
```

**Plan エージェント起動前の貼り付け**: 上記プロンプト内の、`.claude/skills/_shared/orchestrator-common.md` の節名を含み「この位置に貼り付ける>」で終わる貼り付けマーカー（2箇所。マーカー内の `<扱った計画項目の列挙>` は置換値の指定であり、別の貼り付けマーカーではない）は、Plan エージェントを起動する前に、同ファイルの対応節の本文（プレースホルダを実際の値に置換済みのもの）に置き換えること。マーカー文字列そのものを Plan エージェントに送信してはならない。同ファイルを Read できない、または対応節が見つからない場合は、マーカーを残したまま・本文を推測で補ったまま Plan エージェントを起動せず、その旨をユーザーに伝えて終了する。

Step 3 から再開した場合など、手元に Step 1 の調査結果がない場合は、
`## 確認済み不明点` コメントの「探索結果サマリー」を `[探索結果サマリー]` に使う。

### Step 4: 計画承認フェーズ（メイン）← タッチポイント②

Plan エージェントから修正計画書を受け取る。

提示の前に、計画のいずれかの項目で main との差分・分岐点算出（マージベースの特定等）を扱っている場合は、その比較対象が `main` ではなく `origin/main` になっているか・`git fetch origin main` の成否が明記されているかを確認する（根拠: `.claude/skills/auto-loop/SKILL.md`「エスカレーション時の後片付け」節）。ローカル `main` を基準にしたままの記述、または比較対象が明記されていない記述が残っていれば、ユーザーに提示せず Step 3 の Plan エージェントに差し戻す（差し戻しは最大2回。それでも解消しなければ、差し戻した経緯を添えてそのままユーザーに提示し判断を仰ぐ）。

同じく提示の前に、回帰テスト計画で統合テストのケースを `新規` で追加している場合は、プロジェクトのテスト規約（`.claude/rules/` 配下や `docs/architecture/` に統合テストの基準があればそれ。無ければ Step 3 の Plan 指示に書いた既定の基準）を Read し、ケースごとに次のいずれかに当たらないかを照合する:
- 規約（または既定の基準）が挙げる「単体テストで担保が難しい振る舞い」のどれに当たるかの記載がない
- 記載した例に当たらない。具体的には、ロジックを純粋関数・表示コンポーネントに切り出せば単体テストで書ける振る舞い、または他の層（例: hook / Container / ページ）で同じ振る舞いを検証しているもの（計画内の他のケースに加え、既存テストも `git grep` で確認する）

当たるケースがあれば、ケースと該当した理由を添えて、ユーザーに提示せず Step 3 の Plan エージェントに差し戻す（差し戻しは上記の `origin/main` の確認と通算で最大2回。それでも解消しなければ、差し戻した経緯を添えてそのままユーザーに提示し判断を仰ぐ）。

確認できたら、ユーザーに提示する:

```
以下の修正計画を確認してください。
修正したい点があれば指示してください。問題なければ「OK」と返してください。

---
<修正計画書の内容>
---
```

ユーザー（または auto-loop 指揮役）からの応答が、計画そのものの修正・再提示は不要としつつ実装時に踏まえてほしい確認事項を添える「確認事項付き承認」（パターン3）と判断できる場合は、**承認として扱う**。計画の再提示（Step 3 の Plan エージェントへの差し戻し）は行わず、下記の記録処理（`## 承認済み修正計画` の投稿）へ進む（応答に「OK」の語が含まれていなくても同じ扱いとする）。ただし、確認事項が計画のスコープを超える変更を求める内容であれば、応答に「OK」等の承認文言が含まれていてもパターン3とはみなさず、承認としても扱わずに通常のフィードバック（Step 3 への差し戻し）として扱う。

フィードバックを受けて修正する（複数回対応）。ユーザーが「OK」を返したら:
- 以下の形式で `gh issue comment` でissueに記録する:
  ```
  ## 承認済み修正計画

  ### 原因
  <原因>

  ### 修正方針
  <修正方針>

  ### 完了条件の判定方式
  <回帰テスト / AI照合>
  <回帰テストの場合: 回帰テスト計画（機能要件×テストケースの対応表は red の根拠列を含めてそのまま転記し、要約・省略しない。Step 5 の実装エージェントとレビュアーはこのコメントしか読まないため） / AI照合の場合: 照合内容>

  ### 変更対象ファイル
  - `<ファイルパス>`: <変更内容の概要>
  - ...

  ### スコープ外
  <変更しないファイル・範囲>

  ### 注意点
  <既存挙動への影響・エッジケース>

  ### フィードバック履歴
  <何をどう変えたか（変更がなければ「修正なし」）>
  ```

**確認事項付き承認を受けた場合の追加対応**

パターン3（確認事項付き承認）と判断した場合は、上記コメントの「### フィードバック履歴」に、確認事項を次の形で追記する（受け取った応答が箇条書きでも `(1) … / (2) …` の連結表記でも、1件1行の箇条書きに展開する）:

```
### フィードバック履歴
修正なし（確認事項付き承認）

実装時の確認事項:
- <確認事項1>
- <確認事項2>
```

この記録が Step 5 以降への唯一の伝達経路になる（別セッションから Step 0 の再開判定で Step 5 に入った場合も、確認事項はここからしか読めない）。あわせて、その内容を Step 5 の実装エージェント向けプロンプトの `[実装時の確認事項]` ブロックにそのまま転記し、後続フェーズ（実装）へ伝達する。

### Step 5: 実装（general-purpose エージェント）

`subagent_type: "general-purpose"`・`model: "sonnet"` でエージェントを起動する。
承認済み修正計画を渡し、修正を実装させる:

```
以下の承認済み修正計画に従って、バグを修正してください。

[issue番号: <番号>]
※ 承認済み修正計画の詳細は `gh issue view <番号> --json comments --jq '.comments[].body'` で取得すること
  （`## 承認済み修正計画` のコメントを参照）

[実装時の確認事項（`## 承認済み修正計画` のフィードバック履歴に「実装時の確認事項」の記録がある場合のみ）]
<記録された確認事項をそのまま箇条書きで記載する。記録が無い通常ケースでは、このブロック自体を記載しない（Step 4 を経ずに Step 5 から再開した場合も、その場でコメントを読んで判定する）>

実装方針:
- 承認済み修正計画の修正方針・スコープに厳密に従う
- スコープ外のファイルは絶対に触らない
- issue の機能要件に含まれない無関係な変更（リファクタ・機能追加）は行わない
- `[実装時の確認事項]` ブロックがある場合は、その内容も踏まえて実装する。ただし対応は承認済み修正計画の修正方針・スコープの内側に限る（確認事項はスコープを超えない範囲だけが渡される取り決めのため）。スコープの拡大が必要になった場合は実施せず、理由を報告して戻る
- リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
- 完了条件の判定方式が「回帰テスト」の場合、必ず次の順序で進める:
  0. 修正方針に、挙動を変えない切り出し（純粋関数・表示コンポーネントへの切り出し）をバグの修正より先に行う手順がある場合は、先に切り出しだけを行い（バグはまだ直さない）、既存テストが通ることを確認する
  1. 回帰テスト計画に従い、バグを再現する失敗テストを先に書く
  2. テストを実行し、修正前のコードで失敗する（red）ことを確認する。失敗時の出力（アサーションエラー等の要点）を記録する（import エラー・未定義エラーによる失敗は red として扱わない）
  3. バグを修正する
  4. 回帰テストが通る（green）ことを確認する
  （red を確認せずに修正へ進まない。テストが最初から通ってしまう場合は、テストがバグを捉えていないため書き直す）
- 完了条件の判定方式が「AI照合」の場合、修正計画の照合内容を満たすように修正する
- CLAUDE.md・.claude/rules/core.md のコーディング規約に従う
- フォーマットは設定済みのフォーマッタで行い、独自判断で手整形しない（フォーマッタを実行するかどうかは `.claude/rules/core.md`「フォーマット・コード整形」に従う。実行する場合はその適用範囲に含まれる変更に対して実行する）
- 修正完了後、既存テストをすべて実行して通ることを確認する（テストコマンドは docs/specs/technical-environment.md の `## 実行コマンド` を参照）
- 完了確認のためのコマンド実行（回帰テストの red / green の確認・既存テストの実行を含む）は Bash ツールのタイムアウトで打ち切られうる（`timeout` 未指定時の既定は 120000ms、指定できる上限は 600000ms）。既定値を超える見込みの場合は `timeout` を明示し、上限（600000ms）に収まらない見込みの場合は複数回のコマンドに分割して実行する（連続実行は回数で区切り、1回で上限を超える場合は実行対象を分ける。所要時間の見込みが立たない場合は1回分を先に実行して計測する）。各回の pass/fail が判別できる形で結果を記録し、ツールのタイムアウトによる失敗とテスト自体の失敗を区別して報告する。テストランナーの結果サマリー（passed / failed 件数）が出る前に打ち切られた回はタイムアウトとして扱い、テスト失敗（red を含む）とみなしてコード修正に進まず、`timeout` の指定や分割を見直して再実行する
- テスト・フォーマッタの適用範囲外（Markdown・ドキュメントのみの変更等）の部分は実行対象とせず、対象ツールの設定範囲を判断根拠として報告する。適用範囲外であること自体は問題ではない
- 最後に変更したファイルをコミットする（コミット規約は .claude/rules/core.md を参照。`git add` で対象ファイルを個別指定する）
- コミットに続けて、`gh issue comment` で以下を投稿する:
  ```
  ## バグ修正実装完了

  完了条件の判定方式: <回帰テスト / AI照合>

  変更したファイル:
  - `<ファイルパス>`: <変更内容の概要>
  - ...

  回帰テスト（判定方式が回帰テストの場合のみ）:
  - テストファイル: `<パス>`
  - red の確認: <修正前に失敗したことと失敗出力の要点>
  - green の確認: <修正後に通過したこと>

  計画から逸脱した点: <なければ「なし」>
  ```

完了後に以下を返してください:
- 変更したファイルの一覧（ファイルパスと変更内容の概要）
- 回帰テストの red → green の確認結果（判定方式が回帰テストの場合）
- 計画から逸脱した点があれば一覧と理由
- 既存テストの実行結果（テストが適用範囲外の場合はその旨と判断根拠）
```

完了後、実装エージェントが `## バグ修正実装完了` コメントを投稿済みであることを `gh issue view <番号> --json comments` で確認する。
投稿が確認できた場合はそのまま Step 6 のレビューへ進む。
（万一未投稿の場合のみ、返された変更ファイル一覧をもとにメインが同形式で投稿するフォールバックを行う。）

### Step 6〜8: レビュー → 修正ループ（レビュー最大3回・修正最大2回）

#### 各ループの流れ

1. `subagent_type: "bugfix-auto-reviewer"` でレビュアーエージェントを起動する。渡すプロンプト:
   ```
   issue番号: <番号>
   実装ファイル一覧: <Step 5 または前回の修正で変更したファイル一覧>
   ```

   Step 6 から再開した場合など、手元に実装ファイル一覧がない場合は
   `## バグ修正実装完了` コメントから取得して渡す。

2. 結果を受けて（**返答1行目の `判定:` 行を分岐の根拠とする**）:
   - **`判定: 承認`**: Step 9へ進む
   - **`判定: 人間確認が必要`**: 修正ループに入らず（レビュー・修正の回数も消費しない）、以下を `gh issue comment` でissueに記録し、同内容をユーザーに報告して終了する。承認済み修正計画の判定方式そのものが誤っており、スコープ厳守の修正エージェントでは解消できないため:
     ```
     ## /bugfix-auto — 対象外（人間確認が必要）

     レビュー時に、この issue の完了条件が見た目・主観判断を含むと判明したため、/bugfix-auto の自動判定では完了を保証できません。

     ### 判定の根拠
     <レビュアーが返した根拠（どの検証項目がなぜ人間確認なのか）>

     ### 実装済みの変更（コミット済み。破棄・修正は人間が判断してください）
     - ブランチ: `<git branch --show-current の結果>`（PR は作成していないため push されていない場合があります）
     - `<ファイルパス>`: <変更内容の概要>

     ### 再実行するには
     issue の期待動作を検証可能な形に具体化したうえで、このコメントと `## 承認済み修正計画` / `## バグ修正実装完了` を削除して再実行すると、修正計画立案（Step 3）からやり直せます。これらのコメントが残っている限り、`/bugfix-auto` は Step 0 の再開判定で対象外と報告して終了し、`/auto-loop` も Step 1 の除外判定でこの issue を処理対象から外します。
     ```
   - **`判定: 問題あり`**: `subagent_type: "general-purpose"`・`model: "sonnet"` で修正エージェントを以下のプロンプトで起動する:
     ```
     issue番号: <番号>

     以下のレビュー指摘を修正してください。
     <bugfix-auto-reviewer が返した問題リスト>

     制約:
     - `## 承認済み修正計画`（`gh issue view <番号> --json comments --jq '.comments[].body'` で取得）の修正方針・スコープに厳密に従う
     - スコープ外のファイルは絶対に触らない
     - issue の機能要件に含まれない無関係な変更は行わない
     - `## 承認済み修正計画` のフィードバック履歴に「実装時の確認事項」の記録がある場合は、その内容も踏まえる（Step 5 の実装がこれに沿っている場合があるため、確認事項に沿った実装をスコープ外変更として取り消さない）。対応は計画の修正方針・スコープの内側に限る
     - リポジトリ内のテキスト検索を Bash で行う場合は、素の `grep`（`grep -r` 等）ではなく `git grep -n <pattern> -- <pathspec>` を使うこと（`cd <dir> && ...` の形は使わない。未追跡ファイルも対象にする場合は `--untracked` を付ける。ビルトインの `Grep` ツールの使用を禁じるものではない）。理由: worktree には `.env` 系の秘密情報ファイルが実体コピーされていることがあり、素の再帰 grep は permission ダイアログで停止するため（詳細: `.claude/rules/core.md`「リポジトリ内のテキスト検索は git grep を使う」）。
     - 回帰テストを弱める変更（アサーションの削除・緩和・スキップ）でレビューを通そうとしない。テスト側に問題がある場合はその理由を明示して修正する
     - 修正後に既存テストをすべて実行して通ることを確認する（テストコマンドは docs/specs/technical-environment.md の `## 実行コマンド` を参照）。適用範囲外（Markdown・ドキュメントのみ等）の場合は対象ツールの設定範囲を判断根拠として報告する
     ```
     - 修正試行時に `gh issue comment` で試行カウンタを投稿する:
       ```
       ## バグ修正試行 <N>/2

       ### レビュー結果（<N> 回目のレビュー指摘）
       <問題リスト>

       ### 修正内容
       - <変更したファイルと変更内容>
       ```
     - 修正完了後、メインが修正ファイルをコミットしてから（amend・rebase・reset は使わず必ず追加コミット。コミット規約は `.claude/rules/core.md` を参照）、次のレビューに進む

3. レビュアーの返答に `## 参考指摘`（判定に影響しない指摘）が含まれる場合、その内容は修正エージェントに渡さない（`判定: 承認` なら参考指摘の有無にかかわらず Step 9 へ進む）。内容は保持し、Step 9 の完了コメントの `### スキルふりかえり` に転記する。

#### ループ回数の管理

- レビューは最大3回（Step6・Step7・Step8）、修正は最大2回
- 3回目のレビューで `判定: 問題あり` が返ってきた場合: **自動修正を打ち切り**、人間に報告して終了する
- Step 6 に再開した際は `## バグ修正試行 N/2` コメントの最大 N を数え、修正回数=N・レビュー回数=N+1（初回レビュー分）として残り budget を算出し、上限（レビュー3・修正2）判定に使う。ただし失敗マーカー（`## /bugfix-auto — 自動修正できませんでした`）から再開した場合は回数を意図的にリセットする（下記「意図的リセット」参照）。`## バグ修正試行` は budget 復元専用の試行カウンタであり、Step 0 再開表のマーカーには加えない

3回のレビューで解消できなかった場合の報告:
```
## /bugfix-auto — 自動修正できませんでした

3回のレビュー・2回の修正試行で以下の問題が解消できませんでした:

### 未解決の問題
<問題リスト>

### 試行履歴
- 修正1: <変更したファイルと変更内容>
- 修正2: <変更したファイルと変更内容>

手動での確認・修正をお願いします。
```

`gh issue comment` でissueにも同内容を記録し、終了する。

#### 意図的リセット

以下の場合はループ回数を意図的にリセットする（過去の試行カウンタコメントは budget 復元に使わない）:
- 失敗マーカー（`## /bugfix-auto — 自動修正できませんでした`）からの再開（手動修正後の再実行を想定）

これは Step 0 再開表の「`## /bugfix-auto — 自動修正できませんでした` あり → レビュー・修正ループの回数はリセットする」と整合する。

### Step 9: 完了マーカー投稿・PR 作成・完了報告（メイン）

1. `gh issue comment` で以下をissueに記録する（再開判定の終端マーカー。本文に「スキルふりかえり」を同梱する）:

   ```
   ## /bugfix-auto 完了

   ### スキルふりかえり
   - <スキルの指示が曖昧で迷った点・レビュー→修正ループが余計に回った原因などを1〜2行で記録>
   ```

   ふりかえりで特に気づきが無い場合は `- なし` と記録する（`### スキルふりかえり` の見出し自体は必ず入れる）。

   レビュアーが返した `## 参考指摘` がある場合は、`- 参考指摘（<エージェント名>）: <内容>` の形でこの節に転記する。

2. `/create-pr` skill を実行して PR を作成する（ユーザー・指揮役への確認は不要。PR の作成だけでは既存のコードに影響が出ないため、PR 作成に人間の承認はいらない運用とする。プロジェクトの CLAUDE.md が PR 作成に承認を求めている場合はそれに従い、作成せずに完了報告で `/create-pr` の実行を案内する）。作成された PR の URL を 3. の完了報告に含める。マージは行わない。

   PR 作成に失敗した場合は中断せず、失敗理由を完了報告の「PR」欄に記録して 3. へ進む（バグ修正自体は完了しているため）。

3. 以下の形式でユーザーに完了を報告する:

```
## /bugfix-auto 完了 (#<番号>)

### 実行したフェーズ
1. 再現・原因分析（完了条件の判定方式: <回帰テスト / AI照合>）
2. 質問フェーズ（<スキップ / N件の不明点を確認>）
3. 修正計画立案
4. 計画承認
5. 実装（<回帰テスト red → green / AI照合>）
6. レビュー・修正（<N回で承認>）

### 成果物
- 変更ファイル: <一覧>
- 回帰テスト: <テストファイルのパス / AI照合のため無し>
- レビュー結果: <承認 / N回の修正後承認>

### スキルふりかえり
- <1. で issue に記録したふりかえりと同じ内容（無い場合は「- なし」）>

### PR
- <作成した PR の URL / 作成に失敗した場合はその理由>

レビューとマージをお願いします（マージは行っていません）。
```

4. ふりかえりに「なし」以外の気づきがあり、スキル定義（SKILL.md・エージェント定義）の編集に値する場合は、完了報告に続けて起票の確認を行う:

   ```
   スキルふりかえりに以下の気づきがありました。スキル改善 issue として起票しますか？（はい / いいえ）
   - <気づき1>
   - <気づき2>
   ```

   ユーザーが許可した場合のみ、気づき1件につき1つの issue を作成する（1つの気づき = 1 issue）。
   起票とラベル付与は分けて実行する:

   1. `gh issue create --title "bugfix-auto: <気づきの要約>" --body "<本文>" --assignee @me`（`--label` は付けない）
   2. `gh issue edit <作成した issue 番号> --add-label skill-improvement`

   - issue 本文には「対象スキル」「気づきの内容と改善案」「発生した実行（元 issue #<番号>）」を含める
   - ユーザーが拒否した場合・気づきが「なし」の場合は起票せず終了する（ふりかえり自体は 1. のコメントに記録済み）
   - SKILL.md・エージェント定義をこの場で直接編集しない（スキル編集は issue → PR → 人間のマージ承認のゲートを必ず通す）

## 注意事項

- **エスカレーション回答に含まれる前処理はこのスキルの責務ではない**: `/auto-loop` のエスカレーション対応で人間が前処理指示（別issueへの切り出し・他issueの修正指示など）を含む回答を投稿した場合、その前処理の実行は指揮役（`/auto-loop`）が子（このスキル）の起動前に一括で行う。このスキル（オーケストレーター本体および Explore・Plan・実装等の各サブエージェント）は、エスカレーション回答を issue の背景情報として読むだけにとどめ、そこに含まれる前処理を実行してはならない（指揮役と子が同じ回答を読んで重複実行するのを防ぐため。重複実行すると同じ内容の issue が二重に起票されるなどの副作用が出る）。**`/auto-loop` を介さず `/bugfix-auto` を直接起動した場合は前処理を実行する指揮役が存在しない**（`## /auto-loop 前処理完了` コメントが無いことで判別できる）。その場合も自分で実行せず、前処理指示の内容と「まだ実行されていないこと」をユーザーに報告して指示を仰ぐ（黙って進めると、前処理が済んでいる前提の修正計画を立ててしまう）
- 人間・指揮役への質問・承認依頼（Step 2・Step 4）は通常のテキスト応答で行い、
  AskUserQuestion 等の対話ダイアログは使わない（指揮役の /auto-loop が
  pane 経由のテキストで応答するため。ダイアログはオーケストレータから操作できない）
- `gh` コマンドが使えない場合はエラーをそのままユーザーに伝える
- バグ修正は挙動の変更が目的だが、issue の機能要件に含まれない無関係な変更（リファクタ・機能追加）を混入させないことを実装エージェントに明示すること
- レビュアーには issue 本文（機能要件・制約）と承認済み修正計画のissueコメントを必ず参照させる
- issueに記録するコメントは日本語で書く
- コミットはフェーズ単位で実行する: Step 5（実装エージェント、実装完了時。実装エージェントはコミットに続けて `## バグ修正実装完了` を投稿する）・Step 6〜8 の修正ループ（メイン、修正のたびに追加コミット）。Step 9 ではコミットしない
- 修正時のコミットは amend・rebase・reset を使わず必ず追加コミットにする
- コミット対象は変更したファイルのみ。意図しないファイルを混入させない（`git add .` / `git add -A` は使わない）
- **ツール結果の捏造に気づいたら再開運用に乗せる**（汎用ルールは `.claude/rules/core.md` の「ツール結果の捏造禁止」を参照）:
  - 捏造に気づいたら続行せず、`/clear` → `/bugfix-auto <番号>` を再実行 → Step 0 で issue コメントから再開ポイントを判定する
  - **再開前に汚染区間を検証する**: 汚染セッション中に投稿された issue コメント（Step 0 再開表のマーカー: `## /bugfix-auto — 対象外（人間確認が必要）` / `## 確認済み不明点` / `## 承認済み修正計画` / `## バグ修正実装完了` / `## /bugfix-auto — 自動修正できませんでした` / `## /bugfix-auto 完了`）と、その間のコミット差分が捏造情報に基づいていないかを確認する。疑わしいコメント・差分は、再開ポイント判定の根拠にする前に人間が精査し、必要なら破棄する
- 終端マーカーコメントには `### スキルふりかえり` を同梱するが、再開判定・汚染区間検証は見出し行 `## /bugfix-auto 完了` の有無で行う（マーカー見出しの文字列は変更しない）
- ふりかえりコメントの投稿は Step 0 で得たコメント投稿許可の範囲内で行う（追加の許可フローは設けない）。一方、スキル改善 issue の起票はこの許可の範囲外のため、必ず完了報告時にユーザーの許可（はい）を得てから実行する。自動起票はしない
- `skill-improvement` ラベルはリポジトリに作成済みであることを前提とする（存在せず `gh issue edit --add-label` がエラーになった場合は、エラーをそのままユーザーに伝える）
- **実行モデルはエージェント定義と Agent 呼び出しで決まる（skill frontmatter に `model:` は置かない）**:
  skill frontmatter の `model:` は公式仕様上「起動したターンの残りにだけ適用され、次のプロンプトでセッションモデルに戻る」。
  /bugfix-auto は Step 0 の開始時ガードとコメント投稿許可でユーザーの応答を待つため、最初のターンはそこで切れる
  （さらに Step 2 の質問は不明点がなければスキップされるため、以降のターン境界の位置は実行ごとに変わる）。
  つまり frontmatter に `model:` を書いても効くのは Step 0 の同意プロンプトを出すまでで、Step 1 以降の
  オーケストレーターはセッションモデルで動く。「この skill は sonnet で走っている」という誤解を生むだけなので、
  この skill の frontmatter には `model:` を置かない。各フェーズの実行モデルはこれに影響されない——
  Step 1（Explore）・Step 3（Plan）・Step 5（実装）・Step 6〜8（修正）は Agent 呼び出しの `model` 引数で、
  レビュアーは `.claude/agents/bugfix-auto-reviewer.md` の `model:` で、いずれも sonnet に固定されるため
  （原因分析は Step 1〜3 で承認済み計画に落とし込まれ、実装はそれに従うため、opus を要する工程がない。
  原因分析が難航する issue はタッチポイント①・②で人間が方向を補正する）。オーケストレーター自身のモデルを
  固定したい場合は、セッション側（`/model`・`claude --model`）で指定する
